## 2. 协作规则（用户明确要求，必须遵守）

1. **一步一个知识点**，不要一次写大文档。每步节奏：这步解决什么问题 → 给她一个小问题 → 以设计者第一人称给完整思路 → 面试追问预演 → 等她说"继续"。
2. **先定义再分类**。讲新概念先说它是什么，再说分几种。11-04 她反馈过"不用标注 / 要标注"丢得太突然。
3. 她追问具体实现时给**能跑的示意代码**，标明是按简历口径还原的示意实现，不是原项目代码。
4. 她有理解偏差时先纠正、解释清楚再往下走。
5. 她会推回你的说法，而且常常是对的。**承认、纠正、落到后面的设计里**，不要绕。11-04 效果口径我改了三次才稳，每次都是她抓到前后不一致。
6. 中文，直接，不客套，无 emoji。
7. 每步结论写进 `进度交接_项目拆解.md` 第 9 节；完成一个项目的第 8 步后勾掉记忆文件里的进度。

## 3. 每个项目的 8 步模板

1. **为什么做**：业务痛点，带一个数，谁是用户、谁提的需求。成果只有两样：30 秒开场讲法 + "之前"的基线数。"之后"的数不属于这一步。
2. **真正的问题**：难点不是"接个大模型"，是哪几条约束（环境 / 输入形态 / 风险 / 成本与信创）。
3. **结构图**：就那几个组成部分，先画主干，不讲分支。
4. **逐个部件**：每个部件按"问题 → 备选（至少两个，含没选的）→ 为什么选 → 代价"讲，一个部件一回合。
5. **效果归因**：每个数字来自哪个改动，口径（样本量、谁标注、对比基线），评测数据有没有参与训练或调参。要带迭代链讲，不能讲成"上线即得"。
6. **真实问题案例**：至少一个能脱稿讲。四 = 检索到旧版本资料，三 = 微调和 RAG 各多少，一 = 校验失败怎么修，二 = 证据不足怎么处理。
7. **主导 / 参与边界**：主导讲到代码级，参与讲接口与分工理由。
8. **复述与改简历**：她按 1 到 7 讲一遍，逐点校正；按顾问意见改该项目的简历段落与面试展开底稿；生成 v5 并核页（3 页）。

### 项目四已定的口径（细节见进度交接第 9 节）

**两级分流**：交付版跑在客户内网、客户自己问，拦"客户 → L1"的工单；内部版我们自己部署、客户支持 L1 用，拦"L1 → L3"的升级；L3 工单由研发排查（L3 = 研发）。两版共享知识包和切分规则，不共享运行时。

**效果三层数**（11-04 定稿）：

| 层 | 之前（调研 4 周） | 之后（试运行 8 周） |
|---|---|---|
| 整体 L1 工单量 | 周均 109 条 | 周均约 97，降约 11%（头条） |
| 手册可答类到 L1 的量 | 周均 45，占 41.5%（181/436） | 周均约 33，降约 27%，共 264 条；其他类持平（归因用） |
| L1 用内部版的结果 | 该类 181 条中 27 条升 L3，14.9% | 264 条中 240 条用了助手：直接采用 132（55.0%）、补充后采用 72（30.0%）、未解决 36（15.0%）、升 L3 19 条（7.9%） |

**迭代链**（面试要讲的推导过程）：07–08 调研与最简版（固定 512 字切分、单路向量、top5 塞提示词）→ 09–10 首版 3 名 L1 试用两周，五个问题（参数表被切断、错误码查不到、口语召回差、命中旧版本、证据不够时编），Recall@5 66.7%、直接采用约三成 → 11–12 父子分块、表与 SQL 整块、BM25 + RRF、精确通道、版本前过滤，Recall@5 76.0% → 01–02 Reranker、证据约束提示词改了十来版、Multi-Query 开关、评测集扩到 300 并拆检索 / 生成指标，Recall@5 85.0%、忠实度 91.7% → 03–05 交付版随 OCP 发布、内部版全体 L1 8 周试运行加两键反馈，直接采用 55.0%。

**其他已定**：交付版不做反馈机制（数据出不来、问题本来经支持进来、客户对收集数据敏感）；内部版两键"已解决 / 未解决"加"有无补充"，既是效果指标来源也是 Bad Case 入口；每轮问答落日志分三级（审计最小集必须、排障集默认开、完整 prompt 调试开关），字段见第 9 节；intent 改名 kb / live / both / none，含义是"回答需要哪些证据来源"，系统判不是客户选；归因表：正确块不在前 5 → RAG；在前 5 但超出证据 → 先提示词再微调；在前 5 且忠实但结论 / 格式 / 拒答错 → 微调（这是项目三的立项依据）；文档没有 → 文档团队。
