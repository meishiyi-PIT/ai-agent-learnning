## 顾问意见整理（来源 `D:\简历\简历意见整理.txt`，可樂等，2026-11-04；用户要求不含学历、技能两条）

**A. 关于项目职责的写法**（改简历时的标准）
1. 先精简：个人职责只写重点，参与的几大块不用写那么细；职责写得比量化结果还多；指标围绕"解决 xxx 问题、提升 xxx、完成了 xxx"。
2. 顺序上主导放前面、参与放后面；很多描述重复；结合量化指标把工程化思考加进去，职责上强调解决了什么问题，指标上提升了多少。
3. 简历突出核心贡献，具体过程和数据依据留到面试展开。

**B. 关于讲法与面试**（拆解时的标尺）
4. 总体感觉始终在强调"做了什么"，缺工程化思考：为什么要做、是什么问题要这么做、这么做的解决方案有哪些、为什么选这个。→ 每条职责都按"为什么做 → 真正的问题 → 备选（至少两个，含没选的）→ 为什么选 → 代价 → 效果与口径"讲。
5. 按这个维度，让 AI 帮她想问题和解决方案，她结合自己的理解梳理清楚，这样面试时就不担心指标问题。→ 拆解的工作方式：我出问题和"如果我是设计者会怎么做"的方案，她用自己的理解接住、改成自己的话，不是我替她写完。
6. 对着结构图，就那几个组成部分，围绕每个部分做解释；不要觉得"生产级"就很高大上，要有自信；面试官多半也没见过落地，不要怕。
7. 她的问题是"AI 写的实现路径"，要解释清楚为什么这么做。AI 写的还是自己写的不重要，面试官要的是理解中间的思路和流程，能从链路上解释为什么。买菜逻辑：贵了不买、不喜欢也不买，项目同理，成本和信创要求的考量让落地因人而异，只要解释得清就不是问题。

**C. 三个方向建议**
8. ① 四个项目重点拉开：一 = 编排任务，二 = 工单诊断，四 = 知识检索，三 = 效果归因（微调 vs RAG）；共用的部署、评测细节精简。② 理清提升来自哪些改动：微调和 RAG 各带来多少、评测数据有没有参与训练或调参。③ 每个项目准备真实问题案例：编排校验失败怎么修、诊断证据不足怎么处理、检索到旧版本资料怎么办。面试展开底稿在 `D:\简历\面试工程化思考与案例准备_v4.md`，拆解时逐个过并随简历同步改。

## 每个项目的统一模板（2026-11-04 用户要求重拆：之前按技术模块分步的拆解"太随意"，进度交接文档里项目二、四"已讲完"不算进度，老结论只当素材）

每个项目走同样 8 步，一步一个会话回合，每步节奏：这步解决什么问题 → 给她一个小问题 → 我以设计者第一人称给完整思路 → 面试追问预演 → 等她说继续。
1. 为什么做：业务痛点，带一个数，谁是用户、谁提的需求。
2. 真正的问题：难点不是"接个大模型"，而是哪几条约束（环境 / 输入形态 / 风险 / 成本与信创）。
3. 结构图：就那几个组成部分，先画主干，不讲分支。
4. 逐个部件：每个部件按"问题 → 备选（至少两个，含没选的）→ 为什么选 → 代价"讲，一个部件一回合。
5. 效果归因：每个数字来自哪个改动，口径（样本量、谁标注、对比基线），评测数据有没有参与训练或调参。
6. 真实问题案例：至少一个能脱稿讲（四 = 检索到旧版本资料，二 = 证据不足，一 = 校验失败怎么修，三 = 微调和 RAG 各多少）。
7. 主导 / 参与边界：主导讲到代码级，参与讲接口与分工理由。
8. 复述与改简历：她按 1 到 7 讲一遍，我逐点校正，记下讲不顺或与真实经历不符的地方；按 A 组三条改该项目的简历段落与面试展开底稿；改动累积为 v5（v4 不动，脚本复制为 `D:\简历\scripts\build_resume_v5.py`，源稿 `梅某_AI应用开发工程师_修改版v5.md`，末尾追加修改说明），`scripts/check_pages.py` 核页保持 3 页；更新进度交接文档。
