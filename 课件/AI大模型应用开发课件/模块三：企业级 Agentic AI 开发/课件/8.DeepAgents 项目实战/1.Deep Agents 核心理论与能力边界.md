## 第一部分：核心概念与差异
### 1.1 Deep Agents 是什么
Deep Agents 是 Agent Harness（智能体工程套件）。它建立在 LangChain 和 LangGraph 之上，为复杂、长时间运行的任务预装文件工作区、上下文压缩、任务规划和子 Agent 等工程能力。

它不是新的大模型，也不替代 LangChain 或 LangGraph。

| 方案 | 更适合解决的问题 |
| --- | --- |
| LangChain | 模型、Tools（工具）和基础 Agent Loop（智能体循环） |
| LangGraph | 状态机、固定流程、分支、重试、补偿和 Interrupt（中断） |
| Deep Agents | 长任务中的规划、文件管理、上下文治理和专业任务委派 |


### 1.2 与 LangChain 的关键差异
创建代码看起来只换了一个函数：

```python
langchain_agent = create_agent(model=model, tools=business_tools)
deep_agent = create_deep_agent(model=model, tools=business_tools)
```

差异主要在运行时装配。`create_deep_agent()` 会在 LangChain Agent 之上加入一组默认 Middleware（中间件）：

| 默认能力 | Deep Agents 提供的内容 |
| --- | --- |
| Planning（任务规划） | `write_todos` 和任务状态 |
| Virtual Filesystem（虚拟文件系统） | 文件工具与默认 `StateBackend` |
| Context Offloading（上下文结果卸载） | 大型工具结果写入文件，只保留引用 |
| Summarization（对话历史总结） | 长对话达到阈值后压缩旧消息 |
| Subagent Delegation（子智能体委派） | 通用子 Agent 和 `task` 工具 |
| Tool-call Recovery（工具调用恢复） | 修复中断后不完整的工具调用历史 |


Skills（技能包）、Memory（长期记忆）和 Human-in-the-loop（人在回路）提供统一配置入口，但需要开发者显式提供内容与策略。

### 1.3 Deep Agents 不会自动补齐业务能力
`create_deep_agent()` 只是组装入口。一个可用的业务 Agent 仍需要以下内容：

| 必须补充的内容 | 供应商审查示例 |
| --- | --- |
| 业务目标与输出规范 | 风险等级、证据位置、整改条件 |
| 自定义业务 Tools（工具） | 查询 ERP、制裁名单、提交审查结果 |
| 业务规则与知识 | 一票否决项、评分标准、报告模板 |
| 数据、权限与审批 | 文件来源、用户隔离、敏感操作审批 |
| Tests（测试）与 Evaluation（评测） | 漏报率、证据可追溯率、错误审批率 |


```python
agent = create_deep_agent(
    model=model,
    system_prompt=SUPERVISOR_PROMPT,   # 业务目标与执行协议
    tools=[submit_decision],           # 注册给主 Agent 直接调用的自定义业务工具
    subagents=build_subagents(),       # 专业任务分工
    skills=["/skills/"],               # 专业审查方法
    memory=["/memories/AGENTS.md"],    # 长期经验
    backend=backend,                   # 文件生命周期
    store=store,                       # 跨会话存储
    permissions=permissions,           # 文件访问边界
    interrupt_on=interrupt_on,         # 敏感动作审批
    checkpointer=checkpointer,         # 中断后的状态恢复
)
```

只调用 `create_deep_agent()` 得到的是通用 Agent。只有补齐业务工具、规则、数据、安全策略和评测，它才可能成为可交付的业务 Agent。

### 1.4 什么时候选择 Deep Agents
| 任务特征 | 推荐方案 |
| --- | --- |
| 单轮问答、少量工具调用 | LangChain |
| 流程、分支和补偿必须确定 | LangGraph |
| 大量文件、多步骤调查、路径无法预先确定 | Deep Agents |
| 固定主流程中包含开放式调查 | LangGraph + Deep Agents |


核心原则：确定性必须来自业务代码或 Graph（图），不能依赖更长的 Prompt（提示词）。

## 第二部分：Deep Agents 的七个特色机制
| 章节 | 解决的问题 |
| --- | --- |
| 2.1 Virtual Filesystem（虚拟文件系统） | 长任务中的材料、证据和中间产物如何存取 |
| 2.2 Context Compression（上下文压缩） | 活跃上下文不断增长的问题 |
| 2.3 Subagent Delegation（子智能体委派） | 高噪声专业任务如何隔离 |
| 2.4 Planning（任务规划） | 开放式任务如何拆解并跟踪进度 |
| 2.5 Skills（技能包） | 专业方法如何按需加载和复用 |
| 2.6 Filesystem-backed Memory（文件化长期记忆） | 稳定信息如何跨会话保存 |
| 2.7 Permissions and HITL（权限与人工审批） | 文件访问和敏感操作如何受到约束 |


### 2.1 Virtual Filesystem（虚拟文件系统）
#### 2.1.1 它解决什么问题
传统 Agent 容易把原始材料、工具结果和中间结论都放入 Message History（消息历史）。任务越长，每次模型调用携带的无关内容越多。

Deep Agents 给 Agent 提供可寻址的文件工作区。材料和中间结果拥有明确路径，Agent 可以先搜索、再分段读取，并把结论写回文件。

它的价值不是“无限上下文”，而是让 Agent 不必一直携带全部内容，并能在需要时重新找到原始证据。

#### 2.1.2 谁调用，谁执行
```latex
模型选择 read_file（读取文件）并生成参数
    → Deep Agents 的文件中间件接收 Tool Call（工具调用）
    → Backend（存储后端）完成实际读取
    → Tool Result（工具结果）返回模型
```

“Agent 自主调用工具”指模型自主选择工具和参数。模型不会直接访问磁盘，开发者通常也不需要逐条调用这些工具。

开发者负责配置 Backend、文件权限和初始资料；Deep Agents 负责调度工具；Backend 决定文件存储位置并执行操作。

#### 2.1.3 常用文件工具
| 工具（中文注释） | 用途 |
| --- | --- |
| `ls`（列出目录） | 浏览工作区结构 |
| `glob`（路径模式匹配） | 定位一组文件 |
| `grep`（内容检索） | 定位关键词和证据 |
| `read_file`（分段读取文件） | 只读取相关片段 |
| `write_file`（写入文件） | 保存中间结果和交付物 |
| `edit_file`（精确编辑文件） | 修改已有文件 |


这些名称虽然与部分 Shell Command（终端命令）相似，但它们是 Deep Agents 的 Built-in Tools（内置工具），不是直接在操作系统终端中执行的命令。

#### 2.1.4 示例：审查供应商安全材料
本例使用 `StateBackend`（状态后端）。`/data-room/` 和 `/workspace/` 是 Agent 看到的虚拟路径，文件实际保存在当前 Thread（会话线程）的 Agent State（智能体状态）中，不要求操作系统存在这些目录。

本例包含两类代码，作用不同：

| 内容 | 是否需要开发者编写和执行 | 作用 |
| --- | --- | --- |
| Python 初始化与调用代码 | 需要 | 创建 Agent、装入材料并发起任务 |
| `ls`、`grep`、`read_file`、`write_file` 调用轨迹 | 不需要 | 展示 Agent 运行时自动产生的文件工具调用 |


##### 第一步：开发者需要编写并执行的代码
开发者创建 Agent，并在调用时把供应商材料放入虚拟文件系统：

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.backends.utils import create_file_data

agent = create_deep_agent(
    model=model,
    backend=StateBackend(),
)

result = agent.invoke({
    "messages": [{
        "role": "user",
        "content": "检查 ACME 是否存在未整改的高危漏洞，并给出证据位置。",
    }],
    "files": {
        "/data-room/ACME/security-questionnaire.md":
            create_file_data(questionnaire_text),
        "/data-room/ACME/pentest-report.md":
            create_file_data(pentest_text),
    },
})
```

实际运行前还需要配置模型服务，并为 `model`、`questionnaire_text` 和 `pentest_text` 提供具体值。本例省略这些通用准备代码，只展示虚拟文件系统的接入方式。

这里的 `files`（虚拟文件集合）由 `StateBackend` 保存。开发者只负责准备材料并调用 Agent，不需要手动执行下面的文件工具。

##### 第二步：Agent 自动生成的工具调用轨迹
下面的内容不需要开发者复制、编写或手动执行。它只是为了展示运行过程：模型根据任务自主生成 Tool Call（工具调用），Deep Agents 调度工具，`StateBackend` 完成实际的读取和写入。

```latex
# 查看虚拟目录
ls(path="/data-room/ACME/")

# 在虚拟文件中定位 high
grep(
  pattern="high",
  path="/data-room/ACME/",
  output_mode="content"
)

# 只读取命中位置附近的内容
read_file(
  file_path="/data-room/ACME/pentest-report.md",
  offset=40,
  limit=60
)

# 把审查结论写回虚拟文件系统
write_file(
  file_path="/workspace/findings/security.md",
  content="PT-01 曾为高危漏洞，现已修复并通过复测……"
)
```

实际运行时，模型可能调整调用顺序、增加其他检索步骤或跳过不需要的工具。上述轨迹用于解释机制，不代表固定工作流。

执行完成后，原始材料仍位于 `/data-room/ACME/`，审查结论位于 `/workspace/findings/security.md`。这些都是虚拟路径，对应的数据保存在当前 Agent State 中。

因此，本例中的 Virtual Filesystem（虚拟文件系统）由三部分组成：

| 组成部分 | 本例中的内容 |
| --- | --- |
| 虚拟路径 | `/data-room/ACME/...`、`/workspace/findings/...` |
| 文件工具 | `ls`（列出目录）、`grep`（内容检索）、`read_file`（读取文件）、`write_file`（写入文件） |
| Backend（存储后端） | `StateBackend`（状态后端），负责在 Agent State 中实际保存文件 |


`grep.pattern`（内容检索模式参数）使用字面量匹配，不是正则表达式。需要检查多个关键词时，应分别调用 `grep`（内容检索）。

#### 2.1.5 Backend（存储后端）决定文件生命周期
| Backend（存储后端） | 文件生命周期 | 典型用途 |
| --- | --- | --- |
| `StateBackend`（状态后端） | 当前 Thread（会话线程） | 草稿、Todo、大结果卸载 |
| `FilesystemBackend`（本地文件后端） | 本地磁盘长期保存 | CLI、代码库 |
| `StoreBackend`（持久化存储后端） | 跨 Thread | 用户记忆、Agent 经验 |
| `SandboxBackend`（沙箱后端） | 跟随沙箱生命周期 | 隔离执行代码和命令 |


`CompositeBackend`（组合存储后端）可以按路径组合多种 Backend。例如，`/workspace/` 使用线程状态，`/memories/` 使用跨会话存储。

`FilesystemBackend`（本地文件后端）会读写真实磁盘。设置 `virtual_mode=True` 后，Agent 的虚拟路径会被限制在 `root_dir`（根目录）内，并阻止使用 `..`、`~` 或外部绝对路径逃出该目录。

`virtual_mode=True` 不会识别或隐藏敏感文件。如果 `.env`、密钥或凭据位于 `root_dir` 内，Agent 仍可能通过文件工具读取它们。因此，应将敏感文件移出可访问目录，或使用 `permissions`（权限规则）明确禁止访问；不要把服务器根目录直接交给 Agent。

### 2.2 Context Compression（上下文压缩）
Deep Agents 同时使用两种机制，但不是二选一，而是采用“先卸载大内容，再总结旧历史”的分层策略。

| 执行阶段 | 触发场景 | 处理方式 | 原始内容 |
| --- | --- | --- | --- |
| 1. Context Offloading（上下文结果卸载） | Tool Input/Result（工具输入或结果）过大 | 内容写入 Backend（存储后端），活跃上下文只保留文件路径和少量预览 | 完整保留在文件中 |
| 2. Summarization（对话历史总结） | 上下文接近模型窗口上限，且已没有更多内容可以卸载 | LLM（大语言模型）将较早消息压缩为摘要，并保留近期消息 | 原始消息文本写入文件 |


严格来说，Context Offloading 不是对原文进行压缩，而是将大内容移出活跃上下文；Summarization 才是使用 LLM 进行语义压缩。

```latex
大型工具输入或结果
    → 先 Offloading（结果卸载）
    → 上下文仍接近窗口上限
    → 再 Summarization（历史总结）
```

#### 2.2.1 示例：处理大型制裁名单查询结果
供应商审查 Agent 调用制裁名单工具后，工具返回了数万 Token 的匹配记录。Deep Agents 首先执行 Offloading（上下文结果卸载）：完整结果写入 Backend（存储后端），活跃上下文只保留文件引用和预览。

任务继续执行多个步骤后，如果活跃上下文仍接近窗口上限，Deep Agents 再执行 Summarization（对话历史总结）：LLM（大语言模型）把较早的调查消息替换为摘要，同时保留近期消息，并将被总结的原始消息文本另存为对话历史文件。

Summarization（对话历史总结）不会修改或再次卸载先前保存的制裁名单原始结果。此时 Backend（存储后端）中存在两类文件：

| 文件类型 | 保存的内容 | 主要用途 |
| --- | --- | --- |
| 工具结果文件 | 制裁名单工具返回的完整匹配记录 | 查询名单编号、命中原因等原始证据 |
| 对话历史文件 | 被摘要替换的原始调查消息 | 必要时恢复较早的执行过程 |


当最终报告需要引用具体名单编号时，Agent 应使用 `read_file`（读取文件）读取工具结果文件，而不是从摘要或对话历史中猜测编号。

具体触发阈值受 Deep Agents 版本、Model Profile（模型配置档）和 Middleware（中间件）配置影响，因此不能把某个固定 Token 数量当作所有版本都适用的规则。

Offloading（上下文结果卸载）会保留完整原文，但活跃上下文中只保留文件路径和预览；Summarization（对话历史总结）会使用摘要替代较早消息。

当最终结论依赖具体数据、金额、漏洞等级或政策条款时，Agent 应通过 `read_file`（读取文件）重新读取原文并核验证据。

### 2.3 Subagent Delegation（子智能体委派）
子 Agent 在独立上下文中完成搜索、文件读取和分析，主 Agent 通常只接收结果，不接收完整工具调用历史。这种机制称为 Context Quarantine（上下文隔离）。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1784644574728-1a940857-9426-43cb-ac5a-e3fa141b6174.png)

子 Agent 的主要价值不是增加角色数量，而是隔离高噪声过程。适合委派的任务应满足至少一项条件：

+ 能独立完成，依赖关系少。
+ 需要不同专业指令或工具。
+ 中间过程很长，不适合进入主上下文。

#### 2.3.1 示例：并行完成供应商专业审查
主 Agent 把同一供应商分别交给安全子 Agent、法务子 Agent 和财务子 Agent。三个子 Agent 在独立上下文中读取各自材料，不把搜索过程和原始工具结果全部传回主 Agent。

每个子 Agent 把完整证据写入文件，只返回“结论、证据路径、置信度和未解决问题”。主 Agent 最后读取三份短结果，发现冲突时再回到证据文件核验。

自定义子 Agent 应显式配置 `system_prompt`、Skills（技能包）、Tools（工具）和输出格式，不应依赖隐式继承。

推荐返回格式：

```latex
结论 + 证据文件路径 + 置信度 + 未解决问题
```

完整证据写入共享文件，返回主 Agent 的内容保持简短。否则，子 Agent 的长返回会再次污染主上下文。

### 2.4 Planning（任务规划）
Deep Agents 默认提供 `write_todos`（写入任务清单），让模型维护 `pending`（待处理）、`in_progress`（进行中）和 `completed`（已完成）状态。

#### 2.4.1 示例：跟踪供应商审查进度
```python
write_todos([
    {"subject": "盘点供应商材料", "status": "completed"},
    {"subject": "完成安全与法务审查", "status": "in_progress"},
    {"subject": "生成准入报告", "status": "pending"},
])
```

Agent 可以根据新发现增加或调整任务。Todo List（任务清单）适合开放式计划，但不是确定性工作流。

例如，“付款前必须审批”属于硬规则，应放在 LangGraph Edge（图的边）或业务代码中，不能只写在 Todo 或 Prompt（提示词）中。

### 2.5 Skills（技能包）
Skill（技能包）与 LangChain 中的基本概念一致：它描述“这类任务应该怎样完成”。Deep Agents 的特点是将方法、模板和参考资料组织成文件，并通过 Progressive Disclosure（渐进式披露）按需加载。

#### 2.5.1 示例：加载安全审查方法
```latex
skills/
└── security-review/
    ├── SKILL.md
    └── references/
        └── scoring-rubric.md
```

处理安全审查任务时，Agent 读取 `security-review/SKILL.md`，按照其中的检查顺序、风险等级和证据格式工作；只有需要评分时，才继续读取 `scoring-rubric.md`。

Skill 提供工作方法，不提供外部执行能力。即使 Skill 要求查询漏洞数据库，Agent 仍然需要相应的 Tool（工具）才能完成查询。

### 2.6 Filesystem-backed Memory（文件化长期记忆）
Deep Agents 把 Memory（长期记忆）呈现为文件，让 Agent 使用文件工具读取和更新；实际保存位置由 Backend（存储后端）决定。跨 Thread（会话线程）存储时，可以使用由 LangGraph Store（持久化存储）支持的 `StoreBackend`（持久化存储后端）。

#### 2.6.1 示例：跨会话保留报告偏好
第一次审查时，用户明确要求“所有风险结论必须附带原始证据路径”。应用确认该偏好稳定且允许保存后，Agent 将其写入 `/memories/preferences.md`。

下一次创建新 Thread（会话线程）时，配置的 Memory 文件被重新加载，Agent 继续按照相同格式生成报告，用户不需要重复说明。

临时草稿、未经验证的推断和敏感凭据不应写入 Memory。共享 Memory 还需要权限、Namespace（命名空间）和内容审核，避免错误信息或 Prompt Injection（提示词注入）长期传播。

### 2.7 Permissions and HITL（权限与人工审批）
Filesystem Permission（文件系统权限）限制 Agent 可以读写的路径；`interrupt_on`（工具调用中断配置）让支付、删除、外发和提交决策等敏感操作在执行前暂停。

#### 2.7.1 示例：提交准入决定前等待审批
```python
agent = create_deep_agent(
    tools=[submit_decision],
    interrupt_on={"submit_decision": True},
    checkpointer=checkpointer,
)
```

Agent 可以自主读取材料并生成建议。当它调用 `submit_decision`（提交审查决定）时，执行流程暂停；审批人批准后才真正调用工具，拒绝后则不执行。

Human-in-the-loop（人在回路）依赖 Checkpointer（检查点保存器），因为任务需要在人工决定后恢复。

Prompt（提示词）只是行为引导，不是安全边界。真正的安全边界应落在权限、工具实现、身份认证、Sandbox（沙箱）和人工审批上。

## 第三部分：能力边界速查
| Deep Agents 提供什么 | 不代表什么 |
| --- | --- |
| 动态任务规划 | 计划一定完整，或业务状态一定合法 |
| 文件工作区 | 无限上下文，或 Agent 一定能找到正确证据 |
| 上下文卸载与总结 | 所有细节都被保留，或 Token 成本一定下降 |
| 子 Agent 上下文隔离 | 多 Agent 一定比单 Agent 更准确 |
| Skills 与 Memory 文件接口 | Skill 能直接执行动作，或 Memory 会自动进化 |
| 权限与审批接口 | 未配置的敏感操作也会自动受到保护 |
| 复杂任务工程环境 | 业务规则、数据质量和评测可以省略 |


---

## 第四部分：结论
Deep Agents 的核心价值是把复杂 Agent 反复需要的工程模式组装成统一工作环境：

```latex
规划任务 → 搜索与分段读取文件 → 隔离专业子任务
        → 压缩上下文 → 汇总结论 → 敏感动作审批
```

它提升的是长任务的组织能力和持续执行能力，不保证业务结果天然正确。结果质量仍取决于模型、业务 Tools、数据、规则、权限和评测。
