## 一、Skills 核心概念
### 1.1 什么是 Skills
**Skills 是一份可被 Agent 按需发现、按需加载的任务执行说明书。**

它不是某种后台运行的插件或程序，而是将特定任务的经验、规则和执行步骤固化为结构化文档，供 Agent 在恰当的时机读取并执行。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655697874-2311f6da-3f40-4dec-b43f-057f1951e974.png)

**<font style="color:rgb(0, 0, 0);">Skill 是用自然语言写成的领域指令包，通常存放在 </font>**`**<font style="color:rgb(60, 112, 198);">SKILL.md</font>**`**<font style="color:rgb(0, 0, 0);"> 中，模型会在相关任务出现时按需加载它。</font>**

<font style="color:rgb(34, 34, 34);">Skill ：</font>**<u><font style="color:rgb(200, 100, 66);">把某类任务的做法、经验、格式和必要脚本，打包成一个可复用的能力文件。</font></u>**

<font style="color:rgb(34, 34, 34);">你可以把它理解成说明书 + 模板 + 示例 + 工具。</font>

<font style="color:rgb(34, 34, 34);">它像一本菜谱。菜谱里可以写得很详细：先洗菜，再切菜，油温多少，调料比例多少，什么时候出锅。</font>

<font style="color:rgb(34, 34, 34);">但菜谱本身不会做饭。真正做饭的是人，或者是一个能执行菜谱的机器。</font>

<font style="color:rgb(34, 34, 34);">同样，Skill 里可以写工作流步骤，也可以放脚本，但它自己不会主动选择目标、不会管理长期任务、不会判断什么时候该停、不会对业务结果承担执行责任。</font>

### 1.2 Skills 的本质
Skills 的本质是**上下文注入机制**，而非能力增强。它不改变模型的基础能力，而是将项目特有的知识、最佳实践、流程规范以结构化的方式交给 Agent。

| 维度 | 说明 |
| :--- | :--- |
| 定位 | 可发现、可按需加载的任务说明书 |
| 形式 | 一个目录 + SKILL.md 主文件 |
| 本质 | 上下文注入机制，而非能力增强 |
| 价值 | 将散落的经验变成可复用的知识资产 |


### 1.3 什么任务适合做成 Skill
适合做成 Skill 的任务通常具备以下特征：

+ **高频重复**：经常出现的任务类型
+ **一致性要求高**：对输出格式和质量有稳定预期
+ **流程成熟**：已经有相对成熟的做法
+ **复杂度适中**：单靠一句 Prompt 很难稳定跑通

不适合做成 Skill 的场景：一次性小任务、流程尚未跑顺的探索性工作。

## 二、Skills 与相关概念的关系
### 2.1 四种角色的定位
Skills 不是 Prompt、MCP、Function Calling 的替代方案——它们在 Agent 执行链路中承担不同职责。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655713906-d8029685-6fb5-4c7a-ade1-9f32e45b9cc0.png)

| 概念 | 角色 | 核心问题 |
| :--- | :--- | :--- |
| Prompt | 用户意图表达 | 这回要干什么？ |
| Function Calling | 工具调用协议 | 外部调用怎么发起？ |
| MCP | 外部能力对接 | 文件/数据库/GitHub 如何接入？ |
| Skill | 流程与经验沉淀 | 这类任务应该怎么做？ |

## 三、延迟加载与渐进式披露
### 3.1 为什么不能全塞进去
上下文窗口是稀缺资源。塞得多不等于表现好——信息越多，模型需要在更多信息中搜索关键线索，核心规则反而容易被稀释。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655742388-9b7c88b3-7984-4ad7-b0d3-146f2abb24d6.png)

### 3.2 三层加载架构
| 层级 | 加载时机 | 加载内容 | 体量 |
| :--- | :--- | :--- | :--- |
| 广告层 | 启动时 | name + description | 极短 |
| 指令层 | 命中后 | SKILL.md 正文 | 建议 ≤500 行 |
| 资源层 | 执行时 | references/、scripts/ | 按需 |


<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655759834-a8184320-41cb-4156-a8a1-6501857987d2.png)

### 3.3 为什么这样设计
这种设计的核心目的是**节省上下文资源**：

+ **启动时**：只加载极短的元数据，让 Agent 知道"有什么能力可用"
+ **命中后**：才加载完整指令，避免无关信息占用上下文
+ **执行时**：按需读取参考资料，进一步减少不必要的加载

## 四、Skill 与裸 Prompt 的对比
### 4.1 核心差异
将指令直接写进 AGENTS.md（裸 Prompt）还是包成 Skill，核心差异在于上下文管理效率。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655781992-1221b84c-36c3-47f9-97d0-ca8a21e16838.png)

### 4.2 量化对比
| 维度 | 裸 Prompt | Skill |
| :--- | :--- | :--- |
| 平时占 token | 每轮都占（~50 token） | 只占一行摘要（~10 token） |
| 用到时 | 直接可用，零延迟 | 多一次 read（~0.2 秒） |
| 10 个功能 | 每轮多 500 token | 每轮只多 100 token |
| 50 个功能 | context 爆炸 | 依然只多 500 token 摘要 |


### 4.3 Skill 的额外优势
除了省 token，Skill 的包装还带来：

1. **条件加载**：不满足前置条件时自动隐藏
2. **开关控制**：一行配置即可禁用
3. **可分享**：可发布到社区供他人使用
4. **隔离性**：改 Skill 不影响核心 Prompt，反之亦然

### 4.4 什么时候不该用 Skill
有些指令必须每轮都在，不适合做成 Skill：

+ "用中文回复" → 时刻生效
+ "简洁，别说废话" → 同上
+ "你叫小助手" → 身份不能选择性加载
+ "遇到不确定的先问我" → 安全规则必须常驻

**判断方法**：这段话如果某一轮 Agent 没看到，它会不会做出不对的行为？

+ 会 → 写 Prompt，常驻
+ 不会 → 包成 Skill，按需加载

## 五、Skill 路由策略
### 5.1 路由机制
Skill 数量较少时，靠模型扫 description 匹配即可。数量增长后，需要更精细的路由策略。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655915866-6e98eb93-ea4e-4bda-9583-05063f469d97.png)

| 步骤 | 做法 | 要点 |
| :--- | :--- | :--- |
| 粗召回 | 将 name、description、典型 Query 向量化，按余弦相似度取 top-5 | 用户请求同样向量化 |
| 精排 | 同时命中 title、description、examples 的优先级更高 | 高风险 Skill 阈值调高 |
| 兜底 | 最高分都很低时，不选任何 Skill | "不选"经常比"硬选一个"更安全 |


### 5.2 冷启动问题
新上线 Skill 缺乏历史 Query，可通过添加 triggers 字段提升命中率：

```yaml
name: jvm-runtime-diagnosis
description: Diagnose Spring Boot production runtime issues including OOM, Full GC, high CPU, slow APIs, and thread deadlocks.
triggers:
  - "接口卡死了"
  - "频繁 Full GC"
  - "帮我看看这段 Java 堆栈"
  - "服务 OOM 了怎么排查"
```

### 5.3 架构拆分建议
当 Skill 数量增长到一定规模时，建议拆成四个模块：

| 模块 | 职责 |
| :--- | :--- |
| 注册中心 | 维护元信息和向量索引 |
| 路由引擎 | 负责召回与打分 |
| 加载器 | 按需读取正文 |
| 上下文装配器 | 决定内容拼到上下文的哪个位置 |

## 六、原理总结
### 6.1 核心要点
| 概念 | 一句话 |
| :--- | :--- |
| Prompt | 用户这次要做什么 |
| Function Calling | 模型怎么发起工具调用 |
| MCP | 外部能力怎么接进来 |
| Skill | 某类任务该怎么做 |


### 6.2 设计原则
1. **按需加载**：只在需要时才占用上下文资源
2. **渐进披露**：先给摘要，再给详情，最后给资源
3. **职责单一**：每个 Skill 只解决一类问题
4. **可发现性**：通过元数据让 Agent 能找到合适的 Skill
