## 一、先跑起来：A2A 的完整流程
在讲概念之前，先用代码感受一下 A2A 协议到底做了什么。下面的示例会搭建两个角色：

+ **A2A Server**（被调用方）：一个能回答问题的 Agent，对外暴露 A2A 接口
+ **A2A Client**（调用方）：发现这个 Agent 的能力，提交任务，拿回结果

### 1.1 环境准备
```bash
# 安装 A2A Python SDK、ASGI 服务器和 OpenAI 兼容客户端
pip install a2a-sdk uvicorn starlette openai
```

### 1.2 搭建 A2A Server
Server 端需要做三件事：定义 Agent Card（能力描述）、实现任务处理逻辑、启动 HTTP 服务。

```python
# server.py
import uvicorn
from starlette.applications import Starlette

from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.routes import create_agent_card_routes, create_jsonrpc_routes
from a2a.server.agent_execution import AgentExecutor, RequestContext
from a2a.server.events import EventQueue
from a2a.server.tasks import InMemoryTaskStore, TaskUpdater
from a2a.types import (
    AgentCapabilities, AgentCard, AgentInterface, AgentSkill,
)
from a2a.helpers import (
    get_message_text, new_task_from_user_message,
    new_text_message, new_text_part,
)
from openai import AsyncOpenAI


# ── 第一步：实现任务处理逻辑 ──────────────────────────
# AgentExecutor 是你实际干活的地方：收到任务，处理，返回结果

class MyAgent:
    """一个简单的 Agent，用 DeepSeek 回答问题。"""

    def __init__(self):
        self.client = AsyncOpenAI(
            api_key="sk-xxx",
            base_url="https://api.deepseek.com/v1",
        )

    async def invoke(self, user_request: str) -> str:
        response = await self.client.chat.completions.create(
            model="deepseek-chat",
            messages=[
                {"role": "system", "content": "你是一个有用的 AI 助手，请用简洁的中文回答用户的问题。"},
                {"role": "user", "content": user_request},
            ],
            temperature=0.7,
            max_tokens=1024,
        )
        return response.choices[0].message.content


class MyAgentExecutor(AgentExecutor):
    def __init__(self):
        self.agent = MyAgent()

    async def execute(self, context: RequestContext, event_queue: EventQueue) -> None:
        # 1. 获取或创建 Task
        if context.current_task:
            task = context.current_task
        else:
            task = new_task_from_user_message(context.message)
            await event_queue.enqueue_event(task)

        # 2. 更新状态：正在处理
        updater = TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id)
        await updater.start_work(message=new_text_message("正在处理..."))

        # 3. 提取用户输入，调用 Agent
        query = get_message_text(context.message)
        result = await self.agent.invoke(user_request=query) if query else "没有收到有效输入"

        # 4. 把结果作为 Artifact 返回
        await updater.add_artifact(parts=[new_text_part(text=result, media_type="text/plain")])

        # 5. 标记任务完成
        await updater.complete(message=new_text_message("处理完成！"))

    async def cancel(self, context: RequestContext, event_queue: EventQueue) -> None:
        raise NotImplementedError("暂不支持取消")


# ── 第二步：定义 Agent Card ────────────────────────────
# Agent Card 就是 Agent 的「名片」，告诉外界「我是谁、我能干什么」

skill = AgentSkill(
    id="qa_bot",
    name="问答机器人",
    description="一个简单的问答 Agent，接收文本问题并返回回答",
    input_modes=["text/plain"],
    output_modes=["text/plain"],
    tags=["问答", "demo"],
    examples=["你好", "今天天气怎么样"],
)

agent_card = AgentCard(
    name="问答 Agent",
    description="一个通用问答 Agent，基于 DeepSeek 回答各种问题",
    version="1.0.0",
    default_input_modes=["text/plain"],
    default_output_modes=["text/plain"],
    capabilities=AgentCapabilities(streaming=True),
    supported_interfaces=[
        AgentInterface(protocol_binding="JSONRPC", url="http://127.0.0.1:9999", protocol_version="1.0"),
    ],
    skills=[skill],
)


# ── 第三步：组装并启动服务 ─────────────────────────────
request_handler = DefaultRequestHandler(
    agent_executor=MyAgentExecutor(),
    task_store=InMemoryTaskStore(),
    agent_card=agent_card,
)

routes = []
routes.extend(create_agent_card_routes(agent_card))   # 注册 Agent Card 端点
routes.extend(create_jsonrpc_routes(request_handler, "/"))  # 注册 JSON-RPC 端点

app = Starlette(routes=routes)
print("🚀 A2A Server 启动 → http://127.0.0.1:9999")
print(f"   Agent Card: http://127.0.0.1:9999/.well-known/agent-card.json")
uvicorn.run(app, host="127.0.0.1", port=9999)
```

启动 Server：

```bash
python server.py
```

### 1.3 搭建 A2A Client
Client 端做三步：发现 Agent Card → 提交任务 → 获取结果。

```python
# client.py
import asyncio
import httpx

from a2a.client import A2ACardResolver, ClientConfig, create_client
from a2a.helpers import new_text_message
from a2a.types import Role, SendMessageRequest


async def main():
    async with httpx.AsyncClient() as http_client:
        # ── 第 1 步：发现 Agent 能力 ───────────────────
        # 通过固定端点 /.well-known/agent-card.json 获取 Agent Card
        resolver = A2ACardResolver(httpx_client=http_client, base_url="http://127.0.0.1:9999")
        agent_card = await resolver.get_agent_card()
        print(f"[发现] Agent: {agent_card.name}")
        print(f"[发现] 描述: {agent_card.description}")
        print(f"[发现] 技能: {[s.name for s in agent_card.skills]}")

        # ── 第 2 步：创建客户端并提交任务 ──────────────
        config = ClientConfig(streaming=False)
        client = await create_client(agent=agent_card, client_config=config)

        message = new_text_message("什么是 A2A 协议？", role=Role.ROLE_USER)
        request = SendMessageRequest(message=message)

        # ── 第 3 步：获取结果 ─────────────────────────
        print("\n[提交] 发送任务...")
        async for response in client.send_message(request):
            print(f"[结果] {response}")

        await client.close()


asyncio.run(main())
```

运行 Client：

```bash
python client.py
```

## 二、回到问题：为什么需要这个协议？
上面的代码看起来很自然：发现能力、提交任务、拿回结果。但仔细想想——

如果不用 A2A 协议，这两个 Agent 之间要怎么通信？

+ 自己定义 JSON 格式？每个团队定义的字段名不一样
+ 自己写 HTTP 接口？每个 Agent 的路由和参数风格都不一样
+ 自己处理错误和状态管理？每个 Agent 的错误码和状态定义都不一样

**当只有两个 Agent 时，这不是大问题。但当有 100 个、1000 个来自不同团队、不同公司的 Agent 需要协作时——这就是灾难。**

## 三、没有 A2A 之前，Agent 间通信是什么样的
### 同组织内：Supervisor 模式够用
在同一个系统内部，多个 Agent 可以通过 Supervisor 模式协作——总控负责调度，Worker Agent 在进程内通过 handoff 传递控制权。这种方式简单、高效、延迟低。

**但一旦需要跨出组织边界，问题就来了。**

### 场景 1：调用第三方 Agent
你的客服 Agent 需要查快递状态。物流公司的 Agent 提供了查询接口，但格式是这样的：

```python
# 物流公司 A 的接口
POST /api/v1/query
{"tracking_no": "SF1234567", "carrier": "sf"}
# 返回：{"status": "in_transit", "eta": "2025-01-15"}
```

你写了一套适配代码。三个月后，另一个客户要求接入物流公司 B：

```python
# 物流公司 B 的接口
GET /logistics/track?order_id=SF1234567&company=sf
# 返回：{"state": 2, "estimated_delivery": "01/15/2025"}  # 字段名不同，状态枚举不同，日期格式不同
```

又写了一套适配。**每接入一家，就多一套定制代码。**

### 场景 2：团队间复用 Agent
A 团队做了一个翻译 Agent，B 团队想在自己的流程中调用它。

问题是：

+ A 团队的 Agent 接口是 gRPC，B 团队的技术栈是 HTTP
+ A 团队返回的翻译结果是 `{"translated": "..."}`, B 团队期望的是 `{"result": "...", "lang": "..."}`
+ A 团队的 Agent 没有文档说明它能翻译哪些语言，B 团队只能猜

**同一个公司内部，Agent 复用都这么难，更别说跨公司了。**

### 场景 3：多方 Agent 协商
用户让 Agent 订一张机票。Agent 需要：

1. 跟航司 Agent 协商航班和价格
2. 跟支付 Agent 确认支付方式
3. 跟保险 Agent 选购旅行保险

三个外部 Agent，三种接口风格，三种错误处理方式，三种认证机制。

**核心矛盾：每对接一个外部 Agent，就要写一套发现、通信、错误处理的适配代码。N 个 Agent 互相调用，就是 N×M 套适配。**

```plain
没有统一协议时：

  Agent A ←→ 自定义协议 ←→ Agent B
  Agent A ←→ 自定义协议 ←→ Agent C
  Agent B ←→ 自定义协议 ←→ Agent C
  Agent D ←→ 自定义协议 ←→ Agent A
  ...

  N 个 Agent = N×(N-1)/2 套适配代码
```

**缺的不是接口——是统一的「能力发现机制」和「通信协议」。**

## 四、A2A 是什么
A2A（Agent-to-Agent）是 Google 主导的开放协议，专门解决 Agent 之间的互操作问题。

一句话定位：**MCP 让 Agent 能调用工具，A2A 让 Agent 能找到并委托其他 Agent。**

技术基础：

+ 传输层：HTTP
+ 消息格式：JSON-RPC 2.0
+ 流式推送：Server-Sent Events (SSE)
+ 不绑定任何框架、语言或供应商

A2A 解决三件事：

1. **发现**：Agent 通过 Agent Card 声明自己的能力，其他 Agent 可以自动发现
2. **委派**：Client Agent 通过标准接口向 Server Agent 提交任务
3. **回传**：Server Agent 通过标准格式返回结果

---

## 五、A2A 协议核心机制
回到第一节的代码，逐个拆解其中涉及的协议机制。

### 5.1 Agent Card——Agent 的「名片」
Agent Card 是一个 JSON 格式的能力描述文件，暴露在固定端点 `/.well-known/agent-card.json`。任何 Agent 想调用另一个 Agent，第一步就是获取它的 Agent Card。

**类比：** 就像你去一家餐厅，先看门口的菜单——这家店叫什么、做什么菜、怎么点单、要不要预约。

回到代码中的 Agent Card 定义：

```python
agent_card = AgentCard(
    name="问答 Agent",                          # 我是谁
    description="一个通用问答 Agent，基于 DeepSeek 回答各种问题",  # 我能干什么
    version="1.0.0",                           # 版本号
    default_input_modes=["text/plain"],      # 我接受什么格式的输入
    default_output_modes=["text/plain"],     # 我返回什么格式的输出
    capabilities=AgentCapabilities(streaming=True),  # 我支持哪些特性
    supported_interfaces=[                   # 怎么找到我
        AgentInterface(protocol_binding="JSONRPC", url="http://127.0.0.1:9999"),
    ],
    skills=[skill],                          # 我有哪些具体技能
)
```

Agent Card 的关键字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| name | string | Agent 名称 |
| description | string | 功能描述，帮助其他 Agent 判断是否需要调用你 |
| version | string | 版本号 |
| supported_interfaces | list | 通信端点和协议（URL + 协议类型） |
| capabilities | object | 能力声明（是否支持流式、推送通知等） |
| skills | list | 具体技能列表，每个技能有独立的 id、名称、描述、标签 |
| default_input_modes | list | 支持的输入格式（MIME 类型） |
| default_output_modes | list | 支持的输出格式（MIME 类型） |
| security_schemes | map | 认证方式声明（API Key、OAuth、mTLS 等） |


### 5.2 Task 模型——任务的「一生」
A2A 的核心交互单元是 Task。一个 Task 从创建到完成，会经历一系列状态变化。

**类比：** 就像外卖订单——已下单 → 商家接单 → 制作中 → 骑手取货 → 已送达。

回到代码中的状态流转：

```python
# 1. Client 发送消息 → Server 创建 Task，状态为 SUBMITTED
# 2. Server 开始处理  → 更新为 WORKING
await updater.start_work(message=new_text_message("正在处理..."))
# 3. 处理完成        → 更新为 COMPLETED
await updater.complete(message=new_text_message("处理完成！"))
```

完整的 Task 状态枚举：

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| SUBMITTED | 任务已提交，等待处理 | 否 |
| WORKING | 正在处理中 | 否 |
| INPUT_REQUIRED | 需要用户提供更多信息才能继续 | 否（中断态） |
| AUTH_REQUIRED | 需要认证才能继续 | 否（中断态） |
| COMPLETED | 任务成功完成 | 是 |
| FAILED | 任务执行失败 | 是 |
| CANCELED | 任务被取消 | 是 |
| REJECTED | Agent 拒绝执行该任务 | 是 |


**值得注意的是 INPUT_REQUIRED 状态——** 这是 A2A 的一个重要设计：Agent 可以在处理过程中「反向」向调用方要信息。比如你让 Agent 预订酒店，Agent 发现你没说日期，它可以暂停任务，返回 INPUT_REQUIRED 状态并附带消息「请提供入住日期」，而不是直接报错。

### 5.3 Message 与 Artifact——过程 vs 结果
A2A 严格区分了两种数据类型：

| 概念 | 是什么 | 类比 | 用途 |
| --- | --- | --- | --- |
| **Message** | Agent 间的过程通信消息 | 微信聊天记录 | 传递状态更新、追问、中间说明 |
| **Artifact** | 任务的最终交付物 | 快递包裹 | 承载实际结果（文本、文件、结构化数据） |


回到代码：

```python
# Message：状态更新消息（过程信息）
await updater.start_work(
    message=new_text_message("正在处理..."),  # ← 这是 Message
)

# Artifact：最终结果（交付物）
await updater.add_artifact(
    parts=[new_text_part(text=result, media_type="text/plain")]  # ← 这是 Artifact
)
```

**为什么要区分？** 因为调用方关心的是 Artifact（结果），调试时才需要看 Message（过程）。如果混在一起，调用方要从一堆状态消息中提取真正有用的结果，增加了不必要的复杂度。

### 5.4 传输模式——三种通信方式
A2A 支持三种传输模式，适用于不同场景：

| 模式 | 原理 | 适用场景 | 代码中的体现 |
| --- | --- | --- | --- |
| **同步请求/响应** | Client 发请求，等 Server 处理完返回 | 快速任务（秒级完成） | `ClientConfig(streaming=False)` |
| **SSE 流式** | Client 发请求，Server 通过 SSE 实时推送进度 | 长任务，需要实时反馈 | `ClientConfig(streaming=True)` |
| **Push 通知** | Server 通过 Webhook 回调通知 Client | 超长任务（分钟/小时级） | 需配置 `PushNotificationConfig` |


回到代码，同步和流式的区别只在一行：

```python
# 同步：等任务完成才返回
config = ClientConfig(streaming=False)

# 流式：实时收到状态更新
config = ClientConfig(streaming=True)
```

## 六、A2A 与 MCP：不是替代，是不同层
这是最容易混淆的问题——A2A 和 MCP 到底什么关系？

**一句话区分：MCP 管 Agent****↔****Tool，A2A 管 Agent****↔****Agent。**

### 分层关系
```plain
┌─────────────────────────────────────────────┐
│              编排层（Supervisor / Pipeline）    │  ← 决定谁来做什么
├─────────────────────────────────────────────┤
│              协作通信层（A2A）                  │  ← Agent 之间怎么对话
├─────────────────────────────────────────────┤
│              能力接入层（MCP）                  │  ← Agent 怎么调用工具
├─────────────────────────────────────────────┤
│              工具和数据源                       │  ← 搜索、数据库、API...
└─────────────────────────────────────────────┘
```

**同一个 Agent 可以同时使用两者：** 内部通过 MCP 连接工具（搜索、数据库、代码执行），对外暴露 A2A 接口让其他 Agent 调用。

### 对比表
| 维度 | MCP | A2A |
| --- | --- | --- |
| 解决什么问题 | Agent 怎么调用工具 | Agent 怎么跟另一个 Agent 对话 |
| 通信对象 | Agent ↔ Tool（单向调用） | Agent ↔ Agent（双向协作） |
| 协议基础 | 自定义 JSON-RPC | HTTP + JSON-RPC 2.0 + SSE |
| 核心概念 | Tool、Resource、Prompt | Agent Card、Task、Message、Artifact |
| 典型场景 | 让 Agent 能搜索网页、查数据库 | 让客服 Agent 调用物流 Agent |
| 是否替代关系 | — | 不是，各管一层 |


**一个形象的类比：**

+ MCP 像是「工具箱」——Agent 打开箱子，拿出搜索、计算、数据库等工具使用
+ A2A 像是「电话」——Agent 拿起电话，找到另一个 Agent，委托它完成任务

## 七、适用场景与边界
### 适合用 A2A 的场景
| 场景 | 说明 |
| --- | --- |
| 跨组织 Agent 互操作 | 不同公司的 Agent 需要协作（如电商 Agent 调用物流 Agent） |
| 能力市场 / Agent 注册中心 | 集中发布和发现可用的 Agent 能力 |
| 团队间 Agent 复用 | 不同团队用不同框架开发的 Agent 需要互相调用 |
| 异构系统集成 | Python Agent 需要调用 Java Agent，技术栈不同但需要协作 |


### 不适合用 A2A 的场景
| 场景 | 说明 |
| --- | --- |
| 同进程内的 Agent 协作 | 用 Supervisor 模式的 handoff 就够了，没必要走 HTTP |
| 单团队、单一框架 | 内部 Agent 直接函数调用比走网络协议简单得多 |
| 任务简单、Agent 数量少 | 2-3 个 Agent 的场景，直接集成比引入协议更高效 |


### 常见误区
**误区 1：引入 A2A 就能解决任务路由问题**

A2A 解决的是「怎么通信」，不是「谁来做什么」。任务拆解和路由调度仍然是编排层（Supervisor / Pipeline）的职责。A2A 只是让路由的目标可以从「进程内的 Worker」扩展到「网络上的远程 Agent」。

**误区 2：A2A 可以替代 Supervisor 模式**

不能。Supervisor 是编排模式，A2A 是通信协议，它们在不同层工作。你仍然需要一个编排层来决定任务怎么拆、先调谁后调谁。A2A 只是让被调用的 Agent 可以在远程、可以用不同框架实现。

**误区 3：所有 Agent 间通信都应该走 A2A**

杀鸡用牛刀。如果两个 Agent 在同一个进程内、同一个团队维护、用同一个框架，直接函数调用比走 HTTP + JSON-RPC 简单得多。A2A 的价值在于「跨边界」——跨进程、跨团队、跨组织。

## 八、引入 A2A 前必须想清楚的事
| 检查项 | 问题 | 建议方案 |
| --- | --- | --- |
| **认证与授权** | 怎么确认调用方的身份和权限？ | Agent Card 中声明 `security_schemes`；跨组织用 OAuth 2.0，内部用 API Key，高安全场景用 mTLS |
| **超时与重试** | 远程 Agent 挂了或响应慢怎么办？ | 设置合理的超时（建议 30s 起）；可重试错误用指数退避；不可重试错误直接返回失败 |
| **幂等性** | 同一个 Task 重复提交怎么办？ | 利用 `messageId` 去重；关键操作设计幂等键；状态查询天然幂等 |
| **版本兼容** | Agent Card 变了，旧客户端怎么办？ | Agent Card 有 `version` 字段；SDK 支持旧版兼容模式；破坏性变更走版本协商（`A2A-Version` 参数） |
| **审计与可观测性** | 跨服务的调用链怎么追踪？ | 集成 OpenTelemetry；每个 Task 有唯一 `id` 和 `context_id` 串联日志；保留 Message 历史用于审计 |
| **错误处理** | 远程 Agent 返回格式不对怎么办？ | A2A 定义了标准错误类型（认证错误、验证错误、资源错误、系统错误）；对非标准返回做防御性解析 |
| **限流与成本** | 被大量 Agent 调用时怎么保护自己？ | 在 Server 端做速率限制；监控 Task 处理时长和资源消耗；对长时间运行的 Task 设置超时强制终止 |
