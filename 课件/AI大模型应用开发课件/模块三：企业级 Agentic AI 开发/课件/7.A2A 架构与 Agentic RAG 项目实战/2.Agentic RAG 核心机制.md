## 学习目标
+ 理解 **传统 RAG 与 Agentic RAG 的工程差异**。
+ 判断业务是否值得引入 **Agentic RAG**。
+ 理解 **五项核心能力**及其职责边界。
+ 理解 **意图、计划、工具、证据和反思**之间的控制关系。

---

## 一、什么是 Agentic RAG
Agentic RAG 是一种由**意图、状态和证据驱动**的检索增强架构。系统不再固定执行一次向量检索，而是根据问题决定**是否检索、使用哪些数据源、执行多少步骤，以及证据不足时如何修正或停止**。

它解决的不是“如何再接一个向量库”，而是以下业务问题：

+ **有些问题无需外部知识**，应直接生成。
+ **精确统计需要 SQL**，不能依赖语义相似度。
+ **最新信息来自网页或业务 API**，静态知识库无法覆盖。
+ **复合问题需要多个数据源**共同提供证据。
+ 检索结果可能**相关但不充分**，不能直接进入答案生成。
+ 信息缺失、越权或预算耗尽时必须有**明确退出路径**。

> Agentic RAG 不等于让模型自由调用所有工具，也不等于检索失败后重复执行。核心是**结构化决策、受控执行、显式状态和有界循环**。
>

## 二、传统 RAG 与 Agentic RAG 的差异
| 维度 | 传统 RAG | Agentic RAG |
| --- | --- | --- |
| 检索触发 | 默认所有问题都检索 | 根据意图和上下文判断 |
| Query 处理 | 原始问题直接向量化 | 补全、改写、过滤或拆解 |
| 数据源 | 通常是单一知识库 | 文档、SQL、Web、业务 API |
| 执行路径 | 固定线性流程 | 单路、多路、澄清、拒绝、循环 |
| 检索参数 | 固定 Top-K 和阈值 | 根据问题和预算动态设置 |
| 结果使用 | 检索结果直接拼接给模型 | 统一为 Evidence 后检查质量 |
| 失败处理 | 空结果或强行生成 | 重写、换源、降级或停止 |
| 复杂问题 | 一次检索处理全部目标 | 拆成有依赖关系的子任务 |
| 控制方式 | 固定 Pipeline | Node、Edge、条件分支与状态 |
| 可观测性 | 主要记录命中文档 | 记录路由、工具、Query、证据和终止原因 |


> **传统 RAG 并没有被淘汰。**问题类型稳定、数据源单一、一次检索即可满足质量要求时，固定流程通常更简单、更快。
>

## 三、Agentic RAG 的适用边界
### 1. 适合使用
+ **多种问题类型**共用一个用户入口。
+ 答案可能来自**文档、数据库、网页和业务 API**。
+ 问题包含**多个目标**，或步骤之间存在前后依赖。
+ 需要在答案生成前**显式检查证据质量**。
+ 检索失败后存在**可定义的修正动作**。
+ 需要记录**路由、工具调用和终止原因**。

### 2. 不应优先使用
+ **数据源单一且问题类型稳定**。
+ **一次混合检索**已经能够稳定满足要求。
+ **延迟预算极低**，不能接受额外决策和评分。
+ 业务流程必须完全确定，**不允许动态分支**。
+ 工具具有高风险副作用，但系统**没有审批和权限机制**。

### 3. 引入后的成本
+ 路由、规划和评分会增加**模型调用成本**。
+ 多工具调用扩大了**超时、限流和失败面**。
+ 动态控制流提高了**调试和测试复杂度**。
+ 循环必须设置**轮次、时间和调用预算**。
+ 路由、计划、Evidence 和轨迹需要**独立评测**。
+ **网页提示注入、越权访问和数据泄露**风险更高。

> **选择原则：**先确认固定 RAG 的具体失效模式，再引入与该失效模式对应的 Agentic 能力。
>

## 四、Agentic RAG 的五项核心能力
> 这五项能力按照系统运行阶段划分。每项能力都需要明确**输入、输出和失败出口**，但本节只讲职责，不展开代码。
>

### 1. 意图识别与查询路由
**定义**：理解用户的真实目标、知识需求、约束条件和风险，将自然语言问题转换为后续流程可以消费的决策结果。

**核心作用**：

+ 识别解释、比较、统计、改写、查询状态等任务类型。
+ 判断答案需要内部文档、结构化数据、实时状态还是公开信息。
+ 决定直接回答、检索、澄清、拒绝或转人工。
+ 判断问题是单一任务、复合任务还是依赖型任务。
+ 检查用户编号、订单号、商品、时间范围等关键槽位。
+ 在任何数据访问前识别敏感或越权请求。

**应用场景**：

| 用户输入 | 识别结果 | 路由决策 |
| --- | --- | --- |
| 把商品介绍压缩到 50 字 | 文本改写，不需要外部知识 | 直接生成 |
| 耳机拆封后能退货吗 | 售后政策解释，需要内部知识 | 内部政策检索 |
| U1001 最近 30 天买了几单 | 精确订单统计 | 结构化数据库查询 |
| 查询品牌官网最新公告 | 强时效公开信息 | 网页搜索 |
| 我最近买了几单 | 缺少受控用户身份 | 澄清或从登录态补充 |
| 导出所有买家的手机号 | 敏感批量数据请求 | 拒绝 |


### 2. 自适应检索
**定义**：消费路由结果，根据问题表达、实体约束、复杂度和预算，动态生成具体的检索方式、Query 和参数。

**核心作用**：

+ 对指代、省略和口语表达进行补全或改写。
+ 在语义检索、关键词检索、混合检索和结构化查询之间选择。
+ 将商品、政策类型、地区和时间范围下推为过滤条件。
+ 动态设置召回数量、相关性门槛、重排数量和超时时间。
+ 将复合问题拆成多个可并行或串行的检索步骤。
+ 为无结果、低相关和数据源不可用预设降级路径。

**应用场景**：

| 问题特征 | 检索策略 |
| --- | --- |
| 明确退货政策类型 | 政策类型过滤 + 小范围语义检索 |
| 商品名称存在口语别名 | 关键词与语义混合检索 |
| 开放式选购问题 | 多 Query 召回后重排 |
| 多轮对话出现“它” | 补全商品名称后再检索 |
| 同时需要政策和订单 | 政策检索与 SQL 查询并行 |
| 延迟预算严格 | 限制为单轮、小召回和小并行度 |


### 3. 工具调用
**定义**：将 Milvus、SQL、Web Search 和业务 API 封装为具有输入约束、权限、超时和错误语义的可执行能力。

**核心作用**：

+ 用明确的工具契约描述参数、返回值和适用范围。
+ 将模型建议与真实执行隔离，程序层负责最终校验。
+ 对用户身份、订单归属和敏感字段执行权限检查。
+ 将异构结果统一为工具结果和可引用证据。
+ 区分参数错误、权限拒绝、空结果、超时和临时故障。

**应用场景**：

+ **Milvus 工具**检索内部退换货政策。
+ **SQL 工具**统计订单数量和实付金额。
+ **Web Search 工具**查询品牌官网最新公告。
+ **业务 API 工具**读取订单实时配送状态。

### 4. 自我反思
**定义**：在答案生成前检查证据的相关性、约束一致性、覆盖度和充分性，并根据缺口决定下一动作。

**核心作用**：

+ 检查所需数据源是否全部返回证据。
+ 检查用户、商品、政策类型和时间范围是否匹配。
+ 判断证据是否覆盖问题中的全部目标。
+ 识别内部政策与公开网页之间的冲突。
+ 根据失败原因选择接受、重写、换源、澄清或停止。

**应用场景**：

| 检查结果 | 下一动作 |
| --- | --- |
| 政策、订单和官网证据齐全 | 生成完整答案 |
| 政策相关但缺少例外条件 | 改写 Query，补充检索例外条款 |
| 订单属于其他用户 | 拒绝继续执行 |
| 官网搜索无结果 | 标记公开信息缺口，生成部分答案 |
| 多个来源存在版本冲突 | 显示冲突并要求人工确认 |
| 达到最大检索轮数 | 停止继续调用工具 |


### 5. 多步推理
**定义**：将复杂目标拆成多个子任务，建立依赖关系，按串行、并行或汇聚模式执行，并合并各步骤证据。

**核心作用**：

+ 将一个复合问题拆成独立、可验证的步骤。
+ 判断步骤之间是否存在数据依赖。
+ 对无依赖读取任务并行执行，降低总体延迟。
+ 将上游结构化结果绑定为下游工具参数。
+ 合并、去重并对齐不同来源的 Evidence。
+ 在局部步骤失败时决定停止、降级或局部重规划。

**应用场景**：

| 模式 | 示例 |
| --- | --- |
| 单源单步 | 只查询耳机退货政策 |
| 多源并行 | 同时查询订单、内部政策和官网公告 |
| 串行依赖 | 先找出金额最高的商品，再查询该商品政策 |
| 动态展开 | 对订单中的多个商品分别检查价保资格 |
| 汇聚合并 | 将订单事实、政策条款和公开公告合成售后建议 |


### 五项能力的关系
1. **意图识别与路由**先确定用户目标、知识需求和执行方向。
2. **自适应检索**将路由结果转换为数据源、查询语句和检索参数。
3. **工具调用**执行真实的数据访问，并返回统一格式的 Evidence。
4. **自我反思**检查 Evidence 是否相关、完整且满足问题约束。
5. **多步推理**负责复杂任务的拆解、依赖控制、结果合并和局部重规划。

> **五项能力不是五个独立 Agent。**它们可以由规则、模型和程序节点共同实现，关键是职责和状态边界清晰。
>

## 六、工程约束
+ 路由结果必须是**结构化决策**，而不是自由文本。
+ 用户身份来自**认证上下文**，不能由模型猜测。
+ 工具参数必须经过**程序校验**。
+ 最终答案只能引用 **Evidence**。
+ 检索循环必须有**预算和终止原因**。
