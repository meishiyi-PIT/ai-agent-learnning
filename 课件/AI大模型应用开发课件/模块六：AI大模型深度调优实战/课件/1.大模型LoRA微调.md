# 大模型 LoRA 微调

## 第一章 微调这件事：从全量微调到 PEFT
### 1.1 大模型已经很强了，为什么还要微调？
现在的大模型（DeepSeek、Qwen 这些）能写文章、写代码、做总结，通用能力确实强。但一到真实业务里就会发现：**模型"会"，不等于它"稳定地按你的要求会"**。

举几个很常见的场景：

+ 你希望它每次都输出固定结构的 JSON，好让下游程序解析——它隔三差五给你加一段"好的，以下是结果："；
+ 你希望它用你们行业的黑话回答问题，比如法律文书的腔调、客服的话术——它一张嘴就是百科味儿；
+ 你希望它做分类、抽取、评分这类任务时判断标准统一——它心情好了判 A，心情不好判 B。

这些"风格、格式、判断标准"层面的东西，靠提示词能管一时，管不了稳定。这时候就该微调出场了。

一句话说清微调在干什么：**<font style="color:rgb(13, 13, 13);">大模型微调是利用特定领域的数据集对已预训练的大模型进一步训练的过程。它旨在优化模型在特定任务上的性能，使模型能够更好地适应和完成特定领域的任务。</font>**

### 1.2 三条技术路线的分工
实际项目里，定制模型行为有三条路，别搞混了：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789021581792-d8048cb9-0f61-4723-bef4-69f4cfd2b34e.png)

行业里流传一句口诀：**提示词解决临时要求，RAG 解决外部知识，微调解决稳定行为。**

很多新手容易踩的坑是：把"让模型知道公司最新产品价格"这种知识类需求拿去微调——这是 RAG 的活，微调干了也白干，知识还会过时。

### 1.3 全量微调的三座大山
既然要微调，最直接的方式就是全量微调（Full Fine-tuning）：把模型所有参数都放开，接着训。理论上效果上限最高，但工程上有三座大山：

**第一座：显存。** 训练时显存里要同时放四样东西——模型权重、梯度、优化器状态、中间激活值。以一个 7B 模型为例，全量微调轻松吃掉 60GB 以上显存，一张 24GB 的 RTX 4090 根本塞不下。模型越大越离谱。

**第二座：存储。** 全量微调每产出一个任务模型，就是一份完整模型副本。7B 模型一份十几 GB，十个任务就是一百多 GB，硬盘和版本管理都遭罪。

**第三座：风险。** 全量更新参数意味着模型原有的通用能力可能被破坏——新任务学好了，老本行忘了，这就是"灾难性遗忘"。数据质量差、学习率没调好，模型很容易"学歪"。

### 1.4 PEFT：只动一小撮参数的聪明办法
<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789376012258-7624dfdf-5d98-43a4-b703-f6dfc48e8ac7.png)

PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）这一大家子的共同思路是：**冻结原模型绝大部分参数，只训练一小撮参数或新增少量参数，用极低成本逼近全量微调的效果。**

主流方法一张表看懂：

| 方法 | 思路 | 训练参数量 | 特点 | 现状 |
| --- | --- | --- | --- | --- |
| **Adapter** | 在 Transformer 层里插入小型神经网络模块，只训它 | 少 | 会引入额外推理延迟 | 用得少了 |
| **Prompt Tuning** | 不碰模型，只在输入前加可训练的"软提示"向量 | 极少 | 效果依赖模型规模，小模型上偏弱 | 特定场景 |
| **Prefix Tuning** | Prompt Tuning 加强版，每一层都加可训练前缀 | 极少 | 比 Prompt Tuning 强一些 | 特定场景 |
| **BitFit** | 只训练所有 bias 偏置项 | 极少 | 简单到极致，效果有限 | 研究向 |
| **IA³** | 用可学习的缩放向量去缩放激活值 | 极少 | 参数量最省 | 小众 |
| **LoRA** | 冻结原权重，旁路训练两个低秩小矩阵 | 少 | 效果好、无推理延迟、生态成熟 | **绝对主流** |
| **QLoRA** | 基座 4bit 量化 + LoRA | 少 | 显存再砍一半以上，消费级显卡救星 | **主流** |


为什么最后是 LoRA 赢了？几个原因凑在一起：效果能打（多数任务接近全量微调）、实现简单（在线性层旁边挂个分支就行）、推理无额外开销（训练完可以合并回原权重）、生态极好（PEFT、TRL、LLaMA-Factory、Unsloth 全都把它当一等公民）。

所以这份文档的核心就是 LoRA。不过在拆开 LoRA 之前，得先还一笔数学债——"低秩"的"秩"到底是什么。搞懂它，LoRA 的所有设计你都会觉得很自然；搞不懂，调参永远靠猜。

## 第二章 数学地基：把"秩"这件事讲明白
### 2.1 秩：矩阵里"不重复的干货"有多少
教科书定义：矩阵的秩（Rank），是它线性无关行（或列）的最大数目。行秩永远等于列秩，所以统称秩。

定义没错，但约等于没说。换个说法：**秩衡量的是一个矩阵里"真正不重复的信息"有多少。**

用个职场例子。你是个项目经理，手下 5 个人，用矩阵的 5 列代表 5 个人的工作产出：

+ 员工 1：核心后端，写了底层代码（独立贡献）；
+ 员工 2：核心设计，画了全部界面（独立贡献）；
+ 员工 3：产品经理，写了需求文档（独立贡献）；
+ 实习生 A：每天把员工 1 的代码复制一遍，加点注释就当自己的活；
+ 实习生 B：每天把员工 2 的图换个背景色重新交一遍。

这个"5 列矩阵"的秩是多少？**3。** 因为实习生 A 的产出 = 员工 1 的产出 × 某个系数，实习生 B 同理——他俩是"线性相关"的冗余，没有提供任何新的信息维度。你发着 5 个人的工资，真正干活的维度只有 3 个。

> "线性相关"和"线性无关"翻成人话就是：
>
> + **线性相关**：队伍里有重复能力，至少一个人能被别人"组合"出来；
> + **线性无关**：每个人都带来了别人替代不了的新能力。
>



```python
#什么是线性无关？
#一组向量中任意向量都不能表示为其他向量的线性组合时称为线性无关。例如：
# 
independent_cols = [
    [1, 0],  # 无法通过 [0, 1] 的标量倍得到
    [0, 1]   # 也无法通过 [1, 0] 得到
]

# 线性相关的行向量
dependent_rows = [
    [1, 2, 3],
    [2, 4, 6],  # 等于第一行 × 2
    [0, 0, 0]   # 零向量总是线性相关
]
```

### 2.2 三个视角看秩
秩这个概念妙在可以从好几个角度看，而且它们是同一件事。

**视角一：方程组视角——有效线索的数量**

假设你在破案，要确定小偷的身高 x、体重 y、年龄 z，需要 3 条独立线索。目击者给了你三条：

```plain
线索A：身高 + 体重 = 240
线索B：身高 - 体重 = 140
线索C：2 × 身高 = 380
```

看着是三条，但你一算就发现：线索 C = 线索 A + 线索 B。C 完全是句废话，没提供任何新约束。这个方程组的秩只有 2——**方程的秩，就是有效约束的个数**。未知数有 3 个，独立约束只有 2 个，所以解不唯一，有无穷多组。

**视角二：空间视角——能"撑开"多大的空间**

把矩阵的每一列看成一个向量。如果这些列向量互不共线、互不共面，它们就能"张成"（撑开）一个高维空间；如果其中几个是冗余的，撑开的空间就塌了。秩 = 2 的 3×3 矩阵，所有列向量只能铺满一个平面；秩 = 1，全挤在一条线上。

**视角三：变换视角——信息压缩有多狠**

矩阵本质是一个变换器：输入 x，输出 Ax。秩描述的是这个变换器把空间"压扁"到什么程度：

+ 满秩：3 维进，3 维出，信息无损，变换可逆；
+ 秩 = 2：3 维物体被拍成 2 维的"影子"，深度信息丢了；
+ 秩 = 1：所有输出被压到一条线上；
+ 秩 = 0（零矩阵）：万物归一（个原点），信息全灭。

三个视角统一起来：**秩:一个矩阵的秩是指矩阵中线性独立行或列的最大数目.一个矩阵的秩越大，它的信息含量就越大.**

```python
什么是矩阵的秩
对于 m×n矩阵 
A ：
行秩 = 矩阵中线性无关的行向量的最大数量
列秩 = 矩阵中线性无关的列向量的最大数量
关键定理：行秩 = 列秩 （统称为矩阵的秩）
# 秩为1的矩阵示例（只有第一行线性无关）
A = [[1, 2, 3],
     [2, 4, 6],  # 第2行 = 第1行 x 2
     [3, 6, 9]]  # 第3行 = 第1行 x 3

# 秩为2的矩阵示例（前两行线性无关）
B = [[1, 0, 2],
     [0, 1, 3],
     [1, 1, 5]]  # 第3行 = 第1行 + 第2行
```

### 2.3 低秩分解：用两个小矩阵装下大矩阵
当矩阵秩 𝑟≪min(𝑚,𝑛) 时称为低秩矩阵：

现在关键的来了。既然秩衡量"有效信息量"，那一个低秩矩阵里的信息，理论上可以用更少的东西装下。

举个具体的账：一个 512×512 的矩阵有 262,144 个数。如果保留 r = 8 就够了，那么两个小矩阵一共只有 512×8 + 8×512 = 8,192 个数——**压缩率 97%**。

## 第三章 LoRA 原理深度拆解
### 3.1 核心公式，一行就够
<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789377561960-6a096cf7-6b90-4725-8db8-592764ea0816.png)

LoRA（Low-Rank Adaptation，低秩适配），微软研究院 2021 年在论文《LoRA: Low-Rank Adaptation of Large Language Models》中提出。**它通过在冻结的预训练模型权重旁添加小型可训练的低秩矩阵，显著降低了微调过程中的计算和内存需求，无需重新训练整个模型。**核心思想浓缩成一行公式：

```plain
W' = W + ΔW = W + (α/r) · B·A
```

+ **W**：预训练权重，d×d，**冻结**，一个字节都不改；
+ **B**：d×r 的矩阵，可训练（有的论文记作升维矩阵）；
+ **A**：r×d 的矩阵，可训练（降维矩阵）；
+ **r**：秩，远小于 d 和 d，一般取 4~64；
+ **α/r**：缩放因子，控制 LoRA 分支的输出幅度，α 是超参数。

前向传播时，输入 x 走两条路：原路 `Wx` 保留模型的老本事，旁路 `BAx` 学习新任务的增量，最后相加：

```plain
h = Wx + (α/r)·BAx
```

打个比方：全量微调是把整栋楼拆了重装修；LoRA 是在楼里的关键位置加几个可调节装置，主体结构一根钢筋不动，但整栋楼的功能和风格变了。

### 3.2 参数账本：到底省了多少？
以国产模型常见的尺寸算账。比如 Qwen / DeepSeek 这个级别的模型，注意力层一个权重矩阵 4096×4096：

```plain
全量微调这个矩阵：4096 × 4096 = 16,777,216 个参数要更新

LoRA（r = 8）：
  B: 4096 × 8  = 32,768
  A: 8 × 4096  = 32,768
  合计         = 65,536

65,536 / 16,777,216 ≈ 0.39%
```

训练参数量直接砍到原来的 0.4%。放到整个模型上（通常给注意力层的 Q、V 投影都挂上 LoRA），可训练参数一般只占原模型的 **0.1% ~ 1%**。

参数量小了，连锁反应是显存大头全没了。回顾一下显存四笔账：

| 显存构成 | 全量微调 | LoRA |
| --- | --- | --- |
| 权重内存 | 全量加载 | 全量加载（这部分省不掉，基座还得在） |
| 梯度内存 | 所有参数都要存梯度 | 只给 A、B 存，≈ 减少 99% |
| 优化器状态（Adam 的一阶/二阶动量） | 每个参数两份 | 只给 A、B 存，≈ 减少 99% |
| 激活值 | 大 | 基本不变（和 batch、序列长度相关） |


实测数据：7B 模型全量微调约需 60GB 显存，LoRA 大概 23GB——单张 RTX 4090 就能跑。再配合 QLoRA 把基座 4bit 量化加载（第四章实战就是这么跑的），显存还能再砍一大截。训练速度也快，反向传播要算的梯度少了，吞吐能提升接近一倍。

:::info
LoRA 的核心思想是将预训练模型的权重矩阵分解为两个低秩矩阵的乘积。假设原有矩阵权重为W微调过程中拆解成两个低秩矩阵A、B的乘积，冻结原有矩阵`+`两个低秩矩阵的乘积来适应新的任务。 (在不修改模型参数的情况下，通过添加一个额外的可训练模块，对模型行为进行小范围、有针对性的调整。)  
优点：减少了训练参数数量，从而降低了计算和存储成本。资源少的情况下依然可以进行模型微调。灵活行较高能使用多种场景。

目前主流的微调方式就是LoRA低秩矩阵微调，训练速度非常快，节省资源，但训练结果很多时候是不稳定的，有一定玄学在里面，因为微调过程也是依赖模型的反向更新，有时候没有更新到相关知识点，就会导致出现模型幻觉，需要多次尝试，

:::

LoRA 的主要特点和优势

1. 参数高效： LoRA 仅训练少量额外参数，而不是完整的模型权重。典型场景下可训练参数减少 10-100 倍（具体取决于原模型尺寸和r值）
2. 训练速度快： 由于需要更新的参数大幅减少，LoRA 微调比全参数微调速度更快，训练时间更短。
3. 存储空间小： LoRA 适配器通常只有几十到几百 MB，而完整的模型可能需要几十 GB。这使得存储和分发多个专门的微调版本变得更加实际。
4. 推理性能优化： LoRA 权重可以在推理前合并回原始模型，不会增加推理时的计算开销。
5. 可组合性： 多个 LoRA 适配器可以被合并或按不同比例混合，创建具有混合能力的模型。
6. 质量保持： 在许多任务中，LoRA 微调的性能与全参数微调相当甚至更好，同时减少了过拟合风险。

### 3.3 初始化的玄机：为什么 A 随机、B 置零？
LoRA 论文的初始化方案：**A 用小的随机高斯值初始化，B 初始化为全零矩阵。**

这样训练刚起步时，B·A = 0，旁路输出为零，模型和原始预训练模型**逐比特一致**。LoRA 分支从零开始，平滑地"长"出任务需要的能力，不会一上来就用随机噪声污染模型。

反过来想两种作死方案：

+ **A、B 都置零**：ΔW 永远是 0，而损失对 B 的梯度正比于 A、对 A 的梯度正比于 B——俩都是零，梯度也是零，互相锁死，永远学不到东西（梯度消失的死局）；

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789378236933-1b35558f-b9f7-4326-b05f-d86ffbf6be8a.png)

+ **A、B 都随机初始化**：初始时刻 B·A 是个不小的随机矩阵，相当于模型还没训练就先被"打了一拳"，原有能力被随机扰动破坏，收敛变慢甚至翻车。

A 随机（提供对称性破缺，让梯度能流动）、B 置零（保证起点干净），这个不对称设计是深思熟虑的结果。顺带一提，A 用正态分布还有个好处：小的初始值保证训练初期梯度稳定传播，不会消失也不会爆炸。

### 3.4 训练全流程
<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789021881551-a06636b0-17a6-4bc3-9c63-147a99ac623f.png)

训练完成后有两种用法：

1. **合并权重（Merge）**：`W_new = W + (α/r)·BA`，把增量直接加回原矩阵。合并后的模型结构、参数量、推理速度和原模型**完全一样**，零额外延迟。要上线部署就用这种。
2. **保持分离（Adapter 模式）**：LoRA 权重单独存成一个小文件（通常几 MB 到几百 MB），推理时动态加载。一个基座模型可以挂 N 个 LoRA——客服一个、法务一个、写代码一个，几秒钟热切换。多任务场景用这种。

### 3.5 LoRA 加在哪些层？好钢用在刀刃上
Transformer 每层有两类密集权重矩阵：

+ **注意力层**：Q、K、V、O 四个投影矩阵。Wq 决定"关注什么"，Wk 决定"被检索的特征"，Wv 决定"取出什么内容"，Wo 把多头结果拼回隐藏维度；
+ **前馈层（FFN）**：升维、降维两个线性层，负责非线性特征加工。

LoRA 原论文的核心实验结论：

+ **预算有限时，同时适配 Wq 和 Wv 性价比最高**，能逼近全量微调的效果。Q 影响模型"问什么问题"，V 影响"给出什么内容"，调这两个最直接改变模型对任务的理解和表达；
+ 小秩就够：r 开到 4、8 已经能捕捉任务所需的主要变化方向，再加大 r 并没有覆盖更多有意义的子空间；
+ **给更多矩阵挂 LoRA，常常比把单一矩阵的 r 调大更划算**。

```python

target_modules = ["q_proj", "k_proj", "v_proj", "o_proj",
                  "gate_proj", "up_proj", "down_proj"]
```

至于嵌入层、LayerNorm 和 bias：嵌入层参数量大但变动小，冻结最划算；LayerNorm 参数少得可怜，直接更新也不心疼；bias 学得快，不需要 LoRA 辅助。默认都别碰。

### 3.6 LoRA 的边界：什么时候它不灵？
LoRA 不是银弹，这几个场景要有心理预期：

+ **低秩假设失效时**。如果目标任务和预训练数据差异极大（比如让一个纯文本模型突然学一门全新的形式语言），需要的权重变化可能真是高秩的，LoRA 的表达力会不够，老老实实全量微调；
+ **想注入大量新知识时**。LoRA 擅长调"行为"（格式、风格、判断标准），不擅长灌"知识"。知识类需求出门右转找 RAG；
+ **r 和 target_modules 要调**。没有放之四海皆准的最优值，得在评测集上试；
+ **数据不行神仙难救**。LoRA 只降低训练参数量，不会自动修复数据噪声、标注冲突、任务定义不清。微调圈的玄学时刻，八成最后都追溯到数据问题。

### 4.2 数据：质量永远大于数量
LoRA 微调不是把数据塞给模型，而是**用一批高质量、目标明确的样本，把模型往你要的方向轻轻推过去**。几百条精品数据，经常吊打几万条脏数据。

好数据的六个标准：

1. **任务目标单一**：训投诉分类就全是投诉分类，别混闲聊百科；
2. **输入贴近真实**：真实用户有口语、有错别字、有省略，训练数据别写得太"标准"；
3. **输出格式统一**：同类输入的输出结构、字段、详略必须一致；
4. **答案互不冲突**：同一个问题，不能这条数据标 A、那条标 B；
5. **要有边界样本**：模糊输入、异常输入、该拒答的输入，都得教；
6. **留好验证集/测试集**：没有测试集的微调等于闭眼开车。

                          DataCollatorForLanguageModeling,#数据整理器, 用于将分词后的输入数据整理成模型训练所需要的格式

model_name="/root/autodl-tmp/code/model"
#设置微调后模型保存的路径
finetuned_model_path="/root/autodl-tmp/code/fined"

model = AutoModelForCausalLM.from_pretrained(

tokenizer = AutoTokenizer.from_pretrained(model_name)
def preprocess_function(examples):
    """
    标准的 SFT 数据处理流程
    - 只训练 assistant 的回答部分
    - 正确处理截断和 EOS token
    - 保持 chat template 格式
    """
    max_length = 1024

    input_ids_list = []
    labels_list = []

    for question, cot, response in zip(
        examples["Question"],
        examples["Complex_CoT"],
        examples["Response"]
    ):
        # 构建对话消息
        messages = [
            {
                "role": "system",
                "content": "您是一位在临床推理、诊断和治疗计划方面具有高级知识的医学专家。请回答以下医学问题。"
            },
            {
                "role": "user",
                "content": question
            },
            {
                "role": "assistant",
                "content": f"<think>\n{cot}\n</think>\n{response}"
            }
        ]

        # ============ Step 1: 生成完整对话 ============
        full_text = tokenizer.apply_chat_template(
            messages,
            tokenize=False,
            add_generation_prompt=False
        )

        # ============ Step 2: 生成 prompt 部分（不含 assistant 回复）============
        prompt_messages = messages[:-1]  # 去掉最后的 assistant
        prompt_text = tokenizer.apply_chat_template(
            prompt_messages,
            tokenize=False,
            add_generation_prompt=True  # 添加 assistant 开始标记
        )

        # ============ Step 3: Tokenize ============
        full_ids = tokenizer.encode(full_text, add_special_tokens=False,
                                    max_length=max_length,padding="max_length", truncation=True)
        prompt_ids = tokenizer.encode(prompt_text, add_special_tokens=False,
                                      max_length=max_length,padding="max_length", truncation=True)

        # ============ Step 4: 处理截断（保留 EOS）============
        # apply_chat_template 已经自动添加了 EOS，所以只需要处理截断
        if len(full_ids) > max_length:
            # 截断到 max_length-1，然后手动添加 EOS
            full_ids = full_ids[:max_length - 1]
            full_ids.append(tokenizer.eos_token_id)
        # 如果没有超长，full_ids 已经包含 EOS，不需要额外处理

        # ============ Step 5: 构建 labels（关键！）============
        # prompt 部分设为 -100（不计算 loss）
        # assistant 部分保留原值（计算 loss）
        prompt_len = len(prompt_ids)
        labels = (
            [-100] * prompt_len +           # prompt 部分：不训练
            full_ids[prompt_len:]            # assistant 部分：训练（包含 EOS）
        )

        # 确保长度一致
        labels = labels[:len(full_ids)]

        input_ids_list.append(full_ids)
        labels_list.append(labels)

    return {
        "input_ids": input_ids_list,
        "attention_mask": [[1] * len(ids) for ids in input_ids_list],
        "labels": labels_list
    }

dataset = load_dataset(

    data_files={

        "valid": "/root/autodl-tmp/code/data/validation.json"
    }
)
dataset = dataset.map(preprocess_function, batched = True)

#设置微调模型参数

    lora_dropout=0.05,#dropout
    bias='none',#微调偏置
    task_type=TaskType.CAUSAL_LM
)
#获取应用了Lora后的微调模型
model = get_peft_model(model,lora_config)
model.config.use_cache = False
#实际上直接计算所有可训练参数就行。
trainable_params = 0
all_params = 0
for _, param in model.named_parameters():
    num_params = param.numel()
    all_params += num_params
    if param.requires_grad:
        trainable_params += num_params
print(f"可训练参数量: {trainable_params}")
print(f"总参数量: {all_params}")
print(f"可训练参数占比: {100 * trainable_params / all_params:.2f}%")

model.enable_input_require_grads() # 开启梯度检查点时，要执行该方法
#初始化可视化功能
#训练参数配置
training_args = TrainingArguments(
    output_dir=finetuned_model_path,#输出目录，用于保存模型和日志
    label_names=["labels"],  # 显式指定标签名称，确保 Trainer 正确识别 labels
    overwrite_output_dir=True,#覆盖输出目录的现有内容
    num_train_epochs=20,#训练的总轮次
    per_device_train_batch_size=6,#每个训练设备上的批次大小
    per_device_eval_batch_size=6,#每个评估设备上的批次大小
    save_steps=10,#每隔多少步保存一次模型
    save_total_limit=5,#保存的模型文件数量限制
    prediction_loss_only=True,#在评估期间只返回损失
    report_to="tensorboard",  # 关键：启用 tensorboard 上报
    logging_dir="./logs",
    save_strategy="epoch",
    #梯度累积步数
    #通过将多个小批量的梯度累积起来，然后一次性更新模型参数，从而在有限的内存资源下实现相当于更大批量的训练效果。
    #当累积的步数达到预设的 gradient_accumulation_steps 时，使用累积的梯度更新模型参数，并清零累积的梯度。
    #节省内存
    #模拟大批量训练
    #提高训练稳定性
    gradient_accumulation_steps=16, #梯度累积步数
    #梯度检查点，用于减少深度学习模型训练过程中内存占用
    #反向传播需要存储前向传播中每一层的中间激活值（activations），以便计算梯度。
    # 对于非常深的模型或大批量数据，这些激活值会占用大量内存
    #Gradient Checkpointing 的核心思想是只存储部分激活值，并在反向传播时重新计算其他激活值，从而减少内存占用。
    gradient_checkpointing=True,#启用梯度检查点
)

#创建模型数据整理器

    tokenizer=tokenizer,
    mlm=False #准备数据以进行标准语言模型任务

    eval_dataset=dataset["valid"] #评估的数据集

trainer.train()

### 4.4 超参数调优的实用心法
别一上来就网格搜索，按这个顺序来：

1. **先用保守参数跑通**：r=8 或 16，α=2r，lr=2e-4，3 个 epoch，q_proj+v_proj。先证明流程通、数据没格式错误；
2. **小数据配小秩**：<5K 样本，r=8 起步；>50K 样本再考虑 r=32+。数据少秩大，过拟合套餐一份；
3. **复杂任务组合拳**：加大 r 到 32/64 + 开 rsLoRA + 挂载模块扩到 FFN，三件套一起上；
4. **给更多层挂 LoRA，往往比给单一层加大 r 更值**；
5. **学习率别贪大**：LoRA 常用 1e-4 ~ 3e-4，超过 5e-4 很容易把模型训得说胡话。

### 4.5 评测：别只盯着 loss 看
loss 下降只说明模型在"背"训练数据，不代表真实效果好。正确的评测要做**三组对比**：

+ **裸基座模型**：微调到底有没有用？
+ **基座 + 精心写的提示词**：如果微调连一个好提示词都打不过，那这轮微调价值存疑；
+ **LoRA 微调后的模型**：最终选手。

评测维度按任务来：分类任务算准确率/F1；生成任务做人工评分或让强模型（如 DeepSeek-V3）辅助打分；业务任务建一个**固定的 Bad Case 集**，每轮训练后原样重测，防止按下葫芦浮起瓢。重点看：格式稳定性、风格一致性、边界输入表现、幻觉控制。

### 4.6 常见坑清单
1. **以为数据越多越好**——低质量数据越多，模型越乱，小而准 > 大而脏；
2. **目标定得太抽象**——"让模型懂法律"不是微调目标，"让模型按《合同法》第 X 条格式输出审查意见"才是；
3. **拿知识库需求去微调**——知识会过时，用 RAG；
4. **没有测试集**——无法证明模型变好了，全凭感觉；
5. **训练/推理模板不一致**——chat template 对不上，效果莫名其妙地差；
6. **epoch 贪多**——第 3 轮以后多半是过拟合表演时间；
7. **LoRA 训练结果"玄学"**——本质是反向传播没更新到相关知识点，或者数据本身有冲突。先查数据，再调参数，最后才考虑换方案。
