# Vibe Coding 与 Spec Coding 急速开发流
---

## 一、Vibe Coding（交互/直觉式编码）
### 1.1 概念起源
Vibe Coding 这个词最早由 Andrej Karpathy（前 OpenAI/Tesla AI 负责人）在 2025 年初公开提出。他当时的表述大意是：

> 彻底沉浸在直觉节奏里，把代码本身抛到脑后，只管往前冲。
>

用更接地气的话说：**别管代码长什么样，先把你脑子里的画面说出来，AI 帮你落地**。

### 1.2 四条核心信条
1. **意图先行**：告诉 AI "我要什么结果"，而不是手把手教它怎么写
2. **快速试错**：别指望一步到位，走"生成 → 跑一遍 → 改一改"的循环
3. **信任但抽查**：大方向信 AI，关键环节自己过一眼
4. **喂好上下文**：持续把背景信息整理好丢给 AI，它才不会跑偏

### 1.3 什么时候适合用
**放心用的场景：**

+ 快速搭原型、验证点子能不能跑通
+ 个人练手项目，搞砸了也不心疼
+ 边做边摸索方向的探索式开发
+ 前端/UI 这类"一眼就能看出对不对"的工作

**要掂量一下的场景：**

+ 线上核心业务（金融、医疗之类）
+ 涉及密码、密钥、加密的安全敏感模块
+ 对性能有极致要求的场景

### 1.4 本质是什么
Vibe Coding 不是让你瞎搞。它的核心转变是**把注意力从"代码怎么写"挪到"产品好不好用"**。

听起来很美好，但它也不是万能的。当项目规模变大、需要多人协作、或者对代码质量有硬性要求时，光靠直觉就不够了

## 二、Spec Coding（规范驱动编码）
### 2.1 为什么光靠直觉不够
Vibe Coding 做小东西很爽，但项目一膨胀就会撞墙：

+ **质量失控**：AI 搞出能跑但乱七八糟的代码，技术债越堆越多
+ **前后打架**：不同对话里 AI 给出互相矛盾的实现方案
+ **只见树木不见森林**：AI 盯着眼前小功能，不管整体架构
+ **协作噩梦**：没统一规范的话，不同人（或不同会话）写的代码风格天差地别



如何避免？—— **在让 AI 动手之前，先跟它签一份"合同"**——把要做什么、怎么做、做到什么程度全部写清楚。AI 有了这份合同，就不会自由发挥到离谱；你有了这份合同，验收也有据可依。

这就是 **SDD（Specification-Driven Development，规范驱动开发）** 的核心思路。

### 2.2 SDD 到底在干嘛
SDD（Specification-Driven Development）的核心就一句话：**先把规矩定清楚，再让 AI 照着规矩干活**。

这里的"规矩"就是你和 AI 之间的合同，三件事写明白：

+ **做什么**（功能需求）→ 交给 PRD
+ **怎么做**（技术方案）→ 交给 SPEC
+ **做到什么程度**（质量标准）→ 交给质量规范

### 2.3 PRD：需求怎么写
PRD（Product Requirements Document）回答的是"到底要做啥"。

**用户故事的写法套路：**

```plain
我是 [某种角色]，
我想 [做某件事]，
这样我就能 [达到某个目的]。
```

举个例子：

```plain
我是博客读者，
我想按标签过滤文章，
这样我就能快速找到感兴趣的内容。
```

**验收标准怎么定：**

```plain
前提：库里有20篇文章，5篇打了"Python"标签
动作：用户点了"Python"标签
结果：页面只展示这5篇文章
```

**让 AI 帮你出 PRD 的 Prompt：**

```plain
我有一个点子：做个个人书签收藏工具。

帮我出一份 PRD，要包含这些：

1. 一句话说清楚这个东西是干嘛的
2. 谁会用它
3. 功能清单，按优先级分档（必做 / 应做 / 锦上添花）
4. 每个功能配用户故事和验收标准
5. 非功能性要求（性能、安全、兼容性）

输出 Markdown 格式。
```



### 2.4 SPEC：技术方案怎么定
SPEC（Technical Specification）回答的是"具体怎么搞"。

一份完整的技术方案通常涵盖：

| 维度 | 写什么 | 举例 |
| --- | --- | --- |
| 系统架构 | 整体怎么搭的 | 前端怎么跟后端通信 |
| 技术栈 | 用什么框架和工具 | Next.js + Prisma + SQLite |
| 数据模型 | 表结构怎么设计 | 几张表、字段是什么、关系怎么连 |
| 接口定义 | API 长什么样 | URL、入参、出参 |
| 目录规划 | 代码文件怎么组织 | 哪些东西放哪个文件夹 |


**让 AI 从 PRD 生成 SPEC 的 Prompt：**

```plain
我这里有一份 PRD（贴在下面），请基于它出一份技术方案：

[把你的 PRD 贴在这里]

具体要求：

1. 给出技术选型建议，说清楚为什么选它
2. 把数据模型设计完整，包括字段类型和表间关系
3. 列出全部 API 接口，走 RESTful 风格
4. 建议一个项目目录结构
```



### 2.5 规范文件怎么组织
推荐在项目根目录建一个 `specs/` 目录，把所有规范文档归拢：

```plain
my-project/
├── specs/
│   ├── PRD.md              # 需求文档
│   ├── SPEC.md             # 技术方案
│   ├── ARCHITECTURE.md     # 架构说明
│   └── API.md              # 接口文档
├── src/                    # 源码
├── CLAUDE.md               # 给AI看的项目备注
└── package.json
```

这些规范文件最大的好处之一：**直接喂给 AI 当上下文**。你把 SPEC.md 的内容丢给 Claude Code，它就能照着你的技术方案精准地写代码。

### 2.6 两种范式的关系
```plain
Vibe Coding（直觉驱动）
   ↓ 项目长大了，需要更多掌控感
Agentic Engineering（工程化方法）
   ↓ 需要一份精准的"合同"
SDD（规范驱动开发）
```

方法论讲清楚了，接下来的问题是：**用什么工具来落地？**

## 三、AI 编码工具
### 3.1 Claude Code
Claude Code 是 Anthropic 出品的 **AI 编程 Agent**。最早以终端 CLI 形态面世，后来也支持 IDE、桌面端和网页端。它能读懂你的项目代码、改文件、跑命令、装依赖 —— 简单说就是你雇了个全天候在线的远程开发，用大白话指挥它干活就行。

**关键特性一览：**

| 特性 | 解释 |
| --- | --- |
| 多种入口 | 终端、IDE、桌面端、网页都能用，开发者最常用还是终端 |
| 自主执行 | 自己读文件、改文件、跑命令，不用你一行行喂 |
| 项目级理解 | 能把整个项目的代码结构和逻辑搞明白 |
| 200K-1M 上下文 | 一次能装下大量项目背景，具体看用哪个模型 |
| 操作前确认 | 危险动作会先问你一声 |


**凭什么说它是 Agent 而不是聊天框？**

关键机制叫 **LLM Loop（大模型循环）**。

**普通聊天 AI 的工作方式**：你问一句，它答一句，完事。不满意就再问。**你一直掌握主动权**，AI 就是个高级应答机。

**Claude Code 的工作方式**：你给一个目标 → cc 自己拆步骤 → 自己调工具 → 看结果 → 决定下一步 → 继续调工具 → …… 循环到活干完。**主动权移交给了 AI**。这个"想 → 做 → 看 → 再想"的循环就是 LLM Loop。

**Harness 七层扩展架构：**

| 层级 | 模块 | 干什么用 | 啥时候加载 |
| --- | --- | --- | --- |
| ① | **CLAUDE.md** | 项目备注（背景、约定、红线） | 每次开会话自动读 |
| ② | **Hooks** | 生命周期钩子（启动/结束/写文件等事件） | 事件触发 |
| ③ | **Skills** | 可复用的专业方法论（如"代码审查""部署"） | 需要时加载 |
| ④ | **Plugins** | Skills + Hooks + MCP 打包成套 | 装上就一直生效 |
| ⑤ | **LSP**（语言服务器） | 给 AI 装上"跳转定义/查找引用"这类 IDE 能力 | 一直生效 |
| ⑥ | **MCP 服务器** | 让 Claude 能连外部工具（数据库、文档系统、工单系统等） | 一直生效 |
| ⑦ | **Subagents**（子代理） | 独立上下文的 Claude 实例，只把结论带回来 | 需要时创建 |


### 3.2 Cursor
如果 Claude Code 是命令行里的"远程程序员"，那 Cursor 就是坐你旁边、跟你共用屏幕的"编程搭档"。

Cursor 基于 VS Code 改造，是一款 **AI 原生 IDE**。AI 能力直接嵌进了编辑器，你写代码的时候随时能调用。

| 维度 | Claude Code | Cursor |
| --- | --- | --- |
| 界面 | 终端命令行 | 图形编辑器 |
| 怎么交互 | 纯文字对话 | 鼠标 + 键盘 + 对话 |
| 最大优势 | 全自主执行、项目级理解 | 实时补全、可视化编辑 |
| 最适合 | 后端开发、全栈架构 | 前端开发、日常编码 |
| 上手难度 | 得先熟悉终端 | 跟 VS Code 差不多 |


这两者不是死对头，而是互补。很多人的实际用法是：Claude Code 搭骨架和写后端，Cursor 精调前端细节和日常编码。

### 3.3 OpenAI Codex
Codex 是 OpenAI 推出的编程 Agent，跟 Claude Code 是最直接的竞品。其中 **Codex CLI 是开源的**，Codex App / Desktop / IDE 插件更偏产品化。

| 形态 | 说明 | 谁适合 |
| --- | --- | --- |
| **Codex Desktop** | 图形界面客户端，体验最友好 | 新手、喜欢点鼠标的人 |
| **Codex CLI** | 命令行，轻量灵活 | 终端老手 |
| **VSCode 插件** | 在 VSCode 侧边栏直接用 | VSCode 用户 |


**亮点：**

+ **CLI 开源**（Apache 2.0）：想看源码学原理可以直接翻
+ **沙箱 + 审批机制**：通过 sandbox / approval mode 把文件修改和命令执行的风险管住
+ **AGENTS.md**：项目级说明文件，记录规则、上下文和工作约定，方便 Agent 在新会话里快速上手
+ **模型灵活**：原生支持 GPT 系列，也能接 DeepSeek、Ollama、Mistral 等任何 OpenAI 兼容的服务
+ **三档自主度**：`suggest`（步步确认）→ `auto-edit`（自动改文件，命令要确认）→ `full-auto`（完全放手）
+ **推理力度可调**：low / medium / high 三档，根据任务难度在速度和质量间找平衡

**跟 Claude Code 怎么选：**

| 你的情况 | 建议 |
| --- | --- |
| 已经有 ChatGPT 账号或 OpenAI API | Codex 零配置就能用 |
| 看重开源、想研究工具原理 | Codex CLI 可以审计源码 |
| 需要对命令和文件修改做精细风控 | 看重 Codex 的 sandbox / approval 机制 |
| 想用 GPT 系列的代码能力 | Codex 是 GPT 的原生入口 |


工具认识了，但光有工具还不够——**怎么用得好**才是关键。

## 四、Vibe Coding 最佳实践
### 4.1 提示词怎么写更有效
**1. 说清楚具体要什么，别含糊**

```plain
❌ 烂：帮我搞个登录

✅ 好：在 /api/auth/ 下建一个登录接口：
   - POST /api/auth/login
   - 接收 { email, password }
   - 用 bcrypt 校验密码
   - 验证通过返回 JWT token
   - 数据库查询用项目里已有的 prisma client
```

**2. 拿已有代码当参照物**

```plain
✅ 好：照着 /api/bookmarks/route.ts 的写法，
   给 /api/tags/ 也写一套 CRUD 接口。
   数据模型参考 prisma/schema.prisma 里的 Tag 表。
```

**3. 让 AI 先出方案，你点头了再动手**

```plain
✅ 好：我想给书签工具加个搜索能力。
   你先看看要动哪些文件，列个计划给我，
   我确认了你再开干。
```

**4. 一个阶段只解决一个问题**

```plain
❌ 烂：帮我一口气把搜索、标签管理、用户登录、导出全加上

✅ 好：先把搜索做好。要求：
   - 书签列表页加个搜索框
   - 支持按标题和描述模糊匹配
   - 前端实时过滤就行，不用走后端
```

### 4.2 上下文怎么管
| 现象 | 背后原因 | 怎么处理 |
| --- | --- | --- |
| 回答变慢、质量下滑 | 上下文快撑满了 | 先 `/context` 看占比，超过 60% 就 `/compact` |
| AI 开始忘了之前的约定 | 早期内容被挤出去了 | 马上 `/compact` |
| AI 反复问你已经回答过的问题 | 上下文乱了 | `/clear` 重开一个会话 |
| 要换个完全不同的任务 | 上个任务的思路会污染新任务 | `/clear` 重开 |
| 想让某条规则永久生效 | 需要跨会话记忆 | `/memory` 开启 Auto Memory 或写进 CLAUDE.md |


### 4.3 Git 怎么配合
**铁律：让 AI 大改之前，先存档（commit）**

```plain
标准流程：
1. git commit → 把当前状态存好（"存档"）
2. 让 AI 干活
3. 检查结果
   ├── 没问题 → git commit → 继续下一步
   └── 翻车了 → git checkout . → 回到第1步换个思路重来
```

> **踩坑警告**：太多新手不存档就让 AI 大刀阔斧地改，改坏了才发现回不去。这是 AI 编程里最常见也最痛的翻车。**"动手先存档"**，把这五个字刻进肌肉记忆。
>

### 4.4 任务颗粒度要小
在大型代码库里，**一句话甩给 AI 一整个大需求是最坑的做法**。应该这样：

```plain
❌ 反面：帮我把整个支付模块重构一遍，加上新风控、新对账、新通知、新报表

✅ 正面：第一步——在 src/payment/risk/ 下抽出风控规则引擎，
       接口签名看 docs/risk-rules.md，调用方代码先不动
```

**经验值**：单次 Claude Code 任务 ≤ 涉及 5 个文件 / 200 行改动。超了就该拆。

### 4.5 四阶段工作流
官方推荐的节奏：**Explore → Plan → Implement → Commit**

| 阶段 | 你要做什么 | AI 在做什么 | 用什么模式 |
| --- | --- | --- | --- |
| **① 探索** | 告诉 AI 要动哪块 | 读文件、搜引用、理清现状 | Plan Mode |
| **② 规划** | 让 AI 出方案，你审核 | 输出计划、评估边界情况 | Plan Mode |
| **③ 执行** | 确认计划后切出只读模式 | 按步骤改文件、跑构建 | Normal / Auto-Accept |
| **④ 提交** | 让 AI 写 commit message | 生成提交信息、可选开 PR | Normal |


> **一句话判断标准**：如果你能一句话说清要改什么，直接干；说不清，先规划。
>

### 4.6 模型分层用
```plain
简单活（格式化、小修补） ──→ Haiku / DeepSeek Flash / 本地 Qwen（花费：$）
日常开发（功能实现、修 Bug）──→ Sonnet / DeepSeek V4 Pro（花费：$$）
硬骨头（架构设计、疑难杂症）──→ Opus / GLM-5.1（花费：$$$$）
```

不是每次出门都要打专车，也不是每次写代码都要上最贵的模型。

### 4.7 怎么省钱
| 招数 | 怎么做 | 能省多少 |
| --- | --- | --- |
| 分层调用 | 简单任务用便宜模型，复杂任务用好模型 | 30-50% |
| 一次说清 | 减少来回扯皮的轮次 | 20-30% |
| 及时压缩 | 别等上下文爆了才 `/compact` | 10-20% |
| 实时监控 | 用 `/cost` 随时看花了多少 | — |
| 设月度上限 | 在 Anthropic Console 里设预算 | 防爆 |


### 4.8 用 `@` 精准喂上下文
cc 不会把整个项目一股脑塞进上下文（太大也塞不进去），需要的时候才现场搜。**你主动 **`@`** 一个文件，就是在帮 cc 省探路的 token**。

```plain
# 直接 @ 文件路径（输入时会弹出候选）
> 照着 @src/auth/login.ts 的写法，在 @src/auth/ 下新建 register.ts

# 指令太长打不下？先存到 .md 文件里，再 @ 它
> 按 @docs/feature-spec.md 里的需求来实现
```

> **反直觉认知**：你给 cc 的指令**越短，它可能花的 token 反而越多**——因为它得花更多力气去探索项目才能猜到你想要什么。描述越具体 + 明确 `@` 文件，成本反而更低，效果反而更准。
>

### 4.9 该清就清，别恋战
| 时机 | 操作 | 效果 |
| --- | --- | --- |
| 一个独立任务搞定（PR 合了） | `/clear` | 彻底清空，从头来过 |
| 同一个任务聊太长了 | `/compact` | 把历史压成摘要，腾出空间 |
| 想换个思路重做 | 退出 `claude` 重新启动 | 连模式都重置 |


> **心法**：宁可"多 clear 几次重新介绍背景"，也别"一直聊一直聊"。每清一次都是给 AI 一次重新聚焦的机会。
>

### 4.10 配置要定期体检
你给当前模型写的指令，换到下一代模型上可能适得其反。官方举过两个真实案例：

| 过时配置 | 当初为啥加 | 为啥现在没用了 |
| --- | --- | --- |
| CLAUDE.md 里写"每次重构只改一个文件" | 老模型需要保持专注 | 新模型能跨文件协调编辑，这条反而成了绊脚石 |
| Hook 在每次写文件时跑 `p4 edit` | Claude 还不支持 Perforce 的时候 | Claude Code 已经原生支持 Perforce，这个 Hook 多余了 |


**建议**：每 3-6 个月（或每次大版本更新后），把配置文件翻出来过一遍，问自己三个问题："这条还有用吗？""现在有没有更好的写法？""这条是在补哪代模型的短板？"

> **信号灯**：如果你觉得 cc 的表现到了某个天花板怎么也上不去，八成**不是模型的问题，是你的配置没跟上**。模型已经跑远了，你的 CLAUDE.md 可能还停在三个月前。
>

## 五、老项目结合
### 5.1 怎么让 AI 快速读懂已有项目
#### 5.1.1 Agentic Search：像新人入职一样读代码
很多人以为 Claude Code 要先把项目代码传到服务器建索引才能用。**其实完全不需要。**

官方管这叫 **Agentic Search（智能体式检索）**，工作方式跟**一个工程师刚接手项目时一模一样**：

```plain
拿到需求 → 翻目录结构 → 打开关键文件 → grep 搜关键字
→ 顺着调用链往下追 → 在脑子里拼出全景 → 开始干活
```

**跟传统 RAG 检索的区别：**

| 维度 | 传统 RAG | Agentic Search |
| --- | --- | --- |
| 怎么找 | 先把整个代码库转成向量，查询时按相似度捞 | 现场翻文件、grep、追引用链 |
| 要不要服务器索引 | 要，还得维护 | 不用 |
| 代码变了怎么办 | 索引可能过期，返回已删除或改名的代码 | 永远读的是实时代码 |
| 要不要上传代码 | 通常需要预上传或建索引 | 不用预上传；但读进上下文的片段还是会发给模型 |
| 最适合 | 老项目、基本不动的代码库 | **正在活跃开发的项目、百万行级 monorepo** |


> **核心意义**：Claude Code **天然就是为活跃代码库设计的**——它不依赖一份可能已经过时的预建索引，也不用 IT 去部署向量数据库。
>

#### 5.1.2 CLAUDE.md：给 AI 写的"入职手册"
CLAUDE.md 是 Claude Code 体系里**最关键的配置文件**。它就像你给新来的实习生准备的"项目入职须知"——告诉 AI 这个项目是干嘛的、用了什么技术、有哪些规矩、现在做到哪了。

**三个层级（同时生效，互不干扰）：**

| 层级 | 放在哪 | 影响范围 | 适合写什么 |
| --- | --- | --- | --- |
| **全局级** | `~/.claude/CLAUDE.md` | 所有项目都读 | 个人习惯、身份信息、语言偏好（比如"永远用中文回答"） |
| **项目级** | 项目根目录/`CLAUDE.md` | 只对本项目生效 | 技术栈、架构、编码规范、开发进度（可提交 Git，团队共享） |
| **文件夹级** | 子目录/`CLAUDE.md` | 只对该子目录生效 | 模块专属约定（比如 `src/payment/CLAUDE.md` 记录支付模块的坑） |


优先级：文件夹级 > 项目级 > 全局级。

**两种官方推荐的创建方式：**

+ `/init`** 生成项目级**：在项目根目录跑 `claude` 后敲 `/init`，cc 会自动扫描项目生成一版草稿，你再调整。
+ `/memory`** 编辑全局级**：在 cc 会话里输入 `/memory` 选"全局 CLAUDE.md"，会打开文件让你改。

**维护要点：**

1. **要持续更新**：项目有新功能、踩了新坑，同步写进去
2. **要足够具体**：技术栈写清版本号，目录结构跟实际保持一致
3. **要写明红线**：把"不能碰什么"也写上（如"不要动数据库迁移文件"）
4. **要精简**：别写成论文，AI 要的是关键信息不是废话
5. **只写"顶层不变原则"**：放那些长期不变、必须遵守的东西就够了

#### 5.1.3 大型代码库的生存指南
**① 第一件事：用 **`/init`** 生成 CLAUDE.md**

第一次进新项目，**先敲 **`/init`。然后在它生成的草稿基础上**手动补三样东西**：

| 补什么 | 为什么 | 示例 |
| --- | --- | --- |
| **项目地图** | 让 AI 知道去哪找代码 | `认证逻辑在 src/auth/，UI 组件在 src/components/` |
| **禁区清单** | 防止 AI 乱改 | `不要碰 prisma/migrations/，不要动 vendor/` |
| **团队约定** | 统一风格 | `所有 API 返回 { success, data, error }` |


**② 别在仓库根目录启动，钻进子目录再开干**

```plain
❌ 反面：在 monorepo 根目录启动
user@monorepo $ claude
# AI 看到三百个服务、上千个包，上下文瞬间被污染

✅ 正面：钻进你要改的子目录再启动
user@monorepo $ cd services/payment
user@monorepo/services/payment $ claude
# cc 会自动向上遍历加载所有 CLAUDE.md（根目录的也会读）
# 但工作范围被精准限定在了相关代码区域
```

**配套操作**：每个子目录放一份小的 `CLAUDE.md`，写清楚**这个目录专用的测试和 lint 命令**。别让 AI 改了一个服务就去跑整个仓库的测试套件——等着超时吧。

### 5.2 .cursorrules 与系统级 Prompt
#### 5.2.1 Cursor Rules 是什么
Cursor 用 Rules 作为项目级的 AI 行为准则。老项目常见 `.cursorrules` 文件，新版本更推荐放在 `.cursor/rules/*.mdc`。本质上跟 Claude Code 的 CLAUDE.md 是一回事——**把经验固化成可复用的上下文**。

#### 5.2.2 哪里找现成的规则模板
| 资源 | 地址 | 说明 |
| --- | --- | --- |
| **cursor.directory** | [https://cursor.directory/](https://cursor.directory/) | 按技术栈分类的规则模板库 |
| **cursorrules.org** | [https://cursorrules.org/](https://cursorrules.org/) | 旧版规则写法参考，可迁移到新版格式 |
| **awesome-cursorrules** | GitHub: PatrickJS/awesome-cursorrules | 社区精选规则合集 |


#### 5.2.3 不同工具的系统级 Prompt 对照
不管用 Claude Code、Cursor 还是 Codex，"系统级 Prompt"的思路都一样：**把重复解释的成本变成一次性写好的配置文件。**

| 工具 | 配置文件 | 作用 |
| --- | --- | --- |
| Claude Code | `CLAUDE.md`（三级：全局 / 项目 / 文件夹） | 项目上下文、编码规范、禁区 |
| Cursor | `.cursor/rules/*.mdc` 或 `.cursorrules` | 同上 |
| Codex | `AGENTS.md` | 同上 |


**CLAUDE.md 参考模板：**

```markdown
# 项目名称

## 一句话说明
这个项目做什么的。

## 技术栈
- 前端：Next.js 14 + TypeScript + Tailwind CSS
- 后端：Next.js API Routes
- 数据库：Prisma + SQLite
- 部署：Vercel

## 目录结构
​```
src/
├── app/           # Next.js App Router 页面
│   ├── api/       # API 路由
│   ├── layout.tsx # 全局布局
│   └── page.tsx   # 首页
├── components/    # React 组件
│   ├── ui/        # 通用UI组件
│   └── features/  # 业务组件
├── lib/           # 工具函数和配置
├── prisma/        # 数据库 schema 和迁移
└── types/         # TypeScript 类型定义
​```

## 编码约定
- 用函数式组件 + React Hooks
- 组件文件名 PascalCase（如 BookmarkCard.tsx）
- 工具函数名 camelCase
- API 返回统一格式：{ success: boolean, data?: any, error?: string }
- 数据库操作一律走 Prisma Client

## 开发进度
- ✅ 项目初始化
- ✅ 数据库 Schema 设计
- 🔄 书签 CRUD API 开发中
- ⬜ 前端页面待开发
- ⬜ 搜索功能待开发

## 红线
- prisma/dev.db 是 SQLite 数据库文件，不能提交到 Git
- .env 包含敏感信息，不能提交到 Git
- 新功能必须先建 Git 分支再开发
```

#### 5.2.4 怎么维护
**每被 AI 坑一次，马上加一条进 CLAUDE.md。** 过时的规则及时删掉，内容保持精炼。三个月后回头看，这个文件就是"这个项目 AI 犯过的所有错的预防手册"。最高效的一句话是：**"更新 CLAUDE.md，让这件事别再发生"**。
