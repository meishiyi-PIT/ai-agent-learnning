## 1. 阶段定位
> **阶段演进**
>
> 第三阶段完整继承前两个阶段，并将 Agent 从“**咨询与工具调用**”扩展到“**可暂停、可恢复、可人工介入的保单生命周期工作流**”。
>

本阶段的核心业务是退保：

+ **客户申请**：H5 进行退保试算、原因填写和二次确认。
+ **工作流规划**：LangGraph 规划任务并并行评估风险。
+ **风险路由**：低风险自动通过，高风险暂停并交给 PC 端人工审批。
+ **确定性执行**：审批通过后写入退款任务，由独立 Worker 完成退款和保单终止。
+ **异常恢复**：技术失败自动重试，超过上限后进入任务运行中心处理。

## 2. 本阶段新增业务
### 2.1 H5 用户端
+ **退保申请**：对保障中或尚未生效的保单申请退保。
+ **退款试算**：查看确定性退款金额、扣减金额和计算依据。
+ **风险说明**：选择退保原因并填写具体说明；争议类内容进入高风险判断。
+ **二次确认**：确认保单、原因和预计退款金额。
+ **流程时间线**：查看创建、确认、风险评估、审批、退款和保单终止状态。
+ **进度查询**：通过智能顾问查询本人退保进度。
+ **合作资源查询**：通过 Agent 调用 MCP 查询合作医疗机构和服务时间。

退款规则区分：

+ **保障尚未开始**：生效前撤销，全额退款。
+ **保障开始后 10 天内**：犹豫期退保，全额退款。
+ **超过 10 天**：按剩余保障天数折算未满期保费，并按规则扣减。

### 2.2 PC 运营端
+ **退保工作台**：查看全部申请、退款试算、风险等级和当前状态。
+ **Agent 交接**：查看 Planner 计划、风险依据和结构化交接摘要。
+ **人工审批**：对高风险申请审批通过或不予通过；不予通过时必须填写意见。
+ **防止重复处理**：已处理申请的流程控制只读。
+ **Worker 监控**：查看实例、心跳、轮询时间、处理数量、队列和失败原因。
+ **异常处置**：对终止自动重试的任务执行“重新执行”或“终止退保并恢复保障”。

### 3.1 Planner 与并行风险评估
**Planner** 先生成本次退保的工作计划，随后通过 LangGraph `Send` 并行执行金额、原因和保障期间检查，最后聚合风险信号。

当前高风险来源主要包括：

+ 预计退款金额达到人工复核阈值。
+ 退保原因包含投诉、争议、欺诈、冒名、重复扣费、监管或诉讼等事项。

> **风险路由**
>
> **低风险**走自动审批节点；**高风险**生成运营审核摘要并触发 `Interrupt`，暂停等待人工处理。
>

### 3.2 人工中断与恢复
高风险流程暂停后，**LangGraph Checkpoint** 保存当前状态。运营人员在 PC 端审批时，系统使用 `Command` 恢复原工作流，而不是重新执行之前的节点。

客户 Agent 与运营 Agent 不共享完整对话，只交接结构化信息：

+ 退保申请和试算结果。
+ 风险等级与命中原因。
+ Planner 计划。
+ 建议的人工核验重点。

> 结构化交接能够减少无关上下文和敏感信息扩散，并使人工审批依据**可审计**。
>

## 4. Worker 是什么
> **退款 Worker 不是大模型 Agent。**
>
> 它不理解自然语言、不生成计划，也不自主决定是否应该退款。
>

Worker 是一个持续运行的确定性后台任务执行器，职责包括：

1. **接收任务**：接收 Agent 工作流已经批准的退款任务。
2. **执行结算**：按确定性规则执行退款并更新保单状态。
3. **记录异常**：记录执行结果和异常，供任务运行中心查看与处理。
4. **上报状态**：上报实例状态、心跳、最近轮询和累计处理量。

> **Agent 决定流程走向；Worker 负责可靠执行已经批准的确定性任务。**
>

**Outbox、幂等、事务和重试**仍在代码中承担资金安全保障，但它们属于 Agent 外围的确定性执行边界，不是本阶段需要重点展示的 Agent 能力。

## 5. 为什么 FastAPI 与 Worker 独立运行
执行：

```powershell
uv run zbt-serve
```

会看到：

```latex
智保通后端已启动：FastAPI 与退款工作器正在独立运行。
正在启动智保通退款工作器，按 Ctrl+C 停止。
退款工作器已取得单实例锁：<主机名>-<进程号>-<实例ID>
退款工作器初始化完成，开始轮询任务。
```

`zbt-serve` 是一个**本地进程监管器**：对使用者表现为一条启动命令，内部启动两个独立进程。

| 进程 | 职责 | 运行特征 |
| --- | --- | --- |
| **FastAPI** | 接收 H5、PC 和 Agent 请求 | 请求到达时执行，处理完成后返回 |
| **退款 Worker** | 持续轮询并执行已批准的退款任务 | 无用户请求时也需要保持运行 |


**分成两个进程的原因：**

+ HTTP 请求和后台轮询的生命周期不同。
+ Worker 的异常或耗时任务不会阻塞 API。
+ API 重启不应改变已经写入 Outbox 的任务。
+ Worker 可以单独扩容、暂停、观察和恢复。
+ 企业部署时可以将 API 与 Worker 部署成不同服务，而不修改领域规则。

> `zbt-serve` 会监管两个子进程：任一进程异常退出时停止另一个进程，避免本地运行时只剩半套服务。
>

## 6. 为什么默认使用单实例 Worker
第三阶段默认启用 `refund_worker_singleton=true`。Worker 启动后通过 Redis 获取一把**带租约的单实例锁**：

+ 锁租约为 **30 秒**。
+ 每 **10 秒**续约一次。
+ 后启动实例不能获取锁时进入轻量待命。
+ 持锁实例退出、失去连接或租约过期后，待命实例自动接管。

> **为什么默认单实例？**
>
> 退款属于外部资金副作用。本地优先保证同一时刻只有一个主动执行者，便于控制调用节奏、观察状态和解释故障。
>

如果本地同时存在多个主动 Worker，会增加以下问题：

+ 多个进程会竞争同一批退款任务，任务执行顺序和日志顺序变得不稳定。
+ 当任务租约过期、进程暂停或执行时间较长时，两个 Worker 可能先后处理同一任务；如果外部退款渠道缺少可靠幂等能力，就存在重复发起资金操作的风险。
+ 并发调用会增加数据库连接、Redis 请求和退款渠道限流压力，本地测试结果也更难复现。
+ 多个实例的心跳、轮询记录和错误日志会交错，难以判断某次退款究竟由哪个进程执行以及为什么失败。
+ 本地测试和故障排查时，同一操作可能表现出不同的领取者和时间顺序，削弱 Agent 工作流的可解释性。

因此，本地默认只允许一个**主动 Worker**，其他实例进入待命。持锁实例退出或失去租约后，待命实例自动接管。这个设计既保留故障恢复能力，也避免无必要的本地并发。

**单实例锁不是唯一防线：**

+ Outbox 领取任务时带有任务租约。
+ 退款尝试使用幂等键。
+ 结算状态通过数据库事务提交。
+ 已成功退款的任务不能再次恢复或终止。

> **生产扩容边界**
>
> 当前默认单实例是一项本地运行策略。系统已通过任务租约和幂等机制为多 Worker 预留基础，但生产扩容前仍需验证外部渠道幂等、并发领取、任务超时、限流和故障接管。
>

## 7. Agent 与 Worker 的边界
| 能力 | Agent / LangGraph | Worker |
| --- | --- | --- |
| 理解退保原因 | 是 | 否 |
| 生成工作计划 | 是 | 否 |
| 风险检查和路由 | 是 | 否 |
| 生成运营交接摘要 | 是 | 否 |
| 等待并恢复人工审批 | LangGraph | 否 |
| 决定是否进入退款 | 工作流决定 | 只接受结果 |
| 创建退款尝试 | 否 | 是 |
| 执行结算与状态更新 | 否 | 是 |
| 技术重试和 Dead Task | 否 | 是 |
| 心跳和实例监控 | 否 | 是 |


> 这个边界保证**大模型不会直接触碰资金结果**，退款也不会因为模型回答波动而发生变化。
>

## 8. MCP 合作资源查询
第三阶段新增独立的只读 MCP 服务，用于查询合作医疗服务机构：

1. **选择工具**：Agent 根据问题调用 `search_partner_institutions`。
2. **连接服务**：MCP Client 通过 stdio 启动并连接独立 MCP Server。
3. **返回结构**：服务端返回符合 JSON Schema 的机构、区域、服务类型和时间。
4. **解释结果**：Agent 只解释可核验结果。
5. **失败降级**：MCP 不可用或没有结果时明确降级，不编造机构。

> MCP 将外部资源目录与 **Agent Kernel** 解耦。以后替换真实合作机构服务时，Agent 的 Prompt 和工具协议可以保持不变。
>

## 9. 本阶段使用的主要技术
| Agent 与工作流技术 | 在本阶段的作用 |
| --- | --- |
| **LangGraph StateGraph** | 显式描述退保状态和节点 |

| **Send** | 并行执行多个风险检查 |

| **Planner–Executor–Reviewer** | 计划、执行检查和运营复核 |
| **Multi-Agent 结构化交接** | 客户人格向运营人格传递审核摘要 |
| **MCP Client / Server / Tool** | 查询独立合作医疗资源 |
| **LangSmith + OpenTelemetry** | 观察 Agent、LangGraph 节点和工具链路 |
| **确定性执行安全边界** | Worker、单实例租约、幂等与异常恢复承接 Agent 已批准的资金任务 |


> 传统业务仅作为 Agent 工作流的**输入、执行结果和安全边界**，不作为本文重点展开。

## 11. 第三阶段结论
第三阶段完成了从“**对话式 Agent**”到“**可运行的 Agent 工作流**”的演进：

+ LangChain Agent 继续负责咨询、知识和工具调用。
+ LangGraph 负责可暂停、可恢复的复杂业务编排。
+ MCP 负责连接独立的外部资源能力。
+ Worker 负责可靠执行资金类异步任务。
+ 人工审批与异常任务中心保留了生产业务必须具备的控制权。

> **最终结论**
>
> Agent、LangGraph、MCP、Worker 与人工控制各自承担合适职责，共同构成完整的 **Harness Engineering** 项目。
>
