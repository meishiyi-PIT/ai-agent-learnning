# A2A 协议 复习笔记
> 对应课件：1.A2A 协议：让 Agent 之间「说同一种语言」.md

## 一、在知识体系中的位置

这是整门课程「多 Agent 协作」拼图的最后一块，建议带着下面这几个前置概念来读，才能把它放对位置：

- **MCP（对比理解）**：前面学的 MCP 解决的是「一个 Agent 怎么调用工具（搜索、数据库、代码执行）」。A2A 解决的是「一个 Agent 怎么找到并委托另一个 Agent」。一句话记牢：**MCP 管 Agent↔Tool（纵向、接工具），A2A 管 Agent↔Agent（横向、接同伴）**。两者不是替代关系，是不同层，同一个 Agent 可以对内用 MCP 接工具、对外用 A2A 暴露能力。
- **Multi-Agent / Supervisor 模式**：之前学的 Supervisor + handoff 是「同一个进程内」的编排。A2A 不是编排器，它是**通信协议**——它让被编排的 Worker 可以从「进程内函数」变成「网络上的远程 Agent」，但「谁先做谁后做」仍然是编排层的事。
- **RAG 全链路 / LangGraph**：A2A 常和 Agentic RAG 组合出现——你可以把一个完整的 Agentic RAG 系统封装成一个 A2A Server，对外只暴露「问答」这一个技能。

**定位**：A2A 是全课程的收尾综合主题，它本身不产生「智能」，只负责让分散在不同进程/团队/公司的 Agent 之间**能互相发现、能用同一套接口对话**。

## 二、核心知识点精讲

### 2.1 它到底解决什么问题（先想清楚「为什么」）

课件的动机部分讲得很好，核心矛盾就一句话：**没有统一协议时，N 个 Agent 互相调用就是 N×(N−1)/2 套适配代码。**

为什么会这样？因为每个团队/公司自定义的东西太多了：

- JSON 字段名不一样（`translated` vs `result`）
- 传输方式不一样（gRPC vs HTTP）
- 状态枚举、错误码不一样（`status:"in_transit"` vs `state:2`）
- 认证方式不一样（API Key vs OAuth vs mTLS）

只有 2 个 Agent 时无所谓，手写一套适配就行；但一旦到跨组织、跨团队、几十上百个 Agent 协作，适配代码就会指数爆炸。**A2A 缺的不是「又一个接口」，而是统一的「能力发现机制 + 通信协议」。**

关键判断：A2A 的价值只在**跨边界**（跨进程、跨团队、跨组织）时才体现。同进程、同框架、同团队的 Agent，直接函数调用或 Supervisor handoff 更简单——用 A2A 反而是杀鸡用牛刀。

### 2.2 A2A 用什么技术搭起来的

- **传输层**：HTTP(S)
- **消息格式**：JSON-RPC 2.0
- **流式推送**：Server-Sent Events（SSE）
- 不绑定任何框架、语言、供应商

> ⚠️ 课件只说了「HTTP + JSON-RPC 2.0 + SSE」。这在 2024 年的早期版本是对的，但**当前 v1.0 规范已经正式定义了三种传输绑定（protocol binding）**：`JSONRPC`、`GRPC`、`HTTP+JSON`（REST）。JSON-RPC 只是最常见的公网部署方式，gRPC 用于低延迟内部微服务。这一点见第三节勘误。

### 2.3 A2A 解决三件事（发现 → 委派 → 回传）

1. **发现（Discovery）**：Server Agent 把自己的能力写成 **Agent Card**，暴露在固定端点。Client 先拿 Card，才知道对方「是谁、能干嘛、怎么调」。
2. **委派（Delegation）**：Client 通过标准接口向 Server 提交一个 **Task**。
3. **回传（Return）**：Server 把最终结果作为 **Artifact** 返回，把过程信息作为 **Message** 返回。

### 2.4 四个核心概念

| 概念 | 是什么 | 类比 | 关键点 |
| --- | --- | --- | --- |
| **Agent Card** | JSON 能力描述文件 | 餐厅门口的菜单 | 暴露在 `/.well-known/agent-card.json` |
| **Task** | 一次任务的完整生命周期 | 外卖订单 | 有状态机，能中途「反问」 |
| **Message** | 过程通信消息 | 微信聊天记录 | 状态更新、追问、中间说明 |
| **Artifact** | 最终交付物 | 快递包裹 | 实际结果（文本/文件/结构化数据） |

**为什么要严格区分 Message 和 Artifact？** 因为调用方真正关心的是 Artifact（结果）；Message 是调试/审计时才看的过程。如果混在一起，调用方就得从一堆状态消息里捞真正的结果，徒增复杂度。

### 2.5 Task 的一生（状态机）

Task 是 A2A 的核心交互单元，从创建到终结会走一个状态机。课件列的 8 个状态（概念上）是对的：

- 非终态：`SUBMITTED`（已提交）→ `WORKING`（处理中）
- **中断态（可恢复）**：`INPUT_REQUIRED`（需要用户补信息）、`AUTH_REQUIRED`（需要认证）
- 终态：`COMPLETED` / `FAILED` / `CANCELED` / `REJECTED`

**最值得记的是 `INPUT_REQUIRED`**：这是 A2A 的一个精妙设计——Agent 可以在处理中「反向」向调用方要信息。比如你让它订酒店但没说日期，它不会直接报错，而是把 Task 挂起、返回 `INPUT_REQUIRED` 并附一句「请提供入住日期」。这让 Agent 之间可以像人一样多轮澄清。

> ⚠️ 注意：课件把状态写成 `SUBMITTED`/`WORKING` 这种短名，**概念完全正确**，但当前 a2a-sdk v1.0 里实际的枚举值加了前缀，是 `TaskState.TASK_STATE_SUBMITTED`、`TASK_STATE_WORKING`……并且新增了一个 `TASK_STATE_UNSPECIFIED`。见第三节。

### 2.6 三种传输/通信模式

| 模式 | 原理 | 适用 | 代码开关 |
| --- | --- | --- | --- |
| 同步请求/响应 | 发请求，等处理完返回 | 秒级快任务 | `ClientConfig(streaming=False)` |
| SSE 流式 | Server 实时推送进度 | 长任务、要实时反馈 | `ClientConfig(streaming=True)` |
| Push 通知 | Server 用 Webhook 回调 | 分钟/小时级超长任务 | 配 `PushNotificationConfig` |

### 2.7 分层：A2A 与 MCP 各管一层

```
┌─────────────────────────────────────┐
│  编排层（Supervisor / Pipeline）      │  ← 决定谁做什么
├─────────────────────────────────────┤
│  协作通信层（A2A）                    │  ← Agent 之间怎么对话
├─────────────────────────────────────┤
│  能力接入层（MCP）                    │  ← Agent 怎么调工具
├─────────────────────────────────────┤
│  工具与数据源（搜索/DB/API）           │
└─────────────────────────────────────┘
```

形象记法：**MCP 像「工具箱」**（Agent 打开箱子拿工具用），**A2A 像「电话」**（Agent 拿起电话找另一个 Agent 委托任务）。一个 Agent 完全可以同时用两者：内部用 MCP 接工具，对外用 A2A 挂电话给别人。

### 2.8 三个高频误区（很重要）

1. **「引入 A2A 就解决了任务路由」——错。** A2A 只解决「怎么通信」，不解决「谁来做什么」。任务拆解和路由调度仍是编排层的职责。
2. **「A2A 能替代 Supervisor」——错。** Supervisor 是编排模式，A2A 是通信协议，在不同层工作。
3. **「所有 Agent 间通信都该走 A2A」——错。** 同进程、同团队、同框架直接函数调用即可。A2A 的价值只在「跨边界」。

## 四、课件没讲透的关键点补充

### 4.1 A2A 与 MCP 的分工——再钉一遍钉子

课件讲了分层，但很多人还是会混。用一句可操作的判断题记住：

> 你的 Agent 要访问的对象**本身是不是一个「有自主决策、会规划、可能反问你」的 Agent**？
> - 是 → 用 A2A（对方是同伴，双向协作，有 Task 生命周期）
> - 只是个「输入进去、输出出来」的确定性能力（搜索、SQL、计算器）→ 用 MCP（对方是工具，单向调用）

一个物流查询接口，如果只是「输入运单号→输出状态」，那它更适合当 MCP 工具；只有当物流方把它包装成一个会自己规划、会追问、会拒绝的 Agent，才需要 A2A。

### 4.2 治理归属：为什么「捐给 Linux Foundation」很重要（课件完全没提）

这是本课件**最大的时效性断层**。2025 年 4 月 Google 发布 A2A 时它还是「Google 的协议」，企业会担心「绑定 Google」。2025 年 6 月 23 日 Google 把协议规范、SDK 和商标一起捐给了 **Linux Foundation**，成立独立的 **Agent2Agent 项目**，由 AWS、Cisco、Google、Microsoft、Salesforce、SAP、ServiceNow 等作为创始成员共同治理。

**为什么这件事对「学通透」很关键？**

- **中立治理 = 可以放心押注**。企业选协议最怕「被一家公司绑架」。捐给中立基金会后，A2A 才真正具备了成为「行业标准」的资格——这也是它现在被广泛采用的根本原因。
- 你在简历/面试里说「A2A 是 Google 的协议」是会扣分的，正确表述是「A2A 最初由 Google 发起，现已捐赠给 Linux Foundation 中立治理」。

### 4.3 AgentCard 的 v1.0 结构变化（课件用了新写法但没解释为什么）

课件的 Agent Card 用了 `supported_interfaces`（一个 `AgentInterface` 列表），而不是老版本的顶层单个 `url`。**为什么改？** 因为一个 Agent 现在可以同时暴露多个传输端点：

```python
supported_interfaces=[
    AgentInterface(protocol_binding='JSONRPC', url='http://.../jsonrpc/'),  # 公网调用方走这个
    AgentInterface(protocol_binding='GRPC',    url='http://.../grpc/'),     # 内部微服务走这个（低延迟）
]
```

调用方读 Card 时，可以根据自己的技术栈挑一个能力匹配的端点连接。这正是「统一发现、灵活接入」的体现。

### 4.4 Task 的完整生命周期与「幂等 / 版本 / 追踪」（工程化必修）

课件第八节的「引入前必须想清楚的事」其实是精华，但一笔带过。学通透至少要理解这三点为什么存在：

- **幂等性（messageId 去重）**：网络会重试，同一个 Task 可能被提交两次。用 `messageId` 去重、关键操作设计幂等键，否则「订两张机票」。
- **版本协商（`A2A-Version`）**：Agent Card 会升级，旧客户端可能读不懂新字段。A2A 定义了 `A2A-Version` 头做版本协商（这一点课件说对了，规范里确有该 header）。
- **可观测性（`context_id` + `id` 串联）**：跨服务调用链靠每个 Task 的唯一 `id` 和 `context_id` 串日志，配合 OpenTelemetry 做追踪。

### 4.5 安全面：Agent Card 是「公开的攻击面」

课件提到 `security_schemes`，但没点破一个反直觉的事实：**Agent Card 暴露在 `/.well-known/` 是公开可发现的**——任何人扫你的域名就能拿到你有哪些端点、哪些技能。所以：

- Card 里只放「发现」需要的信息，敏感能力放到「认证后才可见的扩展 Card」（v1.0 的 `AgentCapabilities.extended_agent_card`）。
- 跨组织务必上 OAuth 2.0 / mTLS，内部用 API Key。
- 把远程 Agent 的返回**当作不可信输入**做防御性解析（防提示注入）。

## 五、Python 随堂补基础

本讲代码用到的语法点（Python 基础较弱的同学重点看这里）：

### 5.1 async / await 与 asyncio.run —— 异步的入口
`async def` 定义协程，`await` 等待另一个协程完成，`asyncio.run()` 是启动整个异步程序的入口。
```python
import asyncio
async def hello():          # 协程函数
    await asyncio.sleep(1)  # await 等一个「可等待对象」
    return "done"
print(asyncio.run(hello())) # 从同步世界进入异步世界的唯一入口
```

### 5.2 async with —— 异步上下文管理器
和普通 `with` 一样负责「自动开/关」，只是开关动作本身是异步的（如建立/关闭网络连接）。
```python
import httpx
async def fetch():
    async with httpx.AsyncClient() as client:  # 用完自动关闭连接
        r = await client.get("https://example.com")
        return r.status_code
```

### 5.3 async for —— 异步迭代（流式的关键）
一次拿一块、边到边处理，正好对应 A2A 的 SSE 流式返回。
```python
async def read_stream(client, request):
    async for chunk in client.send_message(request):  # 每来一块就处理一块
        print(chunk)
```

### 5.4 类的继承与方法重写
课件的 `MyAgentExecutor(AgentExecutor)` 就是继承框架基类、重写 `execute`。
```python
class AgentExecutor:            # 框架给的基类（约定接口）
    async def execute(self, ctx, q): ...
class MyExecutor(AgentExecutor): # 我来继承并实现具体逻辑
    async def execute(self, ctx, q):
        print("干活")           # 重写父类方法
```

### 5.5 关键字参数 vs 位置参数
`AgentCard(name=..., version=...)` 用的是关键字参数——顺序无所谓、可读性高，构造字段多的对象时首选。
```python
def make(name, age): return f"{name}-{age}"
make("Tom", 3)              # 位置参数：靠顺序
make(age=3, name="Tom")    # 关键字参数：靠名字，顺序随便
```

### 5.6 列表推导式
客户端 `[s.name for s in agent_card.skills]` 就是「从列表里批量取字段」的简写。
```python
skills = [{"name": "翻译"}, {"name": "问答"}]
names = [s["name"] for s in skills]   # ['翻译', '问答']
```

### 5.7 类型注解与 `| None`
`def cancel(self, ...) -> None` 表示无返回值；`str | None` 表示「要么是字符串，要么是 None」。注解只是给人和工具看的提示，不强制。
```python
def find(key: str) -> str | None:   # 可能返回字符串，也可能返回 None
    return None
```

## 七、动手小练习

### 练习 1（约 20 分钟）：读懂并「翻译」Agent Card
不写代码，只做「读」和「说」。找到课件里的 `AgentCard(...)` 定义，逐字段用大白话翻译成「一张名片」：
- `name` / `description` → 这个 Agent 是谁、能干嘛
- `supported_interfaces` → 别人从哪个地址、用什么协议找到它
- `skills` → 它具体会哪几招，每招接受什么输入、产出什么输出
- `capabilities` → 它支不支持流式

**产出**：用 3-4 句中文写出「如果我是调用方，读完这张 Card 我会怎么调用它」。目标是验证你真的理解了「发现」这一步。

### 练习 2（约 30 分钟）：把一个 Agentic RAG 系统「想象成」A2A Server
纸面设计即可（不实现）：假设你要把下一讲的「电商售后 Agentic RAG」包装成一个 A2A Server 对外提供服务。请写出：
1. 它的 Agent Card 该长什么样（`name`、一个 `skill` 的 id/description/input_modes/output_modes）。
2. 当用户问题需要澄清（比如没给用户 ID）时，这个 Task 应该走到哪个状态、返回什么 Message？（提示：`INPUT_REQUIRED`）
3. 当遇到「敏感批量数据请求」被拒绝时，Task 走到哪个终态？（提示：`REJECTED`）

**产出**：一段伪代码 + 一句话说明「为什么这里用 `INPUT_REQUIRED` 而不是直接 `FAILED`」。这个练习能把「A2A 的 Task 状态机」和「Agentic RAG 的路由决策」串起来。
