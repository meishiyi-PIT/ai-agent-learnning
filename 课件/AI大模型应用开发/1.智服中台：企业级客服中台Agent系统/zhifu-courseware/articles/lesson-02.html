客户发来一条消息：“请查询这张键盘订单，并查一下资料中的清洁说明。”订单查询与资料搜索由两个任务分别处理。接下来会遇到普通Web系统中同样存在的问题：两个任务同时返回时由谁保存结果，查询期间订单变化后能否继续使用旧数据，以及进程退出后已经完成的查询是否需要再次执行。

并行执行解决等待时间，状态同步决定结果能否正确使用。本项目通过LangGraph组织查询，通过独立消息与结果副本管理内存数据，通过数据库事务、版本和执行编号控制提交。代码阶段为02-parallel-agents、03-state-consistency与04-durable-execution。

1. 并行查询与开发阶段

一次客户请求需要订单状态和商品资料两组信息。主Agent选择consult_specialists工具后，后端检查当前客户与订单归属，再启动OrderAgent和KnowledgeAgent。前者可以查询订单，后者可以搜索当前店铺的资料。每个角色各自调用模型、执行允许的Python函数，并将查询结果交给协调节点。

例如，一个详情页同时请求订单和商品说明：两个请求有独立的结果，页面等待所需数据后才能完整展示。这里每个角色还会通过模型选择工具与整理答复，因而需要管理各自的消息、调用次数和工具权限。

并行的前提是执行所需的输入已经确定。本项目在进入两个分支前验证指定订单的归属；资料搜索使用传入的问题和当前店铺范围。如果新增查询必须读取另一个查询的返回值，就需要增加明确的前后依赖。协调节点还要在结果齐全后重新检查订单、规则与资料版本。

源码：阶段02协作入口、阶段04来源检查。

等待时间与资源消耗

串行调用的等待时间约为两个查询耗时之和；可以并行的部分约为较慢查询的耗时，再加上分发、保存和结果检查的时间。例如假设两个独立查询分别需要2秒和3秒，串行部分为5秒，并行部分接近3秒。这里是说明执行顺序的计算示例，实际结果需要记录各次请求耗时。

两个Agent同时工作会占用两个并发名额，也会分别产生模型调用。本实现中，每个专业角色通常先请求模型选择工具，执行查询后再请求模型整理回答。增加角色需要同时检查等待时间、调用次数、token消耗和查询质量，不能仅凭“并行完成”判断性能改善。

三个阶段可以沿同一个问题检查：两份结果分别由谁创建、谁持有副本、保存在哪张表、当前是否仍然有效。接下来的代码把这几个问题分别对应到模型工具、事件循环和数据库事务。

2. 专业Agent的调用流程

客户提供了一张本人订单，提出两个问题：“这件键盘是否符合换货条件？说明书里要求如何清洁？”订单状态与换货规则来自业务数据库，清洁说明来自当前店铺发布的商品资料。服务端已经取得订单编号和资料问题后，两项查询可以同时进行；订单编号尚未确定时，需要通过订单查询或补充信息取得输入。

主Agent仍执行“请求模型、执行工具、把结果交回模型”的循环。阶段02的after-sales-v10提供consult_specialists工具，参数是order_id和question。主模型选择这个工具后，build_tool_graph.execute要求本轮只有这一项工具调用，再进入run_specialists。服务端检查客户身份、发布版本和运行状态，并通过get_order核实指定订单归属。是否进入专业协作取决于发布配置、输入条件和主模型返回的工具请求。主模型也可以直接选择普通查询工具。

源码：02 · 主工具执行、协作参数、发布配置。

3. 任务、线程与进程

两个模型HTTP请求都在等待远端响应时，一个事件循环可以继续调度其他工作。asyncio的task表示这个事件循环正在管理的一项异步执行；遇到需要等待的await时，可以让其他任务继续运行。前端使用Promise等待网络响应时也有相似的调度思路。阻塞函数如果直接占用事件循环所在的线程，其他任务仍会一起等待。

名称 对应的对象 状态与同步范围
asyncio.Task 事件循环管理的异步执行 同一事件循环中的任务可以访问同一对象；跨await的读取、检查和修改需要明确协调
Python Thread 同一进程中的操作系统线程 共享进程内存；多个线程访问共同数据时使用线程同步或结果交接
worker进程 独立运行的Python程序 各有自己的内存；共同任务通过MySQL、Redis和稳定操作标识协调
LangGraph thread_id 持久化图状态的逻辑标识 checkpointer据此查找一组状态快照；它不决定Python线程数量

阶段02、03的专业协作直接使用异步节点；阶段03的collect_thread_results提供同步函数结果交接实验，主协作流程没有调用它。需要接入同步SDK时，可以由线程执行有期限的同步工作，再把结果交给事件循环。asyncio.Lock用于协调同一事件循环中的任务；threading.Lock用于协调同一进程中的线程。多个worker进程各有自己的锁对象，共享业务仍通过数据库事务和Redis检查控制。

checkpointer是LangGraph保存图状态快照的组件，thread_id是访问这些快照的逻辑标识。本项目阶段02、03没有配置checkpointer，也没有传入thread_id。主图通过MySQL中的AgentRun.messages、next_node和step读取执行进度，lease_token用于检查当前执行权。源码中的graph.compile()可以直接核对这一点，恢复行为需要继续查看业务状态的保存和读取代码。

源码：02 · 主图构建与读取、AgentRun。框架概念见LangGraph持久化说明，事件循环和跨线程回调见Python asyncio开发说明。

4. 共享状态与线程结果交接

考虑一个共享计数的示例：两个查询线程完成后，都需要把completed_count增加1。初始值为0，两条线程各自读取0，在自己的局部变量中计算出1，再分别写回。最终计数为1，预期计数为2。下图用于说明读取、计算与写入交错的含义，未作为项目实测结果。

共同数据的读取、判断与修改需要作为完整步骤协调。在这个示例中，两个线程各自得到的读取值相同，后一次写入覆盖了前一次增加。实际thread_bridge把完成数量和结果集合交给同一个事件循环管理，线程只发布结果；publication锁负责协调发布动作与接收入口关闭。

假设一个同步查询函数返回订单数量，另一个同步查询函数返回商品资料。两条线程如果直接修改同一个results列表，调用方还需要处理完成次数、错误、取消和重复结果；其中任意一项检查与修改交错，都会影响最终状态。阶段03把责任集中在事件循环：线程完成自己的函数，生成结果副本，提交回调；事件循环统一修改accepted、remaining和等待结果的Future。这里的Future表示一个尚未完成的结果，调用方通过await等待它。

下面是collect_thread_results.execute中的实际片段。Barrier让本次实验的线程到齐后再开始；stopped是各线程可以读取的取消标记。工作函数接收这个标记，自行限制阻塞调用期限。发生异常时，异常对象也通过同一个交接入口传回。

python
        try:
            start.wait()
            if stopped.is_set():
                return
            result = result_snapshot(operation(stopped))
        except BaseException as failure:
            # 工作线程异常需要传播给等待协程，不能使请求永久等待。
            error = failure
        with publication:
            if not stopped.is_set():
                loop.call_soon_threadsafe(receive, result, error)

源码：03 · collect_thread_results.execute。call_soon_threadsafe把receive排入事件循环，回调随后在事件循环线程运行。工作线程负责提交结果，事件循环负责接受结果和修改共享集合。这个调用不会等待结果合并完成，也不会把数据库事务变成线程安全操作。

publication只保护“检查是否允许发布并提交回调”以及“关闭发布入口”这两组动作，锁内不执行模型请求、同步查询或结果合并。receive检查accepting与completed.done()，关闭后即使已有回调进入队列，也不会写入结果。它运行期间没有await，当前事件循环中的其他任务不会在这段回调中间插入执行。具体行为可阅读结果接收与结束等待时的清理。

取消等待时，finally关闭接收、设置stopped并终止Barrier等待。已经进入同步函数的线程仍可能继续运行，因此同步操作需要自己的超时和取消检查。该函数默认等待5秒，一次最多启动32条线程。取消协程后，迟到的线程结果不能重新成为本次请求的有效结果。线程操作也不能把其他task正在使用的AsyncSession作为共享对象继续修改。

源码：03 · result_snapshot。输入限于声明的字段和有效JSON，版本必须是非负整数；集合、NaN、Infinity等内容会被拒绝。工作函数在返回前完成自己结果的修改，接收方使用独立副本。测试会修改原结果的数量和版本，再检查合并结果保持原值，还会修改新返回的副本，确认上一次合并结果不受影响，见副本与稳定重放测试。

练习：取消与迟到回调。同步函数已经开始等待外部结果，调用方取消collect_thread_results。随后同步函数返回，并且另一个回调在取消前已经排入事件循环。分别指出这两种结果在哪里被拒绝，以及哪一段代码负责终止外部等待。

5. 结果合并与冲突处理

阶段02的两个角色分别写order_result和knowledge_result。阶段03把结果放入统一的results列表，使用Annotated[list[BranchResult], merge_results]告诉LangGraph，每次更新都由merge_results处理。这个合并函数称为reducer：它接收已有结果和新增结果，返回下一份结果列表。两个节点直接写同一个普通字段时，需要定义合并规则；本项目的真实LangGraph测试检查这种情况下产生的InvalidUpdateError。

源码：03 · CollaborationState、普通字段并发更新测试。

每个BranchResult保存agent_id、operation_id、source_versions和payload。operation_id标识一次逻辑查询：主工具使用父运行编号、步骤和工具调用标识组成基础编号，角色再附加自己的名称。重放同一项查询时，依据这个编号识别重复。source_versions说明结果使用哪一版订单或资料；payload同时保存角色答复和查询原文。

下面是merge_results的实际函数主体。比较内容时使用固定的JSON键顺序，最后按operation_id排序。完成先后顺序可以变化，相同输入集合得到的合并结果保持一致。列表中的业务顺序仍然保留，例如payload内部数组顺序变化也属于内容变化。

python
    accepted = {}
    fingerprints = {}
    for item in [*(current or ()), *(incoming or ())]:
        result = result_snapshot(item)
        fingerprint = json.dumps(
            result.model_dump(mode="python"), sort_keys=True, ensure_ascii=False, allow_nan=False
        )
        previous = fingerprints.get(result.operation_id)
        if previous is not None and previous != fingerprint:
            raise BusinessError("BRANCH_RESULT_CONFLICT", "相同操作标识对应不同分支结果", 409)
        accepted[result.operation_id] = result
        fingerprints[result.operation_id] = fingerprint
    return [accepted[operation_id] for operation_id in sorted(accepted)]

源码：03 · merge_results。函数逐项创建副本，使用本次调用的字典积累结果，不修改传入的集合。相同操作编号下，角色、来源版本或正文任一内容改变，都会抛出BRANCH_RESULT_CONFLICT，错误状态为409；本次调用不返回部分成功结果。

输入情况 合并结果 对业务的含义
订单和资料按不同先后顺序完成 按操作编号固定排序 展示和后续处理不依赖完成顺序

6. 数据库事务与并发版本

订单查询和资料查询可以同时等待外部服务，写入数据库时仍要检查当前业务状态。一个常见场景是：客户发起查询，后台正在等待资料检索，管理员随后撤回了资料；外部请求返回的候选仍可能包含旧版本。查询开始时有效的权限和数据，在返回时已经发生变化，因此提交阶段需要重新检查。

每个并发任务使用独立Session

项目把sessions这个async_sessionmaker传给各个处理函数。它负责创建Session；每次进入async with sessions.begin() as session，都会创建本次操作使用的AsyncSession和事务。订单分支、资料分支以及HTTP请求分别创建自己的Session，使用完毕后由上下文提交或终止事务并关闭Session。

Session会跟踪读取的对象、待写入的修改和当前事务。两个并发task共享同一个Session时，其中一个任务的查询、刷新或提交会影响另一个任务正在处理的对象。Session由当前任务管理，跨任务传递的是标识、参数和独立结果。模型客户端和检索客户端可以按各自的并发规则共享，业务Session仍按每次数据库操作创建。

在阶段03的read_specialist_tool中，资料分支先在事务内读取当前运行身份和店铺范围，结束该事务后调用检索服务。以下是函数的后半部分：

python
query = SearchInput.model_validate(call["args"])
# 向量调用在事务之外；读取正文时重新检查客户、店铺与资料版本。
candidates = await search_knowledge(tenant_id, store_id, query.query)
async with sessions.begin() as session:
    run, auth = await guard(session, state["run_id"], state["token"])
    require(run.step == state["step"], "RUN_STATE_CHANGED", "协作节点已变化")
    return await verified_results(session, auth, run.store_id, candidates, limit=3)

检索返回后，函数重新创建事务，调用guard检查当前运行，再由verified_results查询当前可访问的资料。外部请求只返回候选，服务端根据数据库中的店铺、发布状态和版本决定哪些内容可以继续使用。

主模型节点采用相同的处理方式：事务内登记调用和读取输入，事务外等待HTTP响应，返回后保存用量，再创建事务检查当前运行与引用资料。等待网络响应期间不持有这段业务事务，可以缩短连接和记录锁的占用时间。返回后的检查仍有必要，单纯把HTTP调用移到事务之外并不能保证旧结果有效。

源码：03 · read_specialist_tool、03 · verified_results、03 · 主模型节点。

7. 执行租约与迟到结果

HTTP请求提交运行后，数据库中的AgentRun进入QUEUED。独立worker负责领取并执行。租约由lease_until和lease_token共同记录：前者表示本次执行权有效到什么时间，后者表示这是第几次领取。worker中断后，其他进程可以在符合条件时重新领取；原进程即使稍后恢复，也必须通过提交检查。

领取条件与执行期限

阶段04的claim在数据库事务内按租户调度顺序和并发额度选择候选，锁定相关记录并重新检查状态。常驻worker还会申请Redis共享额度；额度不足时保留排队状态。正常领取将状态设为RUNNING，令lease_token增加1，并设置125秒后的lease_until。

时间或状态 阶段04的处理
QUEUED 存在可用额度且未超过运行总期限时可以领取
RUNNING且租约有效 当前领取继续有效，其他worker不重新领取
RUNNING且租约到期 未超过运行总期限时可以重新领取，取得更大的token
单次图调用 execute_one用120秒限制一次graph.ainvoke
一次专业协作图 run_specialists用60秒限制这次协作调用
deadline_at 创建运行时设为10分钟以后，重新领取不延长它
等待客户或审批且超过总期限 进入期限清理，标记FAILED，不恢复业务执行

这几个时间分别控制一次图调用、一次领取和整个业务运行。125秒租约到期只允许重新竞争领取；它不会重置累计模型调用次数、业务版本或运行总期限。FAILED、CANCELLED和COMPLETED均不属于自动重新执行的候选。

源码：04 · claim、04 · execute_one、04 · queue_run、04 · run_specialists。

提交时检查当前执行权

假设worker A领取时取得token 11，随后长时间没有完成。原租约到期后，worker B取得token 12。A返回的结果仍携带11，locked_run读取当前数据库记录时会拒绝它。

python
await session.refresh(snapshot, with_for_update=True)
require(
    snapshot.status == "RUNNING"
    and snapshot.lease_token == token
    and snapshot.lease_until is not None
    and snapshot.lease_until > now(),
    "RUN_LEASE_LOST",
    "当前执行权已失效",
)
require(snapshot.deadline_at > now(), "RUN_DEADLINE", "任务已超过执行期限")

有效结果必须同时满足当前状态、当前token、有效租约和运行总期限。即使尚无worker重新领取，A在自己的租约到期后提交也会失败。完整locked_run还会验证访问会话、租户与账户身份、店铺权限，以及会话控制者、控制版本和active_run_id。

这项检查控制节点与分支结果能否进入数据库。已经发送给模型或OMS的HTTP请求仍可能在远端继续执行，所以外部操作还需要稳定操作编号、幂等处理和结果查询。某个旧worker失去提交资格，也不能据此推断远端没有处理过它的请求。

源码：04 · locked_run。

8. 分支记录与进程恢复

主运行把消息、next_node和step保存在AgentRun。重新领取后，主图的load节点读取这些字段，继续执行数据库中保存的下一步。阶段04增加AgentBranch，让每个专业角色已经完成的结果也能独立保存。LangGraph可以通过checkpointer保存图执行状态；这里的主图和专业协作图调用compile()时均未传入这个组件，恢复依赖项目自己的MySQL记录。

操作编号、请求摘要与父运行

operation_id由父运行、步骤、工具调用编号和角色稳定生成。例如同一次consult_specialists中的订单角色，进程重启后继续使用原编号。request_hash是请求摘要，包含角色、操作编号、父步骤及JSON参数；字段排列顺序不影响摘要，请求内容变化会产生冲突。

AgentBranch字段 保存内容与约束
tenant_id + parent_run_id + operation_id 复合主键，限定某个租户、父运行中的一次角色操作
agent_id、parent_step、request_hash 核对角色、步骤和参数，阻止同编号被用于其他请求
lease_token 最近一次有效父运行领取所使用的token
status 仅有RUNNING和COMPLETED；前者还没有已提交结果
result 已完成的JSON结果，包含来源版本；COMPLETED必须具有结果

父外键同时包含租户和运行标识。start_branch与finish_branch都先调用locked_run检查并锁定父运行，再锁定子记录；即使读取已经完成的分支，也需要通过当前授权和执行权检查。

start_branch找到已有记录后的处理如下：

python
matching_request(branch, body, digest)
require(branch.lease_token <= state["token"], "BRANCH_LEASE_LOST", "分支执行权已变化")
# 新父租约重新认领原操作。已完成结果也需要当前父授权，来源版本由汇总方复核。
branch.lease_token = state["token"]
branch.updated_at = timestamp
return result_snapshot(branch.result) if branch.status == "COMPLETED" else None

result_snapshot返回独立结果，调用方修改嵌套字段不会修改已保存的数据。返回None表示当前没有完成结果。同一有效租约下重复调用start_branch可以同时得到None，因此它不单独保证查询只执行一次；当前协作图为每个角色安排一个节点入口，调用方仍需维持这个执行安排。finish_branch对相同结果的重复提交返回原结果，对相同操作的不同结果返回冲突。

源码：04 · AgentBranch、04 · BranchRequest.fingerprint、04 · start_branch、04 · finish_branch。

完成结果的复用条件

存储函数核对请求和父运行，订单、规则与资料版本由业务调用方继续核对。阶段04的execute_specialist取得已完成结果后，会执行以下检查：

python
completed = await start_branch(sessions, guard, state, role, operation_id, request)
if completed is not None:
    async with sessions.begin() as session:
        run, _ = await guard(session, state["run_id"], state["token"])
        require(run.step == state["step"], "RUN_STATE_CHANGED", "协作节点已变化")
        await validate_specialist_results(session, run, [completed.model_dump(mode="json")])

validate_specialist_results重新读取订单、当前换货规则和知识文档，检查租户、店铺、客户归属及来源版本。协调节点和主图提交工具结果时继续检查。已经保存的结果只有在当前授权与来源仍有效时才能复用。订单版本改变或资料撤回后，该结果不能继续成为本次成功协作的内容。

中断位置 已保存的状态 恢复行为
分支尚未登记 没有子记录 通过父运行检查后登记并执行
分支已登记，结果尚未提交 AgentBranch.RUNNING 新租约认领原操作后重新执行角色查询
分支结果已经提交，父图尚未汇总 AgentBranch.COMPLETED 核对请求与来源后复用
模型请求已登记，响应尚未保存 ModelAttempt.STARTED 重新领取时改为UNKNOWN，继续保留计量核对需求
父运行已经标记失败或取消 AgentRun.FAILED/CANCELLED 不自动重新领取，分支也不能单独继续提交

STARTED属于模型尝试记录；分支执行中的状态是RUNNING。未完成角色重新执行时可能产生新的模型尝试，父运行的model_calls和已有预算记录继续累计。远端已经处理请求、本地尚未保存结果时发生中断，结果保存机制无法保证远端调用只发生一次。

源码：04 · execute_specialist、04 · validate_specialist_results、04 · 主图load节点。

9. 取消、失败与人工接管

浏览器关闭页面、用户取消运行、客服接管会话以及模型请求失败，会改变不同的状态。页面断开连接只说明这个连接结束。项目提供独立取消接口来改变数据库中的运行状态，客服接管接口则同时改变会话控制权和活动运行。

取消请求与会话控制权

POST /openapi/v1/agent/runs/{run_id}/cancel验证当前账户、租户和店铺权限，按会话在前、运行在后的顺序取得记录锁。允许取消排队、运行、等待客户和等待审批的任务；重复取消返回当前取消状态，不需要Idempotency-Key。事务把运行改为CANCELLED，清除等待内容和租约。关联会话的活动运行被释放，并生成run.cancelled事件。

客服接管通过POST /openapi/v1/conversations/{conversation_id}/takeover提交expected_control_version和请求键，要求STAFF身份与conversations:manage。接管成功后取消旧活动运行，清空active_run_id，增加control_version，把控制者改为HUMAN并记录接管客服。交还操作只允许当前接管客服执行；交还后，客户再次发送消息才会创建新运行。

取消接口改变可提交的业务状态，不保证远端模型请求立即停止。阶段04的接口没有向执行中的worker直接发送task.cancel()；worker在下一次locked_run检查时发现运行或控制权已经变化。已经提交的换货方案仍然存在，取消Agent运行不会自动取消该业务方案。

源码：04 · cancel、04 · owned_run、04 · control。

分支失败与父运行结束

专业协作需要两个角色的结果都完成，协调节点才会继续检查并返回。某个必需分支失败或协作超过60秒时，本次图调用不能返回成功协作结果，异常继续传给外层worker；协作函数的finally释放额外并发额度。已提交的分支记录继续保留。

阶段04的execute_one处理图执行异常时，只有父运行仍为RUNNING且token仍属于本次领取，才将其改为FAILED并保存错误码。取消或新租约已经改变状态时，旧执行者不能把该运行重新写成自己的失败结果。外层finally释放本次领取的Redis额度。非预算准入类异常继续抛出，当前常驻入口也会结束；已记录为FAILED的运行不会因为进程重新启动而自动执行。

展开运行诊断参考答案

租约有效期间返回None符合领取条件。到期后token增加，说明新执行者取得执行权；旧token被拒绝符合提交检查。已有订单结果可以复用，但调用方仍需重新检查当前身份与来源。规则查询使用原稳定操作编号继续处理，成功以后保存新token。

父状态FAILED时，当前claim不会自动重新执行；访问会话撤销时，读取完成结果仍会在父身份检查处失败；订单来源变化时，业务汇总返回ORDER_VERSION_CONFLICT。历史结果记录可以保留，当前提交需要有效授权和当前来源。诊断中保留实际错误码，不通过修改token或数据库状态绕过检查。

如果租约到期仍无法领取，继续检查任务总期限、租户当前额度、目标run_id和运行状态。claim对已超过期限的任务会保存FAILED及RUN_DEADLINE；需要把该结果与没有取得执行权区分记录。

12.1 并行请求与双提交

绘制一张Mermaid时序图，把“读取订单与查询资料”表示为两个读取任务，把“批准与拒绝同一申请”表示为两个业务提交。每条箭头标明调用方、输入、响应或保存结果。说明哪些数据已经具备，哪些操作需要等待前序结果，并提交第10节的本人测试记录。

记录至少包括：普通字段并发更新错误、相同结果重复合并、相同编号内容冲突、取消后迟到结果、审批200与409、数据库版本增加一次、业务事件一条。解释收到409的页面处理，以及同一次请求响应丢失时幂等键的使用方式。

展开请求与状态参考答案

订单号、客户、店铺及资料问题已确定时，独立读取任务可以并行；资料参数需要订单查询结果时，图中需要对应依赖。两次审批各有自己的业务决定和幂等键，使用同一旧版本时允许一个成功，另一个收到VERSION_CONFLICT。调用方读取最新状态，再判断是否还有新的修改可以提交。

重复网络投递继续使用原键和原正文查询原结果。图结果的重复合并使用operation_id，业务重复请求使用幂等记录，数据库竞争使用锁与业务版本，三者的作用位置需要在图中分别标注。

12.2 只读工单角色开发

从阶段04建立个人练习分支，新增TicketAgent，用于读取客户指定工单的当前进度。现有get_ticket工具可以复用，TicketAgent及其协作接入属于本题新增内容。范围限定当前工单快照，返回ticket_id、status、version、proposal_version及可用的审批和履约状态；项目现有ticket_view提供这些字段。

提交以下内容：

  1. 输入与依赖图：增加工单输入，明确已知工单编号时的并行查询，以及编号来自前序操作时的等待关系。
  2. 权限与调用过程：说明模型返回tool_calls后，Python工具执行代码如何校验名称、参数、当前身份、店铺和客户归属；新角色只允许get_ticket。
  3. 后端实现：补充角色、提示、参数、节点和汇总要求；结果使用稳定操作编号，登记与完成经过父运行检查，每个并发task使用独立Session。
  4. 来源和状态：保存工单版本，扩展来源复核；说明局部消息、图结果、父运行、子任务和业务工单各自的写入位置。
  5. 正确性验证：执行真实工具和MySQL测试，包含授权读取、跨租户或跨客户拒绝、版本变化、重复结果、取消、旧token拒绝和恢复复用。

只读查询仍然需要检查权限；已经完成的查询结果也可能过期。作业的自动验证使用真实业务函数与协调代码，生成调用为0，不以固定文本代替模型响应进行模型验收。模型决策与自然语言答复质量列为本题未执行范围；角色接入代码与权限、状态、数据库验证分别提交。

展开只读角色实现参考答案

输入增加明确的ticket_id，由服务端身份确定租户和客户范围。复用invoke_tool执行get_ticket：Pydantic验证参数，业务服务定位租户内资源，检查店铺及tickets:read，客户身份继续检查资源归属。调用方输入的租户字段不能扩大权限。

当前execute_specialist在看到order_id时读取source_version。工单结果也有order_id，但工单版本字段是version，因此新增工单处理需要明确识别返回类型，并保存ticket:<id>来源；不能直接套用订单字段处理。当前来源验证只接受order和document，需要增加工单的租户、店铺、归属、状态与版本检查。

run_specialists目前建立两个角色节点，汇总要求两份结果。新增角色需要共同调整节点、等待关系、必需结果检查与全局额度申请。父运行累计模型次数不会因增加角色或恢复分支而清零；声明新增角色每次决策及最终答复的调用预算，并核对整个运行上限。

业务状态由Ticket、Approval等记录管理，TicketAgent保存读取快照。来源变化后拒绝旧结果，重新查询需明确新的操作语义与编号；同一已完成操作编号携带不同结果会冲突。各角色的消息列表和Session独立，汇总只接收结构化结果。

12.3 进程中断与交付记录

在真实MySQL环境扩展恢复测试：工单读取已经保存，另一项查询尚未完成时终止测试创建的子进程；等待原租约自然到期，再领取并恢复。核对PID及所属关系后才终止进程，保留工作目录之外的服务。沿用第10节的单项期限和进程树清理方式。

提交旧新token、操作编号、已完成和进行中的分支数量、最终状态及模型尝试数量。分别说明“结果已提交”和“远端已完成但本地结果未提交”两个中断位置。附源文件、迁移变更说明、执行命令、JUnit和JSON结果，以及一段面试说明：这次故障影响了什么状态，哪些查询复用，哪些查询重做，哪些提交被拒绝。

展开恢复验证参考答案

已提交结果可以在有效新token下读取，来源版本仍需复核；进行中的分支使用原操作编号继续执行。旧token的开始与完成均失败，最终记录使用新token。父运行FAILED、取消、权限撤销或任务超期分别执行对应失败检查，不能直接修改数据库恢复执行。

远端已经处理、本地没有保存结果时，查询可能再次发生。只读查询可以重新取得当前事实，业务写入则需要外部稳定操作编号与结果查询。记录已发生的全部模型尝试，未知结果保留其状态；本作业协调实验的生成调用保持0。测试通过表示实际执行过的场景满足断言，未执行的模型与网络条件另行注明。
