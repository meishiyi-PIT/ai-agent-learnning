你接到一个客服系统需求：用户在页面输入“键盘有一个按键失灵，帮我查询能不能换货”，页面持续显示处理进度，最后给出答复或待确认的换货方案。后端需要根据用户的话选择查询订单、检索商品资料等操作。

模型服务可以理解为一个外部HTTP服务：程序把用户消息和可用函数的说明发送过去，模型返回文字，或者返回工具名称和JSON参数。后端检查参数与权限，执行相应函数，再把结果交给模型。这个反复调用的过程，构成了本项目Agent的基本运行方式。

源码使用00-handover和01-business-change两个固定阶段，分别对应现有项目与新增“审批超时提醒”需求；09-course-delivery提供最终实现。

1. 项目功能与业务流程

智服中台是一套服务多个商家的客服与售后系统。前端包含消费者H5、商家后台和平台后台，后端处理商品查询、聊天消息、换货方案、审批和订单系统对接。对开发者而言，可以先把它看作一个包含聊天页面、管理表单和后台任务的Web项目。

以键盘商品页为例，页面通过商品接口获取名称和规格；用户输入“支持哪些连接方式”后，后端从本店发布的说明资料中查找相关内容，再提供给模型生成答复。这种“检索资料，再生成回答”的方式称为RAG。当用户询问换货，程序还要查询本人订单、签收时间、可申请数量和店铺规则。商品数据与工具调用分别位于商品目录接口和业务工具入口。

Agent增加了根据用户输入选择函数的能力，账户认证、数据库查询和审批规则仍由应用代码执行。用户只询问换货资格时，程序执行查询；用户明确申请办理后，才能创建等待客户确认的方案。

商家管理员、客服和主管共用商家后台，服务端按账户授权判断具体动作；平台后台有独立的登录入口。前端菜单和按钮控制可见性，服务端逐次检查操作权限。例如用户修改URL中的订单编号，不能取得其他客户的订单；客服接管聊天后，也仍需等待客户本人确认方案。

一次换货会保存方案、客户确认、审批和外部操作记录。方案记录商品、数量、理由和规则版本，客户与主管分别处理同一个版本；提交者不能审批自己的方案。批准后，后台继续检查权限、规则及可用数量，再向OMS发送换货请求。OMS请求超时时，保留原操作编号并查询结果，防止重复创建换货单。完整检查位于售后服务与履约准备。

00-handover已经包含上述业务、权限检查、重复请求处理、后台任务领取和调用预算。后续版本增加审批超时提醒，以及两个分别负责订单和资料查询的Agent，并完善查询性能、模型输入长度、流式输出与故障恢复。两个Agent的协作需要启用对应运行配置，调用入口可见最终版本的run_specialists。

最终版本通过后端接口、事件、记录和终端检查业务结果：同一方案可以查到确认、审批、到期提醒及履约操作；重复扫描保持通知唯一；取消、权限撤销和进程恢复有对应验证结果；协作运行能找到分支结果与用量。交付同时包含固定源码、迁移、OpenAPI、运行命令和实验报告，使其他人能够复查。

2. 分层架构与数据存储

后端采用按业务模块组织的FastAPI应用，并通过独立worker执行后台任务。create_app注册认证、会话、售后、知识、商家和平台路由。worker可以理解为持续运行的任务处理进程。OMS是独立的订单管理服务，位于src/zhifu/oms，使用自己的数据库。

独立查看项目架构图

聊天请求是异步任务：API把消息和运行记录一起提交到MySQL，worker随后领取，前端通过SSE接收进度。SSE是一条持续返回服务器事件的HTTP连接，页面据此更新处理状态和回答文字。普通配置或审批接口可以直接调用业务服务。工具函数也调用这些服务，因此从聊天入口发起的操作仍经过相同的权限和业务状态检查。

图中的基础设施各有用途：Agent任务通过MySQL领取；RabbitMQ负责已提交业务事件的投递；Redis提供跨进程额度和心跳；BGE-M3把文本转换成用于相似度计算的向量，Milvus据此查询相关资料。生成模型和OMS都是通过HTTP访问的服务，分别处理文本生成与订单业务。

阅读代码时，把模块目录和它操作的表放在一起看。tenant_id区分商家，store_id关联店铺权限，subject_id确定客户；登录身份与store_grants共同限制操作范围。order_projections保存OMS同步来的订单数据，工单表保存本系统的处理状态。聊天文字作为用户输入处理，订单状态以经过授权查询的数据为准。

检索可以理解为带权限过滤的站内搜索。RetrievalClient.search先请求BGE-M3计算问题的向量，再在Milvus中结合向量相似度和BM25关键词匹配查找资料；verified_results回到MySQL检查资料仍已发布且版本有效。搜索结果需要经过当前权限和版本检查，才能加入模型输入。

两套Redis分别处理不同数据：cache用于请求限流；state保存跨进程并发额度、SSE连接额度、worker心跳和授权后的客户记忆内容。“记忆”在这里指后续对话可以使用的客户信息，例如沟通习惯；MySQL的memory_profiles保存用户是否同意、当前版本和内容引用。读取Redis内容前要检查这些字段，见memory.read。

这张时序图对应常见的“数据库事务＋消息队列＋外部HTTP调用”。publish_one等待RabbitMQ确认发布，consume_one在业务事务完成后确认消费。Agent运行和记忆任务直接从MySQL领取。排查任务重启或重复消费时，先找到数据库中的任务状态和操作编号，再追踪后续调用。第5节会继续说明Agent worker内部的函数调用顺序。

OrderAgent与KnowledgeAgent分别发起模型请求，各自能调用的Python函数由程序限制。asyncio调度两个任务的等待，结果合并函数决定重复返回或内容冲突时的处理。线程实验检查多个线程交回结果时的数据访问；多个后台worker进程则通过数据库状态和有期限的执行权记录协调工作。并行成功以后，提交结果还需要复核权限、数据版本和会话控制权。

性能分析沿请求路径展开：前端连接与后端限流 → 任务排队 → 数据库查询与商品资料搜索 → 组装模型请求 → 模型生成 → 保存事件与前端显示。模型输入和输出按token计量，token是模型处理文本的计量单位；SSE是服务端在HTTP连接中持续发送事件的方式。每次优化都记录正确性测试、耗时、质量和费用，明确改善了哪一部分。提醒功能的数据库锁、扫描索引和轮询间隔，也会直接影响处理速度。

源码与实验入口：专业Agent协作、状态合并、进程恢复、上下文、增量响应、部署演练、最终用量核对。

确认请求的调用记录

以POST /openapi/v1/after-sales/proposals/{proposal_id}/confirm为例：路由接收请求，command创建事务并取得AuthContext，其中保存服务端验证过的身份信息；AfterSalesService.execute检查授权、重复请求和业务版本；confirm确认当前DRAFT方案，保存Confirmation和Approval，工单进入WAITING_REVIEW。事件、通知和请求收据与业务结果共同提交。提醒记录加入这份确认事务，使用同一个确认时间。

据此可以确定修改位置：新增提醒配置与处理记录，在确认和业务结束时调用提醒服务，由独立worker查询到期记录。前端继续通过接口保存配置和查询通知，业务权限由后端检查。字段不合法、访问权限不足或版本已变化时，接口返回相应错误，前端根据错误提示补充信息或重新读取当前状态。

源码：应用入口、数据库连接、确认路由、业务执行入口。

5. Agent请求的执行流程

客户在聊天框提供本人键盘订单的UUID，询问：“这张订单的键盘按键失灵，请核对能否换货，并查一下资料里的清洁说明。”前端发送文本和会话信息，后端需要读取订单、换货规则及商品资料。这条消息表达的是查询意图。创建待确认方案还需要客户明确提出办理请求，并通过后端权限检查；确认、审批和履约继续经过各自的业务接口。

Agent是应用层维护的执行循环：调用模型，读取它请求执行的函数，检查并执行函数，再把结果交给模型继续处理。一次工具请求称为tool_call，包含工具名称、JSON参数和用于匹配结果的调用标识。例如，名称是get_order，参数中包含order_id。后端按允许的名称调用对应Python函数，检查参数和业务权限。

HTTP请求与后台任务

前端通过POST /openapi/v1/conversations/{conversation_id}/messages提交消息，携带访问令牌、Idempotency-Key与expected_control_version。接口检查身份、会话归属和控制版本；在AGENT模式且没有活动任务时，同一事务保存用户消息事件message.user与任务记录AgentRun，返回201及run_id。前端收到任务编号后显示处理中，最终正文通过后续事件取得。queue_run还保存模型配置和发布版本，任务初始状态为QUEUED。

后台worker通过claim选择可以处理的任务，检查租户与Redis并发额度，更新状态为RUNNING，保存125秒租约和lease_token。租约表示有期限的执行权，token用于识别本次领取。execute_one随后执行LangGraph流程。各节点提交前调用locked_run，重新检查权限、会话控制权与执行权；客服接管或旧worker失去租约以后，它返回的结果无法覆盖当前状态。

6. 审批超时提醒的业务规则

需求原文是：“客户已经确认换货方案，主管迟迟没有审批，希望系统能够提醒。”对应的开发内容包括管理页面读取和保存提醒配置、客户确认时保存到期时间、后台定时任务查询到期记录，以及主管进入通知页查看待审批方案。接口、数据表和定时任务需要使用同一套时间、版本和接收人规则。

到期时间与配置快照

假设客户10:00确认方案第3版，店铺配置为30分钟。10:29:59时不能发送；10:30:00开始允许检查。管理员10:10通过配置表单把时限修改为60分钟，原方案仍按10:30到期。假设10:20修订并重新确认第4版，则第3版停止产生新提醒，第4版按当时60分钟配置在11:20到期。配置修改只影响后续确认，已有提醒保留确认时的配置。这里的时间用于解释规则，数据库和接口统一使用UTC。

业务规则 数据条件 相关记录
到期时间 当前版本的confirmed_at + delay_seconds 确认记录、时限、配置版本、due_at
发送条件 当前工单WAITING_REVIEW、审批PENDING、版本一致、租户与店铺启用 提交前重新读取的业务状态

首次成功发送以后，提醒进入SENT，后来增加主管不会为该方案版本补发。通知的已读状态只影响展示；业务操作仍根据当前权限、方案和审批状态判断。确认时间和到期时间保存在数据库中，用户关闭通知页、客户端断线和API进程重新启动，都不改变这两个时间。

参考结果

提醒成功发送并提交时，每位当时有效的接收人已经有一条通知，提醒为SENT；随后审批通过，已有通知继续保留。审批先提交时，待处理提醒随业务状态变更成为CANCELLED，扫描不再新增通知。两种结果都需要通过事务提交顺序和最终记录解释；浏览器收到响应的顺序不能单独说明数据库的提交顺序。

Agent调用与既有业务服务

9. 定时任务的并发与运行

提醒worker是持续运行的后台进程，定期查询数据库中的到期记录。due_candidates先返回待检查的标识，process_one再为每条记录创建独立事务，取得业务记录锁，重新读取状态、时间、版本和权限。部署两个worker时，它们可能查询到同一条记录。查询到候选只表示需要检查，发送条件仍在处理事务中确认。

下面的process_one片段依次取得Tenant排他锁、Store共享锁、Ticket排他锁，再通过refresh锁定并重新读取提醒。某个worker等待期间，另一个worker可能已经发送通知；重新读取后发现状态已经变化，本次处理返回skipped。

python
tenant = await session.get(Tenant, snapshot.tenant_id, with_for_update=True)
store = await session.get(Store, snapshot.store_id, with_for_update={"read": True})
ticket = await session.get(Ticket, snapshot.proposal_id, with_for_update=True)
await session.refresh(snapshot, with_for_update=True)
if snapshot.status != "PENDING":
    return "skipped"

接收人查询前，程序按UUID顺序取得有效员工的Principal共享锁，随后读取StoreGrant。管理CLI修改授权也会取得相应账户锁。假设撤权事务先取得账户锁，提醒事务会等待；撤权提交后，提醒继续读取当前授权。本项目使用READ COMMITTED，这次授权查询能够看到刚提交的修改。请求、管理命令与worker需要采用相容的锁顺序，才能共同保护这个过程。

源码：数据库隔离级别。

重复执行与通知唯一性

通知以租户、接收人和事件建立唯一约束。事件键包含方案标识及方案版本，重复写入沿用通知服务的on_duplicate_key_update(id=Notification.id)，保留已有记录与read_at。通知写入和提醒更新为SENT共用一个事务。重复执行不会把已经阅读过的通知重新变为未读。

中断位置 已提交的数据 再次运行的处理
候选查询以后、处理以前 提醒仍为PENDING 再次复核业务并处理
已执行通知写入、事务尚未提交 当前事务的关联写入尚未提交 原事务结束后重新处理待办
通知与SENT共同提交以后 接收通知及完成状态同时存在 读取SENT后结束，不增加通知
到期但无有效接收人 PENDING及推进后的next_check_at 60秒以后重新读取当前权限

本次通知是数据库中的站内通知，用户打开通知页时通过接口读取。调用外部服务的场景还需要处理请求结果未知、接收方去重和状态查询，项目的OMS履约模块提供了相应实现。

源码：process_one、通知唯一约束、notify。

扫描批次与处理延迟

scan_due默认每批100条，允许1至500，整批最长30秒。每个候选分别建立事务；常驻worker完成一批以后等待5秒。无接收人的重查间隔为60秒。某个提醒的实际等待由扫描间隔、前面的候选、锁等待和本次事务耗时共同组成，due_at表示开始允许检查的时间。

计算练习：假设每条处理平均20毫秒且没有锁等待，100条约需要2秒，加上5秒批间等待，连续满批时约每秒处理14.3条。这是根据给定条件计算的结果；实际吞吐需要测量候选数量、每批耗时、到期延迟与锁等待。把batch_size从100增加到200，也会增加一批的处理时间，不能直接得出吞吐增加一倍的结论。

同租户处理受Tenant排他锁限制，增加worker数量不能直接提高同租户同时处理的数量。改变锁范围时，还必须继续证明审批、配置修改、权限撤销与通知提交的顺序正确。

每批输出selected、sent、deferred、cancelled和skipped，提醒记录提供检查时间与停止原因，状态Redis保存reminders进程心跳。心跳表示进程仍在运行，提醒记录表示具体任务是否已经处理。进程正常但通知未出现时，可以继续检查next_check_at、接收人权限、候选积压和数据库等待。

源码：scan_due、worker.main、进程管理。
