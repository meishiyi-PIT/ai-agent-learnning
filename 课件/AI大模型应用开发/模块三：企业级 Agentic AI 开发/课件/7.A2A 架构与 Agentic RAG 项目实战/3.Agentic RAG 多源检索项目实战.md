## 一、业务场景与七类问题
系统定位为**电商售后助手**，使用三类数据：**内部政策、脱敏订单和公开网页**。

| 类型 | 用户问题 | 预期工具 |
| :---: | --- | --- |
| **向量检索** | 耳机拆封后还能七日无理由退货吗？ | **Milvus** |
| **SQL 查询** | U1001 最近 30 天有几笔有效订单，实付总额是多少？ | **SQLite** |
| **网页搜索** | 查询品牌官网关于 XPhone 15 Pro 的最新公告 | **Tavily** |
| **双源组合** | 统计 U1001 最近 30 天订单，并结合内部运费规则说明是否包邮 | **Milvus + SQLite** |
| **三源组合** | 统计 U1001 最近 30 天购买 XPhone 15 Pro 的订单金额，结合内部退货政策和品牌官网最新公告给出售后建议 | **Milvus + SQLite + Tavily** |
| **证据不足** | U1001 的订单 O2026001 现在配送到哪里，预计几点送达？ | **SQLite + Milvus；仍需物流 API** |
| **证据不足** | U1001 的 AirBuds Pro 订单是否已经通过售后审核，退款会在哪一天到账？ | **SQLite + Milvus；仍需售后业务 API** |


> 后两类问题即使已有工具全部执行成功，也**不能直接生成确定答案**。SQLite 只保存订单统计，Milvus 只保存通用政策，二者都不包含实时物流状态和售后审核状态。详细判断见“Evidence Grader 与终止”。
>

> `U1001` 是课程使用的脱敏用户。生产系统必须从**登录态或服务端认证上下文**注入用户身份，不能让模型根据自然语言决定查询谁的订单。
>

## 三、数据准备逻辑
### 1. 内部政策进入 Milvus
**项目准备三份政策：**

```latex
return_policy.md           → 退货、换货、退款
shipping_policy.md         → 运费、包邮、拆单、延迟
price_protection_policy.md → 价保期限和差价规则
```

**每份文档声明两个受控元数据：**

```latex
政策类型：shipping_policy
适用类目：all
```

准备脚本按**二级标题**切分 Chunk，并将 `policy_type`**、**`category`** 与正文**一起写入 Milvus。

```python
documents = [
    chunk
    for path in settings.documents_path.glob("*.md")
    for chunk in split_document(path)
]

store.create_collection(recreate=True)
store.insert_documents(documents)
```

### 2. 脱敏订单进入 SQLite
原始真源位于 `<PROJECT_ROOT>/data/source/orders.csv`：

```latex
days_ago,order_id,user_id,product_name,category,amount,status
1,O2026001,U1001,XPhone 15 Pro,phone,6999.00,paid
5,O2026002,U1001,AirBuds Pro,headphone,1299.00,shipped
```

**字段含义：**

| 字段 | 含义 | 示例与约束 |
| --- | --- | --- |
| `days_ago` | 距离数据导入当天的天数 | `1` 表示一天前，允许范围为 0～3650 |
| `order_id` | 脱敏订单编号 | 格式为 `O` 加 7 位数字，例如 `O2026001` |
| `user_id` | 脱敏用户编号 | 格式为 `U` 加 4 位数字，例如 `U1001` |
| `product_name` | 商品名称 | 用于按商品过滤订单，例如 `XPhone 15 Pro` |
| `category` | 商品类目 | 统一使用小写英文，例如 `phone`、`headphone` |
| `amount` | 订单记录金额 | 必须大于等于 0；只有有效订单才进入实付统计 |
| `status` | 订单状态 | 只允许 `paid`、`shipped`、`completed`、`cancelled`、`refunded` |


**状态是否进入统计：**

| 状态 | 含义 | 是否计入有效订单和实付金额 |
| --- | --- | --- |
| `paid` | 已支付 | **是** |
| `shipped` | 已发货 | **是** |
| `completed` | 已完成 | **是** |
| `cancelled` | 已取消 | **否** |
| `refunded` | 已退款 | **否** |


`days_ago`** 在导入时转换为真实日期。**例如课程当天为 2026-07-16，`days_ago=5` 会写入 `ordered_at=2026-07-11`。这种设计可以保证“最近 30 天”的课程样例不会因固定日期过期。

> **CSV 是可审计的原始真源，SQLite 是由准备脚本生成的查询库。**修改课程订单时应修改 `orders.csv`，然后重新执行数据准备，而不是直接编辑 `shop.db`。
>

课程数据中，`U1001` 最近 30 天有 **4 笔有效订单**，实付总额 **10396 元**，低于 99 元的有效订单为 **0 笔**。

## 四、意图路由与计划生成
### 1. 受控槽位
路由前先提取：

```latex
user_id      → U1001
product_name → XPhone 15 Pro
policy_type  → return_policy / shipping_policy / price_protection
```

订单问题缺少 `user_id` 时返回 `CLARIFY`。敏感批量数据请求直接返回 `REFUSE`，不会执行任何数据工具。

### 2. 多路由判断
```python
routes = []
if needs_docs:
    routes.append(RouteName.MILVUS_SEARCH)
if needs_sql:
    routes.append(RouteName.SQL_QUERY)
if needs_web:
    routes.append(RouteName.WEB_SEARCH)

requires_decomposition = len(routes) > 1
```

> 这里**不能使用 **`if/elif`，否则三源问题只能保留第一条命中的路由。
>

### 3. 三源计划
对于三源组合问题，计划结果为：


## 五、三个工具的关键实现
### 1. Milvus：内部政策
Milvus Query 使用用户问题，`policy_type`** 作为标量过滤条件**。模型**不能直接生成任意 Milvus Filter**。

```python
evidence = vector_store.search(
    query=step.query,
    top_k=step.arguments["top_k"],
    policy_type=step.arguments["policy_type"],
)
```

返回的 Chunk 统一转换为 `source_type="milvus"` 的 Evidence，并保留政策文件、Chunk、类型和相关性分数。

### 2. SQLite：订单统计
**SQL 模板固定**，模型只能提供经过校验的 `user_id`、`days` 和 `product_keyword`。

```python
sql = """
SELECT COUNT(*) AS order_count,
       COALESCE(SUM(amount), 0) AS total_paid,
       SUM(CASE WHEN amount < 99 THEN 1 ELSE 0 END) AS below_99_count
FROM orders
WHERE user_id = ?
  AND ordered_at >= ?
  AND status IN (?, ?, ?)
  AND (? = '' OR product_name LIKE ?)
"""

row = connection.execute(sql, parameters).fetchone()
```

> **不允许模型生成完整 SQL**，也不能把用户输入直接拼接到查询字符串。
>

### 3. Tavily：公开网页
Web Search 只在问题需要**官网、新闻、最新公告或公开资料**时触发。

```python
response = client.search(
    query=query,
    search_depth="basic",
    max_results=max_results,
    include_answer=False,
    include_raw_content=False,
)
```

> 系统只使用 `title`、`url`、`content` 和 `score` 构造 Evidence。搜索服务生成的摘要答案**不能直接作为最终答案**。
>

## 六、并行执行与实际 Query 输出
### 1. 并行执行
```python
if len(steps) <= 1:
    results = [execute_step(step) for step in steps]
else:
    with ThreadPoolExecutor(max_workers=min(len(steps), 4)) as executor:
        results = list(executor.map(execute_step, steps))
```

> 该代码只适用于**无依赖读任务**。存在 `depends_on` 时必须使用**拓扑批次调度**，不能直接把全部步骤提交到线程池。
>

### 2. 记录真实查询
执行完成后，将计划 Query、参数和实际状态写入 `executed_queries`：

```python
executed_queries = [
    {
        "step_id": step.id,
        "tool": result.tool,
        "query": step.query,
        "arguments": step.arguments,
        "status": result.status,
        "latency_ms": result.latency_ms,
    }
    for step, result in zip(steps, results, strict=True)
]
```

## 七、Evidence Grader 与终止
**Grader 先做确定性检查**：计划要求的 `milvus`、`sql`、`web` 是否全部返回 Evidence。Milvus 结果还要达到**最低相关性门槛**。

```latex
来源完整且相关       → accept
来源缺失且仍有预算   → rewrite_query
达到最大检索轮次     → stop
```

> Rewrite 后重新执行原计划，但**不能提高 **`max_rounds`。达到预算仍缺少网页或订单证据时，只能输出**部分结论并标记缺口**。
>

### 1. 证据不足案例：缺少实时物流状态
用户问题：

```latex
U1001 的订单 O2026001 现在配送到哪里，预计几点送达？
```

预期路由：

```latex
SQL_QUERY + MILVUS_SEARCH
```

**当前工具能够获得：**

+ SQLite 返回 `U1001` 最近 30 天的订单统计，但不保存实时物流节点。
+ Milvus 返回配送、运费和延迟送达规则，但不包含具体订单状态。

**仍然缺少：**

+ 订单 `O2026001` 的物流公司和运单号。
+ 当前物流节点、配送员状态和预计送达时间。
+ 订单业务 API 或物流 API 的实时返回结果。

> 系统**不能根据通用配送规则推断订单位置**。达到最大检索轮数后，应返回部分答案并说明需要调用业务 API，终止原因为 `retrieval_budget_exhausted`。
>

### 2. 证据不足案例：缺少售后审核状态
用户问题：

```latex
U1001 的 AirBuds Pro 订单是否已经通过售后审核，退款会在哪一天到账？
```

预期路由：

```latex
SQL_QUERY + MILVUS_SEARCH
```

**当前工具能够获得：**

+ SQLite 只能确认用户存在相关订单，并返回订单数量和金额。
+ Milvus 可以检索质量问题处理条件、仓库验收要求和一般退款时效。

**仍然缺少：**

+ 售后申请编号、审核结果和提交材料。
+ 仓库是否已经验收，以及验收完成时间。
+ 银行或支付渠道的实际处理进度。

> 系统只能说明一般退款流程，**不能判断“已经通过审核”**，也不能给出具体到账日期。达到预算后，应输出证据缺口，而不是把“一至三个工作日”直接换算成确定日期。
>

> 两个案例用于说明：**工具调用成功只代表获得了数据，不代表证据已经覆盖用户问题中的全部目标。**Grader 必须检查实时性、对象一致性和关键业务状态。
>

## 八、模型适配边界
项目通过 `DecisionEngine`** 协议隔离模型**。当前提供确定性 Demo 引擎和 DeepSeek 适配器，替换模型**不需要修改 LangGraph、Tool 或 State**。

DeepSeek 通过 Function Calling 输出 `RouteDecision`** 和 **`QualityGrade`。结构化路由与评分固定关闭 Thinking，避免强制 `tool_choice` 与 Thinking 模式冲突；最终答案可通过 `.env` 的 `DEEPSEEK_ANSWER_THINKING` 单独控制。模型输出进入图之前仍要经过 **Pydantic Schema、路由白名单、权限和预算校验**。

## 十、课后作业：实现企业IT故障诊断助手
### 1. 业务场景
员工使用阿里云 VPN 网关提供的 SSL-VPN 远程办公时频繁断线。IT 服务台需要结合历史工单、内部排障手册和阿里云最新公告，判断故障范围并给出排查顺序。

测试问题：

```latex
今天上午阿里云 SSL-VPN 频繁断开，Windows 客户端提示“认证超时”。
请统计过去 30 天同类故障发生次数，结合内部 VPN 排障手册和厂商官网最新服务公告，
判断更可能是本地配置问题还是公共服务异常，并给出排查步骤。
```

系统需要联合三类证据：

| 数据源 | 需要提供的证据 |
| --- | --- |
| SQLite | 过去 30 天同类故障数量、影响终端和历史解决方式 |
| Milvus | VPN 认证超时的内部排障步骤、适用系统和客户端版本 |
| Web Search | 阿里云官网的最新运维事件、故障公告或版本通知 |


> **作业目标**：在现有项目上完成一次中等规模的业务迁移，覆盖意图识别、三源路由、结构化统计、元数据检索、证据冲突和有限重试。
>

### 2. 作业边界
+ 继续使用项目现有的 **Milvus、SQLite、Tavily 和 DeepSeek**。
+ 不新增工单系统或监控平台 API，不实现自动修改网络配置等写操作。
+ 只处理 `aliyun_ssl_vpn` 的 `auth_timeout` 故障，不扩展其他 IT 服务。
+ Web Search 在自动化测试中可以使用固定的 Mock Evidence，避免网络波动影响结果。
+ 最终产物仍通过现有 `/query` 接口调用，不开发前端页面。

### 3. 实现要求
#### 3.1 准备 SQLite 故障数据
新增 `incidents.csv`：

```plain
days_ago,incident_id,service_name,error_type,client_os,status,resolution
2,INC1001,aliyun_ssl_vpn,auth_timeout,Windows,resolved,refresh_certificate
7,INC1002,aliyun_ssl_vpn,auth_timeout,Windows,resolved,reset_vpn_profile
12,INC1003,aliyun_ssl_vpn,auth_timeout,macOS,resolved,vendor_service_recovered
45,INC1004,aliyun_ssl_vpn,auth_timeout,Windows,resolved,refresh_certificate
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `days_ago` | 距离数据导入日的天数，导入时转换为真实发生时间 |
| `incident_id` | 故障工单编号 |
| `service_name` | 出现故障的服务，本作业固定为 `aliyun_ssl_vpn` |
| `error_type` | 标准化故障类型，本作业固定为 `auth_timeout` |
| `client_os` | 发生故障的客户端操作系统 |
| `status` | 工单状态 |
| `resolution` | 历史解决方式 |


新增参数化查询，按 `service_name`、`error_type` 和时间窗口统计工单，并汇总历史解决方式。45 天前的 `INC1004` 不应进入过去 30 天统计。

#### 3.2 准备 Milvus 排障文档
新增 `vpn_troubleshooting.md`，至少包含：

+ 认证超时的常见原因。
+ Windows 客户端的排查顺序。
+ 证书过期和 VPN Profile 损坏的识别方式。
+ 厂商服务异常时的终止条件和升级方式。

文档写入 Milvus 时声明受控元数据：

```latex
文档类型：troubleshooting_guide
服务名称：aliyun_ssl_vpn
适用系统：Windows
```

检索时使用 `service_name=aliyun_ssl_vpn` 和 `client_os=Windows` 过滤，避免召回其他系统或服务的操作步骤。

#### 3.3 扩展意图识别与路由
从测试问题中识别以下结构：

```latex
task_type=diagnose
service_name=aliyun_ssl_vpn
error_type=auth_timeout
client_os=Windows
time_range=30d
knowledge_types=[structured, internal_doc, realtime]
routes=[sql, milvus, web]
```

+ 缺少服务名称或故障现象时返回 `CLARIFY`。
+ 只问历史次数时路由到 **SQLite**。
+ 只问排障步骤时路由到 **Milvus**。
+ 只问厂商当前状态时路由到 **Web Search**。
+ 完整测试问题路由到 **SQLite + Milvus + Web Search**，三个只读任务可以并行执行。
+ Web Search 必须优先检索配置的厂商官网域名，不使用论坛帖子作为服务状态依据。

#### 3.4 Web Search 的实现方式
课程项目已经提供 `TavilyWebSearchProvider` 和 `WebSearchTool`。学员不需要重新封装搜索 SDK，只需要在 `Decision Engine` 中生成适合本场景的搜索任务。

本作业统一约定：

```latex
VPN 产品：阿里云 VPN 网关（SSL-VPN）
官方资料域名：help.aliyun.com
```

不要直接把完整用户问题作为搜索词。Planner 应提取产品、故障类型和“最新状态”需求，生成受控 Query：

```python
# 只搜索课程约定的阿里云官方资料站点，减少论坛和聚合站的干扰。
vendor_status_query = (
    'site:help.aliyun.com/zh/vpn 阿里云 SSL-VPN '
    '认证超时 运维事件 最新公告'
)

step = PlanStep(
    id="search_vendor_status",
```

真实运行时，现有调用链会自动执行：


搜索结果返回后，只保留官方域名：

```python
from urllib.parse import urlparse


def is_official_vendor_source(source: str) -> bool:
```

#### 3.5 诊断控制流
SQLite 负责确定性统计，不能让模型根据工单文本估算次数：

```python
# 仅统计时间窗口内、服务名称和故障类型均匹配的工单。
matched_incidents = [
    item
    for item in incidents
    if item.service_name == "aliyun_ssl_vpn"
    and item.error_type == "auth_timeout"
    and item.occurred_at >= window_start
]

incident_count = len(matched_incidents)
```

Evidence Grader 按以下规则检查证据：

| 证据状态 | 控制流决策 |
| --- | --- |
| 三类证据完整，厂商公告显示服务异常 | 输出公共服务异常判断，优先给出等待、验证和升级步骤 |
| 厂商无异常公告，内部手册和历史工单支持本地原因 | 输出“优先排查本地配置”，不能表述为已确认根因 |
| 厂商公告与内部证据冲突 | 标记冲突，列出两条验证路径 |
| 缺少厂商状态证据 | 返回部分答案，不能排除公共服务异常 |
| 内部手册未覆盖当前系统或版本 | 改写 Query；超过 `max_rounds` 后停止并建议升级人工处理 |


DeepSeek 负责解释证据和组织排查顺序，不负责虚构根因。只有厂商公告、内部手册或历史工单明确支持时，答案才能给出相应判断。

### 4. 验收要求
#### 功能验收
+ 完整测试问题能够路由到 **SQLite + Milvus + Web Search**。
+ `executed_queries` 能看到三个工具的查询内容、参数、状态和耗时。
+ SQLite 对示例数据统计得到过去 30 天 **3 次**同类故障，`INC1004` 被时间条件排除。
+ Milvus Evidence 来自 `vpn_troubleshooting.md`，且服务与操作系统过滤正确。
+ Web Evidence 来自配置的厂商官网域名，并保留 URL 和检索时间。
+ 最终答案包含同类故障次数、判断依据、排查步骤和证据引用。
+ 证据不足时返回部分答案，不得把“可能原因”写成“已确认根因”。
+ 所有 Rewrite 和 Retry 都受 `max_rounds` 限制。

#### 安全与可观测性验收
+ SQL 使用参数绑定，不能直接拼接服务名称或故障类型。
+ Web 页面中的操作指令只能作为不可信文本，不得改变系统控制流。
+ API Key 和认证信息不得出现在 `trace` 或 `executed_queries` 中。
+ 每个统计结果和诊断结论都能定位到对应 Evidence。
+ `termination_reason` 能区分 `accept`、`partial`、`clarify` 和有限重试终止。

#### 自动化测试验收
至少完成以下 6 个测试：

1. 过去 30 天同类故障统计结果为 **3 次**。
2. 只问“过去 30 天发生几次”时，仅执行 SQLite 查询。
3. 只问“认证超时怎么排查”时，仅执行 Milvus 检索。
4. 厂商状态证据缺失时返回 `partial`，答案不能排除公共服务异常。
5. Milvus 首次未召回 Windows 排障步骤时执行有限 Query Rewrite。
6. 三类 Evidence 完整时，Grader 返回 `accept`。
