## 一、先聊点实在的：工具调用到底疼在哪
写过 LangGraph Agent 的同学对这坨代码应该不陌生：

```python
from langchain_core.tools import tool
from langchain.agents import create_agent
from langchain_deepseek import ChatDeepSeek

# 定义两个数学工具
@tool
def multiply(a: float, b: float) -> float:
    """两数相乘，返回 a × b"""
    return a * b

@tool
def divide(a: float, b: float) -> float:
    """两数相除，返回 a ÷ b（b 不能为 0）"""
    if b == 0:
        raise ValueError("除数不能为零，小学知识请复习一下")
    return a / b

# 组装 Agent
llm = ChatDeepSeek(model="deepseek-chat", api_key="your-api-key")
agent = create_agent(model=llm, tools=[multiply, divide],system_prompt="""你是一个智能助手，可以帮助用户查询天气和进行数学计算。
    使用工具时，请提取必要参数并调用相应工具。""")
result = agent.invoke({"messages": "帮我算一下 51204×4 和 10108283÷2"})
```

这段代码跑起来没什么问题，但细想一下：**每个开发者都在重复造同一种轮子。**

你写一个天气查询工具，隔壁组也写一个；你用 Requests 调高德 API，他用 aiohttp 再封装一遍。查询时间、搜索网页、操作文件、发邮件——这些东西几乎是所有 Agent 的通用的刚需，但没有统一标准，大家各写各的。

这就好比 2005 年的手机充电口：诺基亚是圆口，索尼爱立信是扁口，三星又是另一套。一根线配一个设备，烦得要死。直到 USB-C 出现。

**MCP，就是 AI 工具生态里的 USB-C。**

## 二、MCP 到底是个什么东西
### 2.1 一句话定义
**MCP（Model Context Protocol，模型上下文协议）** 是 Anthropic 在 2024 年底开源的一套通信规范，用于标准化大模型与外部工具、数据源之间的交互方式。

再用更通俗的人话翻译一遍：

> MCP 规定了"工具怎么描述自己、Agent 怎么发现工具、调用请求怎么传、结果怎么返回"这一整套流程。任何人按这套规范写一个 MCP Server，任何支持 MCP 的 Client（Claude Desktop、Cursor、你自己的 LangGraph 应用等）就能直接用，**零适配成本**。
>

### 2.2 一个帮你记住的类比
| 概念 | 类比 |
| --- | --- |
| **MCP** | USB-C 接口协议——管的是物理形状、引脚定义、供电规范 |
| **MCP Server** | 一个具体的 USB-C 外设，比如移动硬盘——提供某种能力 |
| **MCP Client / Host** | 你的电脑 / 手机的 USB-C 口——发现外设、调用能力 |
| **Function Calling** | 操作系统层面"检测到新硬件插入"那个事件——负责表达意图 |


这个类比的核心在于：**MCP 和 Function Calling 根本不是一回事，它们是上下游关系。**

+ **Function Calling** 是大模型"说"的部分——模型说"我想调天气工具，参数是北京"。
+ **MCP** 是接下来"做"的部分——Client 接到这个意图，去对应的 MCP Server 上真正执行调用，拿到数据，再塞回模型。

用一个链路串起来就是：

```plain
用户提问
  → LLM 输出 Function Call（"帮我查天气，城市=成都"）
    → MCP Client 解析调用目标
      → MCP Server 执行（调高德 API / 查数据库）
        → 结果原路返回
          → LLM 用自然语言答复用户
```

### 2.3 MCP 解决的核心问题
1. **标准化**：一套协议，任何语言实现的服务都能接入，告别 ad-hoc 封装。
2. **可复用**：社区写好的 MCP Server（天气、搜索、数据库、文件系统），拿来即用。
3. **安全隔离**：工具运行在独立进程中，权限可控，不像直接 import 一个包那样裸奔。
4. **动态发现**：Client 启动时自动拉取 Server 的工具列表，不用手动注册。

### 2.4 MCP vs Function Calling
这是初学者最容易栽跟头的地方。很多人以为 MCP 是"Function Calling 的替代品"或者"升级版 Function Calling"——**完全不是一回事。**

#### 先各用一句话定义
| 概念 | 一句话 |
| --- | --- |
| **Function Calling** | 大模型的一项**能力**——模型在生成回复时，"说出"它想调用哪个函数、传什么参数 |
| **MCP** | 一套**通信协议**——规定工具如何被描述、发现、调用、返回结果的标准化流程 |


换个角度：**Function Calling 是模型的"嘴"，MCP 是工具生态的"高速公路"。** 嘴负责表达意图，公路负责把意图送到目的地再带结果回来。

#### 核心区别对比表
| 维度 | Function Calling | MCP |
| --- | --- | --- |
| **本质** | LLM 的推理能力，属于模型层的 feature | 客户端-服务端通信协议，属于基础设施层 |
| **谁提供** | 模型厂商（OpenAI、DeepSeek、通义千问……） | 社区 / 厂商 / 你自己写的 MCP Server |
| **标准化程度** | **不统一**——每家模型的 tools 参数格式、调用流程都有细微差异 | **统一**——JSON-RPC 2.0，所有模型、所有 Client 同一套规范 |
| **工具发现** | 开发者在代码里手动 `@tool` 注册，写死 | Client 启动时自动 `tools/list` 拉取，动态发现 |
| **工具运行在哪** | 取决于你的 Agent 框架，通常是同进程直接调用 | 独立进程（stdio 子进程或远程 HTTP 服务） |
| **跨模型复用** | 换底座模型通常要适配 tool schema 格式 | 换模型**零改动**——MCP Client 帮你做格式转换 |
| **跨应用复用** | 每个应用单独写工具封装 | 一个 MCP Server，Claude Desktop、Cursor、你的 LangGraph 应用都能用 |
| **安全隔离** | 工具代码跑在主进程里，挂掉一起挂 | 独立进程，崩溃不拖垮主程序，权限可精细控制 |


#### 一个具体场景帮你彻底分清
假设你写了一个"查天气"的工具函数：

**只有 Function Calling（没有 MCP）的世界：**

```python
# 你得自己写工具定义、自己调 API、自己处理结果
import requests

def get_weather(city: str) -> str:
    """查询城市天气"""
    resp = requests.get(f"https://api.weather.com?city={city}", headers={"Authorization": "Bearer xxx"})
    return resp.json()["forecast"]

# 然后手动注册到模型
tools = [{"type": "function", "function": {"name": "get_weather", "description": "查询城市天气", ...}}]
# ↑ 每个模型这套 schema 格式还不一样，换模型就得改
```

问题在哪？你写了 API 封装、处理了 schema 注册、管了错误重试。隔壁组同事也要用天气，他把你这套又写了一遍——只是 API Key 不同。

**有了 MCP 的世界：**

```python
# 别人已经写好了"高德天气 MCP Server"，你只需要：
mcp_client = MultiServerMCPClient({
    "amap": {
        "url": "https://mcp.api-inference.modelscope.net/xxx/sse",
        "transport": "sse",
    },
})

# 工具自动发现，schema 自动生成，换 DeepSeek 换 Qwen 都不需要改这一行
tools = await mcp_client.get_tools()
```

区别很明显：Function Calling 是**模型的能力**——它决定"要不要调工具"；MCP 是**工具的交付方式**——它解决"工具从哪来、怎么调、结果怎么回"。

#### 它们是怎么配合的
用一句话串起来：**LLM 用 Function Calling 表达调用意图 → MCP Client 接到意图 → MCP Server 执行 → 结果原路返回 → LLM 再次用自然语言回复。**

```plain
┌─────────────────────────────────────────────────────────┐
│                    你的 Agent 应用                        │
│                                                         │
│  用户："成都天气怎么样？"                                  │
│     ↓                                                   │
│  ┌──────────────────────────────────────────────────┐   │
│  │  LLM（DeepSeek / Qwen）                           │   │
│  │  → Function Calling 输出：                         │   │
│  │    tool_name = "weather_query"                    │   │
│  │    arguments = {"city": "成都"}                    │   │
│  │        ↑ 这一步是 Function Calling，模型的能力       │   │
│  └──────────────────────────────────────────────────┘   │
│     ↓                                                   │
│  ┌──────────────────────────────────────────────────┐   │
│  │  MCP Client                                       │   │
│  │  → 解析调用目标，找到对应 Server                      │   │
│  │  → 构造 JSON-RPC 请求                               │   │
│  │        ↑ 这一步是 MCP，协议的职责                     │   │
│  └──────────────────────────────────────────────────┘   │
│     ↓                                                   │
│  ┌──────────────────────────────────────────────────┐   │
│  │  高德 MCP Server（独立进程）                         │   │
│  │  → 真正调高德 API → 拿到 18°C~26°C                  │   │
│  │        ↑ 工具执行，也是 MCP 的范畴                    │   │
│  └──────────────────────────────────────────────────┘   │
│     ↓ 结果沿 MCP → Function Calling 结果回填 → LLM      │
│  "成都今天多云，18到26度。"                                │
└─────────────────────────────────────────────────────────┘
```

#### 一句话记住
> **Function Calling 解决"模型怎么说出它想用什么工具"；MCP 解决"工具从哪来、怎么管、怎么调"。两者不是竞争关系，是上下游协作关系。**
>

## 四、协议层：MCP 的"语法"长什么样
### 4.1 JSON-RPC 2.0——MCP 的通信载体
MCP 的消息全部走 **JSON-RPC 2.0**。为什么选它？三个字：**轻、简、透**。

+ **轻**：纯 JSON 文本，没有二进制帧头，调试时直接 `console.log` 就能看。
+ **简**：只定义三种消息类型——请求、响应、通知，学习成本接近于零。
+ **透**：不绑定传输层，可以跑在 HTTP、WebSocket、stdio 管道上。

#### 请求（Request）
客户端向服务端"要东西"：

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "成都" }
  },
  "id": 1
}
```

+ `jsonrpc`：固定 `"2.0"`，协议版本标识。
+ `method`：调用方法名，MCP 预定义了一套标准方法名（如 `tools/list`、`tools/call`）。
+ `params`：方法参数，可以是数组或对象。
+ `id`：请求的唯一 ID，用于匹配响应——你可以理解为快递单号。

#### 响应（Response）
服务端处理完返回结果：

```json
{
  "jsonrpc": "2.0",
  "result": {
    "content": [
      { "type": "text", "text": "成都今天多云，18°C~26°C，适合出门。" }
    ]
  },
  "id": 1
}
```

出错时返回 `error` 字段而非 `result`：

```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32601,
    "message": "Method not found: 你调的啥玩意儿？没这个工具。"
  },
  "id": 1
}
```

错误码遵循 JSON-RPC 标准：`-32700`（解析失败）、`-32601`（方法不存在）、`-32602`（参数无效）等。

#### 通知（Notification）
只有 `method` 没有 `id`——服务端单向推送，不需要回复：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": { "uri": "file:///data/report.csv" }
}
```

### 4.2 两种传输模式：stdio vs SSE
MCP 官方定义了两类传输机制，对应两种典型部署场景：

| 维度 | stdio | SSE（Server-Sent Events） |
| --- | --- | --- |
| **通信方向** | 双向（请求↔响应） | 服务端→客户端单向推送 + HTTP 请求反向 |
| **适用场景** | 本机工具，如本地文件系统、数据库 | 远程服务，如 SaaS API、云端工具 |
| **启动方式** | Client 作为父进程 spawn Server 子进程 | Server 独立运行 HTTP 服务，Client 连上来 |
| **延迟** | 极低（进程间管道） | 有网络开销 |
| **复杂度** | 简单——标准输入输出就行了 | 需要在 HTTP 上维护长连接 |


**stdio 模式**本质上就是进程间通信：Client 拉起的 Server 子进程，通过 `stdin`/`stdout` 来回传 JSON-RPC 消息。简洁高效，适合本地工具。

**SSE 模式**则更像传统 Web 服务：Server 是一个 HTTP 端点，Client 通过 SSE 长连接接收推送，通过 HTTP POST 发起请求。适合跨网络、跨机器的远程场景。

### 5.3 把 MCP 工具接入 LangGraph Agent
```python
from langchain_deepseek import ChatDeepSeek
from langchain.agents import create_agent
from langchain_core.prompts import ChatPromptTemplate

# 使用 DeepSeek 作为底座模型（国内访问快、性价比高）
llm = ChatDeepSeek(
    model="deepseek-chat",
    api_key="your_api_key_here",  # 替换为你自己的 API Key
)

async def ask_agent(question: str) -> str:
    """
    核心调用函数：从 MCP Server 拉取工具 → 注入 Agent → 执行对话。

    每次调用都会重新拉取工具列表，保证服务端的工具变更能实时生效。
    """
    # 第一步：向所有已配置的 MCP Server 拉取可用工具
    tools = await mcp_client.get_tools()

    # 第二步：用工具 + 模型 + 提示词组装 Agent
    agent = create_agent(
        model=llm,
        tools=tools,
        system_prompt="你是一个出行助手，可以使用地图工具帮用户查天气、规划路线。回答要简洁，不要编造数据。",
    )

    # 第三步：执行对话，让 LLM 自行判断是否需要调用工具
    result = await agent.ainvoke({
        "messages": [{"role": "user", "content": question}]
    })

    # 第四步：返回最后一条消息（即 LLM 的最终回复）
    return result["messages"][-1].content
```

## 六、进阶：写一个自己的 MCP Server
用别人的轮子固然爽，但总有些场景你得自己造——比如公司内部的业务系统接口、私有数据查询。这时候用 **FastMCP**（Python 官方 SDK）来写，10 分钟就能整一个。

### 6.1 最简单的 MCP Server
```python
# my_mcp_server.py —— 一个极简的自定义 MCP 服务
from mcp.server.fastmcp import FastMCP
from datetime import datetime
from urllib.parse import unquote

# ============================================================
# 第一步：创建 FastMCP 实例，相当于初始化一个 Server 框架
# ============================================================
mcp = FastMCP(name="my-tools")


# ============================================================
# 第二步：用 @mcp.tool() 装饰器注册工具
# 装饰器会自动提取函数的 type hints 和 docstring 作为工具描述
# ============================================================

@mcp.tool()
def get_current_time() -> str:
    """
    获取当前日期和时间，返回格式友好的字符串。

    适用场景：当用户问"现在几点"或"今天几号"时调用。
    """
    now = datetime.now()
    return f"现在是 {now.year}年{now.month}月{now.day}日，{now.strftime('%H:%M:%S')}"


@mcp.tool()
def calculate_bmi(weight_kg: float, height_cm: float) -> str:
    """
    根据体重（公斤）和身高（厘米）计算 BMI 指数。

    参数：
    - weight_kg: 体重，单位公斤
    - height_cm: 身高，单位厘米

    返回：BMI 数值 + 健康评级
    """
    height_m = height_cm / 100
    bmi = weight_kg / (height_m ** 2)

    # 按中国标准分级
    if bmi < 18.5:
        level = "偏瘦，多吃点"
    elif bmi < 24:
        level = "正常，继续保持"
    elif bmi < 28:
        level = "偏胖，注意饮食"
    else:
        level = "该运动了兄弟"

    return f"BMI = {bmi:.1f}，{level}"


# ============================================================
# 第三步：用 @mcp.resource() 注册静态资源
# 资源是"模板化"的数据端点，适合暴露文章、配置、文件内容等
# URI 中用 {变量名} 定义路径参数
# ============================================================

# 模拟一个简易知识库
KNOWLEDGE_BASE = {
    "请假流程": "OA 系统提交 → 直属领导审批 → HR 备案。年假需提前 3 天申请。",
    "报销标准": "市内交通实报实销（上限 100/天），住宿标准 350/晚（一线城市 450/晚）。",
    "入职材料": "身份证原件 + 复印件、学历学位证、体检报告、离职证明、银行卡。",
}

@mcp.resource("knowledge://{topic}")
def query_knowledge(topic: str) -> str:
    """
    查询公司内部知识库，返回指定主题的说明文档。

    调用方式（Client 端）：session.read_resource("knowledge://报销标准")
    """
    # MCP 协议中 URI 的非 ASCII 字符会被 Pydantic AnyUrl 自动
    # URL 编码（如 "请假流程" → "%E8%AF%B7%E5%81%87%E6%B5%81%E7%A8%8B"），
    # 但 FastMCP 的 ResourceTemplate.matches() 提取参数时不会自动解码，
    # 所以这里需要手动 unquote。
    topic = unquote(topic)
    print(f"查询知识库：{topic}")
    result = KNOWLEDGE_BASE.get(topic, f"没找到关于「{topic}」的记录，请联系 HR 更新知识库。")
    return result


# ============================================================
# 第四步：启动 Server
# ============================================================
if __name__ == "__main__":
    # SSE 模式：作为独立 HTTP 服务运行，适合远程调用和调试
    mcp.settings.host = "0.0.0.0"
    mcp.settings.port = 8000
    mcp.run(transport="sse")
```

### 6.2 在 LangGraph 中同时使用本地和远程 MCP
前面跑通了远程的高德 MCP，现在把自建的本地服务也接进来：

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

# 一个 Client，同时挂两份 Server：远程高德 + 本地自建
mcp_config = {
    "amap": {
        "url": "https://mcp.api-inference.modelscope.net/xxxxxxxxxxxx/sse",
        "transport": "sse",
    },
    "my-tools": {
        "url": "http://localhost:8000/sse",   # 指向上面启动的 FastMCP 服务
        "transport": "sse",
    },
}

client = MultiServerMCPClient(mcp_config)
```

### 6.3 在代码里读取 MCP Resource
Tool 是 LLM 自动调用的，而 Resource 需要你在代码里**手动读取**。这通常用于加载系统提示词、业务规则、知识库条目等"静态但可能动态更新"的数据。

```python
"""
同时获取多个MCP工具
使用获取资源的函数
使用自己的MCP stdio 与 sse
"""

import asyncio
from langchain_mcp_adapters.client import MultiServerMCPClient

#1. 配置MCP客户端
mcp_server_config = {
    # "12306-mcp": {
    #   "args": [
    #     "-y",
    #     "12306-mcp"
    #   ],
    #   "command": "npx",
    #   "transport": "stdio" #本地使用nodejs 运行
    # },
    "mcp_tools": {
        "transport": "sse",  
        "url": "http://localhost:8000/sse"  # 或使用 自己写MCP  SSE模式
    }
  }  #同时访问多个MCP工具

client = MultiServerMCPClient(mcp_server_config)

async def get_mcp_tools():
        # 获取MCP工具
        tools = await client.get_tools()
        print(f"当前可用工具：{[t.name for t in tools]}")
        # 从指定 MCP Server 的 Resource 中读取数据
        # 每个 Resource 通过 URI 定位，就像访问一个 RESTful 端点
        async with client.session("mcp_tools") as session:
            # 拉取三条公司制度作为增强上下文
            leave_policy = await session.read_resource("knowledge://请假流程")
            expense_policy = await session.read_resource("knowledge://报销标准")
            print(f"[知识库] 请假流程: {leave_policy.contents[0].text}")
            print(f"[知识库] 报销标准: {expense_policy.contents[0].text}")
    
if __name__ == "__main__":
    asyncio.run(get_mcp_tools())
```

## 七、Tool vs Resource：什么时候该用哪个
这是刚上手最容易搞混的问题。简单说：

<!-- 这是一个文本绘图，源码为：flowchart TD
    A["这个 MCP 能力是..."] --> B{"LLM 需要<br/>自己决定<br/>什么时候调？"}
    B -->|"是"| Tool["注册为 Tool"]
    B -->|"否"| C{"是静态数据<br/>还是动态生成<br/>的内容？"}
    C -->|"静态 / 模板化"| Resource["注册为 Resource"]
    C -->|"动态 / 事件驱动"| Prompt["考虑 Prompt Template<br/>（本文暂不展开）"]

    Tool --> T1["例：查天气、算 BMI、发邮件"]
    Resource --> R1["例：公司制度文档、产品目录、配置模板"]
    Prompt --> P1["例：根据任务类型组合 System Prompt"] -->
![](https://cdn.nlark.com/yuque/__mermaid_v3/6518db39c83d457ba5d871b6f8116be5.svg)

| 维度 | Tool | Resource |
| --- | --- | --- |
| **谁触发** | LLM 通过 Function Call 自动触发 | 开发者在代码中手动调用 |
| **典型用途** | 计算、查询、操作（有副作用的动作） | 读取配置、知识库、模板（纯数据） |
| **调用方式** | 自动——LLM 决策 | 显式——`session.read_resource(uri)` |
| **URI 模板** | 不支持（参数通过 JSON 传递） | 支持，如 `knowledge://{topic}` |

## 八、总结 & 建议
MCP 不是一个复杂的东西。它本质上就是三块：

1. **一套消息格式**（JSON-RPC 2.0）——定义请求和响应长什么样。
2. **一种传输机制**（stdio 或 SSE）——定义消息怎么运过去。
3. **一组能力原语**（Tool / Resource / Prompt）——定义 Server 能暴露什么。

搞清楚了这三块，剩下的就是用 `langchain_mcp_adapters` 这一层薄薄的胶水把 MCP 生态接到你的 Agent 架构里。

**几点实战建议：**

+ **优先用社区现成的 MCP Server**。魔搭社区上已经有上百个中文服务了，调用远比手写 API 封装快，而且人家帮你处理了重试、超时、schema 生成这些脏活。
+ **本地开发用 stdio，部署上线用 SSE**。stdio 零网络开销、调试方便；SSE 适合容器化部署和跨机器调用。
+ **把 Tool 和 Resource 分清楚**。不要把配置数据写成 Tool——那样 LLM 每次都要猜要不要调用，又慢又容易出错。静态数据就该走 Resource。
+ **模型选国产的够用**。DeepSeek-V3、通义千问 Qwen-Max 的 Function Calling 能力已经非常能打，配合国内 API 的低延迟和中文友好，日常 Agent 开发完全够了。
