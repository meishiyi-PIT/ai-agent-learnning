## 一、为什么需要多 Agent？单 Agent 的三个结构性局限
一个全能 Agent 看似高效——所有任务都可以由单一系统处理。但在实际工程中，这种方式会迅速暴露瓶颈。单 Agent 架构在工具数量、上下文长度、可调试性三个维度上面临结构性缺陷，当任务复杂度超过一定阈值后，性能下降几乎不可避免。

### 局限一：工具数量增加导致选择错误率上升
**本质理解：** 同时承担多种角色的系统，面对不同语义空间的指令时，容易出现意图判断错误——"切"在烹饪语境和网络语境下含义完全不同。

**工程经验：** 工具数量增加后，模型需要在更大的候选集合中判断工具用途，选择错误、参数错误和无效调用的概率通常会上升。"10 个"不是普适阈值，实际效果还取决于模型能力、工具描述、参数设计、任务类型和评测数据。因此，应通过评测确定拆分边界，而不是机械地按工具数量拆分。

**示例：**

```plain
用户："帮我查一下最近的销售数据，然后发邮件给老板"

单 Agent 手上有 15 个工具：
  - web_search        ← 它可能先搜了"销售数据"（错）
  - code_interpreter   ← 然后想写 Python 分析（对但太早）
  - email_sender       ← 最后发了封没数据的邮件（错）
  - database_query     ← 其实应该先用这个（对）
```

**核心矛盾：** 工具越多，LLM 的「选择空间」越大，工具选择和参数生成的风险通常越高。类似于决策理论中的选择过载效应——候选越多，决策质量可能反而下降，但具体影响必须通过实际评测验证。

### 局限二：上下文堆积导致关键信息被淹没
**本质理解：** 单 Agent 的对话上下文随轮次增长不断膨胀，早期输入会被后续内容淹没，导致模型丢失关键信息。

**实际场景：**

```plain
第 1 轮：Agent 记住了你的需求是"分析竞品"
第 5 轮：中间插入了 4 次 web_search 的返回结果（每次 2000 tokens）
第 8 轮：context window 已经塞满了搜索结果
第 10 轮：你问"刚才分析到哪了？"——它开始生成与实际情况不符的回复（上下文信息丢失现象）
```

**数据说明：**

| 场景 | Token 消耗 |
| --- | --- |
| 用户指令 | ~200 tokens |
| 一次 web_search 返回 | ~1500-3000 tokens |
| 一次代码执行结果 | ~500-2000 tokens |
| 系统 prompt | ~1000 tokens |
| **5 轮交互后** | **可达 15K tokens 以上** |


128K 的上下文窗口看似充裕，但如果不做上下文管理，多轮 tool call 的返回结果会快速消耗 tokens，核心指令也容易被淹没在 tool call 的噪音中——这正是多 Agent 架构通过上下文隔离试图解决的问题之一。

### 局限三：推理路径黑箱化，难以调试
**本质理解：** 单 Agent 的推理路径被封装在一个黑箱中——输入请求，输出结果，中间发生了什么难以观测和追溯。

**排查困境：**

```plain
用户："帮我写一个爬虫抓取竞品价格"
Agent 输出：一段报错的代码

问题出在哪？
  → 是搜索工具没找到正确的网站？（工具层问题）
  → 还是 LLM 理解错了需求？（推理层问题）
  → 还是代码生成工具选错了框架？（执行层问题）

单 Agent：全部混在单一流程中，只能基于最终输出逆向推测根因
多 Agent：每个 Agent 有独立日志，可逐层定位问题所在层
```

> ▲ Supervisor 模式原理：① 用户请求 → ② Supervisor 通过 tool_call/handoff 分发 → ③ 研究/数学/代码 Agent 按序执行 → ④ 结果汇总整合 → ⑤ 最终答案

### 核心思想：职责分离
**一句话总结：** 专家 Agent 专注于执行子任务，Supervisor 专注于任务分发与结果整合。

类比：餐厅的服务模式可以直观说明这一分工——

+ **Supervisor = 前台经理**：负责接收点单、分派任务、整合出品
+ **Worker Agent = 厨师**：专注于烹饪，不关心订单来源和上菜时序<!-- 这是一张图片，ocr 内容为： -->
![](images/supervisor-workflow.png)

> ▲ Supervisor 工作流：① User ↔ Supervisor 双向通信 → ② Supervisor 虚线路由 (route) 到 Agent → ③ Agent 实线返回结果 → ④ Supervisor 返回最终答案
>

### Supervisor 的三大职责
| 职责 | 说明 | 类比 |
| --- | --- | --- |
| **拆解任务** | 理解用户意图，分解成子任务 | 前台经理看菜单，拆成凉菜、热菜、汤 |
| **路由调度** | 决定叫哪个 Agent、按什么顺序 | 分配给凉菜师傅还是热菜师傅 |
| **整合输出** | 把各 Agent 结果拼成最终答案 | 将各道菜品组合成完整的套餐 |


### Worker Agent 的专注
每个 Worker Agent 只关心一件事：**完成所分配的子任务**。

+ 不关注其他 Agent 的执行状态
+ 不关注任务来源与分发逻辑
+ 不关注最终结果的组合方式
+ 任务完成后返回结果，不保留多余状态

这就是「单一职责原则」在 Agent 架构中的落地。需要注意的是，Worker 不拥有全局编排状态，并不等于运行时完全不保留消息历史；图运行时仍可能根据配置把 Worker 的消息带回 Supervisor。

### 2.1 单个 Agent 的三个设计组件
在拆分 Multi-Agent 之前，先把每个 Agent 的边界定义清楚。一个可执行的 Agent 至少由三类组件组成：

| 组件 | 要回答的问题 | 设计要点 |
| --- | --- | --- |
| **模型（Model）** | 它需要什么推理能力、上下文长度和响应速度？ | 根据任务选择模型，不要默认所有 Worker 都使用最高规格模型 |
| **工具（Tools）** | 它能对外部世界执行哪些动作？ | 工具名称、描述、参数和错误返回要清晰；高风险工具还要有权限和人工确认 |
| **指令（Instructions）** | 它负责什么、不负责什么、结果交给谁？ | 写清输入、输出格式、边界条件和失败处理方式 |


一个 Worker 的职责应当可以用一句话描述，并且可以单独测试。例如：研究 Agent 只负责检索和整理证据，数学 Agent 只负责基于明确数字完成计算。模型、工具和指令三者共同决定 Agent 的能力边界，不能只靠 prompt 弥补工具设计问题。

### 2.2 Multi-Agent 的编排本质：Graph、Node、Edge 与 Handoff
Multi-Agent 系统本质上是一个状态图，而不只是多个 prompt 的排列组合：

+ **Graph**：完整的任务执行流程和共享状态。
+ **Node**：一个 Agent、工具调用、校验器或人工审批步骤。
+ **Edge**：节点之间的转移条件，可以是固定顺序，也可以由模型根据结果选择。
+ **Handoff**：把控制权和必要的上下文从一个 Agent 转交给另一个 Agent。

Supervisor 模式中，Supervisor 通常持有路由工具，调用工具后发生 handoff；Worker 完成工作后再把控制权交回 Supervisor。这里要区分两件事：

1. **控制权转移**：下一步由哪个 Agent 执行。
2. **消息传递**：下一个 Agent 能看到哪些用户消息、工具结果和前序 Agent 输出。

如果只设计了路由，却没有定义消息传递范围，Worker 可能拿不到必要事实；如果把全部历史无差别传递，又会重新引入上下文膨胀。

### 3.2 创建研究 Agent（Research Agent）
这个 Agent 专门负责**搜索和调研**，配备 web 搜索工具：

```python
from langchain_community.tools.tavily_search import TavilySearchResults
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

# 初始化大模型（这里用 DeepSeek，兼顾性能与成本）
# 注：DeepSeek API 兼容 OpenAI 接口格式，所以可以用 ChatOpenAI 类，只需替换 base_url
model = ChatOpenAI(
    model="deepseek-chat",
    api_key="sk-你的key",
    base_url="https://api.deepseek.com"
)

# 研究 Agent 唯一的工具：搜索
web_search = TavilySearchResults(max_results=3)

research_agent = create_agent(
    model=model,
    tools=[web_search],
    system_prompt=(
        "你是一个研究代理。\n\n"
        "指令：\n"
        "- 仅协助与研究相关的任务，禁止执行任何数学任务\n"
        "- 任务完成后，直接向监督者回应\n"
        "- 仅返回你的工作结果，不包含任何其他文本"
    ),
    name="research_agent"
)

# 单独测试：让研究 Agent 回答一个问题
inputs = {"messages": [("human", "什么是牛顿第二定律？")]}
for chunk in research_agent.stream(inputs, stream_mode="values"):
    chunk["messages"][-1].pretty_print()
```

**关键点：** 研究 Agent 的 system_prompt 明确限制了它的职责边界——只做研究，不做数学。这就是「职责分离」的代码落地。

### 3.3 创建数学 Agent（Math Agent）
这个 Agent 专门负责**计算**，配备数学工具：

```python
from langchain_core.tools import tool

@tool
def add(a: float, b: float):
    """加法：将两个数字相加。"""
    return a + b

@tool
def multiply(a: float, b: float):
    """乘法：将两个数字相乘。"""
    return a * b

@tool
def divide(a: float, b: float):
    """除法：将两个数字相除。"""
    if b == 0:
        return "错误：除数不能为 0"
    return a / b

math_agent = create_agent(
    model=model,
    tools=[add, multiply, divide],
    system_prompt=(
        "你是一个数学代理。\n\n"
        "指令：\n"
        "- 仅协助与数学相关的任务\n"
        "- 任务完成后，直接向监督者回应\n"
        "- 仅返回你的工作结果，不包含任何其他文本"
    ),
    name="math_agent",
)

# 单独测试
inputs = {"messages": [("human", "(3 + 5) x 7 的结果是多少？")]}
for chunk in math_agent.stream(inputs, stream_mode="values"):
    chunk["messages"][-1].pretty_print()
```

### 3.4 配置 Supervisor
现在把两个 Agent 交给 Supervisor 统一调度：

```python
from langgraph_supervisor import create_supervisor

supervisor = create_supervisor(
    model=model,
    agents=[research_agent, math_agent],
    system_prompt=(
        "你是一个管理两个代理的监督者：\n"
        "- 研究代理：将研究相关任务分配给此代理\n"
        "- 数学代理：将数学相关任务分配给此代理\n"
        "一次仅分配工作给一个代理，不并行调用代理。\n"
        "不要自己执行任何工作。"
    ),
    add_handoff_back_messages=True,
    parallel_tool_calls=False,
    output_mode="full_history",
)

graph = supervisor.compile()

# 可视化整个工作流（如果不在 Jupyter 环境，可以跳过此步骤）
# 如需保存图片到本地，用：graph.get_graph().draw_mermaid_png("workflow.png")
```

### 3.5 运行复合任务
以下是一个**同时需要搜索和计算**的复合任务，用以验证 Supervisor 的多步骤编排能力：

```python
inputs = {
    "messages": [(
        "human",
        "查找 2024 年美国和纽约州的 GDP。纽约州占美国 GDP 的百分比是多少？"
    )]
}

for chunk in graph.stream(inputs, stream_mode="values"):
    chunk["messages"][-1].pretty_print()
```

**执行流程拆解：**

```plain
用户："查找 2024 年美国和纽约州的 GDP。纽约州占美国 GDP 的百分比是多少？"
  ↓
Supervisor 收到任务，拆解成两步：
  ① 搜索数据 → 路由给 research_agent
  ② 计算百分比 → 路由给 math_agent
  ↓
research_agent 搜索后返回：
  "美国 GDP: 28.18 万亿美元，纽约州 GDP: 1.671 万亿美元"
  ↓
Supervisor 收到结果，继续路由：
  "计算 1.671 / 28.18 × 100%" → math_agent
  ↓
math_agent 计算后返回：
  "纽约州占美国 GDP 的 5.93%"
  ↓
Supervisor 整合所有结果，输出最终答案
```

> 注：以上数值是来源文章示例运行时的输出，用于演示 handoff 和计算链路，不应当作为固定事实。GDP 数据会因统计口径、预测/实际值、检索时间和来源不同而变化。生产系统应要求研究 Agent 返回来源、发布日期和原始数值，并由校验步骤检查单位和计算口径。
>

## 四、Supervisor 模式的优缺点
### 优点
| 优点 | 说明 |
| --- | --- |
| **职责清晰** | 每个 Agent 只做一件事，prompt 简洁，工具少，准确率高 |
| **易于调试** | 出问题时，先看 Supervisor 的路由日志，再看对应 Agent 的执行日志，逐层定位 |
| **可扩展** | 新增一个 Agent 只需要定义 tools + prompt，Supervisor 的 prompt 加一行描述即可 |
| **上下文隔离** | 每个 Agent 有独立的对话历史，不会互相干扰 |


### 缺点
| 缺点 | 说明 |
| --- | --- |
| **延迟增加** | 每次路由都是一次额外的 LLM 调用，多了一跳 |
| **Supervisor 成为瓶颈** | 所有任务都经过它，它出错则全局出错 |
| **不擅长并行** | 标准 Supervisor 是串行调度，多任务并行需要额外设计 |
| **成本叠加** | 至少 N+1 次 LLM 调用（Supervisor 路由 1 次 + 每个 Agent 至少 1 次），但每个 Agent 内部可能有多轮 tool call（每轮又是一次调用），实际次数往往数倍于此 |

**类比：** 头脑风暴会议——多角色自由讨论，主持人协调节奏与产出。

### 5.5 群体协作与 Swarm（去中心化交接）
群聊模式和 Swarm 不完全相同。群聊通常由 Moderator 统一协调；Swarm 则允许当前 Agent 根据任务状态直接把控制权交给另一个 Agent，系统没有一个持续负责所有路由的中央 Supervisor。LangGraph 生态中可以使用 `langgraph-swarm` 这类实现来组织这种 handoff。

**适用场景：** 用户可能在不同专家之间来回切换、任务路径难以预先确定，且每个 Agent 都能判断下一步应由谁处理。

**代价：** 去中心化会减少 Supervisor 瓶颈，但也更容易出现循环、上下文丢失和责任边界不清。必须为每个 handoff 定义触发条件、可交接目标、最大步数和返回 Supervisor/结束任务的条件。大多数业务系统仍应优先从 Supervisor 或固定 Pipeline 开始，只有在路径确实需要动态交接时再引入 Swarm。

概念上的代码骨架如下，实际 API 以所安装的 `langgraph-swarm` 版本为准：

```python
from langgraph_swarm import create_handoff_tool, create_swarm

handoff_to_research = create_handoff_tool(
    agent_name="research_agent",
    description="将需要外部资料的任务交给研究 Agent",
)
handoff_to_math = create_handoff_tool(
    agent_name="math_agent",
    description="将需要计算的任务交给数学 Agent",
)

# 每个 Agent 除了自己的业务工具，还暴露允许的交接工具
research_agent = create_agent(
    model=model,
    tools=[web_search, handoff_to_math],
    system_prompt="只做研究；需要计算时交接给 math_agent。",
    name="research_agent",
)
math_agent = create_agent(
    model=model,
    tools=[add, multiply, divide, handoff_to_research],
    system_prompt="只做计算；需要检索时交接给 research_agent。",
    name="math_agent",
)

swarm = create_swarm(
    [research_agent, math_agent],
    default_active_agent="research_agent",
).compile()
```

## 六、如何选择合适的模式？
| 你的情况 | 推荐模式 | 原因 |
| --- | --- | --- |
| 任务明确，子任务少 | Supervisor | 架构简单，成本可控，适合大部分场景 |
| 任务复杂，子任务还有子任务 | 层级 Supervisor | 分层管理，职责更清晰 |
| 流程固定，步骤明确 | Pipeline | 各 Agent 按固定顺序执行，输出确定性高 |
| 需要多角度分析 | 对抗模式 | 正反论证，避免偏见 |
| 需要创意发散 | 群聊模式 | 多视角交互，易于产生多样化输出 |
| Agent 之间需要动态互相转交任务 | Swarm | 去中心化交接，但需要更严格的循环和权限控制 |


**决策优先级：**

1. Supervisor 模式能解决的问题，不升级到层级架构
2. 串行调度能满足需求，不引入并行
3. 从最简单的方案起步，验证可行后再逐步演进，避免过早引入复杂架构

## 七、实战注意事项
项目地址：[https://git.miaoatech.cn/zeroleap/Multi-Agent.git](https://git.miaoatech.cn/zeroleap/Multi-Agent.git)

### 7.1 System Prompt 设计原则
每个 Agent 的 system_prompt 必须明确三点：

1. **你是谁**（角色定义）
2. **你能做什么**（职责边界）
3. **你不能做什么**（硬约束）

```plain
❌ 模糊的 prompt："你是一个助手"
✅ 清晰的 prompt："你是一个研究代理。仅协助与研究相关的任务，禁止执行任何数学任务"
```

### 7.2 最小化工具集原则
每个 Agent 应只暴露完成职责所必需的工具。3-5 个可以作为初始经验范围，但不是硬性规则；工具少而职责混乱，同样会导致错误。最终应通过任务成功率、无效工具调用率、延迟和成本评测工具边界。

```plain
❌ 研究 Agent 配了 15 个工具（搜索 + 计算 + 邮件 + ...）
✅ 研究 Agent 只配搜索工具，计算交给数学 Agent
```

### 7.3 错误处理
当前 LangChain `create_agent` 的公开参数中没有 `max_iterations`。LangGraph 图的循环上限应通过运行时配置 `recursion_limit` 设置；达到上限时会抛出 `GraphRecursionError`。可以在 Supervisor 和 Worker 共用的图运行时设置上限：

```python
result = graph.invoke(
    inputs,
    {"recursion_limit": 50},    # 限制整个图的递归步数
)
```

`recursion_limit` 限制的是整个图的递归步数，不等同于某个 Agent 的精确工具调用次数。若需要更细粒度的限制，应在工具层、Middleware 或自定义状态中记录并拒绝超限调用。对于工具调用中的异常，建议返回结构化、可行动的错误信息，并区分可重试错误与参数/权限等不可重试错误；盲目重试只会让 Agent 带着同样的错误输入反复尝试，浪费 tokens。

### 7.4 可观测性
生产环境必须加日志和追踪：

```python
# 推荐用 LangSmith 追踪每一次 Agent 调用
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "ls-你的key"
```

这样每次 Supervisor 路由、每个 Agent 执行、每次 tool call 都有完整 trace，出现问题时可快速追溯根因。

### 7.5 运行、输入输出与调试
`compile()` 返回的是可执行的 LangGraph。常用调用方式有三种：

```python
# 一次性执行，适合接口返回最终结果
result = graph.invoke(inputs, {"recursion_limit": 50})

# 按状态流式返回，适合展示每个 Agent 的过程
for state in graph.stream(
    inputs,
    {"recursion_limit": 50},
    stream_mode="values",
):
    state["messages"][-1].pretty_print()

# 调试时使用 debug 流模式，具体事件字段取决于 LangGraph 版本
for event in graph.stream(
    inputs,
    {"recursion_limit": 50},
    stream_mode="debug",
):
    print(event)
```

输入通常是包含 `messages` 的状态对象，输出则是图的最终状态；使用 `output_mode="last_message"` 时，托管 Agent 只把最后一条消息带回 Supervisor，使用 `full_history` 时会带回完整消息历史。`create_supervisor` 默认是 `last_message`，本示例显式选择 `full_history` 是为了教学时观察完整链路，生产环境应根据上下文成本和审计需求选择。

### 7.6 消息历史与 handoff 管理
Supervisor 的 handoff 不只是“调用另一个 Agent”。需要明确以下配置和取舍：

+ `output_mode="last_message"`：只传递 Worker 最后输出，消息更短，适合结果明确的 Worker。
+ `output_mode="full_history"`：传递 Worker 的完整消息历史，便于审计和调试，但可能增加上下文和成本。
+ `add_handoff_messages=True`：在历史中记录 handoff 的 AI/Tool 消息，方便追踪控制权转移。
+ `add_handoff_back_messages=True`：在 Worker 返回 Supervisor 时增加回传标记，适合需要清楚展示流程的场景。
+ `handoff_tool_prefix`：统一 handoff 工具命名，避免与业务工具混淆。
+ `parallel_tool_calls=False`：本示例要求一次只交接给一个 Worker；开启并行时要确认模型提供商支持，并处理并发状态写入、结果合并和成本上升。

还应规定 Worker 返回结果的最小契约，例如：`status`、`summary`、`evidence`、`errors` 和 `next_action`。不要把未经筛选的网页全文、调试日志或大段中间结果无条件传回 Supervisor；必要时先摘要、截断或落盘，再传递引用和关键事实。

默认 handoff 工具适合大多数场景，但复杂系统可以自定义 handoff 工具，控制交接时传递的字段、交接目标和权限。例如，研究 Agent 可以只把结构化证据交给数学 Agent，而不是把完整搜索历史全部传过去。也可以使用 `forward_message` 一类的转发工具，在 Worker 的结果已经足够完整时直接把最后一条消息转发给用户，减少 Supervisor 的二次总结和一次额外调用；这时仍应保留来源、权限和审计信息。

### 7.7 生产环境的三类风险
Multi-Agent 的问题不能只归因于“模型不够聪明”，建议按三层定位：

| 风险层 | 常见表现 | 防护方式 |
| --- | --- | --- |
| **系统设计缺陷** | 路由循环、状态边界不清、权限过宽、并行写入冲突 | 明确状态 schema、终止条件、权限边界和幂等策略 |
| **协作失调** | Agent 互相重复工作、结果格式不一致、handoff 丢失上下文 | 约定输入输出契约，限制可路由范围，保留 trace |
| **任务验证失效** | 搜索结果无来源、计算单位错误、最终答案没有验收 | 增加独立校验器、引用检查、结构化输出和人工审批 |


系统至少应为成功率、路由准确率、无效工具调用率、循环次数、延迟、token 成本和人工接管率建立评测指标。对于发邮件、写数据库、下单等副作用工具，还要设置权限隔离、幂等键、审批或模拟执行模式。

### 7.8 MCP、A2A 与扩展路线
当工具数量和 Agent 数量继续增长时，可以把能力接入层与编排层分开：

+ **MCP** 更适合标准化 Agent 与工具、资源、提示模板之间的连接，让能力可以被不同 Agent 复用。
+ **A2A** 更适合跨服务、跨团队或跨平台的 Agent 间通信，关注 Agent 能力发现、任务委派和结果回传。

它们解决的是互操作和连接问题，不会自动解决任务拆解、路由正确性、上下文控制或结果验证。引入前仍应先确定 Agent 契约、身份认证、权限、超时、重试、版本兼容和审计方式。

## 八、总结
| 维度 | 单 Agent | 多 Agent (Supervisor) |
| --- | --- | --- |
| 工具数 | 工具越多，选择空间和错误风险通常越大 | 每个 Agent 只暴露职责所需工具，3-5 个仅作经验起点 |
| 上下文 | 全部集中于单一窗口 | 各 Agent 独立隔离 |
| 调试 | 黑盒，难以定位根因 | 逐层 trace，可快速追溯 |
| 延迟 | 低（一跳） | 稍高（多一跳路由） |
| 成本 | 低 | 稍高（至少 N+1 次，实际往往数倍） |
| 适用场景 | 简单任务 | 复杂多步骤任务 |


**一句话：** 当单 Agent 在工具选择、上下文管理或问题定位上出现系统性困难时，就是应当拆分为多 Agent 架构的信号。不要让一个 Agent 面面俱到，而是让每个 Agent 聚焦单一职责。
