## 一、标准文件结构
### 1.1 目录规范
一个规范的 Skill 以文件夹为单位，最小形态只需一个 SKILL.md 文件：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655980138-d9ac6e79-69ab-41d2-8162-d90de7af5af4.png)

| 文件/文件夹 | 必须？ | 作用 |
| :--- | :--- | :--- |
| `SKILL.md` | ✅ 必须 | 唯一入口，告诉 Agent 这个能力是什么、怎么用 |
| `scripts/` | 可选 | 放可执行脚本，适合反复执行的确定性操作 |
| `references/` | 可选 | 放参考资料，Agent 需要时按需读取 |
| `assets/` | 可选 | 放模板和素材，用于生成固定格式的输出 |


### 1.2 关键规则
+ `SKILL.md` 必须直接放在 `skills/your-skill-name/` 目录下
+ 不能再嵌套一层，`skills/my-skill/src/SKILL.md` 这种结构是错误的
+ 目录名建议与 Skill 名称保持一致，全小写，用连字符分隔

## 二、三个可选目录的使用场景
### 2.1 scripts/ — 让 Agent "跑"的脚本
**使用场景**：同一个操作每次都一样，用脚本比让 Agent 每次重写代码更可靠。

**示例：照片整理脚本**

```bash
#!/bin/bash
# 用法: organize_photos.sh <照片目录>
# 功能: 将照片按拍摄日期自动分类到不同文件夹

SOURCE_DIR="${1:-.}"

for photo in "$SOURCE_DIR"/*.jpg; do
    # 获取照片的拍摄日期（从文件元数据中提取）
    date=$(exiftool -CreateDate -d "%Y-%m-%d" "$photo" | awk -F': ' '{print $2}')
    
    # 创建日期文件夹（如果不存在）
    mkdir -p "$SOURCE_DIR/$date"
    
    # 移动照片到对应日期文件夹
    mv "$photo" "$SOURCE_DIR/$date/"
    echo "已移动: $(basename $photo) → $date/"
done

echo "整理完成！"
```

**为什么用脚本**：手动整理几百张照片要一个个看日期、建文件夹、拖文件，费时费力还容易错。脚本几秒钟搞定，而且每次整理的规则完全一致。

### 2.2 references/ — 让 Agent "看"的参考资料
**使用场景**：信息太长不适合全塞进 SKILL.md 时，拆到 references 中按需加载。

**示例：菜谱大全**

假设你有一个"教你做菜"的 Skill，里面有各种菜的做法：

```markdown
# 菜谱大全

## 红烧肉
- 材料：五花肉500g、冰糖、生抽、老抽、料酒、姜、八角
- 步骤：五花肉切块焯水 → 炒糖色 → 加调料炖煮40分钟 → 收汁
- 技巧：糖色要小火慢炒，肉要冷水下锅焯

## 番茄炒蛋
- 材料：番茄2个、鸡蛋3个、盐、糖、葱
- 步骤：鸡蛋打散炒熟盛出 → 番茄炒出汁 → 加蛋翻炒 → 调味
- 技巧：番茄要炒出汁才好吃，鸡蛋不要炒太老

## 可乐鸡翅
- 材料：鸡翅8个、可乐1罐、生抽、老抽、姜
- 步骤：鸡翅焯水划刀 → 煎至两面金黄 → 倒可乐焖煮 → 收汁
- 技巧：可乐要用常温的，收汁时要不停翻动

...（还有50道菜）
```

**为什么拆开**：用户问"红烧肉怎么做"时，Agent 只需要读红烧肉那部分，其他49道菜的做法完全不需要加载。拆到 references 里，按需读取某一道菜，省掉了大量无关内容。

### 2.3 assets/ — 让 Agent "填"的模板
**使用场景**：需要输出固定格式的内容时，用模板确保每次输出结构一致。

**示例：工作日报模板**

```markdown
# {日期} 工作日报

**姓名：** {姓名}

## 今日完成
{逐条列出}

## 明日计划
{逐条列出}

## 风险/阻塞
{没有填"无"}
```

**为什么用模板**：不用模板的话，周一生成的日报有"姓名"栏，周二就忘了加；周三多了个"备注"栏，周四又没了。

### 2.4 三者的核心区别
| 目录 | Agent 的动作 | 用途 | 典型内容 |
| :--- | :--- | :--- | :--- |
| scripts/ | **跑** | 执行确定性操作 | Python/Bash 脚本 |
| references/ | **看** | 查阅参考资料 | API 文档、规范说明 |
| assets/ | **填** | 套用模板输出 | 报告模板、表单模板 |


<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783655997249-d1df37c6-e1ef-4f2b-b6be-fe0a36efafc6.png)

**何时添加可选目录**：

+ 同样的命令 Agent 老写错 → 抽成 script
+ 正文太长影响阅读 → 拆到 references
+ 输出格式不稳定 → 做个 asset 模板

## 三、SKILL.md 编写规范
### 3.1 文件结构
SKILL.md 由两部分组成：**YAML frontmatter（元数据）** 和 **Markdown 正文（指令）**。

```yaml
---
name: stock-price
description: 查询股票实时价格
metadata: {"openclaw": {"requires": {"env": ["STOCK_API_KEY"]}}}
---

# 查股价

当用户问某只股票的价格时：
1. 用 web_fetch 访问 API
2. 从返回的 JSON 里提取 price 字段
3. 告诉用户当前价格
```

### 3.2 元数据字段说明
| 字段 | 作用 | 说明 |
| :--- | :--- | :--- |
| `name` | 技能的唯一标识 | 系统内部用来查找 |
| `description` | 一句话说明 | Agent 靠它判断是否需要加载 |
| `metadata` | 前置条件 | 不满足时自动隐藏该 Skill |
| 正文 | 真正的指令 | 只有 Agent 决定使用时才会读取 |


### 3.3 name 的命名规则
| 规则 | 说明 |
| :--- | :--- |
| 长度上限 | 64 字符 |
| 允许字符 | 小写字母、数字、连字符（字符就是短横线 -（减号键），用于连接多个单词，code-review） |
| 命名建议 | 使用动名词形式（verb + -ing） |


**命名示例**：

| ✅ 推荐命名 | ❌ 不推荐命名 |
| :--- | :--- |
| processing-pdfs | helper、utils（含义模糊） |
| reviewing-code | documents（过于宽泛） |
| test-driven-development | tools（等于没说） |


### 3.4 description 的编写原则
**原则一：包含用户可能说的原话**

```yaml
# ✅ 好的写法：能力 + 场景 + 触发词
description: 从 PDF 文件中提取文本和表格、填充表单、合并文档。在处理 PDF 文件或用户提及 PDF、表单、文档提取时使用。

# ❌ 差的写法：太模糊
description: 帮助您处理文档
```

**原则二：明确写出不适用场景**

```yaml
description: |
  当用户询问某个话题的最新趋势、热点动态、行业动向时使用。
  触发词：趋势分析、热点、最新动态、行业报告。
  不适用于：历史事件、代码问题、个人决策建议。
```

**原则三：控制在 5 行以内**

过长反而降低检索精度。

## 四、正文编写最佳实践
### 4.1 操作手册不是科普文
```markdown
# ✅ 精准：直接给方案和调用方式
## 提取 PDF 文本
使用 pdfplumber 进行文本提取：
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()

# ❌ 冗余：科普风格
PDF 全称便携式文档格式，广泛用于图文混排场景。
要从 PDF 中提取文字，需借助专门的解析工具。
社区有多个可用方案，包括 pypdf、pdfplumber、PyMuPDF 等...
```

### 4.2 主文件控制在 500 行以内
超出时把细节拆到单独文件，用渐进式披露让 Agent 按需读取。

```markdown
# BigQuery 数据分析

## 可用数据集
- 财务：收入、ARR、账单 → 参阅 reference/finance.md
- 销售：机会、管道、账户 → 参阅 reference/sales.md
- 产品：API 使用、功能采用 → 参阅 reference/product.md
- 营销：活动、归因、电子邮件 → 参阅 reference/marketing.md
```

### 4.3 最有价值的是项目特有的踩坑记录
```markdown
# 这种信息 Agent 推断不出来，必须明确写
users 表采用软删除（逻辑删除）方案。所有正式查询务必追加 WHERE deleted_at IS NULL。

# 这是通用常识，写进去只会浪费上下文
所谓软删除（逻辑删除），就是用字段标记来代替物理删除...
```

## 五、自由度把控
### 5.1 三级自由度
写 Skill 时需要考虑给 Agent 多大的自主裁量权，取决于任务的风险等级：

| 自由度 | 适用场景 | 推荐写法 |
| :--- | :--- | :--- |
| 高 | 判断类任务，答案不唯一 | 给检查方向，不锁定步骤 |
| 中 | 有固定模板，但允许微调 | 给模板、参数和边界 |
| 低 | 操作敏感，出错代价大 | 给精确命令，标注不可修改 |


### 5.2 经验法则
> **涉及改数据、发请求、部署、迁移、删文件的操作，自由度必须收紧；做分析、评审、归纳、生成草稿的任务，可以适当放宽。**
>

### 5.3 对比案例
**低自由度——数据库迁移**：

```markdown
## 数据库迁移
执行以下命令：
python scripts/migrate.py --verify --backup
不要修改命令，不要添加额外参数。
如果命令执行失败，立即停止，将错误输出返回给用户。
```

**高自由度——代码审查**：

```markdown
## 代码审查
重点检查：
1. 是否有明显 Bug 或边界情况遗漏
2. 是否存在安全风险
3. 是否影响性能或资源使用
4. 是否违反项目已有约定
5. 是否有更简单的实现方式
输出时优先写会影响正确性和线上稳定性的问题，不要只做格式建议。
```

## 六、工作流与反馈循环设计
### 6.1 用清单串起步骤
复杂场景下，Agent 容易跳过关键步骤。应对之道是写清楚执行顺序，并标注必须停下来的验证点。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783656016311-fa386f00-87cc-4cd9-a77c-92e0065a86bc.png)

### 6.2 验证清单的编写要求
每个检查项必须是**可判定的具体动作**，不能是"保证质量"这类模糊口号。

```markdown
## 验证清单
- [ ] 每个新函数/方法都有测试
- [ ] 亲眼看到每个测试失败后才实现
- [ ] 每个测试的失败原因符合预期
- [ ] 写了最小代码通过每个测试
- [ ] 所有测试通过
- [ ] 输出没有错误或警告
```

### 6.3 反馈循环设计
复杂任务不要让 Agent 一口气跑到底，要在关键节点强制验证：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/67505257/1783656028991-c5577773-df83-4b20-ad57-8af7fa1cb516.png)

**代码审查的两轮设计**：

1. **第一轮：设计审查** - 整体结构、SOLID 原则、架构问题
2. **第二轮：实现审查** - 安全风险、性能热点、异常处理

### 6.4 条件分支处理
一个 Skill 要覆盖多种情况时，最好显式写出分支：

```markdown
## 文档修改工作流
1. 先判断任务类型
   - 创建新文档？→ 走创建工作流
   - 编辑现有文档？→ 走编辑工作流

2. 创建工作流
   - 使用模板生成文档
   - 导出为目标格式
   - 验证文件可正常打开

3. 编辑工作流
   - 解包现有文档
   - 修改指定内容
   - 每次修改后验证
   - 完成后重新打包
```

分支越来越多时，主文件只保留判断逻辑，具体流程拆出去：

```markdown
workflows/
├── create-document.md
├── edit-document.md
└── export-document.md
```

## 七、常见错误与避坑指南
### 7.1 八个典型错误
| 错误 | 说明 | 正确做法 |
| :--- | :--- | :--- |
| 把 Skill 当 README 写 | 侧重背景、安装、特性 | 强调可执行性：何时触发、执行顺序、失败处理 |
| 一个 Skill 写得太全 | 想做"万能助手" | 拆小，每个 Skill 只解决一类问题 |
| 给 Agent 太多选择 | 列出一堆备选方案 | 给默认方案 + 兜底方案 |
| 术语来回换 | 同一概念用不同名称 | 保持术语一致性 |
| 让 LLM 做确定性工作 | 格式转换、精确计算 | 交给脚本处理 |
| 没有验证清单 | Agent "自认为完成" | 写可判定的具体检查项 |
| 链式引用过深 | SKILL.md → A → B → C | 保持一级引用，主文件直接链接目标 |
| 第三方 Skill 不审就用 | 安全风险 | 企业环境必须审查正文、脚本和参考文件 |


### 7.2 详细说明
**错误 1：把 Skill 当项目 README 写**

README 是给人看的，侧重背景、安装、特性。Skill 是给 Agent 看的，强调可执行性。好的 Skill 至少要覆盖：何时触发、按什么顺序执行、哪些情况不做、失败了如何兜底。

**错误 2：一个 Skill 写得太全**

比如写了一个"系统故障排查器"，塞了 JVM、数据库、K8s、网关、MQ 等各种内容。用户贴段 GC 日志，Agent 得先纠结：这到底是 JVM 的锅还是容器资源的问题？

更好的做法是拆小：

| ✅ 拆小的 Skill | 职责边界 |
| :--- | :--- |
| jvm-metrics-analyzer | 只管 JVM 指标、GC、线程栈 |
| distributed-trace-finder | 只根据 TraceId 追链路耗时 |
| k8s-pod-event-viewer | 只看 Pod 状态和重启原因 |


> **Skill 不怕小，怕边界模糊。** 先把一个具体问题解决稳定，再考虑扩展。
>

**错误 3：给 Agent 太多选择**

```markdown
# ❌ 不推荐：选择太多
你可以使用 pypdf、pdfplumber、PyMuPDF 或 pdf2image 处理 PDF。

# ✅ 推荐：默认方案 + 兜底方案
默认使用 pdfplumber 提取文本。
如果是扫描版 PDF，需要 OCR，再改用 pdf2image + pytesseract。
```

**错误 4：术语来回换**

同一个概念在一个 Skill 里应该只使用一个名称。前面写了"API 端点"，后面就别再替换成 URL、API 路由或路径。

> **别追求行文变化，Skill 不是作文。同一个概念反复用同一个词，反而是优势——对 Agent 来说，一致性比文采重要。**
>

**错误 5：让 LLM 做确定性工作**

| 适合 LLM | 适合脚本 |
| :--- | :--- |
| 理解任务意图 | 解析文件结构 |
| 提取参数 | 格式转换 |
| 决定下一步 | 批量处理 |
| 解释结果 | 校验输出 |


脚本中错误条件要写清楚：

```python
def process_file(path):
    try:
        with open(path) as f:
            return f.read()
    except FileNotFoundError:
        print(f"未找到文件 {path}，正在创建默认文件")
        with open(path, "w") as f:
            f.write("")
        return ""
```

## 八、安全规范
### 8.1 安全自检清单
```markdown
✅ description 与实际执行行为一致
✅ 无硬编码 API Key、密码、路径
✅ scripts/ 中的脚本逻辑透明可读
✅ 权限声明最小化，不索取多余权限
✅ 不包含任何外部数据外传逻辑
✅ 敏感操作有明确的用户确认步骤
```

### 8.2 第三方 Skill 审查要点
SKILL.md 本质上是指令，可能夹带不安全操作。企业环境里至少要审一遍：

1. 正文内容是否与 description 一致
2. 脚本是否包含危险操作
3. 是否有数据外传逻辑
4. 权限声明是否合理

## 十、Skill 的获取与安装
### 10.1 获取 Skill 的三种方式
| 方式 | 适用场景 | 说明 |
| :--- | :--- | :--- |
| 自己编写 | 项目特有需求 | 最了解业务，最可控 |
| 社区下载 | 通用功能 | 从 SkillHub 等平台获取 |
| 团队共享 | 团队内部复用 | 同事之间分享已验证的 Skill |


### 10.2 从社区平台安装
目前主流的 Skill 分享平台有多个，支持不同的 AI 助手：

| 平台 | 支持的 AI 助手 | 特点 |
| :--- | :--- | :--- |
| SkillHub | Claude、GPT、Gemini 等 | 通用型，跨平台兼容 |
| AgentMarket | Claude Code、Cursor 等 | 专注开发者工具 |
| 各平台官方市场 | 对应平台专属 | 深度集成，功能完整 |


以 SkillHub 为例，安装流程如下：

```bash
# 安装单个 Skill
skillhub install stock-price

# 安装指定版本
skillhub install stock-price@1.2.0

# 查看已安装的 Skill
skillhub list

# 搜索 Skill
skillhub search "code review"
```

安装后的目录结构：

```plain
skills/
└── stock-price/
    ├── SKILL.md
    ├── _meta.json      # 自动生成，记录发布者、版本等信息
    └── references/
        └── ...
```

> **提示**：不同平台的命令行工具名称可能不同，具体请参考对应平台的文档。
>

### 10.3 手动安装
如果从同事或网上获取了 Skill 文件：

```bash
# 1. 将 Skill 文件夹复制到 skills 目录
cp -r /path/to/stock-price ./skills/

# 2. 检查目录结构是否正确
```

## 十一、Skill 的更新与迭代
### 11.1 为什么需要迭代
Skill 不是写完就一劳永逸的，需要持续优化：

| 场景 | 原因 |
| :--- | :--- |
| 发现执行错误 | 流程有漏洞或逻辑有误 |
| 用户反馈 | 触发不准确或输出不满意 |
| 需求变化 | 业务规则或流程调整 |
| 性能优化 | 减少 token 消耗或提升响应速度 |


### 11.2 版本管理规范
建议使用语义化版本号：

```plain
版本格式: MAJOR.MINOR.PATCH

MAJOR: 不兼容的重大修改（用户需要重新学习）
MINOR: 向下兼容的功能新增
PATCH: 向下兼容的问题修复

示例:
1.0.0 → 初始版本
1.1.0 → 新增了输出格式选项
1.1.1 → 修复了日期格式错误
2.0.0 → 重构了整个执行流程
```

在 SKILL.md 中记录版本：

```yaml
---
name: my-skill
description: ...
version: 1.2.0
changelog: |
  - 1.2.0: 新增批量处理功能
  - 1.1.0: 支持自定义输出格式
  - 1.0.0: 初始版本
---
```

## 十二、实战总结
### 12.1 写好 Skill 的六条原则
1. **description 写准** — 决定 Agent 何时想到这个 Skill
2. **正文别当 README** — Agent 不需要科普，项目私有约定和执行步骤才是核心
3. **主文件别超 500 行** — 细节拆到 references/、scripts/ 按需加载
4. **自由度看风险** — 高风险操作锁死步骤，分析评审类任务给方向即可
5. **复杂任务必须有验证点** — 别让 Agent 一路跑到底就声称完成
6. **第三方 Skill 务必过审** — SKILL.md 本身就是指令，可能夹带不安全操作

### 12.2 一个好 Skill 的标准
> 1. **Agent 知道什么时候该用它。**
> 2. **用的时候按你预期的方式执行。**
> 3. **输出格式稳定可预期。**
>

达到这三点，这个 Skill 就算合格了。

## 附录 B：在 Claude Code 中使用 Skill
### B.1 Skills 的存储位置
Claude Code 的 Skills 可以放在两个位置：

| 位置 | 路径 | 适用范围 |
| :--- | :--- | :--- |
| 项目级 | `.claude/skills/` | 仅当前项目可用 |
| 全局级 | `~/.claude/skills/` | 所有项目可用 |


```plain
# 项目级 Skills
your-project/
├── .claude/
│   └── skills/
│       ├── code-review.md
│       └── tdd/
│           └── SKILL.md
└── ...

# 全局 Skills
~/.claude/
└── skills/
    └── weekly-report/
        └── SKILL.md
```

### B.2 SKILL.md 的元数据字段
除了 `name` 和 `description`，还有两个控制触发行为的字段：

```yaml
---
name: deploy-app
description: 部署应用到生产环境
disable-model-invocation: true   # 禁止自动触发
user-invocable: false            # 不在斜杠菜单显示
---
```

| 字段 | 默认值 | 作用 |
| :--- | :--- | :--- |
| `disable-model-invocation` | `false` | 设为 `true` 后，只能手动 `/技能名` 触发 |
| `user-invocable` | `true` | 设为 `false` 后，不在斜杠菜单显示，但可自动触发 |


**使用场景**：

| 场景 | 推荐配置 |
| :--- | :--- |
| 普通技能（自动+手动） | 默认即可 |
| 危险操作（部署、删除） | `disable-model-invocation: true` |
| 后台辅助技能 | `user-invocable: false` |


### B.3 单文件与目录形式
Skill 有两种组织形式：

**单文件形式**（简单场景）：

```bash
.claude/skills/code-review.md
```

**目录形式**（复杂场景，需要参考资料/脚本/模板）：

```bash
.claude/skills/weekly-report/
├── SKILL.md
├── assets/
│   └── template.md
└── references/
    └── guide.md
```

当 Skill 包含多个文件时，用 `{baseDir}` 引用当前 Skill 目录：

```markdown
读取模板：read {baseDir}/assets/template.md
参考指南：read {baseDir}/references/guide.md
```

### B.4 最佳实践
1. **description 写精准**：包含触发词和边界说明，决定自动触发的准确度
2. **危险操作加锁**：部署、删除等操作设置 `disable-model-invocation: true`
3. **正文控制在 500 行**：细节拆到 references 按需加载
4. **提交到 Git**：`.claude/skills/` 可以提交，方便团队共享

### B.5 查看和管理已安装的 Skills
**查看已安装的 Skills**：

| 方式 | 操作 | 说明 |
| :--- | :--- | :--- |
| 斜杠菜单 | 输入 `/` | 列出所有可用的 Skill 和命令，可继续打字筛选过滤 |
| 专用命令 | 输入 `/skills` | 专门列出所有已安装的 Skill，更清晰 |


**停用或删除 Skills**：

```bash
# 停用：编辑 SKILL.md，添加元数据
---
name: my-skill
description: ...
disable-model-invocation: true   # 禁止自动触发
---

# 删除：移除 Skill 文件夹
rm -rf ~/.claude/skills/old-skill
```

### 从零编写一个 Skill（实操题）
**题目**：编写一个"生成月度学习总结"的 Skill。

**场景描述**：  
每月底，学生需要向导师提交本月的学习总结，内容包括：

+ 本月学习了哪些核心知识点（按周划分）
+ 完成了哪些作业或项目
+ 本月的学习成果与收获
+ 遇到了什么问题，如何解决的
+ 下月的学习计划与目标

很多学生每次写月度总结都要回顾一整个月的内容，希望 Agent 能根据简单的对话（比如"这个月学了前端三件套和 React"）自动生成结构规范的月度总结。

**要求**：

1. 创建完整的目录结构
2. 编写 SKILL.md，包含：
    - 准确的元数据（name、description）
    - 清晰的触发条件（用户说"写月报"、"生成月度总结"等）
    - 详细的执行步骤（如何引导用户、如何组织内容、如何按周划分）
    - 明确的输出格式（固定的月报模板）
3. 在 assets/ 目录下创建月报模板文件
4. 考虑边界情况（用户信息很少时怎么办、如何处理跨月的情况）

**评判标准**：

| 维度 | 优秀 | 良好 | 需改进 |
| :--- | :--- | :--- | :--- |
| description | 精准包含触发词和边界 | 基本清晰 | 模糊或缺失 |
| 执行步骤 | 完整、可执行、有异常处理 | 基本完整 | 缺失关键步骤 |
| 输出格式 | 有模板、结构清晰、可复用 | 基本明确 | 模糊不清 |
| 用户体验 | 引导自然、交互友好 | 基本可用 | 交互生硬 |


**提交方式**：完整的 Skill 目录，打包为 zip。

### 注意事项
1. **独立完成**：作业需独立完成，可以讨论思路但不能抄袭
2. **按时提交**：截止日期见课程通知，逾期扣分
3. **格式规范**：代码用 Markdown 代码块，文档用 Markdown 格式
4. **命名规范**：文件名使用英文小写，用连字符分隔
