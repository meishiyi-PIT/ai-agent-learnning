# 大模型分布式训练实战指南
---

## 一、为什么单卡撑不住了
### 1.1 两座大山：显存和算力
所谓"分布式"，说白了就是把一个又大又重的任务拆成若干份，交给多台机器（或多张卡）协同完成，而不是指望一个节点单挑全场。这个思想在计算机科学里并不新鲜，但大模型时代它从"可选项"变成了"必选项"，原因就两个：

**第一座山：显存效率。** 大模型的"大"主要体现在参数量上。以 DeepSeek-V3 这类 MoE 模型为例，总参数 671B，哪怕只是推理都要动用多张卡。训练时的账更难算——对于 Adam 优化器，每个参数背后还跟着一阶动量、二阶动量两份状态。粗算一下，一个 10B 参数的模型，用 FP32 训练时：

| 组成部分 | 显存占用估算 | 说明 |
| --- | --- | --- |
| 模型参数 | 40 GB | 4 字节 × 10B |
| 梯度 | 40 GB | 与参数同尺寸 |
| 优化器状态（Adam） | 80 GB | m、v 各一份 FP32 |
| **合计** | **约 160 GB** | 还没算激活值 |


一张 80G 的 A100/H800 都装不下，更别说消费级显卡了。

**第二座山：计算效率。** 海量训练数据意味着海量计算。以 GPT-3 规模的训练为例，单卡跑完需要数十年——这不是工程问题，是物理学问题。唯一的出路就是把计算摊开，让成百上千张卡一起算。

### 1.2 单卡场景下的自救手段
在动用分布式这个"重武器"之前，单卡其实还有两条自救路线，值得先试：

**路线一：减少可训练参数量 —— PEFT（参数高效微调）**

不动主干，只训练一小撮新增参数。主流玩法：

+ **LoRA / QLoRA**：在权重矩阵旁挂一对低秩矩阵，只训练这对小矩阵，显存占用骤降，是目前社区事实标准；

**路线二：降低参数精度 —— 量化训练**

用 bitsandbytes 等库把权重压到 INT8 甚至 NF4（4bit），QLoRA 正是"4bit 基座 + LoRA"的组合拳，让 24G 显存的消费卡也能微调 7B 级别的国产模型（如 Qwen2.5-7B）。

### 1.3 自救手段的天花板
但要清醒：这两条路线都有边界。

+ PEFT 解决的是"**微调**"的显存问题，底座模型本身还是得完整加载进显存；
+ 量化省显存但会损失一定精度，且对**预训练**场景基本无能为力——预训练必须全参数、全精度地更新。

所以当你面对的是"从头训练"或"全参数微调一个装不下的大模型"时，分布式训练就是唯一的答案。用一张 Mermaid 图总结这个决策过程：

## 二、分布式训练的三种并行范式
分布式训练的核心问题只有一个：**怎么切**。切法不同，衍生出三种基本范式。

### 2.1 数据并行（DP）：复制模型，切分数据
每张 GPU 都持有**一份完整的模型副本**，但大家吃不同的数据。一个 batch 被均分到各卡，各算各的梯度，最后把梯度汇总平均、统一更新，保证所有副本始终一致。
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789971385994-c49e3794-be75-4479-b66a-566e4a3e3d6d.png)

前提条件很硬：**每张卡都得能独立跑完整个训练流程**。模型装不下单卡，这条路直接封死。

### 2.2 流水线并行（PP）：按层切模型
模型装不下？那就把模型按层切开，GPU 0 放前几层，GPU 1 放后几层，数据像流水线上的产品一样依次经过各卡。任何一张卡都不再需要装下完整模型。
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789971444526-856665fb-0bdc-41af-b06a-8126484e9bfa.png)

### 2.3 张量并行（TP）：切开每一层
更激进的切法：把**同一层内部**的权重矩阵按行或按列剁开，每张卡只存一块碎片，各自做矩阵乘法，再通过集合通信把结果拼回去。这是"显存换通信"的典型交易——显存压力大幅下降，代价是 GPU 之间高频的数据交换，对互联带宽（NVLink）要求极高。
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789971511743-30d1b00f-ff40-4f34-a3c7-7d22ee533eb6.png)

### 2.4 怎么选？以及 3D 并行
经验法则一句话：**装得下就 DP，装不下就切模型（PP/TP），超大模型三样一起上**。

万卡级别的训练（如 DeepSeek-V3、Qwen 系列大模型的预训练）几乎清一色采用 **3D 并行**——DP + PP + TP 组合拳，编排上有个讲究：

+ **TP 通信最频繁**，放在节点内部（同机多卡，走 NVLink 高带宽）；
+ **PP 通信量最小**（只在 stage 边界传激活值），适合跨节点；
+ **DP 包在最外层**，把 TP+PP 拼好的"超级模型"复制多份，摊大数据吞吐。

### 3.2 DP 的三个坑（血泪经验）
**坑一：**`device_ids`** 的物理卡与逻辑卡映射。** DP 要求模型参数必须先落在 `device_ids[0]` 上。如果 0 号物理卡被别人占着，你想用 2、3 号卡，直接写 `device_ids=[2, 3]` 会报初始化错误。正确姿势是在程序最开头用环境变量重排可见设备：

```python
import os
# 必须在 import torch 之前设置！
# 作用一：按 PCI 总线顺序枚举设备，保证编号稳定
os.environ["CUDA_DEVICE_ORDER"] = "PCI_BUS_ID"
# 作用二：对本进程只暴露物理 2、3 号卡
# 设置后，程序里的 cuda:0 就是物理 2 号卡，cuda:1 就是物理 3 号卡
os.environ["CUDA_VISIBLE_DEVICES"] = "2, 3"

import torch

# 现在 device_ids 用的是"逻辑编号"
device_ids = [0, 1]  # 实际对应物理卡 2 和 3
net = torch.nn.DataParallel(net, device_ids=device_ids)
```

**坑二：主卡显存畸高。** 从八步流程能看出，Loss 计算、梯度汇总全压在主卡上，主卡显存占用明显高于其他卡，batch 开大时主卡先 OOM。

**坑三：快不起来，甚至更慢。** DP 是**单进程多线程**实现，被 Python 的 GIL 锁卡得死死的；再加上每个 step 都要重新广播模型，模型一大，同步开销直接吃掉多卡收益。很多人兴冲冲加上 DP，发现训练速度纹丝不动，就是这个原因。

### 3.3 懒得手写？Hugging Face Trainer
HF 的 `Trainer` 会自动探测可用 GPU 数量，通过 `accelerate launch` 或 `torchrun` 启动即可启用多卡训练，基本零改造。对于标准微调任务，这是最省心的路径，把精力留给数据和调参。

## 四、模型并行：流水并行与张量并行
当模型大到单卡装不下，就必须对模型本身动刀。

### 4.1 流水线并行（PP）与 Bubble 问题
PP 按层把模型切成若干 stage，每卡负责一段。朴素实现有个明显浪费：GPU 0 算前向时，后面的卡全在干等；反向传播时反过来。这段空闲时间就叫 **Bubble（气泡）**。

![](https://cdn.nlark.com/yuque/__mermaid_v3/7a5ba349f102117bc030c0c945c6ae09.svg)

降气泡的三板斧：

1. **增加微批次（micro-batch）数量**：把大 batch 切成更多小份流水推进，微批次越多，气泡占整体时间的比例越低——这是最有效的手段；
2. **均衡切分 stage**：尽量让每段计算量相等，避免某一段成为拖后腿的瓶颈；
3. **改进调度**：GPipe 的微批次调度、PipeDream 的异步权重更新都是为此而生。现代框架（如 Megatron-LM）的 interleaved 1F1B 调度能把气泡压到很小。

### 4.2 张量并行（TP）：显存换通信
TP 针对的是"某一层本身太大"的问题。以 Transformer 的 FFN 层为例，权重矩阵 W 可以按列切开：

+ GPU 0 持有 `W[:, :half]`，GPU 1 持有 `W[:, half:]`；
+ 同一份输入 X 广播给两卡，各自算 `X · W_i` 得到半个输出；
+ 最后 All-Reduce（或 Concat）拼出完整结果。

Attention 层同理——多头注意力天然适合切，每张卡负责一部分 head。

这笔交易的账要算清楚：

+ **收益**：单层显存占用 ÷ TP 卡数，千亿模型推理的标配手段；
+ **代价**：每一层的前向、反向都要跨卡通信，通信频率远高于 PP。所以 TP 组必须放在 NVLink 互联的同机卡之间，跨机跑 TP 基本等于自杀。

### 4.3 TP vs PP 速查
| 维度 | 张量并行 TP | 流水线并行 PP |
| --- | --- | --- |
| 切分粒度 | 层内（切权重矩阵） | 层间（按层分段） |
| 通信频率 | 极高（每层都通信） | 低（仅 stage 边界） |
| 带宽要求 | 必须 NVLink 级 | 普通 IB/RoCE 即可跨机 |
| 解决的问题 | 单层太大放不下 | 整个模型太大放不下 |
| 代表框架 | Megatron-LM | GPipe / PipeDream |

## 五、DeepSpeed 与 ZeRO：显存优化的终极武器
### 5.1 DeepSpeed 是什么
DeepSpeed 是微软开源的深度学习优化库，旨在加速大规模模型的训练和推理。它通过多种优化技术（如分布式训练、混合精度训练、梯度累积和 ZeRO 优化器等）显著减少了训练时间和内存占用，使得训练数十亿甚至数万亿参数的模型成为可能。目标很直白：让大模型训练更快、更省。它基于 PyTorch，大多数项目不用大改就能接入，BLOOM-176B、MT-NLG-530B 这些怪兽级模型都是它训出来的。其软件栈分三层：

### 5.2 ZeRO：把冗余的显存找回来
ZeRO（Zero Redundancy Optimizer，零冗余优化器）是 DeepSpeed 的核心技术之一，旨在解决大规模模型训练中的内存瓶颈问题。通过优化内存使用，ZeRO 使得训练数十亿甚至数万亿参数的模型成为可能。ZeRO 的核心思想是通过**分片（partitioning）**技术，将模型训练过程中占用的内存分布到多个设备（如 GPU）上，从而减少单个设备的内存压力。

传统数据并行有个巨大的浪费：每张卡都完整存了一份参数、梯度和优化器状态——N 张卡就是 N 份冗余。ZeRO（Zero Redundancy Optimizer，零冗余优化器）的思路是**分片（partitioning）**：这些东西不再每张卡各存一份，而是切开摊到所有卡上，谁用谁取。

### **<font style="color:rgb(13, 13, 13);">1. ZeRO 的背景与挑战</font>**
<font style="color:rgb(13, 13, 13);">在深度学习训练中，内存占用主要来自以下几个方面：</font>

1. **<font style="color:rgb(13, 13, 13);">模型参数 (Model Parameters)</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：模型的权重。</font>
2. **<font style="color:rgb(13, 13, 13);">梯度 (Gradients)</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：反向传播计算的梯度。</font>
3. **<font style="color:rgb(13, 13, 13);">优化器状态 (Optimizer States)</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：如 Adam 优化器中的动量 (momentum) 和方差 (variance) 。</font>

<font style="color:rgb(13, 13, 13);">随着模型规模的增大，这些内存占用会迅速增长。例如，训练一个 10 亿参数的模型时：</font>

+ <font style="color:rgb(13, 13, 13);">模型参数：4 GB (FP32) 。</font>
+ <font style="color:rgb(13, 13, 13);">梯度：4 GB (FP32) 。</font>
+ <font style="color:rgb(13, 13, 13);">优化器状态：8 GB (Adam 优化器) 。</font>

<font style="color:rgb(13, 13, 13);">总内存占用可能超过 16 GB，而单个 GPU 的内存通常有限（如 16 GB 或 32 GB）。ZeRO 的目标是通过分片技术，将这些内存占用分布到多个 GPU 上，从而减少单个 GPU 的内存需求。</font>

### **<font style="color:rgb(13, 13, 13);">2. ZeRO 的分阶段优化</font>**
<font style="color:rgb(13, 13, 13);">ZeRO 分为三个阶段 (ZeRO-1、ZeRO-2、ZeRO-3) ，每个阶段都针对不同的内存占用进行优化：</font>

**<font style="color:rgb(13, 13, 13);">ZeRO-1: 优化器状态分片</font>**

+ **<font style="color:rgb(13, 13, 13);">目标</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：减少优化器状态的内存占用。</font>
+ **<font style="color:rgb(13, 13, 13);">实现</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：将优化器状态（如 Adam 的动量和方差）分布到多个 GPU 上，每个 GPU 只存储一部分优化器状态。</font>
+ **<font style="color:rgb(13, 13, 13);">效果</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：减少优化器状态的内存占用，通常可以节省 4 倍内存。</font>

**<font style="color:rgb(13, 13, 13);">ZeRO-2: 梯度分片</font>**

+ **<font style="color:rgb(13, 13, 13);">目标</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：减少梯度的内存占用。</font>
+ **<font style="color:rgb(13, 13, 13);">实现</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：将梯度分布到多个 GPU 上，每个 GPU 只存储一部分梯度。</font>
+ **<font style="color:rgb(13, 13, 13);">效果</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：在 ZeRO-1 的基础上，进一步减少梯度的内存占用，通常可以节省 8 倍内存。</font>

**<font style="color:rgb(13, 13, 13);">ZeRO-3: 模型参数分片</font>**

+ **<font style="color:rgb(13, 13, 13);">目标</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：减少模型参数的内存占用。</font>
+ **<font style="color:rgb(13, 13, 13);">实现</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：将模型参数分布到多个 GPU 上，每个 GPU 只存储一部分模型参数。</font>
+ **<font style="color:rgb(13, 13, 13);">效果</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：在 ZeRO-2 的基础上，进一步减少模型参数的内存占用，通常可以节省与 GPU 数量成比例的内存。</font>

### **<font style="color:rgb(13, 13, 13);">3. ZeRO 的工作原理</font>**
<font style="color:rgb(13, 13, 13);">ZeRO 的核心思想是通过</font>**<font style="color:rgb(13, 13, 13);">分片</font>**<font style="color:rgb(13, 13, 13);">和</font>**<font style="color:rgb(13, 13, 13);">通信</font>**<font style="color:rgb(13, 13, 13);">来实现内存优化。以下是一个简化的 ZeRO 工作流程：</font>

1. **<font style="color:rgb(13, 13, 13);">分片</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：</font>
    - <font style="color:rgb(13, 13, 13);">将优化器状态、梯度和模型参数分片到多个 GPU 上。</font>
    - <font style="color:rgb(13, 13, 13);">每个 GPU 只存储一部分数据。</font>
2. **<font style="color:rgb(13, 13, 13);">前向传播</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：</font>
    - <font style="color:rgb(13, 13, 13);">每个 GPU 使用本地存储的模型参数进行计算。</font>
    - <font style="color:rgb(13, 13, 13);">如果需要其他 GPU 上的参数，则通过通信获取。</font>
3. **<font style="color:rgb(13, 13, 13);">反向传播</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：</font>
    - <font style="color:rgb(13, 13, 13);">计算梯度后，将梯度分片存储到各个 GPU 上。</font>
4. **<font style="color:rgb(13, 13, 13);">参数更新</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：</font>
    - <font style="color:rgb(13, 13, 13);">每个 GPU 只更新本地存储的优化器状态和模型参数。</font>
5. **<font style="color:rgb(13, 13, 13);">通信</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：</font>
    - <font style="color:rgb(13, 13, 13);">在需要时，GPU 之间通过高效的通信机制（如 All-Reduce）同步数据。</font>

### **<font style="color:rgb(13, 13, 13);">4. ZeRO 的优势</font>**
+ **<font style="color:rgb(13, 13, 13);">内存效率</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：通过分片技术，显著减少单个 GPU 的内存占用。</font>
+ **<font style="color:rgb(13, 13, 13);">扩展性</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：支持训练超大规模模型（如万亿参数模型）。</font>
+ **<font style="color:rgb(13, 13, 13);">兼容性</font>**<font style="color:rgb(13, 13, 13);"> </font><font style="color:rgb(13, 13, 13);">：与现有的深度学习框架（如 PyTorch）无缝集成。</font>
+ **<font style="color:rgb(13, 13, 13);">灵活性</font>**<font style="color:rgb(13, 13, 13);"> ：支持多种优化器（如 Adam、SGD）和混合精度训练。</font>

| 阶段 | 分片内容 | 单卡显存 | 通俗理解 |
| --- | --- | --- | --- |
| Baseline（普通 DP） | 啥都不分 | 120 GB | 人手一套完整教材 |
| **ZeRO-1** | 优化器状态 | 31.4 GB（≈4 倍↓） | 作业答案分散给小组成员保管 |
| **ZeRO-2** | 优化器状态 + 梯度 | 16.6 GB（≈8 倍↓） | 连草稿纸也分开存 |
| **ZeRO-3** | 优化器状态 + 梯度 + **参数** | 1.9 GB（随卡数线性↓） | 教材也撕开分，用到哪页跟谁借 |


ZeRO-3 的代价是通信量约为普通 DP 的 1.5 倍——前向反向时需要临时从别的卡拉参数分片。在此之上还有两级扩展：

+ **ZeRO-Offload**：把优化器状态和梯度卸载到 CPU 内存，单卡可训练 10 倍于显存的模型；
+ **ZeRO-Infinity**：进一步卸载到 NVMe 固态硬盘，突破 GPU+CPU 内存总和的限制。

### 5.5 在 TrainingArguments 里配置 DeepSpeed
如果你的训练脚本本来就是 HF `Trainer` 写的，接入 DeepSpeed 不需要 Accelerate，也不用自己调 `deepspeed.initialize`——`TrainingArguments` 原生提供了一个 `deepspeed` 参数，`Trainer` 会在内部替你完成初始化。

**核心用法：一个参数搞定**

```python
from transformers import TrainingArguments, Trainer

training_args = TrainingArguments(
    output_dir="./output",
    # 关键就这一行：传入 ds_config.json 的路径（也可以直接传一个 dict）
    deepspeed="./ds_config.json",

    # 以下常规超参照常写，Trainer 会把它们"注入"DeepSpeed 配置
    per_device_train_batch_size=8,  # 对应 ds_config 的 train_micro_batch_size_per_gpu
    gradient_accumulation_steps=2,  # 对应 gradient_accumulation_steps
    learning_rate=2e-5,             # 对应 optimizer.params.lr
    num_train_epochs=3,
    bf16=True,                      # 对应 ds_config 的 bf16.enabled
    logging_steps=10,
    save_strategy="epoch",
)

trainer = Trainer(
    model=model,           # 普通的 HF 模型，不需要任何包装
    args=training_args,
    train_dataset=train_dataset,
)
trainer.train()  # Trainer 内部自动完成 deepspeed.initialize，无感
```

**ds_config.json 配合写法：善用 "auto"**

这是最容易踩坑的地方。ds_config 里的 batch 相关参数、优化器、学习率调度，如果写死具体数值，而 TrainingArguments 里又写了另一套，两边会对不上甚至静默覆盖。正确姿势是让 DeepSpeed 配置项填 `"auto"`，把主动权交给 TrainingArguments：



规则一句话：**凡是被 Trainer 管理的参数，ds_config 里就写 "auto"；只有 ZeRO 相关和 DeepSpeed 独有的开关（如 **`overlap_comm`**、**`offload`**）才在 json 里写死**。

**启动方式：**

```bash
# deepspeed 启动器
deepspeed --num_gpus=4 train_trainer.py
```
