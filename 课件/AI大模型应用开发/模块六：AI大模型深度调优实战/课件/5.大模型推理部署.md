# 大模型推理的两阶段：Prefill(预填充) 与 Decode(解码)
---

## 1. 从一个日常现象说起
你肯定观察过：给 DeepSeek 或豆包发一条消息，回答永远是这样——先"思考"一小下，然后文字像打字机一样逐字流出。

这不是 UI 特效，而是大模型推理的真实物理过程：

+ **那一下停顿**：模型在一口气读完你的全部输入（Prefill 阶段）；
+ **逐字输出**：模型在一个 token 一个 token 地往后写（Decode 阶段）。

这两个阶段的计算特征完全相反，后续所有推理优化技术——KV Cache、PagedAttention、连续批处理、PD 分离——全都是围绕这对矛盾展开的。所以这是整个推理工程知识体系的"第一性原理"。

## 2. 一次请求的完整链路
先把整体流程跑一遍。假设你向 Qwen3 发送"帮我写一首关于加班的绝句"：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789873645628-e4755dbe-9a59-4aba-a3bf-4b4503141aca.png)

几个关键事实先建立起来：

1. **模型不会"整段想好再输出"**。它永远只干一件事：给定前面的所有 token，预测下一个 token 的概率分布。
2. **输出不是确定的**。同样的 Prompt，采样参数一变，结果就变。
3. **文本变长会变慢**。注意力计算量随长度平方增长，KV Cache 随长度线性吃显存——这是后面所有优化的根源。

## 3. Prefill：并行"读题"阶段
Prefill 干的事：把输入 Prompt 的**所有 token 一次性并行**塞进模型，做完两件事——

+ 算出每个 token 在每一层的 Key / Value 向量，**填满 KV Cache**；
+ 产出第一个输出 token。

这里的关键词是**并行**。Prompt 有 2000 个 token，就是 2000 个位置同时参与矩阵运算。从 GPU 的视角看，这是一大块规整的 **GEMM（矩阵乘矩阵）**，Tensor Core 可以火力全开，利用率轻松打到 80% 以上。

所以 Prefill 是**计算密集（compute-bound）**的：瓶颈在算力，不在数据搬运。它的耗时直接决定了用户体验里的 **TTFT（Time To First Token，首字延迟）**——你按下回车后那一下"思考"的时长。

一个反直觉的点：自注意力的计算量是 O(n²) 的（每个 token 都要和之前所有 token 算相关性），所以 **Prompt 越长，TTFT 恶化得越厉害**，而且是平方级恶化。扔进去一本 10 万字的小说让它总结，首字延迟几十秒很正常。

## 4. Decode：逐字"写作"阶段
Prefill 结束后进入 Decode 循环：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789974988294-eac53d73-2fc0-4dde-8808-d3c851deb271.png)

每一步只处理 **1 个新 token**，但要做两件"亏本买卖"：

1. 把模型的**全部权重**从显存里读一遍（7B 模型 FP16 就是 ~14GB）；
2. 把**全部历史 KV Cache** 从显存里读一遍（长上下文下可能比权重还大）。

算力消耗呢？一个 token 的过模型计算本质是 **GEMV（矩阵乘向量）**，算术强度极低。GPU 的情况是：数据还没搬完，算力早就等闲置了——典型的**访存密集（memory-bound）**。

这就解释了 Decode 阶段的体感：生成速度和模型大小、上下文长度强相关，和"这句话难不难想"无关。模型写"哈哈哈哈"和写量子力学证明，每个 token 的成本一模一样。

Decode 的每步耗时对应指标 **TPOT（Time Per Output Token）**，也就是我们看到的"打字速度"。

## 5. 两阶段的对立统一
把两阶段放在一起对比，矛盾一目了然：

| 维度 | Prefill | Decode |
| --- | --- | --- |
| 计算形态 | 大 GEMM（矩阵×矩阵） | GEMV（矩阵×向量） |
| 瓶颈类型 | 算力（compute-bound） | 显存带宽（memory-bound） |
| GPU 利用率 | 高，Tensor Core 打满 | 低，算力大量闲置 |
| 时延来源 | Prompt 长度（O(n²) 注意力） | 权重 + KV Cache 搬运量 |
| 决定指标 | TTFT（首字延迟） | TPOT / 吞吐 |
| 并行度 | 输入全并行 | 严格串行，逐 token |


记住一句话：**Prefill 是"读题"，Decode 是"写作"；读题可以一目十行并行扫，写作必须一个字一个字来。**

这对矛盾直接催生了后面几篇的所有技术：

+ KV Cache 让 Decode 不用重算历史（空间换时间）；
+ Continuous Batching 把多个请求的 Decode 拼成大矩阵，把 GEMV 强行变回 GEMM；
+ PD 分离干脆把两个阶段拆到不同的机器上，各配各的硬件、各扩各的容。

## 6. 性能指标体系：别再说"有点慢"
做推理优化，先学会用指标说话。业界通用的五个：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789975045381-df82ea26-eed9-441a-976a-f3578ec55dba.png)

+ **TTFT**（Time To First Token）：首字延迟。由 Prefill 决定，直接影响"卡不卡"的体感。对话场景一般要求 < 1s。
+ **TPOT**（Time Per Output Token）：每个输出 token 的平均耗时。决定流式输出是否比人阅读速度快（人约 10~20 token/s，TPOT < 50ms 就够用）。
+ **ITL**（Inter-Token Latency）：相邻两个 token 的间隔。ITL 抖动大 = 输出一顿一顿的，这是 PD 混跑时长 Prompt 插队的典型症状。
+ **E2E Latency**：端到端总时延 = TTFT + 输出长度 × TPOT。
+ **吞吐量**（Throughput）：系统每秒处理的 token 总数（input + output），决定成本。

一个实测参考：在消费级显卡上跑 Qwen3-0.6B 这种小模型，TTFT 约 2 秒、TPOT 约 42ms；换成 671B 的 DeepSeek-V3 满血版，没有多卡并行和一堆优化，TPOT 会是秒级——根本没法用。

**优化顺序的经验法则**：先看 TTFT（Prefill 侧：前缀缓存、Chunked Prefill），再看 TPOT（Decode 侧：量化、投机解码、批处理），最后看端到端吞吐（调度与并行架构）。

## 7. 采样：最后一个 token 是怎么"被选中的"
模型每步输出的其实是词表上的一整组概率（DeepSeek-V3 词表 12 万+），选哪个 token 由采样策略决定。这是产品和工程都绕不开的旋钮：

```python
# 采样策略最小示例（基于 HuggingFace transformers，Qwen3 同理）
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "Qwen/Qwen3-0.6B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

inputs = tokenizer("用一句话解释什么是递归：", return_tensors="pt")

# 关键就这几个参数，逐个说透：
outputs = model.generate(
    **inputs,
    max_new_tokens=100,     # 最多生成 100 个 token，防失控
    do_sample=True,         # False = 贪心解码（每步选概率最大的，输出确定但死板）
    temperature=0.7,        # 温度：>1 拉平分布（更野），<1 锐化分布（更保守）
                            # 数学上等价于 logits / T 后再 softmax
    top_k=50,               # 只在概率最高的 50 个候选里采样，砍掉长尾噪音
    top_p=0.9,              # 核采样：只保留累计概率达 90% 的最小候选集
                            # 业界默认甜点位 0.9~0.95，比 top_k 更自适应
)

print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

工程上的经验：

+ **确定性任务**（代码生成、结构化输出、工具调用）：`temperature=0` 或极低，配合贪心解码。没人希望自己的 JSON 有"创造力"。
+ **开放式写作**：`temperature 0.7~1.0` + `top_p 0.9`。
+ **Agent 场景**：建议固定 `temperature=0`，否则同一个工具调用今天能跑明天挂，排查到怀疑人生。

# 为什么 Prefill 吃算力，Decode 吃带宽：Roofline 性能模型实战
---

## 1. 一个程序员都懂的类比
想象你开了家饺子馆：

+ **Prefill** 像是年夜饭备料：500 个客人的订单一次性全到，后厨 10 个灶眼火力全开，瓶颈是**厨师手速**（算力）。
+ **Decode** 像是给一位客人一粒一粒上饺子：每上一粒，都要把整本菜谱（权重）和这桌已上的所有菜（KV Cache）翻一遍，瓶颈是**传菜员的腿**（带宽）。

同一家店，两种瓶颈。优化备料期要多请厨师，优化上菜期要给传菜员配电动车——搞错方向，钱白花。

Roofline 模型就是把"手速"和"腿速"画在同一张图上的方法。

## 2. Roofline 模型：一张图看懂硬件瓶颈
Roofline 的核心概念只有一个：**算术强度（Arithmetic Intensity）**。

```plain
算术强度 I = 计算量 (FLOPs) ÷ 数据搬运量 (Bytes)
```

直觉理解：每从显存搬 1 字节数据回来，能搭配做多少次浮点运算。搬得少、算得多，I 就高；搬得多、算得少，I 就低。

把它和硬件的两个上限放在一起：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789975103710-fc292949-9ed8-450c-985a-1e5e8f9c70dd.png)

+ 图的左半边是条斜线：性能被**显存带宽**锁死，算力再强也只能等数据。
+ 图的右半边是条平线：性能被**峰值算力**锁死，带宽再大也快不了。
+ 两条线的交点叫 **Ridge Point（平衡点）**，它的横坐标 = 峰值算力 ÷ 峰值带宽。

以 A100 80GB 为例：

```plain
峰值算力（BF16）≈ 312 TFLOPS
HBM 带宽        ≈ 2 TB/s
Ridge Point     ≈ 312 / 2 = 156 FLOP/byte
```

也就是说，在 A100 上，算术强度低于 156 的活都是"带宽受限"，高于 156 的活才是"算力受限"。

## 3. 动手算：Prefill 和 Decode 各落在哪
别停留在定性，写段代码把算术强度算出来。以一个简化场景为例（DeepSeek-V3 单层的注意力投影，道理相同）：

```python
# ========== Roofline 实战计算 ==========
# 场景：一个 batch 的 token 过一层线性层 Y = X·W
# X: [n_tokens, d_model]，W: [d_model, d_model]

d_model = 7168          # DeepSeek-V3 的隐藏维度
bytes_per_elem = 2      # BF16，每个元素 2 字节

def arithmetic_intensity(n_tokens: int) -> float:
    """计算线性层的算术强度（FLOP/byte）"""
    # 计算量：矩阵乘 [n, d] × [d, d]，每个输出元素 d 次乘加 = 2d FLOPs
    flops = 2 * n_tokens * d_model * d_model

    # 数据搬运量（从 HBM 读到片上）：
    #   输入 X:  n_tokens × d_model 个元素
    #   权重 W:  d_model × d_model 个元素（注意：无论多少token，权重都要完整搬一遍）
    #   输出 Y:  n_tokens × d_model 个元素
    bytes_moved = (2 * n_tokens * d_model + d_model * d_model) * bytes_per_elem

    return flops / bytes_moved

# 关键对比：Decode 每步只有 1 个 token，Prefill 一次几千个
for n, stage in [(1, "Decode（每步1个token）"),
                 (128, "小batch Decode"),
                 (2048, "Prefill（2K prompt）"),
                 (8192, "Prefill（8K prompt）")]:
    I = arithmetic_intensity(n)
    verdict = "带宽受限(memory-bound)" if I < 156 else "算力受限(compute-bound)"
    print(f"{stage:28s} n={n:5d}  I={I:8.2f} FLOP/byte  -> {verdict}")
```

跑出来的结果大致是：

```plain
Decode（每步1个token）     n=    1  I=    2.00 FLOP/byte  -> 带宽受限
小batch Decode             n=  128  I=  255.39 FLOP/byte  -> 算力受限
Prefill（2K prompt）       n= 2048  I= 2046.85 FLOP/byte  -> 算力受限
Prefill（8K prompt）       n= 8192  I= 4093.43 FLOP/byte  -> 算力受限
```

（把权重+KV Cache 全算上，Decode 的实际算术强度约 0.5 FLOP/byte，比上面的纯线性层还惨——离 156 的平衡点差了 **300 多倍**。）

这就是结论的定量版：

+ **Decode 单步：I ≈ 0.5~2**，深深陷在带宽墙里。GPU 的 Tensor Core 利用率常年个位数百分比，不是卡不行，是活儿本身"吃不饱"。
+ **Prefill：I 轻松上千**，稳稳贴着算力天花板跑。

## 4. 推论：所有推理加速技术的统一视角
看懂 Roofline 之后，你会发现所有推理优化技术本质上只在做两件事：**把算术强度往右推，或者把需要搬的数据往下砍。**

| 技术 | Roofline 视角下的本质 |
| --- | --- |
| Continuous Batching | 把几十上百个请求的 Decode 拼成大矩阵，GEMV → GEMM，I 提升两个数量级 |
| 权重量化（FP8/INT4） | 同样计算量，权重搬运量砍半甚至到 1/4，斜线部分直接提速 |
| KV Cache 量化 | Decode 每步要读的全部 KV，从 BF16 变 FP8，搬运量减半 |
| FlashAttention | 注意力计算在片上 SRAM 完成，减少 HBM 往返次数，等于变相增大 I |
| GQA / MQA / MLA | KV Cache 体积本身缩小 4~几十倍，Decode 每步少搬数据 |
| 投机解码 | 用小模型的廉价 Decode 换大模型的一次并行验证，把串行 GEMV 变成批量 GEMM |
| Prefix Caching | 命中前缀的 Prefill 直接跳过，算力消耗归零 |


所以下次再看到"某技术提速 X 倍"，你脑子里应该自动弹出三个问题：

1. 它推的是算术强度，还是砍的是搬运量？
2. 测试时的序列长度、batch size、精度是什么？
3. 我的场景（长 Prompt？高并发？流式？）和它的测试场景一样吗？

瓶颈位置是**随序列长度、batch、精度不断迁移**的：batch 开到 512，Decode 可能变成算力受限；量化到 INT4 后，原本带宽受限的 kernel 可能又撞上了别的墙。没有银弹，只有针对当前瓶颈的解法。

## 5. 延伸：两阶段对"网络"的要求也相反
单机内是算力 vs 带宽的矛盾；到了分布式集群（PD 分离、多卡并行），这对矛盾会复刻到**网络**上：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789979762431-bcbbca5f-a1e3-41b0-bd27-8576528f88cf.png)

+ **Prefill 侧**：TP 切分后每层都要 AllReduce 大矩阵，单次几百 MB，追求的是**吞吐量**。就像货运，一次拉一整车，晚到 10ms 无所谓。
+ **Decode 侧**：每个 token 都要跨卡同步一次，单次数据量小但频率极高，任何一次网络抖动都会直接反映成 ITL 的毛刺。就像高频交易，怕的不是总量，是**尾延迟（P99）**。

结论：没有一种网络策略能同时最优地服务两阶段。这也是为什么 PD 分离之后，Prefill 池和 Decode 池往往连网络拓扑、并行策略都分开设计——Prefill 池可以上大 TP，Decode 池优先小 TP + 大 DP，把同步开销压到最低。



# KV Cache 深度解析：原理与显存估算
---

## 1. 为什么需要 KV Cache：一个不能忍的浪费
回到 Decode 循环。假设模型已经生成了 100 个 token，现在要生成第 101 个。注意力的计算要求：新 token 要和**前面全部 100 个 token** 算相关性。

问题来了：第 1~100 个 token 的 Key 和 Value 向量，在生成前面那些 token 的时候**已经算过了**。而且它们不会变——因果注意力的掩码保证了每个 token 只能看过去，过去的表示不会被未来污染。

如果不缓存，每生成一个新 token，就要把整段历史重新过一遍 Transformer：

这就是 KV Cache 的全部本质：**用显存换时间，把 O(n²) 的重复计算变成 O(n) 的缓存查找。** 计算量降到原来的几百分之一——没有任何商量余地，所有推理框架默认开启。

在继续之前，先划定 KV Cache 的三个边界——很多误解都源于没搞清楚它们：

1. **它只服务于推理阶段**。训练时整段序列并行计算，K/V 算一次就够，没有"逐 token 复用"的场景，自然不需要缓存；
2. **它只存在于解码器（Decoder）中**。它优化的是逐 token 生成时的反复矩阵运算；BERT 这类 encoder-only 模型不做生成，没有 KV Cache 的概念；
3. **它加速的是 Q·Kᵀ 与加权求和 V 这两次矩阵相乘**——缓存的是中间结果，不是参数，也不是文本。

核心思想三步走：**缓存历史 token 的 Key 和 Value 向量 → 每步只计算当前 token 的 Q/K/V → 复用缓存的历史 K/V**。

## 2. 矩阵视角：缓存前后，每一步到底在算什么
文字概念不如直接看矩阵。下面两张图把"有无缓存"的差异画到了矩阵形状层面：

**没有缓存时**：每生成一个新 token，Q、K、V 矩阵都整体膨胀一行，然后整个矩阵乘重新算一遍。生成第 4 个 token 时矩阵是 4 行，生成第 1000 个就是 1000 行——越到后面每一步越贵。

### 一个最小生成案例："The cat sat on"
以 Transformer 模型为例，假设我们正在生成一段文本：

1. 初始输入为 "The cat"，模型生成下一个词 "sat"。
2. 在生成 "sat" 时，模型计算 "The" 和 "cat" 的 Key 和 Value 向量，并将它们缓存。
3. 当生成下一个词 "on" 时，模型只需要计算 "sat" 的 Key 和 Value 向量，而 "The" 和 "cat" 的 Key 和 Value 向量直接从缓存中。
4. 重复这一过程，直到生成完整的句子。

通过 KV Cache，模型避免了重复计算历史 token 的 Key 和 Value 向量，从而提高了推理效率。

## 3. 为什么缓存 K 和 V，不缓存 Q？
经典面试题，一句话版本：每一步的注意力是"新 token 的 Q 去查询所有历史的 K，再按相关性加权读出历史的 V"。历史 token 的 Q 只在它自己当"新人"的那一步用过一次，之后永不再用——缓存 Q 纯属浪费显存。

![](images/kv_cache_note_5.png)<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789818585894-20c0f335-7bf0-4093-96ca-428d7e3c0c36.png)

图解版更形象：**Q 是"一次性"的主动查询者**——每个新 token 都会产生自己的新 Q，用完即弃；**K/V 是"被查询"的历史档案**——静态不变、每轮都要参与计算，必须归档。一句话：Q 是临时查询员，K/V 是必须保存的历史资料。

## 4. 代价：显存被吃到什么程度
KV Cache 的显存占用公式（每个请求）：

```plain
KV Cache 字节数 = 2（K和V）× 层数 × KV头数 × 头维度 × 序列长度 × 每元素字节数
```

代入几个真实模型感受一下（BF16，2 字节）：

| 模型 | 层数 | KV头×头维 | 4K 上下文 | 32K 上下文 | 128K 上下文 |
| --- | --- | --- | --- | --- | --- |
| Qwen3-7B（GQA 4头） | 28 | 4×128 | ≈ 0.9 GB | ≈ 7 GB | ≈ 29 GB |
| LLaMA-7B 类（MHA 32头） | 32 | 32×128 | ≈ 4 GB | ≈ 34 GB | ≈ 137 GB |
| 某 96 层大模型 | 96 | — | — | — | ≈ 576 GB |


换算成经验数字：传统 MHA 模型大约 **0.7 MB / token**。一块 A100 80GB，光 KV Cache 的理论上限也就 11 万 token 左右——还是单请求。

再拉到业务视角：一个 70B 模型、8K 上下文、百万 DAU 的在线服务，高峰并发时 KV Cache 总量是 **几十 TB 的 HBM**。要知道 HBM 占一张 GPU 成本的 30~40%——**AI 推理的瓶颈早就不是算不动，而是存不下。**

### 长对话的隐忧：缓存线性增长与"遗忘"现象
<font style="color:rgb(13, 13, 13);">KV Cache通常用于存储模型在处理序列数据时生成的键值对，以便在生成后续内容时能够快速访问之前的信息。</font>

<font style="color:rgb(13, 13, 13);">在实际实验时，每次问答（QA）记录都会增加KV Cache的存储需求，因为模型需要保留之前问答的上下文信息以生成连贯的响应。这种线性增长的内存占用可能会导致在处理长对话或大量问答时，内存需求显著增加，从而影响系统的性能和效率。</font>

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789975511131-9368e1d2-66f4-4a80-9202-8bfbd8512bbc.png)

<font style="color:rgb(13, 13, 13);">由于内存限制，LLM的回复能力确实会随着问答的进行逐渐变差，这种现象可以理解为模型具备一定的"遗忘性"。具体而言，由于硬件资源的限制，KV Cache的大小是有限的。当缓存达到其容量上限时，旧的信息可能会被新的信息覆盖或丢弃。其表现为随着问答的进行，早期的对话内容可能会因为KV Cache的容量限制而被移除或覆盖，导致模型逐渐"遗忘"之前的上下文。由于模型无法访问完整的对话历史，其生成的回复可能会变得不够准确或连贯，尤其是在需要依赖早期信息的情况下。所以，在长对话或多轮问答中，模型的性能可能会显著下降，因为它无法有效地利用整个对话历史。</font>

**<font style="color:rgb(13, 13, 13);">简而言之，KV Cache是一种用内存换取推理速度的技巧。</font>**

一个来自实战的观察：多轮问答中，每一轮 QA 记录都会追加进 KV Cache，显存占用**随对话轮次线性增长**。撞上显存上限之后，旧信息只能被丢弃或换出——外在表现就是模型开始"遗忘"：聊得越久，越记不住开头说过什么，长对话后期回答质量明显下滑。这不是模型变笨了，是缓存被挤爆了。

## 6. 从"省显存"到"省钱"：前缀缓存与磁盘缓存
面对显存压力，除了"少存"，还有一条更划算的路——"存过的不重算"：**Prefix Caching（前缀缓存）**。

企业级场景里，大量请求共享同一个超长前缀：

+ 客服机器人：每个请求都带 5000 token 的系统提示词 + 产品手册；
+ Agent 应用：同一轮对话的每一步工具调用，前面整段历史都不变；
+ RAG 知识库：同一份检索结果服务多个相似问题。

这些相同前缀的 KV Cache 算一次、全员复用。命中时 TTFT 直接砍掉几百毫秒，Prefill 算力消耗归零。

DeepSeek 把这个做成了商业模式：**Context Caching on Disk**——不命中的输入 token 正常价，命中的打约 3 折（便宜约 96.8% 的说法源自早期价格，总之是数量级的差距）。它背后是磁盘级的 KV 存储 + MLA 压缩，把"缓存"从显存扩展到了硬盘。

对开发者的实操建议：**把不变的内容放在 Prompt 前面，会变的放后面。** 系统提示词、知识库文档往前堆，用户问题放最后——前缀命中率直接决定你的账单厚度。

## 7. 动手验证：看一眼真实的 KV Cache
用 HuggingFace transformers 跑 10 行代码，亲眼看看缓存长什么样：

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, DynamicCache

model_name = "Qwen/Qwen3-0.6B"   # 小模型方便本地跑，原理与大模型完全一致
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.bfloat16)

# DynamicCache 是 transformers 官方的 KV Cache 容器
past_kv = DynamicCache()
inputs = tokenizer("大模型推理的核心矛盾是", return_tensors="pt")

# 第一次前向 = Prefill：一次性处理全部输入 token，产出初始 KV Cache
with torch.no_grad():
    out = model(**inputs, past_key_values=past_kv, use_cache=True)

# 打印第 0 层 K 的形状：[batch, KV头数, 已缓存序列长度, 头维度]
k0 = past_kv.layers[0].keys
print(f"Prefill 后第0层K形状: {k0.shape}")
# 输出示例: torch.Size([1, 8, 11, 128])
#   1=batch  8=GQA的KV头数  11=输入token数  128=每个头的维度

# 模拟一步 Decode：只传入 1 个新 token
next_token = out.logits[:, -1, :].argmax(dim=-1, keepdim=True)
with torch.no_grad():
    out = model(input_ids=next_token, past_key_values=past_kv, use_cache=True)

print(f"Decode一步后第0层K形状: {past_kv.layers[0].keys.shape}")
# 输出: torch.Size([1, 8, 12, 128])  <- 序列维度 +1，只新增了这一条
```

注意看第三次打印：Decode 一步之后，缓存的形状只是在序列维度上 +1。模型没有重算前面 11 个 token 的任何东西——这就是 KV Cache 在代码里的样子。

## 1. 先看问题：朴素 Serving 的显存浪费有多离谱
假设你要在一台 8 卡 A100 上部署 DeepSeek 级别的服务，最朴素的做法是：给每个请求**预分配**一块连续的显存来放 KV Cache，大小按 `max_model_len`（比如 32K）算。

这会同时踩两个坑：

**坑一：过度预留（Over-reservation）**

**坑二：内存碎片（Fragmentation）**

![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789874644133-07d8a3ae-5acc-4e23-891c-512890d1d9b8.png)

### 算一笔账：预分配到底吞掉多少显存
光说"浪费"不够直观，拿一个 13B 级别的模型实际算一遍（上一章的显存公式这里正好派上用场）：

+ 模型规格：隐藏维度 5120、40 层、BF16 精度（每元素 2 字节），假设为每个请求按最大生成 2048 token 预分配；
+ **单个 token 的 KV Cache**：`2(K和V) × 5120 × 40层 × 2字节 ≈ 800 KB`；
+ **单个请求的预分配**：`800 KB × 2048 ≈ 1.6 GB`。

也就是说，请求还没开始生成，1.6GB 就没了。就算把整张卡的显存全拿来存 KV Cache，也只能同时容纳**几十条**请求——这就是为什么朴素 Serving 的并发天花板低得可怜。KV Cache 的体积随请求量线性膨胀，**高效管理 KV Cache、把每一 MB 显存榨干，是推理加速的关键战场之一**。

结果：一张卡理论能服务 50 个并发，实际只塞得下 10 个。钱花出去了，算力在睡觉。

### 前缀共享：COW 在推理里的样子
分页带来的隐藏福利是**跨请求共享**。10 个请求都带着同一段 5000 token 的系统提示词？它们的 Block Table 指向**同一批物理 Block**，引用计数 +1 即可。只有当某个请求要继续往共享 Block 里写新 token 时，才复制一份（Copy-on-Write）。

Beam Search 与并行采样同理：N 条候选路径共享同一段 prompt 历史（就像上面流程图最下方画的"一个 prompt 多个输出"），只在分叉处各存各的。论文实测共享场景能省下约 55~67% 的 KV 内存。

## 3. Continuous Batching：让 GPU 永远有活干
### 3.1：为什么需要批处理？
#### 3.1.1 背景回顾：prefill 与 decode 的瓶颈差异
一次 LLM 推理分为两个阶段：

| 阶段 | 计算形态 | 瓶颈类型 |
| --- | --- | --- |
| Prefill | 一次性并行处理整段 prompt，矩阵×矩阵 | 计算受限（Compute-bound） |
| Decode | 每步只处理 1 个新 token，矩阵×向量 | 带宽受限（Memory-bound） |


#### 3.1.2 关键概念：算术强度（Arithmetic Intensity）
**定义**：每从显存读取 1 字节数据，能完成多少次浮点运算。

+ 算术强度**高** → 计算受限 → 瓶颈在算力
+ 算术强度**低** → 带宽受限 → 瓶颈在显存带宽

Decode 是带宽受限的**极端情况**：

+ 模型权重达几 GB 到几十 GB，每一步原样读一遍
+ 这么大代价只产出**区区 1 个 token**
+ 结果：标称几百上千 TFLOPS 的 GPU，实际利用的算力只是零头

#### 3.1.3 批处理的动机：摊薄权重读取成本
> 既然每一步都要把整个模型读一遍，那就让这一步同时给多条请求算。
>

+ 权重读一次，几十条请求共用 → 算术强度随批大小成倍抬升
+ 显存带宽花同样的时间，产出 token 数量放大几十倍

### <font style="color:rgb(51, 51, 51);">3.2：静态批处理（Static Batching）—— 整批同进同出</font>
#### <font style="color:rgb(51, 51, 51);">3.2.1 工作方式</font>
<font style="color:rgb(51, 51, 51);">攒够一批请求 → 拼成大 batch 送进 GPU → 等</font>**<font style="color:rgb(51, 51, 51);">所有</font>**<font style="color:rgb(51, 51, 51);">请求生成完 → 整批返回 → 再收下一批。</font>

#### <font style="color:rgb(51, 51, 51);">3.2.2 短板效应</font>
<font style="color:rgb(51, 51, 51);">同一批请求的生成长度差异很大（如 20 token vs 500 token）：</font>

+ **<font style="color:rgb(51, 51, 51);">短请求陪跑</font>**<font style="color:rgb(51, 51, 51);">：生成完不能先走，占着批内位置直到最长那条结束</font>
+ **<font style="color:rgb(51, 51, 51);">算力空转</font>**<font style="color:rgb(51, 51, 51);">：陪跑期间 GPU 要么算无意义前向，要么塞 pad token 占位</font>
+ **<font style="color:rgb(51, 51, 51);">新请求排队</font>**<font style="color:rgb(51, 51, 51);">：已到达的请求必须等当前批彻底清空才能进</font>

```bash
时间轴示意（静态批处理）：

请求A |██████ 已完成|........... 陪跑空转 ...........|
请求B |████████ 已完成|......... 陪跑空转 ...........|
请求C |██████████████████████ 200步后才结束 █████████|
请求D |—————— 早已到达，门外排队等待 ——————|█████.....
```

**<font style="color:rgb(51, 51, 51);">批内长度差异越大，空转越严重。</font>**

#### <font style="color:rgb(51, 51, 51);">3.2.3 动手实验：用 Transformers 感受静态批处理</font>
<font style="color:rgb(51, 51, 51);">Hugging Face Transformers 的 </font>`<font style="color:rgb(51, 51, 51);background-color:rgb(243, 244, 244);">generate</font>`<font style="color:rgb(51, 51, 51);"> 接口天然就是静态批处理：</font>

```bash
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "Qwen/Qwen3-0.6B"
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, dtype="auto")

# 三条 prompt，预期输出长度差异很大
prompts = [
    "用一句话介绍杭州。",
    "写一首关于秋天的五言绝句。",
    "详细解释为什么天空是蓝色的，不少于三百字。",
]

# 套对话模板，Qwen3 关掉思考模式，让回答尽快收尾
texts = [
    tokenizer.apply_chat_template(
        [{"role": "user", "content": p}],
        tokenize=False,
        add_generation_prompt=True,
        enable_thinking=False,
    )
    for p in prompts
]

# 批式生成要左填充，保证每条序列的最后一个位置就是新 token 的位置
tokenizer.padding_side = "left"
if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token

inputs = tokenizer(texts, return_tensors="pt", padding=True).to(model.device)
prompt_len = inputs["input_ids"].shape[1]

outputs = model.generate(**inputs, max_new_tokens=512, do_sample=False)

for i, out in enumerate(outputs):
    new_tokens = out[prompt_len:]
    n = int((new_tokens != tokenizer.pad_token_id).sum())
    print(f"请求 {i}: 有效生成 {n} 个 token")
    print(tokenizer.decode(new_tokens, skip_special_tokens=True))
```

**实验观察**（实测）：

+ 三条请求分别有效生成 **23、18、290** 个 token，最长与最短相差十几倍
+ `generate` 必须等最长那条结束才返回
+ 短请求先撞上 EOS，后面的位置用 pad token 填满 —— 这些位置的每步前向都是白算的

**结论**：生产环境请求随到随走、量大，静态批处理的空转无法接受。

### 3.3：连续批处理（Continuous Batching）—— 以步为单位调度
#### 3.3.1 **核心思想**：
### 每跑完一步 decode，调度器重新决策一次。
+ 某请求生成 EOS 或达到长度上限 → **立刻移出**、返回结果
+ 等待队列有新请求且显存放得下 → **立刻补入**运行集
+ 批的组成每一步都在变，GPU 不需要等任何人

```plain
时间轴示意（连续批处理）：

请求A |██████ 第20步结束|
请求D                    |███ 第21步立刻顶上 A 的位置 ████|
请求B |██████████ 结束|
请求C |████████████████ 持续生成 ████████████████|
```

空转区域整个消失：每条请求实际生成时间没变，但同一台 GPU 单位时间内服务的请求变多了。

#### 3.3.2 调度器内部：两个队列
调度器维护：

+ **等待队列（waiting）**：已接收但还没开始计算的请求
+ **运行集（running）**：正在逐 token 生成的请求

每跑一步迭代，调度器做三件事：

1. **组批**：遍历运行集，给每条在跑的请求分配本步 KV 块和 token 预算；预算有富余再从等待队列按顺序取请求补入
2. **执行**：拼好的批送进 GPU 跑一步前向，每条请求各产出 1 个新 token
3. **结算**：检查新产出的 token，撞 EOS 或长度上限的标记完成、释放资源、推结果给客户端；空位下一步从等待队列补入

**调度策略**：默认 FCFS（先来先服务）；vLLM 支持优先级调度：

```bash
--scheduling-policy priority   # 数值越小的请求越先被处理
```

### 3.4：调度器调优 —— 吞吐与延迟的权衡
#### 3.4.1 两个关键参数（以 vLLM 为例）
| 参数 | 限制对象 | 含义 |
| --- | --- | --- |
| `max_num_seqs` | 批的**条数**上限 | 单步迭代最多同时跑多少条请求 |
| `max_num_batched_tokens` | 批的 **token 总量**上限 | 单步迭代最多处理多少个 token（所有请求合计） |


启动示例：

```bash
$ vllm serve Qwen/Qwen3-0.6B \
    --max-num-seqs 256 \
    --max-num-batched-tokens 8192
```

#### 3.4.2 调大参数的影响
`max_num_seqs`** 调大**：

+ ✅ 吞吐更高，权重读取摊得更薄
+ ❌ 单请求延迟更差：单步更慢、排队更久

`max_num_batched_tokens`** 调大**：

+ ✅ 吞吐更高，长 prompt 的 prefill 更快完成，TTFT 变好
+ ❌ decode 的 token 间隔（ITL/TBT）可能变差

#### 3.4.3 核心权衡：吞吐与延迟不可兼得
+ 批越大 → 每步算的 token 越多 → 单步耗时越长 → token 间隔越差；请求多了要排队 → TTFT 也变长
+ 批越小 → 越接近单请求延迟水平 → 但吞吐回落

**调优目标**：不是把批开到最大，而是在 **SLO（Service Level Objective，服务水平目标）** 允许的范围内把吞吐做高。

> SLO 示例：TTFT ≤ 2 秒、token 间隔 ≤ 100 毫秒。批的大小以不越过这条线为限。
>

# PD 分离与并行推理架构：从单机到分布式推理集群
> 当一张卡装不下野心，问题就从"显存管理"升级为"系统架构"。这篇讲两件事：为什么 Prefill 和 Decode 要拆开跑（PD 分离），以及大模型在多卡多机之间到底怎么切（TP/PP/EP/DP + 投机解码）。
>

---

## 1. PD 分离：一对性格不合的室友
回顾前两篇的结论：

+ **Prefill**：计算密集，吃算力，耗时和输入长度强相关；
+ **Decode**：访存密集，怕延迟、怕抖动，对 ITL 极其敏感。

把这两个绑在同一批 GPU 上混跑，会发生什么？

**长 Prompt 阻塞流式输出。** 一个用户扔了篇 3 万字的文档进来，Prefill 要跑好几秒；这几秒里同卡上所有正在 Decode 的请求集体卡顿——那边正在给付费用户流式输出呢，ITL 突然飙升，P99 直接爆炸。就算有 Chunked Prefill 缓解，两阶段的资源诉求依然互相干扰：给 Prefill 配的机器对 Decode 是浪费，反之亦然。

PD 分离（Prefill-Decode Disaggregation）的答案很直接：**性格不合就分居。**

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789975947994-8a8b6198-aa44-4ccb-88a2-afa904c593c5.png)

拆开之后各自美丽：

+ **独立扩容**：大促期间长文档总结需求暴涨？只加 Prefill 节点。对话并发暴涨？只加 Decode 节点。资源利用率不再有结构性浪费。
+ **独立优化**：Prefill 池可以用激进的 TP=8 追求单请求速度；Decode 池用 TP=2 + DP 拉满并发。
+ **指标解耦**：TTFT 由 Prefill 池的排队深度决定，TPOT 由 Decode 池的负载决定，容量规划第一次变得可计算。

## 2. PD 分离的代价：KV Cache 要"搬家"
分居不是免费的。Prefill 算出来的 KV Cache 必须完整、快速地送到 Decode 节点，而它可能大得吓人：128K 上下文的大模型，单个请求的 KV 就有**几十 GB**。

这就是 PD 分离的核心工程难点：

+ **传输介质是硬门槛**：普通 TCP 网络直接出局，必须上 RDMA（InfiniBand/RoCE）或 NVLink 域内互传，否则省下来的 GPU 时间全赔进网络里。
+ **传输必须异步分块**：等整个 KV 传完再开始 Decode，TTFT 会劣化。工程上是 chunk 级流水线——Prefill 边算边传，Decode 边收边跑（vLLM 的 `kv_transfer` connector、Mooncake 的传输引擎都是这个思路）。
+ **调度要算总账**：路由层选择 Prefill 节点时，不仅要看谁闲，还要看它和 Decode 节点之间的链路状况。推理系统越来越像一个**以 KV Cache 为中心的分布式缓存调度系统**。

## 3. 一个实例：5 万字论文生成任务的时序解剖
用一个具体任务把全流程串起来：用户输入 50 个 token——"帮我写一篇关于新能源产业的 5 万字研究报告"，要求带深度思考（Reasoning）并能联网检索。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789976209809-5e648601-e93b-4628-bcce-6d16a73b2d00.png)

几个容易被忽略的认知点：

1. **首 token 不一定是可见字符**。Reasoning 模型的第一个 token 可能是思考链的开始标记，用户看到的"思考中"动画背后，Decode 早就在跑了。
2. **联网搜索会触发新的 Prefill**。检索回来的几千 token 内容要走一遍（Chunked）Prefill 生成增量 KV——所以 Agent 类任务会在 P/D 之间反复横跳。
3. **这种任务 99% 的时间花在 Decode 实例上**。50 token 输入换 5 万字输出，Prefill 池几乎没压力，Decode 池才是扩容重点。反之，"传一本书进去只问一句话"的文档问答场景，压力全在 Prefill 侧。

**容量规划的第一课：先分析业务的输入/输出 token 比例，再决定 P/D 池的配比。** 客服问答（长输入短输出）和创意写作（短输入长输出）需要的集群形态完全不同。

## 4. KV Offloading：显存不够，内存/磁盘来凑
PD 分离把 KV 的管理显式化之后，一个自然的延伸是 **KV 分级存储**：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789976311396-1db88fd1-1be2-4164-93d2-89d7b5d5faec.png)

典型玩法：

+ 被抢占的请求，KV 换出到 CPU 内存，恢复时换回，比重算便宜；
+ DeepSeek 的 Context Caching on Disk 把共享前缀的 KV 持久化到磁盘，跨请求甚至跨会话命中；
+ Mooncake 把集群里所有空闲内存/磁盘组织成分布式 KV 池，缓存成为一等公民。

代价是延迟：HBM 是微秒级，CPU 内存是百微秒级，NVMe 是百微秒到毫秒级。**用延迟换容量，用容量换免重算**——又是一笔要算总账的买卖。
