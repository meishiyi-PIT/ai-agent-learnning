# 大模型架构之争 —— Decoder-Only
## 一、先回到原点：Transformer 的左手和右手
2017 年的Transformer 是个标准的序列到序列（Seq2Seq）结构，左半边编码器（Encoder），右半边解码器（Decoder），各司其职。

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789894381351-0751c9b5-6703-49f8-a0c5-e1401a949913.png)

两个组件的核心差异就两点：

| 维度 | 编码器 | 解码器 |
| --- | --- | --- |
| **职责** | 把输入序列压缩成连续的语义表示 | 结合编码器输出和已生成内容，自回归地产出序列 |
| **注意力** | 双向自注意力，每个位置能看到全部上下文 | 因果掩码自注意力（只能看左边）+ 交叉注意力（看编码器输出） |


打个比方：编码器像一个阅卷老师，可以把整篇作文通读一遍再打分；解码器像考场上写作文的学生，写到第 N 个字的时候只能回头看自己写过的内容，没法预知后面要写什么。

后来的故事大家都知道了：三大架构路线，本质上就是对这个结构做"截肢手术"——只留左手、左右都留、只留右手。

## 二、技术路线
### 2.1 Encoder-Only：BERT 的完形填空
**代表模型**：BERT 及其衍生家族

**预训练任务**：自编码（Auto-Encoding）。先把句子故意弄坏——随机挖掉一些词换成 `[MASK]`，再让模型把挖掉的词猜回来。另外还配了个"下一句话预测"（NSP）的辅助任务，判断两句话在原文里是不是挨着的。

这个任务设计和 Transformer 编码器简直是天作之合：既然是猜被遮住的词，当然要把上下文都看清楚——双向注意力正好干这个。

**适合干什么**：理解类任务。文本分类、情感分析、命名实体识别、阅读理解……反正不需要"写"，只需要"懂"。

**短板也很明显**：

+ **天生不会生成**。预训练就是猜词，你让它写文章，它没学过这门手艺
+ **上下文窗口小**。输入一般卡在 512 token，长文档只能切断了喂，上下文信息白白丢掉
+ **微调依赖重**。下游任务和预训练语料领域不匹配时，得老老实实准备标注数据微调
+ **多任务适应性差**。换个任务就要微调一版，想要一个模型通吃？难

### 2.2 Decoder-Only：GPT 开的头，国产模型接的棒
**代表模型**：GPT 系列起头，如今是 DeepSeek-V3/R1、Qwen3、GLM-4（Decoder 路线）、Kimi 的天下

**预训练任务**：自回归语言建模——给定前面 n 个 token，预测下一个。说白了就是你的手机输入法：你打"今天天气"，它猜"不错"。只不过大模型把这件事做到了极致。

**结构**：就是把 Transformer 解码器里的交叉注意力砍掉，留下带因果掩码的自注意力 + 前馈网络，堆几十上百层。

GPT 系列的两个历史贡献：

1. **验证了"预训练 + 微调"范式**：先在无标注语料上做生成式预训练，再用少量监督数据适配下游任务，当年 12 个任务里 9 个拿到 SOTA
2. **统一任务输入格式**：不管是分类、问答还是蕴含，统统拼成一段连续文本序列喂进去。从此不再需要为每个任务单独设计模型结构——这个"万物皆序列"的思想，是后来 prompt 时代的地基

## 三、为什么 Decoder-Only 赢了
如果只看 2.1 和 2.2，三条路线本该各占一块地盘相安无事。但现实是 Decoder-Only 通吃了。原因分理论层和工程层两面看。

### 3.1 理论层面
**① 注意力矩阵满秩，表达上限更高**

Decoder-Only 的因果注意力矩阵是严格下三角带对角线的形式，数学上保证满秩；双向注意力在训练中有退化成低秩状态的风险。秩满意味着状态空间没被压缩，理论上能建模更复杂的函数。

**② 任务越难，逼出来的表征越强**

Next-token prediction 每个位置只能看左边，信息最少、预测难度最大。模型规模和数据量堆上去之后，"困难任务 + 大数据"反而逼出了更强的通用表征——有点"穷养的孩子早当家"的意思。

**③ In-Context Learning 的天然亲和**

Prompt 和 few-shot 示例可以被看作对模型的"隐式微调"。Decoder-Only 里 prompt 的信息直接贯穿每一层，信号传递路径最短；Encoder-Decoder 两段式结构里，prompt 要先过编码器再过交叉注意力，效果打折扣。这就是 Decoder-Only 的 few-shot/zero-shot 泛化能力明显更强的原因。

**④ 兼顾理解与生成的涌现能力**

参数量不大时，Decoder-Only 的 zero-shot 性能就领先；规模上去、涌现能力出现之后，甚至能匹敌 Encoder-Decoder 专门微调的效果。一个模型包打天下，谁还愿意维护两套？

**⑤ 隐式位置编码与外推便利**

Decoder-Only 把输入输出当成一条连续序列，只依赖相对位置关系。想扩展上下文窗口？RoPE 插值、LongRoPE 之类的技术微调一下就行。Encoder-Decoder 要处理两套位置系统的兼容，麻烦得多。

### 3.2 工程层面
**① KV-Cache 友好，多轮对话的绝配**

因果注意力保证每个 token 的表示只依赖它之前的内容，KV-Cache 可以一路复用到底。vLLM 的 PagedAttention、FlashAttention、Megatron-LM 这些底层优化，全都优先围着因果路径转。Encoder-Decoder 和 PrefixLM 想蹭这个红利？结构上就吃亏。

**② Scale Up 成本最低**

Scaling Laws 的实践中，相同参数量下训练效率排序：

```plain
Decoder-Only > Encoder-Only > Encoder-Decoder
```

在现有分布式并行策略下，可扩展的参数量上限和集群规模上限也是同样的排序。对于烧钱的大模型训练，这不是小优势，是生死线。

**③ 生态滚雪球**

MoE、量化、蒸馏、投机采样……这些提效技术在单一解码器结构上实现起来最顺滑，于是新优化优先支持 Decoder-Only，Decoder-Only 因此更强，强者愈强。

**④ 多模态的"早融合"最优解**

如今主流多模态方案（GPT-4o、Qwen-VL 系列等）都是把图像/音频切成 token 直接拼进文本序列，交给同一个解码器处理。结构上不用动手术，工程上最省事。

**⑤ 轨迹依赖：历史的车轮**

说句大实话：OpenAI 先验证了这条路的训练方法和 Scaling Law，后来者面对时间和算力成本，没人愿意在结构上豪赌。于是大家继续沿用 Decoder-Only，把精力花在 MoE、长上下文、多模态这些收益更确定的迭代上。DeepSeek-V3/R1 就是在 Decoder-Only 骨架上把 MoE 和推理能力做到极致的典型。

## 四、一张表收尾
| 维度 | Encoder-Only | Encoder-Decoder | Decoder-Only |
| --- | --- | --- | --- |
| 代表模型 | BERT | T5、GLM | GPT 系列、DeepSeek、Qwen3 |
| 预训练任务 | 掩码重建（完形填空） | 序列到序列映射 | 下一词预测（接龙） |
| 注意力 | 双向 | 双向 + 因果 + 交叉 | 因果掩码 |
| 擅长 | 理解（分类、NER、抽取） | 翻译、摘要、多模态编码 | 生成 + 理解通吃 |
| KV-Cache | 不适用 | 部分可用 | 完美复用 |
| Scale Up 效率 | 中 | 低 | 高 |
| 当今地位 | 退居垂直场景 | 少数派 | 绝对主流 |

## 一、大模型不是"写"出来的，是"训"出来的
传统软件的逻辑是程序员一条条敲死的：输入 A，执行 B，返回 C。

大模型完全是另一个物种。它的"智能"不存在于任何一行代码里，而是沉淀在几十亿个参数中。训练前这些参数基本是随机数，训练后，语法、常识、代码模式、推理套路全都压缩进了这个参数空间。

所以记住第一句话：

> 大模型的聪明不来自规则库，而来自**数据 × 架构 × 训练目标 × 算力**共同捏出来的参数空间。
>

后面所有阶段，本质上都是在给这块"毛坯参数"做不同精度的雕刻。

这套机制还带来一个巨大的工程红利——**迁移学习**：不必为每个新任务从零训练，拿预训练好的参数（包括底层的词嵌入）当起点，在新任务上继续训就行。省下的不只是算力，更是让"小团队玩大模型"这件事成立的前提。

## 二、第 0 步：数据要先把人话翻译成数字
模型不识字。它眼里只有 Token ID 和向量。

一句话进来，流程是这样的：

![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789895401174-2e4d9f2a-5410-4153-b7c1-4abb4f6fd693.png)

+ **Token 是入口**：分词器（BPE 是主流）把文本切成碎片单元
+ **Embedding 是翻译器**：一层可学习的查找表，把 ID 变成低维稠密向量
+ **Transformer 是加工厂**：后面专门讲

### 🔧 MiniMind 实战：6400 词表的"抠门"哲学
MiniMind 自己训了一个 BPE + ByteLevel 分词器，词表只有 **6400**——对比 Qwen2 的 151643、Llama3 的 128000，砍了两个数量级。好处很实际：embedding 层参数占比暴降，64M 的小身板才能把更多参数留给真正的计算层。

它还预置了 `<tool_call>`、`<tool_response>`、`<think>` 这类特殊标记——这暗示了一个 2025 年后的行业共识：**工具调用和思考链已经不是后加的补丁，而是从分词器层面就要规划的基建**。

> 注意：官方不建议重训 tokenizer，词表一变，权重和生态兼容性全废。
>

## 三、阶段一：预训练 —— 让模型成为"通才"
<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789896095270-2cb3d144-7c27-4790-abd3-d04ee98f8b7d.png)

### 原理：文字接龙，接出整个世界
预训练的任务简单到令人发指：**给定上文，预测下一个 Token**。

"人工智能正在改变" → 下一个词是"世界"？"生产力"？"软件开发"？

但这个简单目标藏着巨大的杠杆：想把下一个词猜准，模型被迫学会语法、事实、常识、逻辑、代码结构、数学表达……**表面是接龙，实质是压缩人类知识**。翻译、摘要、问答这些能力，全是这个过程中"涌现"出来的副产品。

预训练练的不只是记忆，更是**表示能力和模式抽象能力**——问题和答案怎么对应、论证怎么展开、推导怎么分步。这一阶段最贵、最决定上限，练完的是一块"能力底座"。<font style="color:rgba(0, 0, 0, 0.9);">预训练阶段结束后，模型已经具备很强的语言能力和世界知识。</font>

### 🔧 MiniMind 实战：
```bash
# 进入训练脚本目录（所有训练操作都在 trainer/ 下执行）
cd trainer

# 单卡跑预训练，--from_resume 1 表示支持断点续训
# 训练数据读取 ./dataset/pretrain_t2t_mini.jsonl（1.2GB，格式为 {"text": "..."}）
python train_pretrain.py

# 多卡版本：torchrun 启动 DDP 分布式训练，N 为卡数
torchrun --nproc_per_node 2 train_pretrain.py
```

产出 `out/pretrain_768.pth`。

### 为什么预训练模型还不能直接上岗
此刻的模型更像一台"互联网腔模仿器"。你问它"解释一下 RAG"，它的反应是开盲盒：

+ 可能正经回答，也可能继续模仿网页往下续写
+ 输出格式飘忽不定，这次三段式下次一大坨
+ 可能说着说着就跑题，扯出一堆无关内容
+ 完全没有安全边界的概念，什么都敢接

根因一句话：**它学的是语言分布，不是用户意图**。知道很多，但不听话；能生成，但不一定有帮助；会续写，但不知道什么时候该拒绝、该澄清、该给结构化答案。

预训练解决的是"能力底座"，"可用性"这堂课要留给后训练来上。

## 四、阶段二：后训练 —— 从"会说"到"好用"
<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789896506733-b4669224-18b0-4524-8e6a-acd091b11d73.png)

后训练（Post-training）不是单一技术，而是一整套把"续写机器"改造成"可靠助手"的流程。先给个工具箱清单：

+ **SFT**（监督微调）：教模型听懂指令
+ **RLHF**（人类反馈强化学习）：教模型符合人类偏好
+ **RLAIF**（AI 反馈强化学习）：用 AI 代替人做标注，降成本
+ **DPO**（直接偏好优化）：RLHF 的简化平替
+ **安全对齐训练**：教模型守住边界
+ **工具使用训练**：教模型调用外部工具
+ **推理过程训练**：教模型"先想后答"

一句话总目标：**让模型从"预测下一个 Token"变成"按照人类意图完成任务"**。逐个拆。

### 5.1 SFT：先给模型看"标准答案"
监督微调（Supervised Fine-Tuning）的做法很朴素：准备大量"用户指令 → 高质量回答"的样本对，让模型学**面对指令应该怎么回**。

像老师给学生讲例题：预训练阶段模型读的是整个互联网（什么腔调都有），SFT 阶段它只看优秀答卷。练完，模型从"语言模型"进化成"助手模型"。

```bash
# 全参数 SFT，数据为 ./dataset/sft_t2t_mini.jsonl
# 多轮 conversations 格式，且已混入 Tool Call 数据（<tool_call> 标记在此学会使用）
python train_full_sft.py

# 训完立刻测试对话效果
python eval_llm.py --weight full_sft
```

### 5.2 RLHF：教模型"人类更喜欢哪种回答"
SFT 解决"会答"，但很多开放问题没有标准答案。比如"分析一下 DeepSeek 为什么能在推理模型上快速追平国际头部"——可以答得空泛，也可以答得深刻；可以结构清晰，也可以废话连篇；可以事实准确，也可以逻辑混乱。**没有唯一正确答案，但有明显的好坏之分**。这时要靠**偏好学习**。

经典 RLHF 四步：

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/21571931/1789897487469-afc50cdd-1dcc-48a1-b457-bc91a026c604.png)

RLHF 教的不是知识，是**品味**：更有帮助、更诚实、更安全、结构更清晰、更少胡说、更少危险建议。走完这一步，模型从"能回答"进化成"回答得像个可靠助手"。

### 5.3 DPO：把 RLHF 的麻烦事省了
RLHF 强是强，但要养一个奖励模型 + 跑强化学习，工程复杂度和显存开销都不小。DPO（直接偏好优化）的思路是：**不训奖励模型了，直接拿"好回答/坏回答"的偏好对来优化模型**——同一个问题，让模型向 A 靠拢、离 B 远点。流程短、稳定性好，是如今 SFT + DPO 组合流行的原因。

```bash
# DPO 训练：数据 dpo.jsonl 为 {"chosen": [...], "rejected": [...]} 格式
# Off-Policy，无需奖励模型，显存友好
python train_dpo.py
```

### 5.4 PPO / GRPO / CISPO：真刀真枪的强化学习
想体验完整的在线强化学习，MiniMind 也备齐了（默认奖励模型用国产的 InternLM2-1.8B-Reward）：

```bash
# PPO：Actor-Critic 双网络，显存约为普通训练的 1.5~2 倍，效果稳但贵
python train_ppo.py

# GRPO：单网络，组内归一化优势估计，DeepSeek-R1 带火的方案，性价比高
python train_grpo.py

# CISPO：在 GRPO 脚本里把 loss_type 改为 'cispo' 即可
# 通过裁剪权重乘 log 概率，避免梯度被直接截断，训练更稳定
python train_grpo.py --loss_type cispo
```

### 5.5 安全对齐与推理训练
+ **安全对齐**：Agent 时代模型能调工具、操作文件、查数据库，说错话是小事，**做错事是大事**。什么时候该拒绝、该澄清、该给替代方案，都是后训练刻意塑造的，预训练里长不出来
+ **推理能力训练**：DeepSeek-R1 之后，"先想后答"成了标配。训练配方通常是高质量数学/代码/逻辑题 + 多步思维链数据 + 验证器反馈 + 自我反思数据，再配上强化学习和**过程监督**——不只判最终答案对错，还要看每一步推导是否成立：数学题盯着推导链条，代码题盯着能不能跑过测试。模型由此学会拆问题、定计划、逐步求解再下结论，而不是张口就来。本质上，这是后训练从"回答质量优化"走向"任务求解能力优化"。MiniMind 的 `<think>` 标记和 `open_thinking` 开关，就是这套思路的最小实现

## 五、阶段三：微调 —— 从"通用助手"到"行业专才"
### 原理：先想清楚要不要微调
微调和后训练常被混淆，一句话区分：**后训练让模型"像助手"，微调让模型"像你的助手"**。前者是模型厂商把基础模型变成通用助手（指令遵循、偏好优化、安全对齐），后者是企业或开发者把它按进具体场景（行业知识、任务格式、专用风格）。

举个具体的例子感受差异：一个基础模型预训练后会写中文；后训练后它会按你的要求写文章；而微调后，它能学会**你的**写法——标题怎么起、开头怎么抓人、段落怎么推进、结尾怎么收。一个是"通用可用"，一个是"场景可用"。

更要紧的判断是**什么时候不需要微调**：

| 需求 | 该用什么 |
| --- | --- |
| 固定输出格式、引用外部知识、简单风格模仿 | Prompt / RAG 就够了，别急着微调 |
| 长期无法稳定遵循复杂格式、强领域术语、风格高度一致、要砍掉超长 Prompt 的延迟成本 | 微调，而且多半 LoRA 就够 |


判断标准不是"微调听起来更高级"，而是：**这个能力能不能用 Prompt 和 RAG 稳定解决？能，就别微调；不能，再考虑。**

### 微调的三档火力
| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **全量微调** | 更新模型大量乃至全部参数 | 适配能力最强 | 成本高、显存大，容易把原模型能力"训丢" |
| **参数高效微调（PEFT）** | 冻结原参数，只训少量新增参数 | 成本骤降 | 适配深度略逊 |
| **LoRA**（PEFT 主流） | 在部分权重旁挂低秩矩阵，只训它 | 成本低、显存省、多任务可存多个 LoRA 权重热插拔 | 不是万能，但性价比最好 |


**LoRA 的核心思想**：不动原模型参数，在部分权重旁挂一个低秩矩阵，只训这点新增参数。同家族还有 Adapter、Prefix Tuning 等，思路相近。大模型时代，全量微调对普通团队基本不友好，LoRA 是默认起手式。

### 🔧 MiniMind 实战：手写版 LoRA
```bash
# 准备垂域数据 lora_xxx.jsonl（比如医疗问答、自我认知数据）放到 dataset/
# train_lora.py 为纯手写实现，不依赖 peft 库，适合读源码学原理
python train_lora.py

# 训完把 LoRA 权重合并回基础模型，导出标准格式方便部署
python scripts/convert_model.py convert_merge_base_lora
```

另外还有**知识蒸馏**可选：黑盒蒸馏 ≈ 拿 DeepSeek-R1 / Qwen3 的输出当 SFT 数据；白盒蒸馏用 `train_distillation.py`，CE + KL 混合损失拟合教师分布——小模型快速"偷师"的常规操作。

## 六、阶段四：推理 —— 模型真正开始上班
### 原理：每一次回答都是一场受控的采样
推理的基本循环：Prompt → Token → 逐个预测下一个 Token → 拼回上下文 → 直到结束。看似在"思考"，底层是一次次概率采样。而采样是可以调的：

| 参数 | 作用 | 经验 |
| --- | --- | --- |
| temperature | 控制发散度 | 写代码/问答调低（0~0.3），写故事调高（0.8+） |
| top_p / top_k | 截断采样范围 | 防止低概率烂词混入、避免陷入复读循环 |
| max_tokens / stop | 控制长度与终止 | 省钱、防爆 |
| frequency / presence penalty | 惩罚重复 | 长文生成时防车轱辘话 |


同一个问题问两次答案不同？不是模型善变，是采样在掷骰子。还有个经典翻车案例：早期模型放开自由生成时容易陷入复读循环，一个词刷到底——top-k 采样（只从概率前 k 的候选里挑）就是当年治这个病的药方之一。

### 推理增强：从"一问一答"到"多步干活"
2026 年的推理也早已不是"输入问题、输出答案"。Agent 场景下，一次请求是一条完整的工作流。比如你说"帮我看看这个项目最近为什么老报错，给个修复建议"，一个合格的 Agent 会：

拆任务、检索、调工具、读结果、修正计划、继续执行——每一步背后都是一次推理。所以未来模型推理的竞争，不只是单次回答质量，而是**长任务执行能力**：模型不光要会说，还要会查、会想、会试、会改、会验证。**推理系统本身就是应用工程的核心战场**。

## 七、为什么大模型训练越来越像"系统工程"
早期做模型，大家比的是算法。今天训大模型，算法只是入场券，真正拉开差距的是一整条工业流水线：

| 环节 | 要操心的事 |
| --- | --- |
| 数据工程 | 清洗、去重、过滤、配比、版权、质量评估 |
| 模型架构 | Transformer、MoE、长上下文、多模态结构 |
| 训练框架 | 分布式训练、并行策略、混合精度、显存优化 |
| 算力集群 | GPU、网络、存储、调度、容错 |
| 后训练流程 | SFT、RLHF、DPO、安全对齐、推理增强 |
| 评测体系 | 知识、数学、代码、推理、安全、长上下文、工具调用 |
| 推理部署 | 量化、KV Cache、批处理、路由、延迟、成本控制 |


所以别再幻想"一个天才算法颠覆一切"的剧本了。**真正强的模型公司，强的是完整工程体系**——数据、模型、算力、工程、产品一起优化出来的结果。

## 八、开源和闭源的差距到底在哪
以 DeepSeek、Qwen 为代表的开源阵营越来越强，但闭源模型仍有壁垒。差距通常不在参数规模，而在这些"看不见的地方"：

+ 数据质量和训练稳定性
+ 后训练数据与偏好优化的精细度
+ 安全对齐的成熟度
+ 推理优化、多模态数据、工具使用数据
+ 长任务评测和**产品反馈闭环**

很多时候基础模型分数差距不大，但后训练和产品反馈会拉开体验差距——这也解释了为什么有些模型 benchmark 漂亮，真用起来却别扭。模型能力不能只看"考试分数"，还要看：**听不听指令、稳不稳定、少不少幻觉、会不会澄清、会不会用工具、能不能执行长任务**。这些多半来自后训练和推理系统，而不是预训练。

## 九、开发者最该关注的四件事
绝大多数人不需要从零训模型，但这四件事值得投入：

1. **理解模型能力边界**——知道哪些能力模型自带，哪些要靠 RAG、Tool Calling 或微调补
2. **构建高质量上下文**——模型输入什么决定输出什么；系统提示词、历史对话、检索结果、工具返回，全是上下文工程
3. **设计工具和工作流**——Agent 的核心不是 Prompt，而是模型 + 工具 + 记忆 + 协议 + 权限的组合
4. **学会评测**——别凭"看起来答得不错"下结论；搭测试集，量化准确率、稳定性、成本、延迟、安全性

未来 AI 应用开发，不是调一个 API 就完事，而是**围绕模型构建一个可靠系统**。

## 十、收尾：不是魔法，是新型工业流程
大模型看着像魔法：一句话进去，文章、代码、分析、解题、调工具全出来了。拆开看却并不神秘——

+ **预训练**：从海量数据里学语言和世界规律（通识教育）
+ **后训练**：学会按人类偏好和安全边界作答（职业素养）
+ **微调**：适配具体行业、任务和风格（岗位培训）
+ **推理**：结合上下文、工具、记忆在真实场景干活（正式上岗）

四者层层递进，缺一不可：没预训练没底座，没后训练不好用，没微调不专业，没高质量推理系统，能力释放不出来。
