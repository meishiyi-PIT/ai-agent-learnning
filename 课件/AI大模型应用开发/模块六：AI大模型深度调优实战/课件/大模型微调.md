## QLoRA：基座怎么存、谁被量化（2026-09-28 学《2.低精度训练与量化》第 4 章时的讨论总结）

### 一张最简单的图（五句话）

1. 一个模型就是一大堆数（权重），训练前躺在磁盘文件里。
2. 加载 = 把这些数搬进显存。搬的时候可以选每个数占多大地方：4 字节（FP32）、2 字节（BF16）、半字节（4bit）。占得越小越省显存，数越糙。
3. QLoRA 把**基座**用半字节（4bit）搬进去。基座 = 预训练模型自带的全部权重（每一层的 W）。它在训练中不改动，糙一点无所谓。这一份在显存里从头待到尾。
4. 显卡不会直接算半字节的数。做乘法时把用到的那一小块临时还原成 2 字节（BF16）算一下，算完扔掉，显存里留着的还是半字节那份。**这一步只发生在 W 上。**
5. 真正被训练的 A、B 很小，用正常精度存（FP32），正常算梯度、正常更新，和上周 LoRA 训练里一模一样。

### 三种微调，基座各怎么搬进显存

```
全量微调   基座 FP32 主副本存着（要被更新）+ BF16 副本算   → 每个参数 16 字节那笔账，7B 约 160 GB
LoRA       基座 BF16 存着（不更新，2 字节够用）            → lora_train_fixed.py 的 torch_dtype=bfloat16，4090 上实测 19–21 GB
QLoRA      基座 4bit 存着（不更新，半字节也够用）          → USE_4BIT=1 那个分支，约 10–12 GB
```

### 一条原则，把第 2 章混合精度和 QLoRA 串起来

**谁会被更新，谁就得用细精度（FP32）存；不被更新的，存多糙都行。计算这一步永远是 BF16。**

- 全量微调：所有参数都被更新 → 全都 FP32 存。
- LoRA / QLoRA：基座不被更新 → BF16 甚至 4bit 存；被更新的只有 A、B → 按混合精度规矩 FP32 存。
- 第 2 章说的"FP32 存、BF16 算"指的是**被更新的**权重，不是所有权重。

### 对着公式看每一项谁在哪

```
h = W·x  +  B·(A·x)
    ↑          ↑
 W：4bit 常驻，乘之前临时解压成 BF16，乘完丢        A、B：FP32 常驻，乘之前转 BF16（普通混合精度）
```

三份东西分开叫：磁盘上的原始权重（BF16，Qwen/DeepSeek 发布格式）→ 显存里的常驻版（4bit，加载时压出来）→ 算的时候的临时版（BF16，每步解压、用完丢）。
"默认 FP32"是 `from_pretrained` 不指定精度时的加载行为（把 BF16 升成 FP32 放，白占一倍），不是磁盘上的格式。
4bit 不是"FP32 ÷ 8"算出来的：先定好只用 4 个比特、16 个刻度，再把每个权重重新编码成 0–15 的一个编号，旁边配一个块级 scale（编号怎么定见 4.2/4.3 NF4）。
权重 = 模型里那一大堆数本身（h = W·x 里的 W，一张数字表；BERT 一层 query 权重就是 768×768 = 589,824 个数）；"参数"= 权重 + 偏置，偏置极少，日常当同一个词。

### 为什么 24 GB 卡放得下 14 GB 的 BF16 权重，还要用 4bit

训练显存 = 权重 + 激活值 + 优化器状态 + 碎片，不只是权重那一笔。

```
BF16 LoRA   权重 14 + 激活约 5 + 其他约 1.5  ≈ 20 GB   贴着 24 GB 上限，batch 只能 2
4bit QLoRA  权重  5 + 激活约 5 + 其他约 1.5  ≈ 11 GB   余量 13 GB：batch 开大、序列拉长、16 GB 卡也能跑、24 GB 卡能上 13B
```

QLoRA 里被量化的部分本质上是在"训练里跑推理"：基座只读不写，角色和推理时一样，所以能用推理级的 4bit 存；第 3 章"INT8 不能训练"的问题（小梯度被等距刻度归零）碰不到它，因为它没有梯度、不更新。
课件开头写 QLoRA"压缩模型权重和梯度"，后半句不对：只压冻结的基座权重，梯度只流向 A、B，不量化。

### 要记

- 基座 = 预训练模型全部权重；LoRA/QLoRA 冻结它，只训旁路的 A、B
- 谁被更新谁细存（FP32），不被更新的可以粗存（BF16 / 4bit）；计算永远 BF16
- W：4bit 存、用时临时解压 BF16、用完丢；A、B：FP32 存、BF16 算、正常更新
- 训练显存 = 权重 + 激活 + 优化器 + 碎片；BF16 LoRA 在 24 GB 上贴上限，4bit 才有余量

### 追问：NF4 里的"块"是什么、用来做什么、怎么分的？（4.3–4.4）

- **是什么**：权重表先按行拉直成一条长队，从头每 64 个数切一段，一段就是一块。纯按位置切，不排序、不看大小，第 i 个数属于第 i÷64 块。BERT 一张 768×768 的表 = 589,824 个数 = 9,216 块；7B 的线性层 65 亿个数 ≈ 1.1 亿块。
- **用来做什么**：每块各自取最大绝对值 absmax，块内的数除以它归一化到 [-1, 1]，再就近对到 NF4 的 16 值表上，只存索引（4 bit）。块切小了，离群值只祸害同块的 63 个邻居，不污染整张表。
- **为什么每块要带着 absmax**：索引记的是"本块 absmax 的几分之几"，不是绝对值。同一个索引 9，在 absmax=2.71 的块里是 0.1609×2.71=0.436，在 absmax=0.05 的块里是 0.008，差 50 倍。没有 absmax 就还原不了，它是索引的另一半含义，和"1234 分"必须知道"当时乘的是 100"才能读回元一回事。
- **64 怎么来的**：不是算出来的，是 QLoRA 作者试出来的折中。块越小越准但钥匙越多（开销 = 32 ÷ 块大小，64 → 0.5 bit/参数），块越大开销小但离群值祸害的邻居多；顺带是 2 的幂，对显卡按 32 线程一组干活友好。bitsandbytes 4bit 默认 64，二级 scale 用 256。
- **提前算好的是什么**：是 NF4 那 16 个刻度值（一把固定的尺子），不是数据；absmax 每块加载时现算。误差只来自"就近取整"这一步，单个数有误差，模型整体效果实测不掉。
- **absmax 为什么也要压（双重量化）**：一个 absmax 4 字节不起眼，1.1 亿个就是 0.41 GB；按 256 个一组压成 8bit 后 0.10 GB，7B 省 0.3 GB。开关 `bnb_4bit_use_double_quant=True`。

### 第 4 章故事线一句话 + 本章要记（4bit 与 QLoRA）

  4bit 只有 16 格，等距切分死于"中间人挤、两头空跑"，救星是按人数均分的分位数量化；NF4 用标准正态的分位数预先算好一张 16 值的尺子，
  每 64 个权重一块、除以块内 absmax 后就近对尺；双重量化把 1.1 亿个 absmax 再压成 8bit 省 0.3 GB；分页优化器把优化器状态的显存峰值换到 CPU；
  四件合体 = QLoRA：冻结基座 4bit 只读、A/B 正常精度训，7B 微调从 LoRA 的 20 GB 降到 10–12 GB，24 GB 消费卡能跑。

  🔖 本章要记
  - 4bit 线性量化误差 18% 级，病根是等距切分不看分布；NF4 = 固定 16 值尺子（中间密两头疏、含精确 0），按块归一化后就近对尺
  - 双重量化：absmax 按 256 个一组压 8bit，每参数 0.5 bit → 0.127 bit；分页优化器：状态平时在 GPU，显存爆时换到 CPU
  - QLoRA 四件：4bit NF4 冻结基座 + LoRA + 双重量化 + 分页优化器；BitsAndBytesConfig 四字段 = 开 4bit / nf4 / 算用 BF16 / 双重量化
  - 量化只在加载那一行起作用（改权重的存法，不改结构和代码），LoRA 只在 get_peft_model 那一行；prepare_model_for_kbit_training 三件事 = 冻结、Norm 转 FP32、开梯度检查点

  追问：量化到底在做什么？
  把精确的小数四舍五入到一把粗尺子上，只存"第几格"。体温 36.62 按 0.1 度一格记成第 366 格，用时 366×0.1 还原，差的 0.02 就是量化误差。
  INT8 是 256 格的尺子（格号 1 字节），4bit 是 16 格（半字节），"一格是多少"= scale/absmax，几十个权重共用一个。省地方，代价是小误差；
  前几章所有花样（absmax、离群值、NF4）都在回答"怎么选尺子让误差不伤模型"。

  追问：训练和推理有什么区别？
  推理是"用"模型：输入乘过去得到输出，权重只读。训练是"改"模型：多三步——输出和标准答案比出误差、反向算每个数该往哪改（梯度）、优化器改数；
  为此还要留前向的中间结果（激活值）和优化器的历史（AdamW 两份状态）。显存：推理 ≈ 权重；训练 = 权重 + 梯度 + 优化器状态 + 激活值。
  被改的数不能量化（等距刻度加不上小更新），只读的数才能——所以 INT8 只用于推理，QLoRA 只压不改的基座。

  追问：微调在整条流水线里的位置？
  四站：预训练造通才（大厂，几千卡几个月，产物 base）→ 对齐成助手（大厂，产物 Instruct）→ 微调成专才（你，一张卡几小时，方法全参/LoRA/QLoRA）→ 部署推理（vLLM，INT8 省显存）。
  微调 = 在别人训好的模型上用小数据改一点"怎么答"，不是灌知识（灌知识找 RAG，改格式先试提示词）。

  追问：微调六步里，量化和 LoRA 各在哪一步？
  六步 = 备数据 → 装基座 → 挂 LoRA → 训练循环（前向 → 比误差 → 反向 → 改 A/B）→ 保存 adapter → 验证。
  量化只在第 2 步（加载时把 W 压成 4bit 并冻结），LoRA 只在第 3 步（get_peft_model 长出 A/B），第 4 步两者一起用：W 每步临时解压成 BF16 算 W·x，A/B 正常算并被更新。
  加载选项只决定"每张权重表在显存里每个数占几字节"：torch_dtype 选小数格式（FP32 4 字节 / BF16 2 字节），quantization_config 选整数编号（INT8 1 字节 / 4bit 半字节），后者开启时 bnb_4bit_compute_dtype 接管"翻回来用哪种小数"。



## 分布式训练 第一章：为什么单卡撑不住（2026-09-28 学《3.分布式训练实战指南》）

  第 1 章故事线一句话：训练要装四样东西，fp32 下每参数 16 字节，10B 就是 160 GB，最大的单卡 80 GB 装不下（显存山）；
  GPT-3 量级单卡要算几十年（算力山）。单卡先自救：LoRA 省梯度和优化器状态，量化省权重；
  但 LoRA 省不掉基座权重、量化不能用于预训练，所以"预训练"或"全参微调一个装不下的模型"只剩分布式一条路。

  🔖 本章要记
  - 两座山：显存是装不下，算力是算不完
  - 两条自救：LoRA 省梯度和优化器状态，量化省权重本身
  - LoRA 减的是"可训练参数"不是"参数"：基座整份在显存，adapter 文件小是磁盘的账
  - 预训练、或全参微调装不下的模型，必须分布式

  追问：LoRA 训练的参数很少，是不是也省了权重？权重就是参数吧？
  权重 = 参数，对。但 LoRA 减的是"可训练参数"不是"参数"：基座权重一个不删、全部冻结、整份在显存，旁边加小矩阵 A、B；
  省的是梯度和优化器状态只给 A、B 开。7B bf16：全量 = 权重 14 + 梯度 14 + 优化器 56 GB；LoRA = 权重 14 + 不到 1 GB 零头。
  adapter 文件几十 MB 是磁盘的账，不是训练显存。权重账只有量化能省 → 这就是 QLoRA 存在的理由。

## 分布式训练 第二章：三种并行范式

  第 2 章故事线一句话：核心问题只有"怎么切"。DP 复制模型切数据，只提速不省显存，装不下就不能用；
  PP 按层切成几段，每卡一段，只在段边界传激活值，通信最少；TP 切开一层内部的矩阵，每卡半个输出，
  下一层要完整输入所以层层都要拼，通信最频繁只能走同机 NVLink。装得下 DP，装不下切模型，超大 3D 并行。

  ```
  DP  复制模型、切数据、平均梯度       每卡整份模型      通信：每步同步一次梯度
  PP  按层切段、数据依次流过           每卡 1/N 的层     通信：段边界传激活值（前向）/ 激活值的梯度（反向），最少
  TP  切开一层的矩阵、算完拼回         每卡 1/N 的权重   通信：每层都拼，最频繁，必须同机 NVLink
  ```

  为什么 PP 要传激活值：激活值 = 上一层的输出 = 下一层的输入。第 16 层在 GPU 0、第 17 层在 GPU 1，
  第 17 层的输入躺在 GPU 0 显存里，必须拷过去；反向时"损失对激活值的梯度"再传回来。只在切分点各一次。

  为什么 TP 每层都要拼：X=[1,2]，W 左列 [1,2]、右列 [3,4]，GPU 0 算出 5、GPU 1 算出 11，完整输出 [5,11] 各卡只有一半；
  下一层的每一列都要乘完整的 [5,11]，所以进下一层前必须交换凑齐。层被切碎 → 每层输出都残缺 → 层层拼。
  （补充：Megatron 用"列切接行切"省一半，一个 Transformer 层前向实际 2 次通信，仍是逐层发生。）

  3D 并行排布：TP 通信最频繁放机器内走 NVLink；PP 通信最少可跨机器；DP 包最外层，把拼好的一套复制多份吃数据。

  🔖 本章要记
  - DP：复制模型、切数据、平均梯度；只提速不省显存
  - PP：按层切，段边界传激活值，通信最少；TP：切层内矩阵，层层拼，通信最频繁
  - 装得下 DP，装不下切模型，超大 3D；3D 排布 = TP 机器内、PP 跨机器、DP 最外层

## 分布式训练 第三章：数据并行实战

  第 3 章故事线一句话：DataParallel 八步全绕主卡转（正本只在主卡、每步重新复制），所以主卡畸高、被 GIL 卡、快不起来；
  DDP 改成每卡一个进程、All-Reduce 平均梯度、没有主卡，三个坑一起消失；Trainer 代码零改造，但 python 跑是 DP、torchrun 跑是 DDP。

  🔖 本章要记
  - DP 八步绕主卡转：主卡畸高、GIL、每步复制 → 慢
  - DDP：每卡一进程 + All-Reduce 平均梯度，没有主卡；用 torchrun 启动
  - 卡号映射：import torch 之前设 CUDA_VISIBLE_DEVICES="2,3"，程序里只用逻辑编号 0、1

  追问（反复问了四轮）：坑一"卡号映射"到底在说什么、为什么要设 "2,3"、目的是什么？

  - nvidia-smi = 显卡驱动自带的命令，显卡的任务管理器：列出每张卡的编号、显存占用、利用率、谁在用。租卡第一条命令；训练时 `nvidia-smi -l 2` 盯显存。
  - 两套编号：物理编号是机器数的（nvidia-smi 最左列）；逻辑编号是程序对"看得见的卡"从 0 重新数的。
    ```
    机器上的卡（nvidia-smi）：   物理0     物理1     物理2     物理3
    不设变量，torch 看到：       cuda:0    cuda:1    cuda:2    cuda:3
    设 "2,3" 后，torch 看到：    看不见    看不见    cuda:0    cuda:1     ← Java：mine = all.subList(2,4)，mine.get(0) 是 all 的第 2 个
    ```
  - 为什么是 "2,3"：共用服务器上 nvidia-smi 看到 0、1 被同事占着，只有 2、3 空着。数字不固定，谁空写谁；租来独占的机器不用设。
  - 目的（对照代码看）：
    ```python
    net = net.cuda()                              # 不带编号 = 放 cuda:0（物理 0，被占）
    net = DataParallel(net, device_ids=[2, 3])    # DP 检查：模型必须在 device_ids[0]=cuda:2 → 实际在 cuda:0 → 报错（是自己两行代码矛盾，与同事无关）
    
    os.environ["CUDA_VISIBLE_DEVICES"] = "2,3"    # 藏掉 0、1
    import torch
    net = net.cuda()                              # 还是 cuda:0，但此时 cuda:0 = 物理 2
    net = DataParallel(net, device_ids=[0, 1])    # 检查通过，代码一行不改
    ```
    一句话：让"我要用的第一张空卡"在程序眼里变成 cuda:0，所有默认写法（.cuda()、to("cuda")、device_ids 从 0 起）都不用动，换机器只改环境变量。
    不用白名单也行（net.cuda(2) + output_device=2），但每处 .cuda() 都要改，漏一处就错。
  - CUDA_DEVICE_ORDER=PCI_BUS_ID：让 CUDA 编号顺序和 nvidia-smi 一致（默认按"最快的卡在前"排，可能对不上）。
  - 放 import torch 之前：变量在 CUDA 初始化时只读一次，放文件最顶上最保险。

## 分布式训练 第四章：模型并行（流水并行与张量并行）

  第 4 章故事线一句话：PP 按层切段后上下游互相干等，空档叫气泡，最有效的解法是把 batch 切成很多微批次让各段同时忙，
  再加均衡切分和更好的调度（GPipe / PipeDream / Megatron 1F1B）；TP 把 FFN 按列切、Attention 按头切，单层显存除以卡数，
  但层层都要通信，只能放同机 NVLink。TP 治"单层太大"，PP 治"整体太大"。

  ```
  气泡占比 ≈ (段数 - 1) ÷ (微批次数 + 段数 - 1)     4 段 × 1 份 = 75%    × 16 份 ≈ 16%    × 64 份 ≈ 4.5%
  ```

  🔖 本章要记
  - 气泡 = 流水线上下游互相干等的空档；多切微批次是压气泡最有效的手段
  - TP：FFN 按列切、Attention 按头切，层层通信只能同机 NVLink
  - TP 治单层太大要 NVLink，PP 治整体太大能跨机；代表框架 Megatron-LM / GPipe、PipeDream

## 分布式训练 第五章：DeepSpeed 与 ZeRO

### 故事线一句话

DP 每张卡都存全套的优化器状态、梯度、参数，N 卡 N 份重复；ZeRO 分三档把它们切开分着存（1 切优化器状态、2 再切梯度、3 再切参数），每卡照样算整个模型，用到哪块临时向别的卡借、用完丢；1、2 档几乎零代价，3 档通信量 1.5 倍；还不够就 Offload 挪到 CPU 内存、Infinity 挪到硬盘。DeepSpeed 是实现它的库：一份 ds_config.json + TrainingArguments 里一行 `deepspeed="ds_config.json"`，Trainer 管的键写 auto、DeepSpeed 独有的写死。

```
7B 全参微调、混合精度、2 张卡，每卡显存：  普通 DP 112GB → ZeRO-1 70GB → ZeRO-2 63GB → ZeRO-3 56GB
课件那张表（ZeRO 论文 Figure 1）：7.5B、64 张卡：120GB → 31.4 → 16.6 → 1.9GB（课件没写这个前提）
```

### 🔖 本章要记

- ZeRO 三档：1 切优化器状态，2 再切梯度，3 再切参数；2 张卡最多减半，卡越多省越多
- Offload 挪 CPU、Infinity 挪硬盘，和三档是独立开关，用速度换显存，够用就别开
- ds_config 只决定两件事：stage 选几档、offload 开不开；接 DeepSpeed 只加一行 deepspeed=，Trainer 管的写 auto、DeepSpeed 独有的写死
- 启动 `deepspeed --num_gpus=2` 或 `torchrun --nproc_per_node=2`；分布式 = 微调脚本 + 一行 deepspeed= + 换启动命令

### 追问 Q&A（2026-09-28）

**Q：概念太多没懂，为什么要用 DeepSpeed 和 ZeRO？**
数据并行的浪费：4 张卡存 4 份一模一样的权重、梯度、优化器状态（"人手一套完整教材"），优化器状态一项就占一半。ZeRO：同样的东西别存 N 份，切开分着存，谁要用谁去借 → DP 第一次也能省显存。7B 全参每卡 112GB，两张 80GB 装不下；ZeRO 切两半每卡 56GB 就装下。DeepSpeed = 把 ZeRO 写好的库，你只写配置选档。

**Q：ZeRO 切东西，和 TP / PP 切东西有什么区别？**
TP、PP 切的是计算：每张卡永远只算模型的一部分。ZeRO 切的只是存放：每张卡照样把整个模型算一遍，平时不放全套，算到第 5 层时两卡互发另一半、各自凑出完整的第 5 层、各自算、算完丢。所以 ZeRO 仍是数据并行（各吃各的数据、算整个模型、平均梯度），是 DP 的省显存版。

**Q：DP 是干什么的？ZeRO 在 DP 基础上做了什么？**
DP 目的是快：模型复制 N 份、数据切 N 份、梯度平均，训练时间除以卡数，但每卡放整份、不省显存。ZeRO = DP 加"分着存"的补丁：流程一模一样，只把存放改成分片。分开存的是模型的三样东西，不是训练数据，训练数据仍各吃各的。

### 追问 Q&A（2026-09-29：脚本与判断）

**Q：这份训练脚本 train_dist.py 和微调脚本有什么区别？我是不是只需要关注 json？**
主体是同一套：加载模型、造数据、TrainingArguments、Trainer.train()。分布式只改三处：
1. TrainingArguments 多一行 `deepspeed=` 指向 json；
2. 启动命令从 python 换成 torchrun（决定单卡还是 DDP）；
3. ZeRO-3 时 TrainingArguments 必须先于加载模型。
关注点只有两样：json 里的 stage 和 offload，启动命令用哪个、卡数写几。

**Q：怎么判断装不装得下、stage 选几、offload 开不开？**
一把尺子 + 三档阶梯：
1. 尺子（估"要装的东西多大"）：全参每 10 亿参数约 16GB；LoRA 每 10 亿参数约 2GB；再给激活值留三成余量。
2. 阶梯：比单卡显存小 → stage 2（或只用 DDP）；比单卡大、比所有卡总和小 → stage 3；比总和还大 → stage 3 + offload。
3. 估不准就选一档跑起来看 nvidia-smi，爆了升一档，一次就够。

**Q：尺子里的数字怎么来的，每个参数是什么意思？**
- **参数**：模型里的一个数（权重表里的一个格子）。B = billion 十亿；0.5B = 5 亿个数，7B = 70 亿个数。
- **全参 16 字节/参数**：训练时每个参数在显存里有四份：权重 4 字节（fp32）+ 梯度 4 + Adam 的 m 4 + v 4 = 16。混合精度也是 16：bf16 权重 2 + bf16 梯度 2 + fp32 主权重 4 + m 4 + v 4。所以 1B × 16 字节 = 16GB。
- **LoRA 2 字节/参数**：基座冻结，只剩权重这一份，bf16 存 2 字节；梯度和优化器状态只给 A、B 开，A、B 只有几百万个数，忽略不计。所以 1B × 2 = 2GB。（QLoRA 基座 4bit = 0.5 字节 → 1B 约 0.5GB。）
- **三成余量给激活值**：前向的中间结果，大小随 batch 和序列长度变，不能按参数量算，经验值留 30%，或跑一下看。
- **单位**：口算按 1GB = 10 亿字节，显卡标的 24GB 也是这个口径。
- 套一遍：0.5B 全参 = 0.5 × 16 = 8GB，加三成约 10GB；7B LoRA = 7 × 2 = 14GB，加三成约 18GB；7B 全参 = 7 × 16 = 112GB。
- **勘误：** 本文档 QLoRA 一节写的"全量微调 … 7B 约 160 GB"，按 16 字节/参数应是 112GB；160GB 是课件里 10B 的例子。

### 勘误（课件 5.3）

- **标题与场景不符：** 标题写"全参数微调"、正文场景是"LoRA 微调"，显存账差十倍。
- **缺 5.4：** 5.3 之后跳到 5.5，缺的正是训练脚本（已补在 meishiyi/09_HuggingFace/dist/train_dist.py）。
- **卡数对不上：** 启动命令写 --num_gpus=4，场景却是 2 卡。
- **offload 只是演示：** 两张 80GB 跑 7B LoRA 不需要 offload，开了每步多一趟 CPU 往返慢好几倍。

## 分布式训练 全篇总结 + 租卡实验清单（2026-09-29）

### 这节课学了什么（六句话）

1. **为什么要分布式**：训练要装权重、梯度、优化器状态、激活值，fp32 下每参数 16 字节，10B 就 160GB 单卡装不下；LoRA 省不掉基座权重、量化不能用于预训练，所以预训练或全参微调大模型只能分布式。
2. **怎么切**：DP 复制模型切数据只提速不省显存；PP 按层切通信最少；TP 切层内矩阵通信最多只能同机。装得下 DP，装不下切模型，超大三个一起上。
3. **数据并行怎么落地**：老 DataParallel 绕主卡转（主卡爆、GIL、每步复制）；正确做法是 DDP，每卡一进程、All-Reduce 平均梯度，torchrun 启动，Trainer 代码不改。
4. **模型并行的代价**：PP 有气泡靠多切微批次压；TP 用通信换显存必须 NVLink。课程不要求动手。
5. **ZeRO 让数据并行也省显存**：三档切开分着存、用时借用完丢；不够就 Offload 挪 CPU。DeepSpeed 接入 = 一份 json + 一行 deepspeed=。
6. **工具**：LLaMA Factory 把以上全部变成 yaml 几行。

学完能做的事：拿到一个模型和几张卡，用"尺子 + 阶梯"判断装不装得下，决定 json 里 stage 选几、offload 开不开，然后用 torchrun 启动。

## 量化实战：quant_demo.py 在 AutoDL 4090 上实测（2026-09-28，《2.低精度训练与量化》第 2–4 章加载代码）

### 故事线一句话

同一个 7B 模型只换 from_pretrained 那一行参数，report() 量收益（省了多少显存），generate() 让它答同一个问题量代价（答案变没变、每秒写几个 token）；
INT8 省四成显存、答案只差一个词，但慢到 1/3；NF4 省六成多、改了半句意思没错，速度只掉两成；QLoRA 准备好可训练时总共 7.25 GB。

```
          显存（GiB）  速度           输出和 bf16 比
bf16    14.19        37.9 token/s   基准
int8     8.11        12.8 token/s   只差一个词（计算量 → 计算效率）
nf4      5.07        29.8 token/s   改了半句，意思没错
nf4 → prepare 后 7.10（Embedding/lm_head 升 FP32，+2）→ 挂 LoRA 后 7.25（可训 40,370,176 = 0.53%）
```

### 🔖 本章要记

- report 量收益（显存），generate 量代价（答案、速度）；do_sample=False 保证答案变了只能怪量化
- BF16 → INT8 只在加载时做一次：按行找 absmax、× 127/absmax 取整、存整数 + absmax；之后一直是 INT8，不转回、不存回
- 只量化线性层（占 86% 参数、每写一个 token 都要全读一遍）；Embedding 是查表、lm_head 决定选哪个词，都留 16 位

### 追问 Q&A（2026-09-28）

**Q：脚本里为什么要"生成 token"、还要数个数？**
量化是拿精度换显存的交易。report() 只看得到收益；权重变成近似值后模型会不会变笨、变慢，只能让它真干一次活。
generate() 让三种模式回答同一句话，do_sample=False（每步挑最高分的词、不掷骰子），同一模型每次答案一模一样，答案变了只能是量化误差。
模型是一次写一个 token 的循环，所以速度 = 写了几个 token ÷ 用了几秒（quant_demo.py:79-80）。词表固定 15 万个，但"下一个写哪个"每一步都要把全部权重过一遍来算。

**Q：token 是什么？**
模型读写文字的最小单位，分词器把句子切成段，每段对应词表里一个编号。"用一句话解释什么是模型量化："14 个字 → 8 个 token（第一个是自动加的开头标记），
演示见 deepLearning/quant/s4_token.py。

**Q：torch_dtype 和 quantization_config 有什么不同？**
torch_dtype=bfloat16 只是换一种小数格式，PyTorch 自己一步转完；INT8 要换成整数 + 每行一个 absmax + 专门的乘法内核，PyTorch 不会，
交给 bitsandbytes 库，入口就是 quantization_config=BitsAndBytesConfig(load_in_8bit=True)。别的量化库也走这个槽（如 GPTQConfig）。

**Q：BF16 → INT8 具体怎么变？是不是更新时转 INT8、存时再转回 BF16？**
不是。INT8 只做推理，权重不更新；转换只在 from_pretrained 那一行发生一次，方向只有 BF16 → INT8，磁盘文件一直是原来的 BF16。过程：
1. 按 config 搭空架子，把每个 nn.Linear 换成 bitsandbytes 的 Linear8bitLt（lm_head 跳过）；
2. 逐张读权重（如第 0 层 q_proj，3584×3584 的 BF16 表），搬上 GPU 时按行压：找行内 absmax → × 127/absmax → 四舍五入到 -127~127 → 存整数（1 字节）+ 这行的 absmax → 丢掉 16 位原件；
3. Embedding / lm_head / Norm 不压，直接 16 位放进去（没传 torch_dtype 时被强制成 float16）。

一行例子：0.83 -1.27 2.56 -3.18 → absmax 3.18、倍数 39.9 → 存 33 -51 102 -127；用时 ÷ 39.9 得 0.826 -1.277 2.554 -3.18，差在小数点后第三位。
之后每次乘法：输入也临时按行压成 INT8，整数相乘，再除掉两边的倍数变回 16 位小数交给下一层；权重本身一直是 INT8。

**Q：为什么只量化线性层？Embedding 为什么不是线性层？**
线性层是"输入向量 × 权重矩阵"，占 7.62B 里的 6.53B，每写一个 token 都要全读一遍，压它收益最大；transformers 加载时也只把 nn.Linear 换成 bitsandbytes 的层。
Embedding 是"按编号取第几行"（"量化" id 108048 → 取第 108048 行），是查表不是乘法，每个 token 只读一行，压它只省显存不提速。

**Q：为什么 Embedding 和 lm_head 不量化？**
lm_head 给 15 万个候选词打分，直接决定下一个写哪个词，误差一点就可能换词，默认跳过它保精度；Embedding 原因同上。
代价：Qwen 词表 15 万，这两张表共 1.09B 参数、约 2 GB，所以实测 INT8 8.1、NF4 5.1，比课件按 LLaMA 3 万词表算的 7~8、3.7 高。

**Q：为什么 INT8 反而最慢？**
LLM.int8() 每次乘法多几道杂活：挑出离群列走 FP16、其余压成 INT8、算完还原、两路相加。batch=1 时杂活比"权重小了读得快"省下的时间还多。
NF4 的解压和乘法融合成一步，所以只慢两成。

**Q：nf4 那几行输出怎么读？**
uint8 3.26B 是 6.53B 个 4bit 权重两两塞进一个字节，q_proj 形状 (6422528, 1) = 3584×3584÷2 同理；已分配比 footprint 多 0.1 是每块的 absmax（footprint 不算它）。
挂 LoRA 后 q_proj 还叫 Linear4bit，但已是 peft 的同名外壳（peft/tuners/lora/bnb.py:298），里面装着原 4bit 层 + lora_A / lora_B。

**勘误（上面第 4 章要记第 4 条）：** prepare_model_for_kbit_training 不只把 Norm 转 FP32，而是所有没被量化的参数（Norm + Embedding + lm_head）都升 FP32；
Embedding / lm_head 很大，所以实测涨了 2 GB。

### 追问 Q&A（2026-09-29：量化在整条线上的位置）

**Q：量化在"训练 + 推理"整条线上出现在哪？**
6 站：预训练、对齐（大厂，改所有权重）→ 微调（全参 / LoRA / QLoRA）→ 合并 → 部署加载 → 每个请求。一条规则：正在被改的权重不能量化，只读的才能。
量化只在两处：QLoRA 的冻结基座搬进显存时（lora_train_fixed.py:63-73）、上线推理加载时（quant_demo.py:109-114，边加载边压：读一张压一张，峰值只多一张表的临时空间）。
另有离线 GPTQ / AWQ 另存一份 INT4 文件（课件 5），这是唯一把量化权重写到磁盘的情况。乘法里的 BF16 ↔ INT8 是临时的，显存里的权重和磁盘文件都不变。

**Q：为什么 QLoRA 要压成 NF4？"之后每一次计算"指什么？**
显存不够才压：BF16 基座 14 GB + 训练中间数据 ≈ 20 GB 贴着 24 GB，NF4 基座 5 GB 总共 11 GB；不压也能训（USE_4BIT=0）。
每一次计算 = trainer.train()（:174）里每一步的前向，每层算 W·x 的那一瞬间 bitsandbytes 把这张 W 临时解压回 bnb_4bit_compute_dtype（:70，BF16），乘完丢。
这行代码在 bitsandbytes 的 Linear4bit.forward 里，自己的文件里看不到。

**Q：LoRA 把基座按 BF16 放显存，为什么不叫量化？FP32 → BF16 为什么不算？**
降精度 = 小数变更短的小数（3.14159 → 3.14），GPU 直接乘、没有尺子，课件第 2 章；量化 = 小数变整数编号 + 尺子（0.83 → 33，尺子 3.18÷127），用前必须还原，课件第 3、4 章。
判断标准：有没有 absmax。另外模型文件本来就是 BF16，torch_dtype=torch.bfloat16（:79）只是照原样读；不写它反而升成 FP32 白占一倍。

**Q：合并是什么意思？**
训练完手里是两份：W（没改）+ A、B。推理每层要走两条路 W·x + B·(A·x) 再相加，还得装 peft。合并 = W′ = W + B·A 一次算好、存成普通模型，只剩一条路，和原模型一样用。
NF4 是整数编号、加不了数，所以 merge.py:27 重新按 BF16 读原件，:28 挂 A/B，:29 merge_and_unload，:31 存 merge/。（peft 也能直接在 4bit 基座上合并：解压 → 加 → 再压回 NF4，带舍入误差警告；读 BF16 原件更无损。）

**Q：为什么要打印生成的文字？答案不应该一样吗？**
同一个模型每次一样；换了模式就不是同一个模型，几十亿个权重各差一点点，某一步第二名翻上来之后全变。打印是为了看误差有没有改坏答案。个数固定 64 是封顶，看点是秒数。

**Q：为什么要把模型搬到显存里？**
磁盘上的 15 GB 文件自己不会算；算的是 GPU，GPU 只能读自己的内存（显存），碰不到硬盘和内存条。硬盘是仓库，显存是 GPU 的工作台，`device_map="cuda"` 就是"搬上台面"。
非要 GPU 是因为写一个 token 要把 76 亿个权重全乘一遍，GPU 上万个小核并行，CPU 慢几十倍。工作台只有 24 GB，所以压缩发生在"搬上去"的那一刻——这就是量化为什么在 from_pretrained 里。

**Q：这一章的代码和以前的训练 / 推理代码，唯一区别就是 from_pretrained 里选精度吗？**
是。推理（quant_demo.py）三种模式只差 from_pretrained 那一行：`torch_dtype=torch.bfloat16` 选 2 字节小数，`quantization_config=BitsAndBytesConfig(...)` 选 1 字节整数 / 半字节编号，report、generate 不改。
训练（lora_train_fixed.py）LoRA 和 QLoRA 只差那一行 + 紧跟的 `prepare_model_for_kbit_training(model)`（:74，不是量化，是"量化后的模型要拿来训"的收尾：冻结、升 FP32、开梯度检查点），LoraConfig / get_peft_model / Trainer / 保存全一样。
改了这一行后自动变、不用写的：显存变小、速度变化、输出可能差几个词、QLoRA 里没压的层变 FP32。

### NF4 的四步与 BitsAndBytesConfig 四字段（2026-09-29）

**Q：NF4 具体怎么压？和 INT8 差在哪？**
同一套动作，只改两处：分组按每 64 个数一块（不按行）；尺子是固定的 16 个刻度（不是 -127~127）。16 个刻度是 bitsandbytes 写死的表，按标准正态分位数算好，中间密两头疏，7 号正好是 0。
拿 [0.83, -1.27, 2.56, -3.18] 当一块：
1. 块内 absmax = 3.18
2. 每个数 ÷ 3.18 → [0.261, -0.399, 0.805, -1.0]
3. 在 16 个刻度里取最近的编号 → [10, 3, 14, 0]
4. 两个编号塞一个字节 → 2 字节 + 这块的 absmax

用时编号查表 × 3.18 → [0.783, -1.256, 2.299, -3.18]。INT8 存这 4 个数要 4 字节、最大误差 0.007；NF4 只要 2 字节、最大误差 0.261（2.56 落在 0.723 和 1.0 之间只能二选一）。半字节换更大误差，靠"刻度中间密"和"块只有 64 个"压住。
实测对得上：uint8=3.26B 就是第 4 步两个编号一字节（6.53B ÷ 2）；已分配比 footprint 多的 0.1 GB 是每块的 absmax。

**Q：NF4 和 INT8 代码上有区别吗？**
只有 `BitsAndBytesConfig(...)` 括号里的内容，from_pretrained 其余参数和 generate 全一样：
- INT8：`BitsAndBytesConfig(load_in_8bit=True)`（quant_demo.py:112）。只要一个开关，因为尺子固定、按行分组、解压格式跟着输入走；可选 `llm_int8_threshold=6.0` 是离群列门槛，默认即可。
- NF4（quant_demo.py:123-128，lora_train_fixed.py:67-72 相同）四个字段对应四步：`load_in_4bit=True` 开关选半字节；`bnb_4bit_quant_type="nf4"` 选第 3 步查的那张表（另一个可选 "fp4" 等距、误差大）；`bnb_4bit_compute_dtype=torch.bfloat16` 管用时解压回什么（不写默认 FP32，慢一倍）；`bnb_4bit_use_double_quant=True` 管第 4 步存的 absmax 再压一次。

**Q：双重量化压的是什么？**
7B 线性层 65 亿个数 ÷ 64 = 1 亿块，每块一个 float32 absmax 共 0.4 GB。把这 1 亿个 absmax 当数据再压：先减平均值，每 256 个一组，用另一张 256 值表压成 1 字节，每组留一个 float32。0.4 → 0.1 GB，省 0.3 GB；代价是用时多查一次表还原 absmax。
分页优化器不在 BitsAndBytesConfig 里，是 `TrainingArguments(optim="paged_adamw_32bit")`：显存快爆时把优化器状态临时挪到内存条。

### 勘误（对照 bitsandbytes 0.50.2 / peft 0.15.2 / transformers 4.51.3 源码，改我之前说过的话）

- **"全参 / 普通 LoRA 全程 BF16 算、FP32 存"不准：** lora_train_fixed.py 基座 BF16 加载就以 BF16 存，只有 A/B 被 peft 升成 FP32；全参若 BF16 加载 + bf16=True，Trainer 只把前向包进 autocast，
  W 和优化器状态都是 BF16、没有 FP32 主副本；FP32 加载 + bf16=True 才是课件的"BF16 算、FP32 存"。
- **"每个线性层旁边长出 A、B"不准：** lora_train_fixed.py:130 只挂 q/k/v/o_proj 四个注意力层，MLP 的 gate/up/down 没有旁路；quant_demo.py 的 nf4 演示才 7 个全挂。
- **真实链路是 BF16 → FP16 → INT8/NF4：** 没传 torch_dtype 时 transformers 先把张量统一成 FP16，bitsandbytes 再压。
- **双重量化不是 -127~127 尺子：** 先减去所有 absmax 的平均值，再每 256 个一组、用另一张 256 值的表压成 1 字节，每组留一个 float32 absmax；还原 = 查表 × 组 absmax + 平均值。
- **NF4 用时比 INT8 简单：** 不量化输入 x、没有离群列拆分；逐 token 生成时用融合内核边读边解压，不落一份完整的 16 位 W。

演示脚本：deepLearning/quant/s5_int8_row.py（逐行 INT8 手算 + 共用尺子反例）、s6_quant_flow.py（推理 INT8 / 训练 QLoRA 两条线逐步回放）。

## 微调数据集指南 第一章：训练数据的底层逻辑（2026-09-29 学《4.大模型微调数据集完全指南》）

## 微调数据集指南 第二章：五类 SFT 任务（2026-09-29）

### 故事线一句话

微调九成是 SFT（有监督：问答对、只对回答算 loss，区别于预训练自监督全 token 算 loss）；SFT 样本按形态分五种：指令三元组（任务/材料/答案）、多轮对话（角色列表，练上下文和指代）、领域适配（按行业分，形式可套前两种）、文本分类（text + label，答案封闭）、推理微调（加思维链，和答案一起算 loss）。自己的 train.json = 领域适配 + 推理微调的叠加。

### 🔖 本章要记

- 预训练自监督、全 token 算 loss；SFT 有监督、prompt 标 -100 只对回答算 loss

- 领域数据最难造：先搜现成，再专家标注，AI 生成必须人工二次校验
- 推理微调只给多步任务用，简单任务会想太多；CoT 数据三来源：现成数据集、从 R1 蒸馏、引导普通模型生成

### 追问 Q&A（2026-09-29）

**Q：NLP 是什么？文本分类为什么值得单列一类？**
NLP 是自然语言处理，让计算机处理人类语言的整个领域。分类单列的唯一原因是答案是封闭集合，只能从固定标签里选，带来两个后果：评估最简单（直接算准确率）；可以不走生成路线（小模型接分类头输出整数标签，或大模型把标签当文本生成）。

**Q：CoT 数据来源第二条"从推理模型蒸馏"怎么理解？**
蒸馏 = 强模型（老师）先回答一批问题，把回答存成数据去微调小模型（学生）。推理模型蒸馏就是老师换成 R1，把它返回的思考过程和答案一起存成 Complex_CoT 和 Response。o1/o3 隐藏思考过程拿不到，R1 开放，所以开源 CoT 数据大多以 R1 为老师。基座 DeepSeek-R1-Distill-Qwen-7B 名字里的 Distill 就是这个：R1 生成 80 万条推理数据去微调 Qwen 7B。

## 推理部署 第一~三部分：vLLM 起步、两阶段与采样、Roofline（2026-09-29 学《5.大模型推理部署》）

### 故事线一句话

`vllm serve` 一条命令起一个 OpenAI 兼容服务，LangChain 的 ChatOpenAI 改 base_url 就能调；一次请求分两段：Prefill 一次并行读完整段输入（卡算力，决定首 token 延迟 TTFT），Decode 每步只生成一个 token（卡显存带宽，决定每 token 耗时 TPOT），每步的 token 由采样参数从整张词表的概率里挑；Roofline 解释了为什么：每步都要把全部权重从显存搬一遍，这一步有 n 个 token 共用这一趟，Decode 单请求 n=1、算术强度 I≈1，远低于 A100 平衡点 156，计算核心大部分时间在等数据。

### 🔖 本章要记

- Prefill 并行、卡算力、管 TTFT；Decode 串行、卡显存带宽、管 TPOT；E2E = TTFT + 输出长度 × TPOT；优化顺序 TTFT → TPOT → 吞吐
- 采样：每步输出是整张词表（Qwen3 15 万个）的概率；temperature = logits ÷ T 再 softmax（T 小变尖、T 大变平），top_k / top_p 砍长尾，do_sample=False 是贪心
- I = 计算量 ÷ 搬运量，低于平衡点卡带宽、高于卡算力；推高 I 两种手段：分子变大靠凑批（提吞吐），分母变小靠量化 / 缩小缓存（单请求也变快）
- 多卡后单卡瓶颈不变，多了卡间通信：Prefill 要网络带宽大，Decode 要网络延迟稳 → PD 分离后 Prefill 大 TP、Decode 小 TP + 大 DP

### 追问 Q&A（2026-09-29）

**Q：Decode 时 GPU 也在计算，为什么说它卡带宽？**
算是在算，但算得快、搬得慢。每生成一个 token 都要把全部权重（和全部 KV Cache）从显存搬一遍，只配 1 个 token 的运算：7B 模型搬 14 GB 约 7 毫秒，算只要 0.05 毫秒，计算核心大部分时间在等数据。

**Q：采样 demo 里"函数 / 重复 / 定义"是什么？是答案分类吗？**
不是分类，是"递归是一种通过"之后下一个词的候选，像 IDE 的自动补全列表；0.74 是它被选中的概率，每个候选会接出一句不同的话。温度调的是这张候选表的形状：T=0.3 时"函数"0.74 一家独大，T=1.5 时降到 0.26，其余候选抬头。

**Q：n 和 I 是什么？什么关系？**
- n：这一步一起过模型的 token 行数。Decode 单请求 n=1，凑 128 个请求 n=128，Prefill 2K 输入 n=2048。
- I：这一步的运算次数 ÷ 搬的字节数，就是算术强度，意思是每搬 1 字节能配套做几次运算。
- 关系：n 是输入，I 由 n 算出。n 变大运算次数成倍涨，搬运量几乎不变（大头是只搬一次的权重），所以 I 跟着涨。

**Q：运算次数和搬的字节数具体指什么？**
- 运算次数：计算核心做的乘法和加法。输入 3 个数乘 3×3 权重，每个输出 3 乘 2 加约 6 次，3 个输出共 18 次；换成 7168 维，每行约 2×7168×7168 ≈ 1.03 亿次。
- 搬的字节数：从显存（仓库）搬到计算核心（工作台）再写回的数据。权重 7168×7168 个数 × 2 字节 ≈ 1.03 亿字节，每行输入 + 输出合计约 2.9 万字节。
- n=1：1.03 亿次 ÷ 1.03 亿字节 = 1，每搬 1 字节只配 1 次运算。

**Q：n=2048 时 I 为什么只有 1303，不是 2048？这个计算要会吗？**
不用会算，记结论即可。搬运量 = 权重 1.03 亿字节（固定）+ 每行输入输出 2.9 万 × n。n=128 时后者才 367 万、可忽略，I≈124；n=2048 时涨到 5872 万，分母变成 1.61 亿，I 就打折成 1303。

**Q：推高 I 为什么能加速？I 不是算力 ÷ 搬运量吗？**
分子是计算量（这一步要做多少运算），不是算力（卡每秒最多做多少，硬件定死）。Decode 时计算核心在等数据，多塞进去的活填的是等待时间：7B 模型一步约 7 毫秒，1 个请求产 1 个 token；64 个请求凑批还是约 7 毫秒，产 64 个。提升的是吞吐，单请求每 token 耗时不变。

**Q：减少搬运量不也是在推高 I 吗？**
是。推高 I 是目标，手段有两个：
1. 分子变大：凑批，一步时间不变、产出变多 → 提吞吐；
2. 分母变小：量化 BF16 → INT4，权重 14 GB 变 3.5 GB，一步从约 7 毫秒到约 2 毫秒 → 单请求也变快。

I 超过平衡点后就转成卡算力，再推没有收益。

**Q：Prefill 的瓶颈不是显存吗？第 5 节 Prefill 要带宽、Decode 怕延迟，是不是反了？**
不是反的，两个"带宽"不是一回事。
- 单卡内：Prefill 卡算力（不是显存），Decode 卡显存带宽（仓库到工作台的传送带）。
- 多卡之间：TP 每层都要 AllReduce 合并结果。Prefill 一次传上百 MB，要网络带宽大；Decode 一次只传十几 KB 但极频繁，怕某一次卡住（尾延迟，用 P99 衡量，表现为 ITL 毛刺），要网络延迟稳（工厂之间的公路）。

**Q：多卡的时候瓶颈会变吗？**
单卡瓶颈不变，多了卡间通信这一层；网络没配对它就成新瓶颈。比如 Decode 用大 TP 走慢网络，每个 token 每层都要等同步，所以 Decode 尽量少切 TP。

### 勘误与补充（课件第一~三部分）

- **vLLM 调用处的注释不适用：** 注释写"未启用鉴权时填任意非空字符串"，但启动命令已加 `--api-key ds123456`，所以 api_key 必须填 ds123456，不能随便填。
- **temperature=0 在 transformers 里会报错：** vLLM / OpenAI 接口里 temperature=0 就是贪心；transformers 的 generate 要写 do_sample=False，do_sample=True 配 temperature=0 会报错。
- **Roofline 的"运行结果"和它自己的代码对不上：** 课件贴 n=1 时 I=2.00、n=128 时 I=255（算力受限）；代码实际输出 1.00、123.6，n=128 仍卡带宽，batch 约 160 才过 A100 平衡点 156。
- **采样示例漏了 Qwen3 的思考开关：** apply_chat_template 要加 `enable_thinking=False`，否则先输出一大段 `<think>`（课件后面静态批处理的例子加了）。

演示脚本：meishiyi/09_HuggingFace/inference_deploy/s1_sampling.py（温度改变候选表 + 贪心 vs 采样）、s2_roofline.py（五个 n 的算术强度）。

## 推理部署 第四部分：KV Cache（2026-09-29）

### 故事线一句话

Decode 每步只把上一步生成的 1 个 token 送进模型。历史 token 的 K、V 在它们进模型的那一轮就算好存起来，每层一份 K、一份 V；之后每步只算新 token 的 K、V 追加进去，再用全部历史 K、V 读上文。省掉的是历史 token 每步重过整个模型，本机实测 200 个 token 快 4.9 倍，输出一字不差。代价是显存：上下文一长、请求一多就存不下，批凑不大，I 就上不去。所以 KV 头数（GQA）和缓存管理成了推理优化的主战场；开头相同的请求还能用前缀缓存共用同一段 K、V。

### 🔖 本章要记

- 存的是每层两份独立的张量 K 和 V，不是乘积，形状 [请求数, KV头数, token数, 头维度]；每步只"算"新 token 的 K、V，但要"用"全部历史的 K、V
- 显存公式：2 × 层数 × KV头数 × 头维度 × 序列长度 × 字节数；部署先算账：缓存池 = 可用显存 − 权重 − 预留，池子大小决定能同时服务几个请求
- KV 头数是最大的开关：同是 7B，LLaMA-2（32 个 KV 头）每 token 524KB，Qwen2.5（4 个）57KB，差 9 倍
- 前缀缓存：开头逐 token 相同就复用，结果和重算一模一样；写提示词时不变的放前面、会变的放后面

### 追问 Q&A（2026-09-29）

**Q：缓存存的是 K 和 V 两个向量，还是 K 和 V 的乘积？**
两份独立的张量。注意力是"新 token 的 Q 乘所有历史 K 得到相关度，再按相关度加权所有历史 V"。Q 每步都是新的，乘积没法提前算好，只能把原料 K、V 存下来。

**Q：每步 Decode 要不要重算 QKV？上一步的 token 从哪来？**
上一步的输出就是一个 token 编号，这一步把这 1 个编号送进模型，只算它自己的 Q、K、V，并把它的 K、V 追加进缓存。缓存不负责还原 token，token 本来就在手上。

**Q：没有 KV Cache 时怎么拿到历史的 K、V？**
每步把"输入 + 已生成的全部 token"整段编号重新送进模型，从第 1 层算到最后一层，历史 token 的 K、V 全部重算，只用最后一个位置的输出。第 N 步要重算 N 个 token，越往后越慢。

**Q：K、V 不是编码器一次性生成好交给解码器的吗？**
那是编码器-解码器模型（原版 Transformer 翻译、T5）的交叉注意力。Qwen、LLaMA、DeepSeek 只有解码器：Prefill 一次算好问题部分每层的 K、V，Decode 每步再追加一份新 token 的。

**Q：28 层是固定的吗？每层的 K、V 为什么不同？"64 个一块"和"7B"是什么？**
- 层数由模型结构定死，写在 config.json 的 num_hidden_layers。Qwen3-0.6B 和 Qwen2.5-7B 恰好都是 28 层，Qwen3-8B 是 36 层。
- 每层权重不同，token 的向量每过一层也会被改写，所以每层算出的 K、V 都不同，要各存一份。
- "64 个一块"是 NF4 量化里每 64 个权重共用一个缩放系数，和层数无关；"7B"是参数总量 70 亿，也不是层数。

**Q：config.json 里要看哪些字段？hidden_size 是什么？**
- hidden_size 1024：对，就是每个 token 查词表得到的向量宽度，全程保持这个宽度；num_hidden_layers 28：层数
- num_attention_heads 16 / num_key_value_heads 8：16 个 Q 头、8 个 KV 头，每 2 个 Q 头共用一组 K、V（GQA）；head_dim 128：每个头的向量宽度
- intermediate_size 3072：MLP 中间层宽度；vocab_size 151936：词表大小；max_position_embeddings 40960：最长上下文；torch_dtype bfloat16：每个数 2 字节；eos_token_id：结束符编号
- 算 KV Cache 只用四个：层数、KV 头数、头维度、字节数

**Q：只要算当前 token 的 K、V 就能推出下一个词，为什么还要历史 token 的 K、V？**
分清"算"和"用"。算：每步只算当前 token 的 K、V。用：当前 token 要读上文才知道接什么，它的 Q 得和全部历史 token 的 K 比相关度，再按相关度取历史 V 的内容。缓存就是把"用"要的历史 K、V 留着，不必重算。

**Q：真实部署的缓存账怎么算？I 为什么上不去？**
- 4090（24GB）跑 DeepSeek-R1-Distill-Qwen-7B：可用 21.6GB = 权重 15.2 + 预留 1.4 + 缓存池 5.0GB；每 token 57KB，池子约装 86K 个 token；每个请求 4K 最多同时 21 个，32K 只剩 2.6 个。
- I 上不去主要是分子小：池子装不下，批凑不大；其次是分母大：上下文越长，每步要搬的缓存越多。1 个请求 × 4K 时 I≈1.1，20 个 × 512 时 I≈19.5，5 个 × 16K 时 I≈5.5。
- 更正当时的理解"token 变多、被除数变大"：搬运量是除数（分母）。分母变大只是一面，更大的影响是批凑不大。

**Q：计算量到底怎么算？（⏳ 课后重看）**
统一规则：每个 token 经过每个权重算 2 次（一乘一加），整个模型约 2 × 参数量；再加注意力一项，约 2 × 2 × 层数 × Q头数 × 头维度 × 上下文长度，随上下文变长而增加。Roofline 那节只算一个矩阵乘法，这里算整个模型走一步，规则相同、范围不同。

**Q：前缀缓存会不会让回答不准？缓存不是只存当前这个对话吗？**
- 不会不准：每个 token 的 K、V 只取决于它自己和它前面的 token，开头逐 token 相同，K、V 就和重算一模一样（本机实测下一个词的打分一致）。会答错的是"语义缓存"：问题相似就直接返回旧答案。
- 能跨请求：vLLM 有全局缓存池，按 16 个 token 一块存，每块用"本块内容 + 前面所有块"算指纹建索引；请求结束后块先留着，新请求开头指纹对上就直接引用，显存不够时按 LRU 回收。参数 `--enable-prefix-caching`，新版本默认开；DeepSeek API 还把前缀缓存存到磁盘上。
- 开头一个 token 变了，后面全部作废，所以时间、用户名这类会变的内容放到末尾。

### 勘误与补充（课件第四部分）

- **"KV Cache 加速的是 Q·Kᵀ 和加权求和 V"不准：** 这两次乘法开了缓存每步照做；省掉的是历史 token 每步重过整个模型（每层的 K/V 投影、MLP 等）。
- **显存表格的数字大了一倍：** 标的是 BF16，却按 4 字节算；"Qwen3-7B"不存在，28 层 + 4 个 KV 头是 Qwen2.5-7B。
- **"传统 MHA 约 0.7MB/token"：** LLaMA-2-7B 按 BF16 实际是 0.5MB/token。
- **"缓存满了导致遗忘"不准：** 缓存池满了是新请求排队、或已有请求被抢占后重算，不会让模型忘掉上文；忘上文是超出上下文窗口被截断。
- **"缓存命中约 3 折"已过时：** 第三方站点显示约为未命中价的 1/50，以 DeepSeek 官网为准。

演示脚本：inference_deploy/s3_kvcache_speed.py（开 / 关缓存耗时对比）、s4_kvcache_size.py（实测缓存 vs 公式 + 三个模型对比）、s5_kvcache_example.py（4090 部署账 + I）、s6_prefix_cache.py（前缀命中快 17 倍 + 开头加时间全作废）。

## 推理部署 第五部分：PagedAttention 与 vLLM 架构（2026-09-29）

### 故事线一句话

朴素 Serving 给每个请求按最大长度预留一整段连续显存放 K、V，踩两个坑：过度预留（大部分位置空着别人也用不了）和碎片（空闲总量够、但没有连续的一整段）。根源是"一个请求的缓存必须连续"，PagedAttention 照搬操作系统分页把它拆成固定大小的小块，用一块领一块，几个请求还能共用同一批块（COW）。显存省下来能同时放更多请求，接着要解决怎么把它们凑成批：静态批处理整批同进同出，短请求陪跑白算；连续批处理每步重新组批。

### 🔖 本章要记

- 朴素预分配两个坑：过度预留 + 碎片；vLLM 论文实测旧系统 KV 显存利用率只有 20~40%
- 本机账（4090、缓存池 5GB、请求平均 1134 token）：按 8192 预留只放得下 10 个、利用率 14.7%；按 16 个 token 一块分配 40 个全放下、利用率 99.3%
- Block Table：显存切成大小相同的物理块（vLLM 默认 16 个 token 一块），每个请求一张表记"第 i 个逻辑块在几号物理块"；写满一块才领下一块，领哪块都行；读时按表顺序拼回连续序列。浪费只剩每个请求最后一块没填满的几格，碎片消失
- 代价：注意力读缓存要多查一次表，vLLM 为此自己写了注意力计算代码；块大小是折中，太小表长、查表开销大，太大最后一块浪费多
- 前缀共享 + COW：几张表指向同一批块，引用计数记"有几张表在用"；要往计数 > 1 的块里写，先复制一份给自己再写。写满的块永远共用，只有最后没写满的块可能被复制
- 静态批处理（HF 的 generate 就是）：整批等最长那条写完才一起返回，短请求陪跑、每步照算 pad。本机 3 个请求 22 / 18 / 372 个 token，整批跑 372 步、45 秒，白算 63%
- 连续批处理：等待队列 + 运行集，每步"组批 → 执行 → 结算"，写完立刻走、空位立刻补；离不开 PagedAttention 的随时领块还块。模拟 6 个请求、一步最多 3 个：全部做完 572 → 372 步，平均拿到结果第 472 → 126 步
- 调度两参数，都是"一步塞多少"：max_num_seqs 管条数（本机 1 → 16 个请求：吞吐 11 → 99 token/秒，token 间隔 89 → 161 毫秒）；max_num_batched_tokens 管一步 token 总量，先排 Decode 再用剩余预算做 Prefill，超出就切块（Chunked Prefill）。调参 = 先定 SLO，再在不越线的前提下把批开大
- 九驿站：① API Server → ② 模板 + 分词 → ③ 调度组批、分块 → ④ GPU 执行 → ⑤ Prefill 出缓存 → ⑥ Decode 循环（每步回调度器，结束就回收块）→ ⑦ 采样 → ⑧ 增量转文字 → ⑨ SSE 流式推送；⑥~⑨ 每步都走一遍。工程细节：CPU 活（分词 / 转文字 / HTTP）和 GPU 计算分进程互不等待；调度器不分 Prefill / Decode，只看"这步处理几个 token"

### 追问 Q&A（2026-09-29）

**Q：块是怎么分的？**
1. 启动时切一次：缓存池（可用显存 − 权重 − 预留）÷ 每块大小。4090 跑 7B：一块 16 token × 57KB ≈ 0.9MB，5GB 切出约 5400 块，编号后全进空闲列表（启动日志 "GPU KV cache size"）。
2. 按位置切，不看内容：请求第 0~15 个 token 进逻辑块 0，第 16~31 个进逻辑块 1，每 16 个一刀。
3. 一个块号管全部层：每层各有一套同样编号的块，"块 3"指这 16 个 token 在全部 28 层的 K、V。

**Q：COW 的"分叉只加计数、写时才复制"没看懂？**
类比两个同学共用一页笔记，各自要在空行上写不同的结尾：
1. 分叉：两张表都写着 [0, 1]，数据没复制，只是多一张表指向它，块 1 计数 1 → 2。
2. 样本 1 写"，"：块 1 计数是 2，别人也在用，直接写的话样本 2 会读到不属于自己的"，"；所以复制成块 2 再写，样本 1 的表改成 [0, 2]，块 1 计数 2 → 1。
3. 样本 2 写"而"：块 1 计数是 1，只有自己在用，直接写。

计数的第二个用处：请求结束时表里每块计数 −1，减到 0 才还回空闲列表。已写满的块没人会再写，一直共用。

**Q：max_num_batched_tokens 怎么调？**
它是每步的 token 预算：先排所有 Decode（各占 1 个），剩余给 Prefill，放不下就切块。本机实测（8 个在 Decode + 来一个 2000 token 的新请求）：预算 256 → 切 9 步，TTFT 13.5 秒、老用户每步卡 1.5 秒；1024 → TTFT 8.5 秒、卡 4.2 秒；2048 → TTFT 8.7 秒、卡 8.7 秒。调大 TTFT 先改善后持平，token 间隔一直变差，有拐点。调法三步：
1. 硬约束：≥ max_num_seqs，否则 Decode 请求一步都放不下。
2. 按场景起步（vLLM 官方文档）：聊天流式看 ITL → 小值如 2048；长文档 / RAG 看 TTFT、离线跑吞吐 → 大于 8192，大显卡跑小模型尤其如此。
3. 压测看 P99 的 TTFT 和 token 间隔，对照 SLO：有余量往大调，越线往小调。调小还能减少缓存不够时的抢占重算。

**Q：s14 里缓存为什么是 18 + 34？18 个 token 是什么？**
18 是问题套上对话模板后的 token 数：问题"用两句话介绍长城。"只占 6 个（用 / 两 / 句话 / 介绍 / 长城 / 。），其余 12 个是模板标记（`<|im_start|>user`、`<|im_end|>`、关思考时塞的空 `<think></think>` 等）。Prefill 存下这 18 个的 K、V，之后每步 Decode 送进 1 个刚挑出的 token、追加它的 K、V，34 步后是 52；最后的结束符不再送进模型，不算在内。

**Q：⑥~⑨ 每步都走，⑧ 不就是把当前 token 转成文字吗？**
每步都走，但交给 ⑧ 的是"目前为止全部编号"，不是只有当前 1 个。常用字是整 token，只解码当前 token 也行；但生僻字、新 emoji 会被按字节拆成几个 token，单独解码是乱码"�"（本机实测"龘"= 2 个 token）。所以 ⑧ 全部一起解码、切掉已输出的前缀；结尾还是"�"说明字没凑齐，这一步先不推，下一步凑齐再推。vLLM 的增量 Detokenizer 也这么做。

### 勘误与补充（PagedAttention 第 1~2 节）

- **"共享场景能省约 55~67% KV 内存"说大了：** vLLM 论文 6.3 节原文：并行采样只省 6.1%~9.8%（Alpaca）/ 16.2%~30.5%（ShareGPT），beam search 省 37.6%~55.2% / 44.3%~66.3%；55%、66% 只是 beam search 的上限（beam 之间还会共用后来生成的部分）。
- **新版 vLLM 前缀缓存只共用写满的块：** 跨请求共享基本用不到复制，COW 主要在同一请求分叉（并行采样、beam search）时起作用。
- **3.2.3 代码的 `dtype="auto"`：** 是 transformers 4.56 起的新参数名；本机 4.51 要写 `torch_dtype`，写 dtype 不报错但被悄悄忽略。
- **3.2.3 实测 23 / 18 / 290 token：** 本机 CPU float32 跑出 22 / 18 / 372，精度不同导致贪心解码后段分岔，结论不变。

## 推理部署 第六部分：PD 分离与并行推理架构（2026-09-29）

### 故事线一句话

Prefill 吃算力、Decode 怕卡顿，混在同一批卡上会互相拖累（长 prompt 一步 Prefill 让所有正在 Decode 的用户集体卡住，Chunked Prefill 只能缓解）。PD 分离把两者拆成两个池子各自扩容、各自优化，代价是 Prefill 算出的 KV Cache 要跨机器搬给 Decode。

### 🔖 本章要记

- PD 分离三好处：独立扩容；独立优化（Prefill 大 TP 追单请求速度，Decode 小 TP + 大 DP 拉并发）；指标解耦（TTFT 看 Prefill 池、token 间隔看 Decode 池）
- 小规模（一两张卡）用 Chunked Prefill 就够；DeepSeek V3、Kimi Mooncake 这类大规模线上服务才上 PD 分离
- KV 搬家三难点：链路（普通 TCP 出局，要 RDMA / NVLink）；时机（逐层边算边传，把传输藏进 Prefill）；调度（挑 P 节点要看它到 D 节点的链路）。70B、32K token：缓存 10.7GB、Prefill 约 1.9 秒，TCP 整包 3.5 秒，RDMA 0.21 秒、流水后几乎不多等
- 5 万字论文任务三认知点：首 token 不一定可见（推理模型第一个 token 是 `<think>`，监控 TTFT 0.5 秒，用户 21 秒后才见答案，中间的思考全在 Decode 池）；联网搜索会触发新的 Prefill（前缀缓存复用旧 KV，只算新增的搜索结果，Agent 任务在 P/D 间来回跳）；短输入长输出的任务 99% 时间在 Decode
- 容量规划第一课：先看业务输入/输出 token 比再定 P/D 池配比。客服问答、RAG 长进短出多配 P；创意写作、推理模型短进长出多配 D；推理模型的输出长度要按"思考 + 答案"算

### 追问 Q&A（2026-09-29）

**Q：拆开后 KV 交接难在哪？（我答：带宽）**
对，带宽是第一关，还有两关：一是时机，等全部算完再整包传，传输时间全加到 TTFT 上，所以要逐层边算边传；二是调度，挑 Prefill 节点要连同它到 Decode 节点的链路一起考虑。

**Q：认知点 1 的 demo 为什么突然说到"还剩两个苹果"？**
苹果题只是实验用的问题（CPU 小模型写不了 5 万字），换任何问题现象都一样。模型依次吐出 `<think>`（0.5 秒，看不见）→ 198 个思考 token（折叠成"思考中…"）→ `</think>` → "还剩2个苹果。"（21 秒）。类比：同事 0.5 秒就"嗯……"一声，低头想 20 秒才说"2 个"，监控把"嗯"当成已回答。

**Q：这说明什么问题？**
两件事：一是指标失效，推理模型只看 TTFT 发现不了"用户觉得慢"，要另盯"首个可见字时间"；二是 D 池负担被低估，思考 token 看不见，但每个都要 Decode 一步、占 KV Cache，容量规划时输出长度要按思考 + 答案算。

### 勘误与补充（PD 分离）

- **"128K 上下文单请求 KV 几十 GB"看模型：** LLaMA-3-70B 约 43GB 属实；DeepSeek V3 用 MLA 把 K、V 压成小向量，约 9GB；Qwen2.5-7B 约 7.5GB。KV 越小搬家越便宜。

演示脚本：inference_deploy/s16_kv_transfer.py（三种链路传 KV 的耗时 + 逐层流水）；s17_think_ttft.py（思考模式下引擎 TTFT 与用户首个可见字的差距）。

## 架构与训练全流程 上半篇：架构之争（2026-09-29 学《6.大模型架构与训练全流程》）

### 故事线一句话

Transformer 左手编码器（双向注意力，负责读懂）、右手解码器（因果掩码只看左边，负责逐字写），三条路线就是只留左手（BERT，完形填空，只懂不会写）、两手都留（T5）、只留右手（GPT，下一词预测）；Decoder-Only 赢在"万物皆序列"，任务写进文字不用换头，加上因果掩码带来的 KV-Cache 一路复用、结构单一好扩展，生态和多模态都围着它长，强者愈强。

### 🔖 本章要记

- 编码器双向、解码器因果 + 交叉注意力；BERT 猜中间被挖的词，GPT 猜句尾下一个词
- BERT 短板根因是没学过生成：窗口卡 512（绝对位置表）、换任务要挂新头微调
- Decoder-Only 理论优势：因果矩阵满秩、难任务逼出强表征、prompt 示例直达每层（few-shot 强）、RoPE 相对位置好外推
- 工程优势：旧 token 的 K、V 永远不变 → KV-Cache 复用；一种层反复堆 → 好并行、好扩展；多模态切 token 拼进同一序列

### 追问 Q&A（2026-09-29）

**Q：BERT 的 512 是写死的吗？**
是这个训练好的模型写死的，不是 Transformer 结构写死的。BERT 用"绝对位置编码表"：一张 512 行的查找表，第 0 到 511 个位置各存一个训练出来的向量；第 513 个 token 没有对应行，等于 Java 数组长度 512 却去取下标 600。要加长得新增行并重新训练。后来 Decoder-Only 模型改用相对位置的 RoPE，只记"我和你隔几格"，才能稍微微调就外推到几万 token。

**Q：为什么 BERT 换任务就得微调？**
因为它的输出是向量不是文字，没有统一的"任务接口"。做情感分类要在 [CLS] 位置的向量上外挂一个随机初始化的分类头（一个小线性层，输出 3 个类别），做 NER 要给每个 token 挂一个标签头，头不同、标签数不同，每个头都得用标注数据从零训。GPT 把所有任务都变成"文字进、文字出"，任务写在 prompt 里，不用换头，所以一个模型通吃。

**Q：所以 Encoder 和 Decoder 的差别就是分类头不同、加上 Decoder 要预测下一个词？**
对，但"预测词"两边都做，差在预测哪个词、往哪看：BERT 猜句子中间被挖掉的词，左右都看；GPT 猜句尾的下一个词，只看左边。分类头的差别是这个差别的后果：GPT 训练时用的输出头就是"从整张词表里选一个词"，下游任务照样用这个头，任务写进文字即可；BERT 训练时的头只会填空，下游每个任务都得另外挂一个新头。

**Q：课件 3.2 末尾那张"Transformer vs LLaMA"图怎么理解？**
LLaMA 就是 Decoder-Only 的标准骨架，Qwen3、DeepSeek 都沿用。跟一个 token 从下往上走，和 2017 原版比有五处改动：
1. 砍掉整个编码器和解码器中间那层交叉注意力，只剩右边一座塔，这就是"只留右手"。
2. 位置编码从"底部加一次正弦波"改成 RoPE：每层注意力里给 Q、K 按位置转一个角度，点积只取决于两个词隔几格。
3. 归一化从"子层之后 LayerNorm"（Post-Norm）改成"子层之前 RMSNorm"（Pre-Norm）：残差那条直通路上干干净净，几十上百层也训得稳；RMSNorm 去掉减均值，只按大小缩放，更省算。
4. 注意力换成 GQA（分组查询注意力）+ KV Cache：多个 Q 头共用一组 K、V，KV 缓存成倍缩小，对应课件 5 的 Decode 卡显存带宽。
5. 前馈网络换成 SwiGLU：多一个"门"矩阵决定每个维度放行多少，同参数量下效果更好。
顶上 Linear + Softmax 输出整张词表的概率，两边一样。

**Q：这张图需要记下来吗？**
图不用背，也不用会画。要记两样：
- 一层里的顺序：RMSNorm → 注意力（Q、K 上加 RoPE，GQA）→ 残差相加 → RMSNorm → SwiGLU 前馈 → 残差相加，堆 N 层，最后 RMSNorm + Linear + Softmax 出词表概率。
- 四个替换各配一个动机：RoPE 外推好，Pre-Norm + RMSNorm 训得稳，GQA 缓存小，SwiGLU 效果好。
能说出"LLaMA 相比原版 Transformer 改了什么、为什么改"，就到面试深度了。

### 勘误与补充（课件上半篇）

- **3.1 ⑤"隐式位置编码"措辞不准：** Qwen3、DeepSeek、Llama 用的 RoPE 是显式写进注意力计算的；"隐式"指的是因果掩码本身带顺序信息、不加位置编码（NoPE）也能学到位置感。记"相对位置编码 RoPE 便于外推"即可。
- **3.2 ② 效率排序无来源：** T5 论文（2019）同算力对比中 Encoder-Decoder + 去噪效果最好；Decoder-Only 的真实优势是只预训练时 zero-shot 最强 + 结构单一好扩展，别背这个排序。
- **3.2 ④ 多模态"直接切 token"简化了：** Qwen-VL 这类方案先过一个视觉编码器（ViT）把图片变成向量，再投影成和文字同维度的 token 拼进序列；解码器不用改，但前面有一个图像编码器。
- **第四节表格把 GLM 列为 Encoder-Decoder 不准：** 初代 GLM 是单个 Transformer 做"自回归填空"（前缀双向、生成部分因果），不是两套塔；GLM-4 已是 Decoder-Only（课件 2.2 自己也这么写）。

## 架构与训练全流程 下半篇：训练四站（2026-09-29）

### 故事线一句话

预训练用"文字接龙"把世界知识压进参数，但只会续写；后训练先用 SFT 教它按对话格式答题，再用偏好学习和强化学习（RLHF → DPO → GRPO → CISPO）教它答得好、会先想再答、知道什么不能做；微调把通用助手变成"你的助手"，但能用 Prompt / RAG 解决就别训；推理时模型逐词采样，Agent 场景下一个请求就是很多次推理。第七~十节收尾：模块六的每一课正好是这条工业流水线上的一个环节（数据、架构、训练框架、后训练、评测、推理部署）。

### 🔖 本章要记

- 预训练和 SFT 的 loss 完全一样，都是"预测下一个词"；SFT 只换了数据、加了对话模板和掩码（提问部分 label = -100）。SFT 管"数据和 loss"，全量 / LoRA 管"更新哪些参数"，两者独立。
- 偏好学习的演进：RLHF 要 4 个模型（actor / ref / reward / critic）；DPO 离线用偏好对，只要 actor + ref 2 个；GRPO 用组内平均分代替 critic 当基线；CISPO 把裁剪后的 ratio detach 成权重去乘 log p，梯度保留、只封上限。
- 推理能力靠"可核对的题目 + 结果奖励 + GRPO"练出来；思考模式就是模板里的 `<think>` 开关，用更多 token 换正确率，所以按需打开。
- 微调改"怎么说"，不负责"知道什么"；LoRA 属于 PEFT；黑盒蒸馏 = 老师造数据 + 普通 SFT，白盒蒸馏要改 loss，且师生必须共用词表。

### 追问 Q&A（2026-09-29）

**Q：MiniMind 有什么用？我们能用它来做吗？**
它是一个教学用的开源项目，用纯 PyTorch 手写，从零实现一个约 64M 参数的小模型，覆盖全部训练阶段：训分词器、预训练、SFT、LoRA、DPO、PPO/GRPO、蒸馏、Agent 强化学习。用处是把大厂几千张卡的流程缩成一张卡能跑完的版本，让人亲手走一遍；模型本身能力很弱，不用于生产。它的结构就是 LLaMA 那一套（RMSNorm、RoPE、GQA 8 个 Q 头配 4 组 KV），所以也能当课件 7 的源码对照。能用，分两处：
1. 本机 CPU：下载 minimind-3 权重聊天，读模型代码对照 LLaMA 图，跑 LoRA（官方说明 CPU 也能较快跑完）。
2. 租卡日：单张 3090 预训练 + SFT 各跑 1 轮，约 2.3 小时、3 元，从随机参数训出一个能对话的模型。

**Q：SFT 的格式就是 `<|im_start|>` 那样吗？之前不是学过别的标注格式？**
是两层格式，课件 4 学的是第一层，这里看到的是第二层：
1. 存储格式（Alpaca / ShareGPT JSON）：数据集文件里怎么存，跟模型无关，人和框架都能读。
2. 对话模板（chat template）：训练前框架把 JSON 字段填进模型自己的模板，拼成一段带角色标记的文字，再算掩码。每个模型家族一套：Qwen 用 `<|im_start|>user`，DeepSeek-R1 蒸馏版用 `<｜User｜>` / `<｜Assistant｜>`。
同一个 JSON 能喂给不同模型，但模板必须和模型配套（LLaMA-Factory 里 template 参数就选这个）；选错模板，模型看到的是没见过的标记，微调效果会变差。

**Q：所以 JSON 是存下来的数据，训练和推理时模型真正看到的是对话模板拼出的文字？**
对。推理时也是同一个模板，而且是自动套的：模板存在模型目录的 tokenizer_config.json 里，调 vLLM 的 OpenAI 接口传 messages 列表，服务端会自动拼成 `<|im_start|>user…` 再送进模型。所以训练和推理必须用同一套模板，微调时选错模板，推理时就对不上。

**Q：CISPO 说"裁剪只限制更新的幅度，但保留梯度"，这是怎么做到的？**
先说 ratio：一个 token 现在的概率 ÷ 采样那一刻的概率。例子：反思词"等等"采样时概率 0.10，更新几步后 0.15，ratio = 1.5；这条回答优势 A = +1，该鼓励。
1. GRPO/PPO 的写法：min(ratio × A, 裁到 1.2 的 ratio × A) = 1.2。结果是个常数，参数怎么动它都不变，所以梯度 = 0，这个 token 本轮白学。
2. CISPO 的写法：先把 ratio 裁到上限，再 `.detach()` 冻成一个普通数字 1.2 当权重，loss = −1.2 × A × log p("等等")。梯度走 log p 这条路，所以还在，只是力度被权重封顶。
3. 为什么偏偏卡住关键 token：低概率 token 的 ratio 最容易跳（0.10→0.15 就是 1.5，而 0.90→0.95 只有 1.06），"等等""再检查"这类反思词恰好是低概率的。
本机 demo（arch_train/s5_cispo_grad.py）同一个 token 算两种 loss：grpo 梯度 0.000，cispo 梯度 −1.200。
MiniMind 源码 trainer/train_grpo.py 里只有算每个 token loss 的那几行按 loss_type 分叉，采样、打分、组内算优势全都共用，所以"换个参数就行"：
```python
if args.loss_type == "cispo":
    clamped_ratio = torch.clamp(ratio, max=args.epsilon_high).detach()
    per_token_loss = -(clamped_ratio * advantages.unsqueeze(1) * per_token_logps - args.beta * per_token_kl)
else:  # grpo（源码是三行，这里合成一行，A 即 advantages.unsqueeze(1)）
    clipped_ratio = torch.clamp(ratio, 1 - args.epsilon, 1 + args.epsilon)
    per_token_loss = -(torch.min(ratio * A, clipped_ratio * A) - args.beta * per_token_kl)
```
补充：源码里 loss_type 默认就是 cispo，上限 epsilon_high 默认 5.0（只封上限、不封下限），比 GRPO 的 1.2 宽得多。

**Q：（第五节微调）"要改行为和格式才上微调"，格式到底什么时候靠 Prompt、什么时候要微调？**
标准：规则能"说清楚、说得短"就写 Prompt；只能靠示范，或者写清楚要很长，才微调。
1. 先写 Prompt 加两三个示例，拿约 100 条真实输入跑一遍，数合格率，够用就停。
2. 要严格 JSON：先用推理框架的结构化输出（生成时强制按格式），不用训练。
3. 以下情况才微调：规则多到 Prompt 几千 token，每次调用都付延迟和钱；示例给了，长尾输入仍反复跑偏；写不成条文的东西，比如"公司口吻"，只能拿上千条样本示范。
对照例子："输出含 name/age/city 的 JSON"用 Prompt 或结构化输出；"客服按 40 条话术规范、语气始终一致"用微调。

**Q：知识蒸馏不是属于数据集、处理数据的流程吗？应该是在后训练时做？**
对一半。蒸馏是一种技术，不是训练流程里固定的一站：
- **黑盒蒸馏 = 造数据 + 普通 SFT**：就是数据集第二章 CoT 来源里的"从 R1 蒸馏"，老师回答一批题，存成数据集，训练代码不变。"蒸馏"这个动作确实发生在数据流程里。
- **白盒蒸馏改的是训练**：训练时老师要在场，或提前存好老师的概率分布；loss 在交叉熵之外加一项"和老师分布的 KL 距离"，不是换数据就能做到的。前提是师生共用同一套词表。
在哪个阶段做，取决于谁做：厂商做小模型多放在后训练（例如 Qwen3 小尺寸模型用大模型蒸馏；Gemma 2 的小模型在预训练阶段就用了蒸馏）；开发者拿 GPT/R1 的输出造数据来微调自己的模型，所以课件把它放在"微调"一节。

**Q：SFT 是什么？**
SFT = Supervised Fine-Tuning，监督微调。"监督"指每条数据都带人给的标准答案：预训练喂的是一堆文本，SFT 喂的是"这个问题 → 应该这样答"。好比预训练是让学生自己读完整座图书馆，SFT 是老师拿着题和标准答案一道道示范。
- 技术上 loss 和预训练一样，都是"预测下一个词"。区别只有两点：数据按对话模板拼成一问一答；只对回答部分算 loss，提问部分的 label 设成 -100。
- 它在流程里出现两次：后训练的第一步（厂商做），以及你拿自己的数据去微调（你做）。
- 最容易混的一点：SFT 说的是"用什么数据、算什么 loss"，全量微调 / LoRA 说的是"更新哪些参数"，两个维度互相独立，所以"用 LoRA 做 SFT"是一句正常的话。

## 模块详解 1：RMSNorm（2026-09-30 学《7.大模型模块详解 / RMSNorm》）

### 故事线一句话

归一化是把每个 token 的向量缩放到标准大小、防止层层相乘后数值爆炸；LayerNorm 要"减均值 + 除标准差"，RMSNorm 发现真正起作用的是缩放，就只"除以均方根、再乘 γ"，省计算、效果持平，成了 LLaMA / Qwen / DeepSeek 的标配。

### 🔖 本章要记

- RMS（均方根）= 平方 → 取平均 → 开根号。RMSNorm(x) = x ÷ RMS(x) × γ，比 LayerNorm 少了减均值这一步和平移参数 β。
- 手算例子 [2, 4, 4, 6]：LayerNorm 得 [-1.41, 0, 0, 1.41]（中心挪到 0）；RMSNorm 得 [0.47, 0.94, 0.94, 1.41]（比例不变、均方根 = 1）。
- 实现细节：先转 float32 再算平方均值，算完转回 BF16，因为 BF16 精度低，平方求和容易放大误差。
- 位置：每层两个 Pre-Norm（注意力前的 input_layernorm、前馈网络前的 post_attention_layernorm，名字里有 post 但在前馈网络之前）+ 最后一个 norm；Qwen3-0.6B 另有每层的 q_norm / k_norm（QK-Norm），共 113 个。demo：meishiyi/09_HuggingFace/arch_train/s7_rmsnorm.py。

### 追问 Q&A（2026-09-30）

**Q：应该不止每层两次吧？课件 6 的 LLaMA 图里，Embeddings 之后、注意力之前还有一次 RMSNorm。**
那一个就是每层两个里的第一个，不是额外多出来的。关键看图里的虚线框和右边的 **Nx**（框里的内容重复 N 次，每层一份）。图右半边从下往上一共画了 3 个 RMS Norm：
1. Embeddings 正上方、注意力之前：在框内，就是 input_layernorm。它紧贴 Embeddings 画，看着像"嵌入后单独做一次"，其实第 2~N 层前面也各有一个。
2. Feed Forward（SwiGLU）下面：在框内，就是 post_attention_layernorm。
3. 最上面、Linear 下面：在框外，全模型只有一个 norm。
所以是 2N + 1：Qwen3-0.6B 的 N = 28，得 57 个；再加 Qwen3 独有、图里没画的 q_norm / k_norm 56 个，共 113 个。
读图补充：从 Embeddings 出来有一根线绕过 RMS Norm 和注意力直接接到 ⊕，这是残差。Pre-Norm 的完整含义是：只有送进注意力的那一份先归一化，走旁路的那一份原样保留，再和注意力输出相加；原版 Transformer 则是先相加、再在 Add & Norm 里归一化（Post-Norm）。

**Q：Pre-Norm 实际计算时，是 x + (RMSNorm + 注意力) 作为下一个 RMSNorm 的输入吗？图里还有位置编码是怎么回事？**
对，括号改成"套"而不是"加"：先 RMSNorm，再把结果送进注意力。一层完整算两步：
1. h = x + Attention(RMSNorm(x))：h 就是下一个 RMSNorm（前馈网络前那个）的输入。
2. out = h + FFN(RMSNorm(h))：out 就是下一层的 x，进入下一层第一个 RMSNorm。
Qwen3 源码 transformers/models/qwen3/modeling_qwen3.py 的 Qwen3DecoderLayer.forward 就是这几行：`residual = hidden_states` → `input_layernorm` → `self_attn` → `residual + hidden_states` → 再来一遍 `post_attention_layernorm` → `mlp` → `residual + hidden_states`。
对比 Post-Norm（原版 Transformer）：x = LayerNorm(x + Attention(x))，归一化压在相加之后，残差主干每层都被归一化一次。
为什么选 Pre-Norm，根因一条：残差这条"主干道"上没有任何归一化，从最后一层到第一层是一路相加直通，梯度能原样传回去，所以几十上百层也训得稳；Post-Norm 的每次归一化都挡在主干道上，层数一深就难训，要靠学习率预热（warmup）小心伺候。
位置编码：图里 Q、K 旁边的蓝色小圆圈，图例写的是 Rotary Positional Encodings，即 RoPE。和原版的区别有三点：
- 原版在最底下把位置编码加到词向量上，只加一次；RoPE 在每一层的注意力里面做。
- 只作用在 Q 和 K 上，V 不动。因为位置影响的是"谁该关注谁"，这由 Q·K 打分决定；V 是被搬运的内容，不需要位置。
- 顺序：Q/K 投影 →（Qwen3 的 q_norm/k_norm）→ 旋转（apply_rotary_pos_emb）→ 算注意力分数。
RoPE 怎么"转"留到课件 7 第三篇讲。

**Q：LLaMA 第一个就是 RMSNorm，怎么说主干道上没有归一化？是不是说反了，原版才没有？图里带圈的 + 到底是位置编码还是残差？请把原版 Transformer 和 LLaMA 分别理一遍，RoPE 也没懂。**
先确认你的理解：归一化 = 把数稳在一个大致范围；残差 = 把输入原样往上传、防梯度消失。都对。两张图的差别就一件事：归一化放在"主干道"上，还是放在"支路"上。
- **主干道**：残差那条线，负责把输入原样往上传。
- **支路**：分出去做计算（注意力或前馈网络），算完回来和主干道相加。汇合点就是相加。

原版 Transformer（左图，以左边编码器为例），一层的流程：
1. Input Embedding 得到词向量。
2. 底部带正弦波图标的 ⊕：加位置编码。你原来理解对，这个 ⊕ 是位置编码，全模型只加一次。
3. 进 Nx 框后分两路：支路进 Multi-Head Attention；主干道是那根绕过注意力、直接连进 Add & Norm 的线。
4. Add & Norm：Add 就是残差相加（原版没画成 ⊕，藏在方框里），Norm 是相加之后做 LayerNorm。x1 = LN(x + Attn(x))。
5. 前馈网络同样：x2 = LN(x1 + FFN(x1))，x2 进下一层。
关键：LN 在汇合之后，下一层接到的主干道数据每层都被 LN 重新缩放一次，所以原版是"主干道上有归一化"，叫 Post-Norm（归一化在相加之后）。

LLaMA（右图），一层的流程：
1. Embeddings 得到词向量，底部没有 ⊕，位置不在这里加。
2. 进 Nx 框后分两路：支路先 RMSNorm → 投影出 Q、K、V → Q、K 用 RoPE 转（蓝色小圈）→ 注意力；主干道是左边那根从 Embeddings 直接绕到 ⊕ 的线，它跳过了 RMSNorm。
3. ⊕ 是残差相加：h = x + Attn(RMSNorm(x))。⊕ 在注意力之后，RMSNorm 在支路入口，两者不挨着。
4. 前馈网络同样：out = h + FFN(RMSNorm(h))，⊕ 后面没有归一化，out 原样进下一层。
5. N 层之后：最后一个 RMSNorm → Linear → Softmax。主干道一路只做加法、数会越加越大，所以出口前补一次。
关键：你看到的"第一个 RMSNorm"在支路上，不在主干道上；归一化在子层之前，叫 Pre-Norm。

归一化加在哪合适：Pre-Norm 让两个目的都更彻底。归一化是为了让"送去计算的数"范围稳定，Pre-Norm 恰好在送进注意力 / 前馈网络之前做；残差是为了原样传递，Pre-Norm 的主干道上只有加法，没人改它，梯度从最后一层一路直通回第一层。原版每层都在主干道上 LN 一次，层数一深梯度要穿过几十次 LN，难训，要靠学习率预热（warmup）。代价是 Pre-Norm 主干道数值会累积变大，所以最后补一个 norm。

图里的 ⊕ 归纳：原版底部带正弦波的 ⊕ = 位置编码；原版的残差相加藏在 Add & Norm 的 Add 里；LLaMA 的两个 ⊕ = 残差相加；LLaMA 的位置编码是 Q、K 旁边的蓝色小圈。

RoPE 直观版：
1. 为什么要位置：注意力打分只看内容，"我爱你"和"你爱我"打分一样，必须告诉模型谁在前谁在后。
2. 原版做法：把一个"位置向量"加到词向量上（底部 ⊕），是绝对位置，训练见过多长就只认多长（BERT 的 512）。
3. RoPE 做法：不加，改成"转"。把 Q、K 看成钟表指针，第 m 个位置就转 m × θ。
4. 为什么有用：打分 = Q·K，两根指针的点积只取决于夹角，所以打分只和"相隔几格"有关（相对位置），和绝对位置无关，这就是上半篇说的外推方便。
demo（arch_train/s8_rope_intuition.py，二维，θ = 0.3）：位置 5 对 3、位置 105 对 103 都是相隔 2 格，打分都是 0.947；位置 5 对 4 相隔 1 格，打分 0.810。
只转 Q、K 是因为位置只需要影响打分。真实模型怎么把几千维切成多组、各转不同速度（rope_theta），在课件 7 RoPE 篇讲。

**Q：到底什么时候做残差和归一化？"每一层"的层怎么理解，RMSNorm 算一层吗？**
RMSNorm 不算一层，它是层里面的零件。"28 层"数的是 Nx 虚线框：一个框 = 一层（Transformer 层 / 解码层），框里装着 4 个零件：2 个大零件（注意力、前馈网络）和 2 个小零件（2 个 RMSNorm）。LayerNorm 名字里的 Layer 是"对一整个向量做归一化"的意思，和"28 层"的层无关。
Qwen3-0.6B 骨架打印（arch_train/s9_layer_parts.py）：
- 整个模型 = embed_tokens（词向量表）→ layers（28 个层）→ norm（最后那个 RMSNorm）→ lm_head（图里的 Linear）；rotary_emb 只负责算 RoPE 的旋转角度。
- layers[0] 里的零件 = self_attn、mlp、input_layernorm、post_attention_layernorm。
什么时候做：规则只有一条，**每个大零件外面都包同一套"三步包装"**，一层有 2 个大零件，就包 2 次：
1. 留底：把当前的 x 存一份（这份就是残差）。
2. 归一化后加工：复制一份做 RMSNorm，送进大零件（注意力或前馈网络）算。
3. 加回：把大零件的输出加到留底的那份上（图里的 ⊕）。
类比：一份原稿要依次经过 28 个车间，每个车间 2 个工位。每个工位都不直接改原稿，而是复印一份、把复印件调成标准亮度（归一化）、在复印件上算出"要补充的内容"，最后把补充贴回原稿（残差相加）。原稿本身从不被调亮度，这就是 Pre-Norm；原版 Post-Norm 则是贴完之后把原稿整体再调一次亮度。
所以 Qwen3-0.6B 一次前向一共做 28 × 2 = 56 次"留底 → 归一化 → 加工 → 加回"，最后再做 1 次 RMSNorm。

**Q：为什么 RMSNorm 要放在注意力和前馈网络之前？有什么意义？**
一句话：注意力和前馈网络只在"正常大小的数"上好用，而主干道上的数会越加越大，所以每次进门前都要把数调回正常大小。
1. 主干道为什么越来越大：每个工位都是 x = x + 新内容，只加不减。Qwen3-0.6B 读"人工智能正在改变世界"实测（arch_train/s10_why_prenorm.py），主干道上 x 的大小（RMS）：第 0 层 0.03 → 第 1 层 0.32 → 第 7 层起约 105，涨了三千多倍；而进门前经过 RMSNorm 后只有 0.14 ~ 9.41。进门后的大小 = 1 × γ，γ 是每层训练学出来的旋钮，所以后面几层偏大是模型自己选的，不是历史累积失控。
2. 数太大会怎样：注意力要做 softmax。同一组打分 [2, 1, 0.5, 0]，正常时权重是 [0.58, 0.21, 0.13, 0.08]，四个词都看；放大 20 倍后变成 [1, 0, 0, 0]，只盯一个词。而且此时打分再怎么微调，输出都还是 [1, 0, 0, 0]，梯度约等于 0，学不动（和 CISPO 那里"裁成常数梯度就没了"是同一个道理）。
3. 为什么放门口，不放在主干道上：放主干道会每次改动原稿（原版 Post-Norm），残差"原样传递"就打了折扣，深层难训；放门口既保护了零件，又不碰原稿。
类比：调音台上各路信号混在一起，总线越来越响（主干道）；每个效果器入口都有一个输入增益旋钮（RMSNorm + γ），把音量调到效果器能处理的范围，不然就爆音（softmax 饱和）；总线本身不去动它。

**Q：那原版的 Post-Norm 有什么问题？按这么说它不是没意义了吗？**
有意义。Post-Norm 解决的是同一个问题，只是换了个位置：相加之后把主干道整体归一化，下一层拿到的数自然也是正常大小。原版 Transformer（6 层）、BERT（12 / 24 层）都用 Post-Norm，训得很好。
它的问题只在层数深了才出现：每层都把"原稿 + 新内容"整体缩回标准大小，原稿在里面的份额每层被压一次，越传越淡。玩具实验（arch_train/s11_post_vs_pre.py，只改 Norm 位置，看最后输出和最初输入的相似度，1 = 一模一样、0 = 毫无关系）：
- 6 层：Post-Norm 0.85，Pre-Norm 0.87，几乎一样。
- 12 层：Post-Norm 0.71，Pre-Norm 0.77。
- 48 层：Post-Norm 0.25，Pre-Norm 0.50。
反过来看训练也一样：梯度从最后一层往回传，Post-Norm 每经过一层都被归一化压一次，传到前面几层已经很弱，深层模型容易训崩，必须靠学习率预热（warmup，原版 Transformer 预热了 4000 步）小心起步。
大模型动辄几十层（Qwen3-0.6B 28 层、DeepSeek-V3 61 层），一次训崩就是几百万的算力白烧，所以选更稳的 Pre-Norm。这是取舍不是淘汰：有研究（微软 DeepNet，2022）发现 Post-Norm 只要训得稳，最终效果还略好，于是专门改进它去训上千层的模型。
（玩具实验只有前馈网络、没训练，数字只看趋势。）

### 勘误与补充（课件 RMSNorm）

- **结论图说"GPT-NeoX 普遍采用 RMSNorm"不对**：GPT-NeoX 用的是普通 LayerNorm；正确例子是 LLaMA、Qwen、DeepSeek。
- **结论图说"训练稳定性优于 LayerNorm"**：与课件正文和原论文的"基本持平"矛盾，以"持平"为准。
- **"少一次统计，少一次同步（分布式要通信）"不成立**：LayerNorm / RMSNorm 都只在单个 token 自己的向量内统计，不跨卡；要跨卡同步统计量的是 BatchNorm。
- **课件没提 QK-Norm**：Qwen3 在注意力里给 Q、K 各加一个 RMSNorm，用来防止注意力分数过大；LLaMA 没有。

## 模块详解 2：从 MHA 到 MQA 与 GQA（2026-09-30 学《7.大模型模块详解 / 从MHA到MQA与GQA》）

### 故事线一句话

解码时每生成一个 token 都要把整份 KV Cache 从显存读一遍，缓存大小和 KV 头数成正比；Q 只用一次不缓存，K、V 却要为全部历史存着，所以只在 K、V 上省：MHA 每个 Q 头配一份 K/V，MQA 全部 Q 头共用一份，GQA 折中成几个 Q 头一组共用一份，缓存砍到几分之一、质量几乎不掉，成了主流。

### 🔖 本章要记

- 只省 K、V 不省 Q 的根因：KV Cache 只存 K、V（历史 token 每步都要用），Q 只有当前 token 用一次、不缓存；Q 还决定每个头"找什么"，是多头多样性的来源。
- KV Cache = 层数 × KV 头数 × head_dim × 2（K 和 V）× 每个数的字节 × token 数。Qwen3-0.6B（28 层、16 Q 头、8 KV 头、head_dim 128、BF16）4096 token：MHA 896 MB，GQA 448 MB，MQA 56 MB。
- 分组规则：Qwen3-0.6B 每 2 个相邻 Q 头共用 1 个 KV 头（Q0、Q1 → KV0 …… Q14、Q15 → KV7）；KV 头数 = Q 头数时是 MHA，= 1 时是 MQA。
- 实现：缓存里存的是 8 个 KV 头（实测第 0 层 K 形状 [1, 8, token数, 128]）；算注意力时才用 repeat_kv 临时复制成 16 份。demo：arch_train/s12_gqa_cache.py。

### 勘误与补充（课件 GQA）

- **MQA、GQA 两张图的 KV Cache 公式错了**：图上写 MQA 是"n_heads + 1 个/层"、GQA 是"n_heads + n_heads / g 个/层"，把 Q 也算进了缓存。Q 不缓存，正确是 MQA 每层 2 个（1 个 K + 1 个 V），GQA 每层 2 × 组数；只有 MHA 图的 n_heads × 2 是对的。
- **"LLaMA-2、GPT-3 等采用 GQA"不对**：GPT-3（2020）用的是普通 MHA，GQA 论文是 2023 年才出的；LLaMA-2 也只有 34B / 70B 用了 GQA，7B / 13B 仍是 MHA。
- **MQA"计算量减少"说得不准**：每个 Q 头照样要和 K 算打分，注意力计算量基本不变；省的是 KV Cache 显存和每步要读的字节数。解码卡在带宽上（课件 5 Roofline），所以读得少就快。
- **GQA"每组生成独立的 Q 矩阵"措辞不对**：是每个头一个独立的 Q，组内共享的只有 K、V。
- **课件示例代码没有因果掩码**：文档字符串写了 mask 参数，但 forward 里没有；用在解码器里要加上"只能看前面"的掩码。

## 模块详解 3：RoPE 旋转位置编码（2026-09-30 学《7.大模型模块详解 / RoPE旋转位置编码》）

### 故事线一句话

注意力本身不认顺序，必须加位置信息。原版 Transformer 在最底下把位置向量加进词向量，位置和内容搅在一起，而且只加一次。RoPE 改成在每层注意力里把 Q、K 按位置转一个角度：位置 m 的 Q 转 mθ，位置 n 的 K 转 nθ，点积后只剩角度差 (n−m)θ，于是打分只看"内容 + 相隔几格"，和绝对位置无关。真实模型把 head_dim 128 拆成 64 对，每对转速不同，快的看近处的先后，慢的看远距离。

### 🔖 本章要记

- 位置：每层注意力里，q_norm / k_norm 之后、算打分之前，只转 Q 和 K，不转 V（V 是要取走的内容，不参与打分）；不像原版那样在 Embedding 后加一次。
- 核心性质：转过的 Q 与 K 点积 = 原 q 与 k 夹着"转 (n−m)θ"再点积，只依赖相对距离。实测同一对 q/k，位置 (5,3)、(1005,1003) 打分都是 7.635。
- 多转速：64 对的转速 θ_i = rope_theta^(−2i/128)。Qwen3-0.6B 的 rope_theta = 1,000,000，第 0 对 6 格转一圈、第 32 对约 6283 格、第 63 对约 506 万格，像秒针、分针、时针。
- 外推：RoPE 本身超出训练长度也会变差，长上下文靠改转速（NTK / YaRN 等）。Qwen3 原生 32K，用 YaRN 扩到 128K。demo：arch_train/s13_rope_freq.py。

### 勘误与补充（课件 RoPE）

- **"正余弦编码计算效率低、需额外存储位置向量"不对**：正余弦编码是用公式现算的，没有参数、不占存储。需要存一张位置表的是"可学习的绝对位置编码"（BERT、GPT-2 那种 512 / 1024 行的表）。正余弦编码真正的问题是只在最底下加一次、和内容混在一起，相对位置要靠模型间接学。
- **"注意力分数完全由相对位置差决定"说过头了**：打分 = q、k 的内容 + 相对距离，和绝对位置无关。内容仍然是主体，同样相隔 2 格，换一对 q、k，打分完全不同。"模型无需额外学习位置关系"同理：距离信息会自动进入打分，但"怎么利用距离"仍要靠训练学出 q、k。
- **正文写 (m−n)、公式写 R(n−m)**：两者只差正负号，都表示相对距离，按公式 (n−m) 理解即可。
- **图里的 10000 是原版 RoFormer / LLaMA-1、2 的底数**：Qwen3、MiniMind 都用 1,000,000。底数越大，慢指针越慢，能区分的距离越长，这是长上下文模型的常见改法。
- **图里是相邻两维 (x1, x2) 配对，HF 源码是"前一半配后一半"**：rotate_half 让第 i 维和第 i+64 维配对。两种写法数学上等价，但权重要按对应写法训练或转换，不能混用。
- **"很好地支持长序列外推"要打折**：纯 RoPE 超出训练长度后效果也会明显下降，实际靠 NTK / YaRN 等缩放转速来扩长度。
- **手写图小笔误**：x_m 下面的三个箭头应是 q_m、k_m、v_m，图里写成了 k_n。
- **课件第二张图是作者本机路径**（D:\HuaweiMoveData\…），打不开，内容可忽略。

## 模块详解 4：图解 MoE 结构（2026-09-30 学《7.大模型模块详解 / 图解MOE结构》）

### 故事线一句话

MoE 只换掉每层后半段的 FFN：把一个大 FFN 换成 N 个小 FFN（专家），再加一个路由。每个 token 在每一层由路由挑出 k 个专家来算，结果按路由概率加权求和。这样总参数（能装的知识）变得很大，但每个 token 实际算的只有一小部分，所以同样的计算量能换来更大的模型。代价是显存仍要装下全部专家，而且路由容易偏心，需要负载均衡（第三部分）。

### 🔖 本章要记

- 位置：每层 = 注意力 + FFN，MoE 只替换 FFN 那半（post_attention_layernorm 之后）。注意力、RMSNorm、RoPE、残差都不变。外面看 MoE 层就是一个 FFN，输入输出形状一样。
- 路由三步：x 乘路由权重 W（一个无偏置的 Linear，hidden → 专家数），softmax 变概率，取 top-k。输出 = Σ（选中专家的概率 × 该专家的输出）。每个 token、每一层各选各的；专家不分领域，只有 token 层面的偏好。
- 省的是计算，不是显存：Qwen3-30B-A3B 每层 128 个专家选 8 个，总参数 30.5B，每个 token 只算约 3.3B，但 30.5B 全要装进显存。MiniMind 的 minimind-3-moe 是 198M-A64M（4 个专家选 1 个）。demo：arch_train/s14_moe_router.py。
- 负载均衡：路由会强者愈强，最后都挤到一个专家。解法有三种。
  - 辅助损失：主流是 Switch 版，= 专家数 × Σ（专家 i 分到的 token 比例 × 路由给它的平均概率）。均匀时约 1，偏心时变大（实测 1.00 对 3.03），乘一个小系数（Qwen3-MoE 默认 0.001）加进总损失。
  - 专家容量：每个专家最多收 N 个 token，满了走第二志愿；都满就"溢出"，这层输出 0，只靠残差传下去。
  - DeepSeek-V3 改用"无辅助损失"：给每个专家的路由分数加一个偏置，被选多了就调低。demo：arch_train/s15_moe_balance.py。

### 勘误与补充（课件 MoE 第一、二部分）

- **"每个医生只治一种病、专注特定领域"（第 08 节图注）和第 02 节自相矛盾**：第 02 节说得对，专家并不专攻某个领域，只在 token 层面有些偏好。图注这段比喻是错的。
- **"What is 1+1?" 整句送进 Numbers 专家的几张图是简化**：实际上每个 token 在每一层都单独选专家，同一句话里 "What"、"1"、"?" 走的专家可以都不一样。
- **第 02 节那张图只画了一个 Router，还标了 "Expert 2n"**：实际每个 MoE 层都有自己的路由；"2n" 是笔误，应为 Expert 2。
- **"路由本身也是一个 FFNN"不准**：Mixtral、Qwen3-MoE 的路由就是一个无偏置的 Linear（hidden → 专家数），没有隐藏层和激活函数。第 08 节写的 x·W 才是对的。
- **第 05 节表格"计算成本下降 >80%"要说清跟谁比**：跟"同样 10 亿总参数的稠密模型"比，计算只剩约 2/10。但跟表里 1 亿的稠密模型比，k=2 的 MoE 每次要算 2 亿，反而多一倍。而且显存要装下全部 10 亿，这一点表里没写。
- **"MoE 表现往往比稠密模型更好"要加条件**：同样的计算量，MoE 通常更强；同样的总参数，稠密模型通常更强。
- **"MoE 更快"是按计算量算的理论值**：MiniMind README 说，用朴素 PyTorch 训练时，token 要先按专家分桶、再逐个专家前向，调度开销很大。4 专家 top-1 的训练反而比同尺寸稠密模型慢约 50%，要靠融合算子（DeepSpeed-MoE、Megatron、Triton kernel）才能兑现。
- **第 03 节的 FFN 是原版结构**（512 → 2048 → 512，两个矩阵）：Qwen3 / LLaMA 的 FFN 和每个专家都是 SwiGLU（gate / up / down 三个矩阵）。一个 Qwen3-30B-A3B 专家 = 3 × 2048 × 768 ≈ 4.7M 参数。SwiGLU 留到重讲 LLaMA 图时讲。

### 勘误与补充（课件 MoE 第三部分）

- **第 09 节开头"此外，KeepTopK 策略……"前面缺了一段**：原文（Maarten Grootendorst《A Visual Guide to MoE》）先讲的是 Noisy Top-k，即给路由分数加随机噪声，让弱专家也有机会被选中，再只保留 top-k。课件删了加噪声这一步。光有 top-k 本身并不均衡负载。
- **第 10 节第一句"由此得到重要性分数"缺了定义**：重要性 = 一批 token 里，路由给某个专家的概率加起来。
- **CV 第二张图的 0.19 应约为 0.21**：标准差 0.055 被四舍五入成 0.05 后再除，结果偏小。第一张图的 1.11 没问题（实算 1.12）。
- **CV² 辅助损失是 2017 年的老做法**：Switch Transformer 之后的主流（Mixtral、Qwen3-MoE 在 HF 里的 load_balancing_loss_func）是"token 比例 × 平均概率"那个版本，前面乘小系数 router_aux_loss_coef（Qwen3-MoE 默认 0.001）。DeepSeek-V3 主要靠"无辅助损失"的偏置调节。
- **"达到容量后自动路由到下一个可用专家"不准**：是去这个 token 自己 top-k 里的下一个志愿，不是随便找空闲专家。都满就溢出，这层 MoE 对它输出 0，靠残差原样传到下一层，这正是残差"主干道"的作用。
- **专家容量主要用在训练（尤其专家并行）里，用来固定张量形状**：HF 的 Mixtral / Qwen3-MoE 实现和 vLLM 推理都是不丢 token 的（没有容量上限）。
- **错别字**：标题"如何选择激专家"应为"如何选择激活专家"；"Expert Capacity4"的 4 是原文脚注编号残留。

## 重讲 Transformer vs LLaMA 结构图（2026-10-02，课件 6 架构图 × MiniMind 模型代码）

### 故事线一句话

LLaMA 图从下往上分三段：Embeddings 只做一次；中间 Nx 框里的那一层重复 N 次，前半段是 RMSNorm、带 RoPE 的 GQA 注意力、⊕ 残差，后半段是 RMSNorm、SwiGLU 前馈、⊕ 残差；最上面是最后一次 RMSNorm、Linear 和 Softmax。和原版 Transformer 相比，砍掉了编码器和交叉注意力，零件换了五处：LayerNorm 换成 RMSNorm、Post-Norm 换成 Pre-Norm、底部加位置换成每层转 RoPE、MHA 换成 GQA、ReLU 前馈换成 SwiGLU。MiniMind（对齐 Qwen3）就是这张图的完整代码，另外多了 q_norm / k_norm。

### 🔖 本章要记

- 一层的真实调用顺序（MiniMind 实测）：input_layernorm → q/k/v_proj → q_norm、k_norm → RoPE（只转 Q、K）→ 注意力（KV 头 repeat_kv 扩成 Q 头数）→ o_proj → ⊕ 残差 → post_attention_layernorm → gate_proj、up_proj → SiLU(gate)×up → down_proj → ⊕ 残差。N 层之后接 model.norm → lm_head。
- 五处替换各一个动机：RMSNorm 省掉减均值、更快且效果相当；Pre-Norm 让主干道不被归一化打断，深了也稳；RoPE 让打分直接带相对距离；GQA 把 KV Cache 砍成几分之一；SwiGLU 同参数量下效果更好（经验结论）。
- SwiGLU = down( SiLU(gate(x)) × up(x) )，三个矩阵。gate 像每一维的水龙头，决定 up 的这一维放多少过去。SiLU(x) = x·sigmoid(x)，负数不硬截成 0：手算 SiLU([2, −2, 0]) = [1.76, −0.24, 0]，ReLU 是 [2, 0, 0]。
- 参数大头在 FFN：minimind-3（hidden 768、8 层、8 Q 头 / 4 KV 头、中间维 2432）一层注意力 1.77M、FFN 5.60M，全模型 63.9M。这也是 MoE 只拆 FFN 的原因。demo：arch_train/s16_llama_walk.py（minimind_model.py 为官方源码拷贝）。

### 勘误与补充（LLaMA 图）

- **图上写"Grouped Multi-Query Attention"是 LLaMA-2 大模型 / LLaMA-3 的画法**：LLaMA-1 和 LLaMA-2 7B / 13B 仍是 MHA（见 GQA 章勘误）。
- **图里没有 q_norm / k_norm**：这是 Qwen3（以及对齐它的 MiniMind）在 LLaMA 之上加的，用来稳住注意力打分的大小。LLaMA 本身没有。
- **最上面多出的 RMS Norm 不是装饰**：Pre-Norm 让主干道一路只做加法，最后输出的数很大（Qwen3 实测 RMS 约 100），所以在 Linear 之前必须再归一化一次。原版 Post-Norm 每层出口已经归一化，所以不需要。
- **SwiGLU 的中间维为什么不是 4 倍**：三个矩阵比原版两个多一个，为了总参数量不变，中间维从 4d 缩到约 8/3·d（LLaMA-1 7B：4096 → 11008）。MiniMind 用 ⌈d·π/64⌉·64 = 2432（约 3.17 倍），Qwen3-0.6B 是 1024 → 3072（3 倍）。
- **为什么 SwiGLU 更好没有理论证明**：提出它的论文（Shazeer 2020《GLU Variants Improve Transformer》）只给了实验结果，原文自嘲"归功于神的眷顾"。面试时答"同参数量下困惑度更低，是经验结论"即可。
- **图顶上的 Softmax 只在推理采样时用**：训练时 logits 直接进交叉熵（MiniMind 的 F.cross_entropy 内部自带 softmax）。
