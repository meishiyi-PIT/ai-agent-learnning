## 1. 一句话抓住这个项目

**多商家电商的客服 + 售后系统：用户在 H5 聊天 → LangGraph Agent 查订单/查资料/生成换货方案 → 客户确认 → 主管审批 → 后台 worker 经 RabbitMQ 推到外部 OMS 执行换货。**
模型只能"提候选动作"（返回工具名 + 参数），权限、事务、幂等、审批全部由应用代码判定——和智保通"模型提候选，Harness 管裁决"是同一条脊柱。

课程的真正主题是**后端工程**：并发、状态一致、任务恢复、性能测量、流式输出、部署运维。Agent 是载体。

### 课件五层架构图 ↔ 代码目录对照

（图：`zhifu-platform/docs/architecture/zhifu-platform-architecture-v2.png`，标注为"目标架构"）

| 层 | 图上写的 | 代码里实际在哪 | 备注 |
|---|---|---|---|
| 01 接入层 | H5 / 后台 / Webhook / Nginx / FastAPI / SSE | `frontend/`（Vue3+Vite，H5 用 Vant，后台用 Element Plus）；`src/zhifu/app.py` 注册 15 个 router；SSE 在 `modules/conversations/stream.py`；Webhook 在 `modules/channels/` | 多副本入口用的是 HAProxy（`ops/haproxy`），没有 Nginx |
| 02 业务与 Agent 层 | 八个能力格 | `modules/identity`、`channels`、`conversations`、`after_sales`、`knowledge`+`memory`、`agent_runtime`、`billing`（模型与用量）、`integrations`（OMS 集成）；控制面 = `merchant/`（发布 AgentRelease）+ `platform/`；`storefront/` 商城、`notifications/`、`reminders/` | 全部在**同一个进程**里互相直接调用（模块化单体） |
| 03 数据与中间件 | MySQL / Redis×2 / Milvus / RabbitMQ+Celery / OSS | MySQL（`migrations/` 31 个版本）；Redis cache（限流）+ Redis state（并发额度、心跳、记忆）；Milvus + BGE-M3 推理服务（`modules/knowledge/inference.py`，HTTP :8200）；RabbitMQ 用 `aio-pika` 直连（`integrations/worker.py`） | **Celery、OSS 代码里不存在**，只是目标架构 |
| 04 基础设施 | Docker Compose / K8s / vLLM | `Dockerfile`、`compose.yaml`（中间件）、`compose.runtime.yaml`（应用进程）、`compose.scale.yaml`（多副本）；vLLM 材料在课件 `materials/inference/` | K8s、GPU 未实施 |
| 05 运维与交付 | OpenTelemetry / Prometheus / Grafana / pytest | `monitoring/api.py`（独立进程，`/metrics`）+ `core/telemetry.py`；`ops/{prometheus,alertmanager.yml,grafana}`；`operations/release_check.py`；`tests/`（84 个文件，其中 37 个 `*_acceptance.py` 需真实组件） | **OpenTelemetry 不存在** |

## 3. 主链路 A：一条聊天消息怎么变成回复

```mermaid
flowchart TD
  U[用户在 H5 发消息] --> M["POST /openapi/v1/conversations/{id}/messages<br/>conversations/api.py:188 message"]
  M --> AM["accept_message  conversations/api.py:206<br/>一个事务：authenticate → 会话控制权/版本 → 幂等(command_key)<br/>→ 选最近 12 条历史 → queue_run → 写 conversation_events(message.user) + agent_runs(QUEUED)"]
  AM --> R["返回 201 + run_id（不等模型）"]
  R --> SSE["前端订阅 GET /conversations/{id}/events<br/>conversations/stream.py:84 events<br/>Last-Event-ID 续传，Redis sse:* 名额"]

  W["agent worker 循环<br/>agent_runtime/worker.py:218 main"] --> C["claim  worker.py:30<br/>选租户(轮询 tenant_dispatch) → 选最早 run<br/>→ Redis 额度 acquire(capacity.py:75, Lua)<br/>→ status=RUNNING, lease_token+1, lease_until=+125s"]
  C --> E["execute_one  worker.py:139<br/>build_graph(runtime.py:255) → graph.ainvoke(超时 120s)"]
  E --> L["load 节点 runtime.py:261<br/>locked_run(:51) 复核 → 读 next_node"]
  L -->|model| MD["model 节点 runtime.py:266<br/>T1 复核+校验引用 → 事务外：select_context(context.py:48) 选历史<br/>→ ChatOpenAI.astream（bind_tools）→ DraftStream 草稿事件(streaming.py:12)<br/>→ T3 复核后写 messages / step / next_node"]
  MD -->|返回 tool_calls| T["tools 子图 runtime.py:99<br/>T1 复核 → 事务外：search_knowledge(Milvus) / run_specialists<br/>→ T2 复核 → invoke_tool(tools.py:67) 走 AfterSalesService<br/>→ 写 ToolMessage，next_node=model"]
  T --> L
  MD -->|返回正文| F["finish_run  conversations/service.py:96<br/>写 message.assistant，active_run_id=None，run COMPLETED"]
  T -->|需补充信息 / 需客户确认+审批| WAIT["status=WAITING_USER / WAITING_APPROVAL，next_node=wait<br/>inputs.py:48 pause_for_input / business_wait.py:30 pause_for_business"]
  WAIT -. "客户补充 /inputs 或 审批事件 reconcile(business_wait.py:157) → 重新 QUEUED" .-> C
  F --> SSE
```

模型可调的工具（`tools.py:36 DEFINITIONS` + `:46 model_tools`）：`search_orders`、`get_order`、`get_ticket`、`create_exchange_proposal`、`search_knowledge`、`consult_specialists`（发布配置开启协作才有）、`request_clarification`。
**确认、审批、取消、提交 OMS 都不在工具清单里**——模型永远碰不到这些动作。

```mermaid
flowchart TD

  S1["主管 POST /approvals/{id}/decisions<br/>api.py:173 decide"] --> CMD2["execute → decide service.py:505<br/>不能自审 → approvals=APPROVED, tickets=APPROVED<br/>+ business_events(after_sale.approved)  ← Outbox"]
  CMD2 --> PUB["fulfillment worker · publisher<br/>publish_one integrations/worker.py:78<br/>领取 PENDING 事件(FOR UPDATE SKIP LOCKED, 30s 租约)<br/>→ RabbitMQ publish 等 confirm → 标 SENT"]
  PUB --> MQ[(RabbitMQ)]
  MQ --> CON["consumer · consume_one :104<br/>→ prepare_event fulfillment.py:46<br/>事务外 GET OMS 订单快照 → 事务内 consumer_receipts 去重"]
  CON --> PREP["prepare :85<br/>复核租户/店铺/审批人/确认人/规则/连接器/数量<br/>→ external_operations(稳定 operation_id :175) + reservations(HELD)<br/>+ tickets=PROCESSING"]
  PREP --> EXE["executor×4 · execute_due :216<br/>领取到期操作(120s 租约) → OmsClient.process(client.py:50)<br/>首次 PUT /exchanges/{operation_id}，重试先 GET"]
  EXE --> OMS["OMS 服务 oms/api.py:181 submit<br/>按 operation_id 幂等"]
  OMS --> RR["record_result :245<br/>None→RESULT_UNKNOWN 5s 后再查<br/>FAILED→释放预占 / COMPLETED→消费预占，工单 COMPLETED"]
```

### 4.1 链路 B 的表

| 表 | 关键约束 | 作用 |
|---|---|---|
| `tickets` / `proposal_versions` / `confirmations` / `approvals` | `approvals` 唯一 (proposal_id, proposal_version)；状态 CHECK | 一个方案版本只有一次确认、一次审批 |
| `command_receipts` | PK (tenant, actor, route, key) | Idempotency-Key 幂等：同 key 同 body 返回原响应，不同 body 409 |
| `business_events` | `delivery_status` PENDING→SENT + 租约 | **Outbox**：业务改动和事件同事务写入 |
| `consumer_receipts` | PK (consumer, event_id) | **Inbox**：同一事件不重复消费 |
| `external_operations` / `reservations` | 唯一 (ticket, proposal_version)；`operation_id` 稳定 | 对 OMS 的幂等键 + 库存预占 |
| `approval_reminders` / `staff_notifications` | PK (proposal_id, version)；`uq_notification_event` | 一个方案版本一条提醒；一个收件人一条通知 |
