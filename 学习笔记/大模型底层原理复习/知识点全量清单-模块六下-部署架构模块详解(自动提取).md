# 5.大模型推理部署

- vLLM 简介与安装
  - vLLM 是 2023 年提出的推理框架：把 GPU 显存管理起来，让大模型跑得更快、硬件利用率更高；覆盖主流模型架构，硬件横跨 NVIDIA、AMD 和一批国产加速卡
  - 安装指南链接：vllm.hyper.ai/docs/getting-started/installation；docs.vllm.com.cn engine_args/#modelconfig
  - 【代码】启动服务：`vllm serve /root/autodl-tmp/model --served-model-name deepseek-r1 --api-key ds123456`
  - 【代码】LangChain 调用本地 vLLM：`ChatOpenAI(model="deepseek-r1", base_url="http://localhost:8000/v1", api_key="ds123456", temperature=0.7, max_tokens=1024)`；`llm.invoke([SystemMessage, HumanMessage])`；model 需与 `--served-model-name` 一致；未启用鉴权时 api_key 填任意非空字符串
- 大模型推理的两阶段：Prefill(预填充) 与 Decode(解码)
  - 日常现象：先"思考"一下（Prefill 一口气读完全部输入）→ 文字打字机式逐字流出（Decode 逐 token 写）
  - 【结论】两阶段计算特征完全相反，KV Cache、PagedAttention、连续批处理、PD 分离全都围绕这对矛盾展开——推理工程的"第一性原理"
  - 一次请求的完整链路：三个关键事实
    - 模型不会"整段想好再输出"，永远只做：给定前面所有 token，预测下一个 token 的概率分布
    - 输出不是确定的：同样 Prompt，采样参数一变结果就变
    - 文本变长会变慢：注意力计算量随长度平方增长，KV Cache 随长度线性吃显存
  - Prefill：并行"读题"阶段
    - 把 Prompt 所有 token 一次性并行塞进模型：算出每个 token 每层的 K/V 填满 KV Cache；产出第一个输出 token
    - Prompt 2000 token = 2000 个位置同时参与矩阵运算，是一大块规整 GEMM（矩阵乘矩阵），Tensor Core 利用率轻松 80% 以上
    - 【结论】Prefill 是计算密集（compute-bound），瓶颈在算力；耗时决定 TTFT（Time To First Token 首字延迟）
    - 自注意力计算量 $O(n^2)$，Prompt 越长 TTFT 平方级恶化；10 万字小说总结，首字延迟几十秒正常
  - Decode：逐字"写作"阶段
    - 每步只处理 1 个新 token，但要：读一遍全部权重（7B FP16 约 14GB）；读一遍全部历史 KV Cache（长上下文可能比权重还大）
    - 一个 token 过模型本质是 GEMV（矩阵乘向量），算术强度极低，数据没搬完算力已闲置
    - 【结论】Decode 是访存密集（memory-bound）；生成速度和模型大小、上下文长度强相关，和"这句话难不难想"无关，写"哈哈哈哈"和写量子力学证明每 token 成本一样
    - Decode 每步耗时对应 TPOT（Time Per Output Token），即"打字速度"
  - 两阶段的对立统一（对比）
    - 计算形态：Prefill 大 GEMM（矩阵×矩阵）；Decode GEMV（矩阵×向量）
    - 瓶颈类型：Prefill 算力（compute-bound）；Decode 显存带宽（memory-bound）
    - GPU 利用率：Prefill 高、Tensor Core 打满；Decode 低、算力大量闲置
    - 时延来源：Prefill Prompt 长度（$O(n^2)$ 注意力）；Decode 权重 + KV Cache 搬运量
    - 决定指标：Prefill TTFT；Decode TPOT / 吞吐
    - 并行度：Prefill 输入全并行；Decode 严格串行逐 token
    - 【结论】口诀：Prefill 是"读题"，Decode 是"写作"；读题可以一目十行并行扫，写作必须一个字一个字来
    - 催生的技术：KV Cache 让 Decode 不重算历史（空间换时间）；Continuous Batching 把多请求 Decode 拼成大矩阵，GEMV 强行变回 GEMM；PD 分离把两阶段拆到不同机器
  - 性能指标体系（业界通用五个）
    - TTFT（Time To First Token）首字延迟：由 Prefill 决定；对话场景一般要求 < 1s
    - TPOT（Time Per Output Token）：每个输出 token 平均耗时；人阅读约 10~20 token/s，TPOT < 50ms 就够用
    - ITL（Inter-Token Latency）：相邻两 token 间隔；ITL 抖动大 = 输出一顿一顿，是 PD 混跑时长 Prompt 插队的典型症状
    - E2E Latency：端到端总时延 $= \text{TTFT} + \text{输出长度} \times \text{TPOT}$
    - 吞吐量（Throughput）：系统每秒处理 token 总数（input + output），决定成本
    - 实测参考：消费级显卡跑 Qwen3-0.6B，TTFT 约 2 秒、TPOT 约 42ms；671B DeepSeek-V3 满血版无多卡并行时 TPOT 秒级
    - 【结论】优化顺序经验法则：先看 TTFT（Prefill 侧：前缀缓存、Chunked Prefill）→ 再看 TPOT（Decode 侧：量化、投机解码、批处理）→ 最后看端到端吞吐（调度与并行架构）
  - 采样：最后一个 token 怎么"被选中"
    - 模型每步输出的是词表上整组概率（DeepSeek-V3 词表 12 万+），选哪个由采样策略决定
    - 【代码】`AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")`、`AutoTokenizer.from_pretrained`、`tokenizer(..., return_tensors="pt")`、`model.generate(**inputs, max_new_tokens=100, do_sample=True, temperature=0.7, top_k=50, top_p=0.9)`、`tokenizer.decode(outputs[0], skip_special_tokens=True)`
    - 参数含义
      - max_new_tokens=100：最多生成 100 个 token，防失控
      - do_sample：False = 贪心解码（每步选概率最大，输出确定但死板）
      - temperature：>1 拉平分布（更野），<1 锐化分布（更保守）；数学上等价于 logits / T 后再 softmax
      - top_k=50：只在概率最高的 50 个候选里采样，砍掉长尾噪音
      - top_p=0.9：核采样，只保留累计概率达 90% 的最小候选集；业界默认甜点位 0.9~0.95，比 top_k 更自适应
    - 【结论】确定性任务（代码生成、结构化输出、工具调用）：temperature=0 或极低 + 贪心解码；开放式写作：temperature 0.7~1.0 + top_p 0.9；Agent 场景：固定 temperature=0，否则同一工具调用今天能跑明天挂
- 为什么 Prefill 吃算力、Decode 吃带宽：Roofline 性能模型实战
  - 饺子馆类比：Prefill 像年夜饭备料，瓶颈是厨师手速（算力）；Decode 像一粒一粒上饺子，每上一粒要翻整本菜谱（权重）和这桌所有菜（KV Cache），瓶颈是传菜员的腿（带宽）
  - Roofline 模型
    - 核心概念：算术强度 $I = \text{计算量 (FLOPs)} \div \text{数据搬运量 (Bytes)}$，即每从显存搬 1 字节能搭配做多少次浮点运算
    - 图左半边斜线：性能被显存带宽锁死；右半边平线：性能被峰值算力锁死
    - Ridge Point（平衡点）横坐标 $= \text{峰值算力} \div \text{峰值带宽}$
    - A100 80GB 例子：峰值算力（BF16）≈ 312 TFLOPS，HBM 带宽 ≈ 2 TB/s，Ridge Point ≈ 312 / 2 = 156 FLOP/byte
    - 【结论】A100 上算术强度低于 156 是"带宽受限"，高于 156 才是"算力受限"
  - 动手算：Prefill 和 Decode 各落在哪
    - 场景：一个 batch 的 token 过一层线性层 $Y = X \cdot W$，X: [n_tokens, d_model]，W: [d_model, d_model]；d_model = 7168（DeepSeek-V3 隐藏维度），BF16 每元素 2 字节
    - 【代码】`flops = 2 * n_tokens * d_model * d_model`；`bytes_moved = (2 * n_tokens * d_model + d_model * d_model) * bytes_per_elem`；`I = flops / bytes_moved`；判定 `I < 156` 为带宽受限
    - 计算量：每个输出元素 d 次乘加 = 2d FLOPs；搬运量 = 输入 X + 权重 W（无论多少 token 权重都要完整搬一遍）+ 输出 Y
    - 结果：n=1（Decode 每步 1 token）I=2.00 带宽受限；n=128（小 batch Decode）I=255.39 算力受限；n=2048（Prefill 2K）I=2046.85 算力受限；n=8192（Prefill 8K）I=4093.43 算力受限
    - 把权重 + KV Cache 全算上，Decode 实际算术强度约 0.5 FLOP/byte，离 156 平衡点差 300 多倍
    - 【结论】Decode 单步 I ≈ 0.5~2，深陷带宽墙，Tensor Core 利用率常年个位数百分比，不是卡不行，是活儿本身"吃不饱"；Prefill I 轻松上千，贴着算力天花板跑
  - 推论：所有推理加速技术的统一视角
    - 【结论】所有推理优化本质只做两件事：把算术强度往右推，或把需要搬的数据往下砍
    - Continuous Batching：几十上百个请求的 Decode 拼成大矩阵，GEMV → GEMM，I 提升两个数量级
    - 权重量化（FP8/INT4）：同样计算量，权重搬运量砍半甚至到 1/4
    - KV Cache 量化：Decode 每步要读的全部 KV 从 BF16 变 FP8，搬运量减半
    - FlashAttention：注意力计算在片上 SRAM 完成，减少 HBM 往返，变相增大 I
    - GQA / MQA / MLA：KV Cache 体积缩小 4~几十倍，Decode 每步少搬数据
    - 投机解码：用小模型的廉价 Decode 换大模型一次并行验证，串行 GEMV 变批量 GEMM
    - Prefix Caching：命中前缀的 Prefill 直接跳过，算力消耗归零
    - 看到"某技术提速 X 倍"自动问三个问题：推的是算术强度还是砍搬运量？测试时序列长度、batch size、精度是什么？我的场景和它的测试场景一样吗？
    - 【结论】瓶颈位置随序列长度、batch、精度不断迁移：batch 开到 512 Decode 可能变算力受限；量化到 INT4 后可能撞上别的墙；没有银弹
  - 延伸：两阶段对"网络"的要求也相反
    - Prefill 侧：TP 切分后每层 AllReduce 大矩阵，单次几百 MB，追求吞吐量（像货运，晚到 10ms 无所谓）
    - Decode 侧：每个 token 跨卡同步一次，单次数据小频率极高，网络抖动直接反映为 ITL 毛刺（像高频交易，怕尾延迟 P99）
    - 【结论】没有一种网络策略能同时最优服务两阶段；PD 分离后 Prefill 池可上大 TP，Decode 池优先小 TP + 大 DP
- KV Cache 深度解析：原理与显存估算
  - 为什么需要 KV Cache
    - 已生成 100 个 token 要生成第 101 个，新 token 要和前面全部 100 个算相关性；第 1~100 个 token 的 K/V 已经算过且不会变（因果掩码保证只看过去）
    - 不缓存则每生成一个新 token 要把整段历史重新过一遍 Transformer
    - 【结论】KV Cache 本质：用显存换时间，把 $O(n^2)$ 的重复计算变成 $O(n)$ 的缓存查找；计算量降到原来几百分之一，所有推理框架默认开启
    - 三个边界
      - 只服务于推理阶段：训练时整段序列并行计算，K/V 算一次就够
      - 只存在于解码器（Decoder）中：BERT 这类 encoder-only 模型不做生成，没有 KV Cache 概念
      - 加速的是 $Q \cdot K^T$ 与加权求和 V 这两次矩阵相乘，缓存的是中间结果，不是参数、不是文本
    - 核心思想三步：缓存历史 token 的 K/V → 每步只计算当前 token 的 Q/K/V → 复用缓存的历史 K/V
  - 矩阵视角：缓存前后每一步在算什么
    - 没有缓存：每生成一个新 token，Q、K、V 矩阵整体膨胀一行，整个矩阵乘重算；生成第 4 个 token 矩阵 4 行，第 1000 个就 1000 行；预测第 1001 个 token 时 QK 矩阵 1000×1000
    - 有缓存：每步只有新 token 那一行参与计算，历史 K/V 直接从缓存取；矩阵乘规模从"整段序列"缩到 1×N，输出形状 (1, emb_size)
    - KV cache 只在多个 token 生成步骤中发生、仅在 decoder 进行（GPT 等 decoder-only，或 T5 的解码部分）
    - 最小生成案例 "The cat sat on"：输入 "The cat" 生成 "sat" 时计算并缓存 "The"、"cat" 的 K/V；生成 "on" 时只计算 "sat" 的 K/V，"The"、"cat" 从缓存取
  - 为什么缓存 K 和 V，不缓存 Q
    - 每一步注意力是"新 token 的 Q 去查询所有历史的 K，再按相关性加权读出历史的 V"；历史 token 的 Q 只在它自己当"新人"那一步用过一次
    - 【结论】Q 是"一次性"的主动查询者（临时查询员，用完即弃）；K/V 是"被查询"的历史档案（静态不变、每轮参与计算，必须归档）；缓存 Q 纯属浪费显存
  - 代价：显存被吃到什么程度
    - 公式（每个请求）：$\text{KV Cache 字节数} = 2\,(K和V) \times \text{层数} \times \text{KV头数} \times \text{头维度} \times \text{序列长度} \times \text{每元素字节数}$
    - 真实模型（BF16，2 字节）
      - Qwen3-7B（GQA 4 头）：28 层、4×128；4K ≈ 0.9 GB，32K ≈ 7 GB，128K ≈ 29 GB
      - LLaMA-7B 类（MHA 32 头）：32 层、32×128；4K ≈ 4 GB，32K ≈ 34 GB，128K ≈ 137 GB
      - 某 96 层大模型：128K ≈ 576 GB
    - 经验数字：传统 MHA 模型约 0.7 MB / token；一块 A100 80GB 光 KV Cache 理论上限约 11 万 token（单请求）
    - 业务视角：70B 模型、8K 上下文、百万 DAU，高峰并发 KV Cache 总量几十 TB HBM；HBM 占一张 GPU 成本 30~40%
    - 【结论】AI 推理的瓶颈早就不是算不动，而是存不下
    - 长对话的隐忧：缓存线性增长与"遗忘"现象
      - 每次问答（QA）记录都会增加 KV Cache 存储需求，显存占用随对话轮次线性增长
      - 缓存达容量上限时旧信息被覆盖或丢弃 → 模型"遗忘"早期对话，长对话后期回答质量下滑；不是模型变笨，是缓存被挤爆
      - 【结论】KV Cache 是一种用内存换取推理速度的技巧
  - 速记：优势与局限
    - 优势：减少计算量（$O(n^2) \to O(n)$）；提高推理速度；支撑长序列生成
    - 局限：显存占用增加（随序列线性增长）；实现复杂度高（分页、调度、分级存储都是为治它而生）
  - 从"省显存"到"省钱"：前缀缓存与磁盘缓存
    - Prefix Caching（前缀缓存）："存过的不重算"
    - 企业场景共享超长前缀：客服机器人每请求带 5000 token 系统提示词 + 产品手册；Agent 同一轮对话每步工具调用前面历史不变；RAG 同一份检索结果服务多个相似问题
    - 命中时 TTFT 直接砍掉几百毫秒，Prefill 算力消耗归零
    - DeepSeek Context Caching on Disk：不命中正常价，命中约 3 折（"便宜约 96.8%"源自早期价格）；背后是磁盘级 KV 存储 + MLA 压缩
    - 【结论】实操建议：不变的内容放 Prompt 前面，会变的放后面；系统提示词、知识库文档往前堆，用户问题放最后——前缀命中率决定账单厚度
  - 动手验证：看一眼真实的 KV Cache
    - 【代码】`from transformers import AutoModelForCausalLM, AutoTokenizer, DynamicCache`；`model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.bfloat16)`；`past_kv = DynamicCache()`；`model(**inputs, past_key_values=past_kv, use_cache=True)`；`past_kv.layers[0].keys.shape`；`next_token = out.logits[:, -1, :].argmax(dim=-1, keepdim=True)`；`model(input_ids=next_token, past_key_values=past_kv, use_cache=True)`
    - DynamicCache 是 transformers 官方的 KV Cache 容器；第一次前向 = Prefill
    - 第 0 层 K 形状 [batch, KV头数, 已缓存序列长度, 头维度]：Prefill 后 torch.Size([1, 8, 11, 128])（1=batch，8=GQA KV 头数，11=输入 token 数，128=头维度）；Decode 一步后 torch.Size([1, 8, 12, 128])，序列维度 +1
    - 【结论】Decode 一步后缓存形状只在序列维度 +1，模型没有重算前面 11 个 token 的任何东西
- PagedAttention 与 vLLM 架构全解析
  - 朴素 Serving 的显存浪费
    - 朴素做法：给每个请求预分配一块连续显存放 KV Cache，大小按 max_model_len（如 32K）算
    - 坑一：过度预留（Over-reservation）：请求实际只生成 500 token 却按 32K 留位（给每个人预留 20 人大桌）；实测显存利用率只有 20~40%
    - 坑二：内存碎片（Fragmentation）：请求来了走、走了来，显存切成大小不一碎块；总共剩 20GB 空闲但不连续，需要 8GB 连续空间的请求进不来；同操作系统外部碎片
    - 算一笔账（13B 级模型）：隐藏维度 5120、40 层、BF16 2 字节、每请求按最大生成 2048 token 预分配
      - 单 token KV Cache：$2\,(K和V) \times 5120 \times 40\,\text{层} \times 2\,\text{字节} \approx 800\,\text{KB}$
      - 单请求预分配：$800\,\text{KB} \times 2048 \approx 1.6\,\text{GB}$
      - 请求还没开始生成 1.6GB 就没了；整张卡只能同时容纳几十条请求
    - 【结论】高效管理 KV Cache、把每一 MB 显存榨干，是推理加速的关键战场之一；一张卡理论能服务 50 并发，实际只塞得下 10 个
  - PagedAttention：操作系统分页思想的 GPU 版
    - 【结论】vLLM 论文核心洞察：KV Cache 管理问题和操作系统管理物理内存同构，解法照搬——分页
    - 一次完整读写流程（跟着 Block Table 走）
      - 逻辑 KV Cache（左侧）：模型看到的"虚拟"视图，似乎拥有连续按顺序的 KV Cache；Prompt "中国的历史非常悠久" 切为多个 Block（Block1 存"中国的历史非常"，Block2 存"悠久"）；每个 Block 含固定数量 Slot，每 Slot 存一个 token 的 K 和 V；逻辑上 Block 连续，物理上不一定
      - 映射表（Mapping Table，中间）：PagedAttention 的"页表"，维护逻辑 Block → 物理 Block 映射；逻辑 Block1 → 物理 Block1 已填 4 槽（"中国""的""历史""非常"）；逻辑 Block2 → 物理 Block3 已填 1 槽（"悠久"）
      - 物理显存 KV Cache（右侧）：GPU 显存实际存储处，Block 物理存在且不需要连续；Block4、Block5 展示多序列共享
    - 前缀共享：COW 在推理里的样子
      - 10 个请求带同一段 5000 token 系统提示词，Block Table 指向同一批物理 Block，引用计数 +1；某请求要往共享 Block 写新 token 时才复制一份（Copy-on-Write）
      - Beam Search 与并行采样同理：N 条候选路径共享 prompt 历史，只在分叉处各存各的
      - 【结论】论文实测共享场景能省约 55~67% 的 KV 内存
  - Continuous Batching：让 GPU 永远有活干
    - 为什么需要批处理
      - 背景回顾：Prefill 一次性并行处理整段 prompt、矩阵×矩阵、计算受限；Decode 每步 1 个新 token、矩阵×向量、带宽受限
      - 算术强度定义：每从显存读 1 字节数据能完成多少次浮点运算；高 → 计算受限；低 → 带宽受限
      - Decode 是带宽受限极端情况：权重几 GB 到几十 GB 每步原样读一遍，只产出 1 个 token；标称几百上千 TFLOPS 实际只用零头
      - 批处理动机：摊薄权重读取成本——既然每步都要读整个模型，就让这一步同时给多条请求算；权重读一次几十条请求共用，算术强度随批大小成倍抬升
    - 静态批处理（Static Batching）——整批同进同出
      - 工作方式：攒够一批 → 拼成大 batch 送 GPU → 等所有请求生成完 → 整批返回 → 再收下一批
      - 短板效应（如 20 token vs 500 token）：短请求陪跑（生成完不能先走）；算力空转（算无意义前向或塞 pad token）；新请求排队（必须等当前批清空）
      - 【结论】批内长度差异越大，空转越严重
      - 【代码】Transformers `generate` 天然是静态批处理：`tokenizer.apply_chat_template([...], tokenize=False, add_generation_prompt=True, enable_thinking=False)`；`tokenizer.padding_side = "left"`；`tokenizer.pad_token = tokenizer.eos_token`；`tokenizer(texts, return_tensors="pt", padding=True)`；`model.generate(**inputs, max_new_tokens=512, do_sample=False)`；统计有效 token `(new_tokens != tokenizer.pad_token_id).sum()`
      - 批式生成要左填充，保证每条序列最后一个位置是新 token 位置；Qwen3 关掉思考模式让回答尽快收尾
      - 实验观察：三条请求分别有效生成 23、18、290 个 token，相差十几倍；generate 必须等最长那条结束；短请求撞 EOS 后 pad 位置每步前向白算
      - 【结论】生产环境请求随到随走、量大，静态批处理的空转无法接受
    - 连续批处理（Continuous Batching）——以步为单位调度
      - 核心思想：每跑完一步 decode，调度器重新决策一次
      - 某请求生成 EOS 或达长度上限 → 立刻移出返回；等待队列有新请求且显存放得下 → 立刻补入运行集；批的组成每步都在变
      - 时间轴：请求 A 第 20 步结束，请求 D 第 21 步立刻顶上 A 的位置
      - 【结论】空转区域整个消失：每条请求实际生成时间没变，但同一台 GPU 单位时间服务的请求变多
      - 调度器内部两个队列：等待队列（waiting，已接收未开始计算）；运行集（running，正在逐 token 生成）
      - 每步迭代三件事：组批（遍历运行集分配本步 KV 块和 token 预算，有富余从等待队列按顺序补入）；执行（拼好的批送 GPU 跑一步前向，每请求产出 1 个新 token）；结算（撞 EOS 或长度上限的标记完成、释放资源、推结果；空位下一步补入）
      - 调度策略：默认 FCFS（先来先服务）；【代码】vLLM 优先级调度 `--scheduling-policy priority`（数值越小越先处理）
    - 调度器调优——吞吐与延迟的权衡
      - 【代码】`max_num_seqs`：批的条数上限，单步迭代最多同时跑多少条请求；`max_num_batched_tokens`：批的 token 总量上限，单步最多处理多少 token（所有请求合计）
      - 【代码】启动示例：`vllm serve Qwen/Qwen3-0.6B --max-num-seqs 256 --max-num-batched-tokens 8192`
      - max_num_seqs 调大：吞吐更高、权重读取摊更薄；单请求延迟更差（单步更慢、排队更久）
      - max_num_batched_tokens 调大：吞吐更高、长 prompt 的 prefill 更快完成、TTFT 变好；decode 的 token 间隔（ITL/TBT）可能变差
      - 【结论】吞吐与延迟不可兼得：批越大 → 每步 token 越多 → 单步耗时越长 → token 间隔越差，请求多了排队 TTFT 也变长；批越小 → 接近单请求延迟但吞吐回落
      - 【结论】调优目标不是把批开到最大，而是在 SLO（Service Level Objective）允许范围内把吞吐做高；SLO 示例：TTFT ≤ 2 秒、token 间隔 ≤ 100 毫秒
  - vLLM 全貌：一条请求的九驿站
    - EngineCore 主循环非阻塞：GPU 跑第 N 步时 CPU 同时调度第 N+1 步，流水线重叠，调度开销藏进 GPU 计算时间
    - 调度器统一抽象：vLLM 不区分"Prefill 请求"和"Decode 请求"，只有"这个请求这一步要处理多少 token"；新请求 = 一次处理 prompt_len 个 token，老请求 = 一次处理 1 个
    - 【结论】OpenAI API 兼容是护城河：`pip install vllm` 后一行命令起兼容 `/v1/chat/completions` 的服务，存量代码零成本迁移；生态比性能更能锁定用户
- PD 分离与并行推理架构：从单机到分布式推理集群
  - PD 分离：一对性格不合的室友
    - Prefill 计算密集、吃算力、耗时和输入长度强相关；Decode 访存密集、怕延迟怕抖动、对 ITL 极其敏感
    - 混跑问题：长 Prompt 阻塞流式输出——3 万字文档 Prefill 跑好几秒，同卡所有 Decode 请求集体卡顿，ITL 飙升，P99 爆炸；Chunked Prefill 缓解但资源诉求仍互相干扰
    - 【结论】PD 分离（Prefill-Decode Disaggregation）：性格不合就分居
    - 拆开后的好处：独立扩容（长文档需求涨只加 Prefill 节点，对话并发涨只加 Decode 节点）；独立优化（Prefill 池 TP=8 追求单请求速度，Decode 池 TP=2 + DP 拉满并发）；指标解耦（TTFT 由 Prefill 池排队深度决定，TPOT 由 Decode 池负载决定，容量规划可计算）
  - PD 分离的代价：KV Cache 要"搬家"
    - Prefill 算出的 KV Cache 必须完整快速送到 Decode 节点；128K 上下文大模型单请求 KV 几十 GB
    - 传输介质是硬门槛：普通 TCP 出局，必须 RDMA（InfiniBand/RoCE）或 NVLink 域内互传
    - 传输必须异步分块：chunk 级流水线，Prefill 边算边传，Decode 边收边跑（vLLM 的 `kv_transfer` connector、Mooncake 传输引擎）
    - 调度要算总账：选 Prefill 节点不仅看谁闲，还看它与 Decode 节点的链路状况
    - 【结论】推理系统越来越像一个以 KV Cache 为中心的分布式缓存调度系统
  - 实例：5 万字论文生成任务的时序解剖
    - 任务：输入 50 token"帮我写一篇关于新能源产业的 5 万字研究报告"，带深度思考 + 联网检索
    - 首 token 不一定是可见字符：Reasoning 模型第一个 token 可能是思考链开始标记
    - 联网搜索会触发新的 Prefill：检索回来的几千 token 走一遍（Chunked）Prefill 生成增量 KV；Agent 任务在 P/D 之间反复横跳
    - 这种任务 99% 时间花在 Decode 实例上；"传一本书只问一句话"的文档问答压力全在 Prefill 侧
    - 【结论】容量规划第一课：先分析业务的输入/输出 token 比例，再决定 P/D 池配比；客服问答（长输入短输出）和创意写作（短输入长输出）集群形态完全不同
  - KV Offloading：显存不够，内存/磁盘来凑
    - KV 分级存储典型玩法：被抢占的请求 KV 换出到 CPU 内存，恢复时换回，比重算便宜；DeepSeek Context Caching on Disk 把共享前缀 KV 持久化到磁盘，跨请求甚至跨会话命中；Mooncake 把集群所有空闲内存/磁盘组织成分布式 KV 池
    - 延迟代价：HBM 微秒级，CPU 内存百微秒级，NVMe 百微秒到毫秒级
    - 【结论】用延迟换容量，用容量换免重算——又是一笔要算总账的买卖

# 6.大模型架构与训练全流程

- 大模型架构之争——Decoder-Only
  - 先回到原点：Transformer 的左手和右手
    - 2017 年 Transformer 是标准 Seq2Seq：左半边编码器（Encoder），右半边解码器（Decoder）
    - 编码器：职责是把输入序列压缩成连续语义表示；双向自注意力，每个位置看到全部上下文
    - 解码器：结合编码器输出和已生成内容自回归产出序列；因果掩码自注意力（只看左边）+ 交叉注意力（看编码器输出）
    - 比方：编码器像阅卷老师通读整篇再打分；解码器像考场写作文的学生，写到第 N 个字只能回看
    - 三大架构路线 = 对这个结构做"截肢手术"：只留左手、左右都留、只留右手
  - 技术路线
    - Encoder-Only：BERT 的完形填空
      - 代表模型 BERT 及衍生家族
      - 预训练任务：自编码（Auto-Encoding），随机挖词换成 `[MASK]` 再猜回来；辅助任务 NSP（下一句话预测）
      - 适合理解类任务：文本分类、情感分析、命名实体识别、阅读理解
      - 短板：天生不会生成；上下文窗口小（一般卡在 512 token）；微调依赖重；多任务适应性差
    - Decoder-Only：GPT 开的头，国产模型接的棒
      - 代表模型：GPT 系列起头，如今 DeepSeek-V3/R1、Qwen3、GLM-4（Decoder 路线）、Kimi
      - 预训练任务：自回归语言建模——给定前 n 个 token 预测下一个（手机输入法"今天天气"→"不错"）
      - 结构：砍掉 Transformer 解码器的交叉注意力，留下带因果掩码的自注意力 + 前馈网络，堆几十上百层
      - GPT 两个历史贡献：验证"预训练 + 微调"范式（12 个任务里 9 个 SOTA）；统一任务输入格式（"万物皆序列"，prompt 时代地基）
  - 为什么 Decoder-Only 赢了
    - 理论层面
      - 注意力矩阵满秩，表达上限更高：因果注意力矩阵是严格下三角带对角线，数学上保证满秩；双向注意力有退化成低秩的风险
      - 任务越难，逼出来的表征越强：Next-token prediction 每位置只看左边，信息最少预测难度最大；"困难任务 + 大数据"逼出更强通用表征
      - In-Context Learning 的天然亲和：Prompt 和 few-shot 示例是"隐式微调"，Decoder-Only 里 prompt 信息直接贯穿每一层，信号路径最短；Encoder-Decoder 要先过编码器再过交叉注意力
      - 兼顾理解与生成的涌现能力：规模上去后能匹敌 Encoder-Decoder 专门微调的效果
      - 隐式位置编码与外推便利：只依赖相对位置关系，RoPE 插值、LongRoPE 微调一下就能扩上下文；Encoder-Decoder 要处理两套位置系统
    - 工程层面
      - KV-Cache 友好：因果注意力保证每个 token 表示只依赖之前内容，KV-Cache 一路复用到底；vLLM PagedAttention、FlashAttention、Megatron-LM 都优先围着因果路径转
      - Scale Up 成本最低：相同参数量训练效率排序 `Decoder-Only > Encoder-Only > Encoder-Decoder`；可扩展参数量上限和集群规模上限同样排序
      - 生态滚雪球：MoE、量化、蒸馏、投机采样在单一解码器结构上实现最顺滑
      - 多模态的"早融合"最优解：GPT-4o、Qwen-VL 把图像/音频切成 token 直接拼进文本序列
      - 轨迹依赖：OpenAI 先验证了训练方法和 Scaling Law，后来者不愿在结构上豪赌；DeepSeek-V3/R1 在 Decoder-Only 骨架上把 MoE 和推理能力做到极致
  - 一张表收尾（对比）
    - 代表模型：Encoder-Only BERT；Encoder-Decoder T5、GLM；Decoder-Only GPT 系列、DeepSeek、Qwen3
    - 预训练任务：掩码重建（完形填空）；序列到序列映射；下一词预测（接龙）
    - 注意力：双向；双向 + 因果 + 交叉；因果掩码
    - 擅长：理解（分类、NER、抽取）；翻译、摘要、多模态编码；生成 + 理解通吃
    - KV-Cache：不适用；部分可用；完美复用
    - Scale Up 效率：中；低；高
    - 当今地位：退居垂直场景；少数派；绝对主流
- 大模型训练全流程
  - 一张图看懂全局：四个阶段
    - 预训练：学会语言和世界知识；后训练：学会听指令、讲道理、守边界；微调：适配具体任务、行业和场景；推理：真实使用时生成答案、调用工具、完成任务
    - 培养员工比方：预训练是通识教育（读万卷书），后训练是职业素养培训，微调是岗前培训（财务还是法务），推理是正式上岗
  - 大模型不是"写"出来的，是"训"出来的
    - 传统软件逻辑由程序员敲死；大模型的"智能"沉淀在几十亿参数中，训练前基本是随机数
    - 【结论】大模型的聪明不来自规则库，而来自数据 × 架构 × 训练目标 × 算力共同捏出来的参数空间
    - 迁移学习红利：拿预训练好的参数（含底层词嵌入）当起点，在新任务上继续训；是"小团队玩大模型"成立的前提
    - 【代码】MiniMind：模型 modelscope.cn/models/gongjy/minimind-3；代码 github.com/jingyaogong/minimind；数据集 modelscope.cn/datasets/gongjy/minimind_dataset；环境 `pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple`
  - 第 0 步：数据要先把人话翻译成数字
    - 模型不识字，只有 Token ID 和向量；Token 是入口（分词器，BPE 主流）；Embedding 是翻译器（可学习查找表，ID → 低维稠密向量）；Transformer 是加工厂
    - MiniMind 实战：6400 词表的"抠门"哲学
      - 自训 BPE + ByteLevel 分词器，词表 6400；对比 Qwen2 的 151643、Llama3 的 128000，砍了两个数量级；embedding 层参数占比暴降，64M 小身板把更多参数留给计算层
      - 预置 `<tool_call>`、`<tool_response>`、`<think>` 特殊标记——工具调用和思考链从分词器层面就要规划
      - 【结论】官方不建议重训 tokenizer，词表一变，权重和生态兼容性全废
  - 阶段一：预训练——让模型成为"通才"
    - 任务：给定上文，预测下一个 Token（"人工智能正在改变"→"世界"/"生产力"/"软件开发"）
    - 【结论】表面是接龙，实质是压缩人类知识；翻译、摘要、问答能力全是涌现出来的副产品；这一阶段最贵、最决定上限，练完是"能力底座"
    - 【代码】MiniMind：`cd trainer`；单卡 `python train_pretrain.py`（`--from_resume 1` 断点续训；数据 `./dataset/pretrain_t2t_mini.jsonl` 1.2GB，格式 `{"text": "..."}`）；多卡 `torchrun --nproc_per_node 2 train_pretrain.py`（DDP）；产出 `out/pretrain_768.pth`
    - 为什么预训练模型还不能直接上岗："互联网腔模仿器"，开盲盒：可能继续模仿网页续写、格式飘忽、跑题、没有安全边界
    - 【结论】根因：它学的是语言分布，不是用户意图；预训练解决"能力底座"，"可用性"留给后训练
  - 阶段二：后训练——从"会说"到"好用"
    - 工具箱：SFT（监督微调，听懂指令）；RLHF（人类反馈强化学习，符合人类偏好）；RLAIF（AI 代替人做标注，降成本）；DPO（直接偏好优化，RLHF 简化平替）；安全对齐训练；工具使用训练；推理过程训练（"先想后答"）
    - 【结论】总目标：让模型从"预测下一个 Token"变成"按照人类意图完成任务"
    - SFT：先给模型看"标准答案"
      - 大量"用户指令 → 高质量回答"样本对；预训练读整个互联网，SFT 只看优秀答卷；从"语言模型"进化成"助手模型"
      - 【代码】`python train_full_sft.py`（数据 `./dataset/sft_t2t_mini.jsonl`，多轮 conversations 格式，已混入 Tool Call 数据）；`python eval_llm.py --weight full_sft`
    - RLHF：教模型"人类更喜欢哪种回答"
      - 开放问题没有唯一正确答案但有明显好坏之分 → 偏好学习；经典 RLHF 四步（图）
      - 【结论】RLHF 教的不是知识，是品味：更有帮助、更诚实、更安全、结构更清晰、更少胡说、更少危险建议
    - DPO：把 RLHF 的麻烦事省了
      - 不训奖励模型，直接拿"好回答/坏回答"偏好对优化：向 A 靠拢、离 B 远点；流程短、稳定性好，SFT + DPO 组合流行
      - 【代码】`python train_dpo.py`（数据 dpo.jsonl 为 `{"chosen": [...], "rejected": [...]}`；Off-Policy，无需奖励模型，显存友好）
    - PPO / GRPO / CISPO：真刀真枪的强化学习（默认奖励模型 InternLM2-1.8B-Reward）
      - 【代码】`python train_ppo.py`：Actor-Critic 双网络，显存约为普通训练 1.5~2 倍，效果稳但贵
      - 【代码】`python train_grpo.py`：单网络，组内归一化优势估计，DeepSeek-R1 带火，性价比高
      - 【代码】`python train_grpo.py --loss_type cispo`：裁剪权重乘 log 概率，避免梯度被直接截断，训练更稳定
    - 安全对齐与推理训练
      - 安全对齐：Agent 时代能调工具、操作文件、查数据库，说错话是小事，做错事是大事；拒绝/澄清/替代方案是后训练刻意塑造
      - 推理能力训练：高质量数学/代码/逻辑题 + 多步思维链数据 + 验证器反馈 + 自我反思数据 + 强化学习 + 过程监督（看每一步推导是否成立：数学题盯推导链，代码题盯测试）；MiniMind 的 `<think>` 标记和 `open_thinking` 开关是最小实现
      - 【结论】后训练从"回答质量优化"走向"任务求解能力优化"
  - 阶段三：微调——从"通用助手"到"行业专才"
    - 【结论】后训练让模型"像助手"，微调让模型"像你的助手"；例：预训练会写中文 → 后训练按要求写文章 → 微调学会你的写法（标题、开头、段落、结尾）
    - 什么时候不需要微调
      - 固定输出格式、引用外部知识、简单风格模仿 → Prompt / RAG 就够
      - 长期无法稳定遵循复杂格式、强领域术语、风格高度一致、要砍掉超长 Prompt 的延迟成本 → 微调，多半 LoRA 就够
      - 【结论】判断标准：这个能力能不能用 Prompt 和 RAG 稳定解决？能就别微调，不能再考虑
    - 微调的三档火力
      - 全量微调：更新大量乃至全部参数；适配能力最强；成本高、显存大、容易把原模型能力"训丢"
      - 参数高效微调（PEFT）：冻结原参数，只训少量新增参数；成本骤降；适配深度略逊
      - LoRA（PEFT 主流）：在部分权重旁挂低秩矩阵只训它；成本低、显存省、多任务可存多个 LoRA 权重热插拔；同家族 Adapter、Prefix Tuning
      - 【结论】大模型时代全量微调对普通团队不友好，LoRA 是默认起手式
    - 【代码】MiniMind 手写版 LoRA：垂域数据 `lora_xxx.jsonl` 放 `dataset/`；`python train_lora.py`（纯手写不依赖 peft 库）；合并导出 `python scripts/convert_model.py convert_merge_base_lora`
    - 知识蒸馏：黑盒蒸馏 ≈ 拿 DeepSeek-R1 / Qwen3 的输出当 SFT 数据；白盒蒸馏 `train_distillation.py`，CE + KL 混合损失拟合教师分布
  - 阶段四：推理——模型真正开始上班
    - 基本循环：Prompt → Token → 逐个预测下一个 Token → 拼回上下文 → 直到结束；底层是一次次概率采样
    - 采样参数
      - temperature：控制发散度；写代码/问答调低（0~0.3），写故事调高（0.8+）
      - top_p / top_k：截断采样范围；防低概率烂词混入、避免复读循环
      - max_tokens / stop：控制长度与终止；省钱、防爆
      - frequency / presence penalty：惩罚重复；长文生成防车轱辘话
    - 同一问题问两次答案不同是采样在掷骰子；早期模型复读循环，top-k 采样是当年药方之一
    - 推理增强：Agent 场景一次请求是一条工作流——拆任务、检索、调工具、读结果、修正计划、继续执行，每步背后都是一次推理
    - 【结论】未来推理竞争是长任务执行能力：会说、会查、会想、会试、会改、会验证；推理系统本身是应用工程的核心战场
    - 【代码】MiniMind 三分钟起服务：`modelscope download --model gongjy/minimind-3 --local_dir ./minimind-3`；命令行 `python eval_llm.py --load_from ./minimind-3`；WebUI `cd scripts && streamlit run web_demo.py`；生产 `vllm serve ./minimind-3 --served-model-name "minimind"`
  - 为什么大模型训练越来越像"系统工程"
    - 数据工程（清洗、去重、过滤、配比、版权、质量评估）；模型架构（Transformer、MoE、长上下文、多模态）；训练框架（分布式训练、并行策略、混合精度、显存优化）；算力集群（GPU、网络、存储、调度、容错）；后训练流程（SFT、RLHF、DPO、安全对齐、推理增强）；评测体系（知识、数学、代码、推理、安全、长上下文、工具调用）；推理部署（量化、KV Cache、批处理、路由、延迟、成本控制）
    - 【结论】真正强的模型公司，强的是完整工程体系
  - 开源和闭源的差距到底在哪
    - 差距不在参数规模：数据质量和训练稳定性；后训练数据与偏好优化精细度；安全对齐成熟度；推理优化、多模态数据、工具使用数据；长任务评测和产品反馈闭环
    - 【结论】模型能力不能只看"考试分数"，还要看听不听指令、稳不稳定、少不少幻觉、会不会澄清、会不会用工具、能不能执行长任务——多半来自后训练和推理系统
  - 开发者最该关注的四件事
    - 理解模型能力边界（哪些自带，哪些靠 RAG、Tool Calling 或微调补）；构建高质量上下文（系统提示词、历史对话、检索结果、工具返回都是上下文工程）；设计工具和工作流（模型 + 工具 + 记忆 + 协议 + 权限）；学会评测（测试集，量化准确率、稳定性、成本、延迟、安全性）
    - 【结论】未来 AI 应用开发是围绕模型构建一个可靠系统
  - 收尾：不是魔法，是新型工业流程
    - 预训练（通识教育）→ 后训练（职业素养）→ 微调（岗位培训）→ 推理（正式上岗）
    - 【结论】四者层层递进缺一不可：没预训练没底座，没后训练不好用，没微调不专业，没高质量推理系统能力释放不出来

# 7.大模型模块详解/RMSNorm

- 先从 LayerNorm 说起
  - 归一化层作用：把每一层输入分布稳住，让训练不崩
  - LayerNorm 对单个 token 特征向量做两件事：先减均值（re-centering），再除以标准差（re-scaling）（公式以图片给出）
  - 不爽之处：计算步骤偏多——一次均值、一次方差、减均值、再除标准差，每层每 token 都来一遍；几百亿参数模型里归一化层调用次数极其恐怖，积少成多是实打实的训练开销
- RMSNorm 的思路：均值那步，不要了
  - 作者观察：LayerNorm 起作用的关键是缩放（re-scaling），不是中心化（re-centering）；干脆砍掉减均值，只用均方根（RMS）做缩放（公式以图片给出）
  - 省掉均值统计、减均值操作，连可学习的平移参数 $ \beta $ 也省了
  - 【结论】原论文报告不同任务和模型规模上提速 7% ~ 64%，精度和 LayerNorm 基本持平
- 为什么砍掉均值还能 work
  - 真正防炸的是缩放：深层网络数值爆炸来自特征量级失控，除以 RMS 把向量模长归一到稳定范围，梯度就稳
  - 中心化是隐式完成的：后续线性层自带偏置、残差连接不断混合信息，"均值不为零"不会累积成灾难
  - 少一次统计，少一次同步：分布式训练里归一化统计量计算牵涉通信，步骤越少越友好
  - 【结论】不是 RMSNorm 全面碾压 LN，个别对均值敏感的任务 LN 仍有优势；但对主流 LLM 架构 RMSNorm 是性价比之王
- 手写一个 RMSNorm（PyTorch）
  - 【代码】`class RMSNorm(nn.Module)`，`__init__(self, dim: int, eps: float = 1e-6)`；`self.weight = nn.Parameter(torch.ones(dim))`（可学习缩放 γ，初始化为 1）；eps 1e-6 是 LLaMA 同款默认值
  - 【代码】核心 `_norm`: `x * torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)`，即 $x / \text{RMS}(x)$
    - `x.pow(2).mean(-1)`：沿特征维算平方的均值（Mean Square）
    - `torch.rsqrt`：一步到位算 $1/\sqrt{\cdot}$，比先 sqrt 再取倒数更快、数值更稳
    - `keepdim=True` 保持维度以便广播：[B, T, dim] → [B, T, 1]
  - 【代码】`forward`: `output = self._norm(x.float()).type_as(x)`；`return self.weight * output`
    - 先转 float32 再归一化：FP16/BF16 下平方和容易溢出或精度不足，工业界标准做法（LLaMA、Qwen 源码都这么写），算完转回原 dtype
  - 测试：`x = torch.randn(2, 128, 4096, dtype=torch.bfloat16)`，`RMSNorm(4096)`；输出形状 torch.Size([2, 128, 4096])，输出 dtype torch.bfloat16（与输入一致）
- 小结（对比 LayerNorm vs RMSNorm）
  - 统计量：均值 + 方差 vs 仅均方根
  - 可学习参数：γ、β vs 仅 γ
  - 计算步骤：多 vs 少（提速 7%~64%）
  - 效果：基准 vs 基本持平
  - 生态：老牌通用 vs LLM 事实标准（Qwen/DeepSeek/LLaMA）

# 7.大模型模块详解/从MHA到MQA与GQA

- 为什么要在注意力头上动刀
  - 标准 MHA 每个头独立一套 Q、K、V 投影；训练阶段矩阵一块算没问题
  - 自回归解码阶段：每生成一个新 token 要把之前所有 token 的 K、V 从显存读出来算注意力；历史 K、V 缓存在显存即 KV Cache
  - 【结论】KV Cache 大小和"头数"成正比；头越多、序列越长显存越夸张，每步解码要完整读一遍——显存带宽成为推理速度瓶颈
  - 思路：Q 必须保持多样性（决定每个头"关注什么"），K、V 让几个头拼团共用
  - MHA：全员独立的"豪华配置"
    - H 个头，H 份 Q，H 份 K，H 份 V；表达能力最强，KV Cache 存 `2 × H` 份矩阵，推理最烧钱
    - 计算复杂度 $O(n^2 \cdot d)$（n 序列长度，d 模型维度），需存储 $3 \cdot H$ 个投影矩阵；头数 H 增加或序列长度 n 变长时计算和内存开销成瓶颈
  - MQA：K/V 只留一份的"极简主义"
    - 核心思想：所有注意力头共享同一个 K 和 V 矩阵，仅 Q 保持独立；生成 H 个不同 Q，1 个共享 K 和 V
    - 优势：显著减少 K/V 投影矩阵数量，降低内存占用；计算量减少（尤其解码自回归阶段），只需缓存一组 K 和 V
    - 缺点：性能可能略低于 MHA，共享 K/V 限制对不同注意力模式的捕捉能力
    - 应用场景：推理密集型任务（如大语言模型生成阶段）
  - GQA：拼团式折中（当前主流）
    - 核心思想：介于 MHA 和 MQA 之间，H 个头分成 G 组，每组共享同一个 K 和 V；例 G=8、H=64 时每组 8 个头；每组独立 Q
    - 极端情况：G=H 退化为 MHA；G=1 退化为 MQA
    - 优势：平衡计算效率和模型表达能力，调整 G 灵活控制权衡；比 MQA 更接近 MHA 性能，同时显著减少计算量
    - 应用场景：LLaMA-2、GPT-3 等模型采用 GQA
- 算笔账：KV Cache 到底省多少
  - 公式：$ \text{Bytes} = \text{层数} \times \text{KV头数} \times \text{head\_dim} \times 2 \;(K和V) \times \text{精度字节数} \times \text{序列长度} $
  - 7B 级典型配置（28 层、28 个 Q 头、head_dim=128、FP16、序列长度 1024）
    - MHA：KV 头数 28，≈ 392 MB，1×
    - GQA（G=4）：KV 头数 4，≈ 56 MB，省 86%
    - MQA：KV 头数 1，≈ 14 MB，省 96%
  - 【结论】GQA 用 4 个 KV 头砍掉八成半缓存，质量几乎贴着 MHA——这就是它胜出的原因；batch 开大、上下文拉长后差距进一步放大
- 国内模型都在怎么选
  - Qwen2 / Qwen3 全系：GQA，Qwen2-7B 是 28 个 Q 头配 4 个 KV 头；GLM 系列：GQA
  - 【结论】纯 MHA 在新一代大模型里基本绝迹，大家都在给 KV Cache 瘦身
- 实战建议
  - 【结论】自己训模型：默认上 GQA，KV 头数取 Q 头数的 1/4 ~ 1/8 是稳的甜点位；资源管够再考虑 MHA
  - 【结论】部署推理：选支持 GQA 感知 kernel 的框架（vLLM、SGLang 原生支持），否则显式复制 K/V 把省下的显存吃回去
  - 【结论】还想更极致：DeepSeek 的 MLA——低秩压缩 K/V，KV Cache 瘦身最前沿打法
- GQA 代码实现
  - 【代码】`class GroupedQueryAttention(nn.Module)`，`__init__(self, d_model, num_heads, num_groups, dropout=0.1)`；断言 `d_model % num_heads == 0`、`num_heads % num_groups == 0`
  - 【代码】`self.head_dim = d_model // num_heads`（512/8=64）；`self.group_size = num_heads // num_groups`（8/2=4）
  - 【代码】投影矩阵：`self.Wq = nn.Linear(d_model, d_model)`（Q 独立，每头各自投影）；`self.Wk = nn.Linear(d_model, self.head_dim * num_groups)`（分组共享，2*64=128）；`self.Wv` 同 K；`self.Wo = nn.Linear(d_model, d_model)`
  - 【代码】forward 步骤
    - 投影 Q/K/V：`Q = self.Wq(x)`、`K = self.Wk(x)`、`V = self.Wv(x)`
    - 形状调整：`Q.view(batch_size, seq_len, self.num_heads, self.head_dim)`；`K.view(batch_size, seq_len, self.num_groups, self.head_dim)`，V 同
    - 广播 K/V 到所有头：`K.repeat_interleave(self.group_size, dim=2)`，V 同；[batch, seq, num_groups, head_dim] → [batch, seq, num_heads, head_dim]
    - 注意力分数：`Q.transpose(1, 2)`；`K.transpose(1, 2).transpose(-1, -2)`；`scores = torch.matmul(Q, K) / torch.sqrt(torch.tensor(self.head_dim, dtype=torch.float32))`，scores 形状 [batch, num_heads, seq_len, seq_len]；`attn_weights = F.softmax(scores, dim=-1)`；`self.dropout(attn_weights)`
    - 应用到 V：`output = torch.matmul(attn_weights, V)`，[batch, num_heads, seq_len, head_dim]
    - 合并头：`output.transpose(1, 2).contiguous().view(batch_size, seq_len, self.d_model)`；`return self.Wo(output)`
  - 测试：d_model=512、num_heads=8、num_groups=2（每组 4 头共享 K/V）、batch_size=2、seq_len=10；输入形状 [2, 10, 512]，输出形状 [2, 10, 512]

# 7.大模型模块详解/RoPE旋转位置编码

- 正余弦位置编码 vs 旋转位置编码
  - 传统正余弦位置编码存在哪些问题
    - 位置编码作用：给不同位置的 token 向量"打上位置标记"，让模型知道谁在前谁在后
    - 传统 Transformer 相加融合：`最终输入 = 词嵌入 + 位置编码`
    - 问题：位置信息间接性（需通过复杂注意力计算"学会"位置关系，无法在向量操作中直接体现相对位置）；外推能力受限（超过训练长度效果显著下降，超长序列失去区分度）；计算效率低下（需额外位置编码向量存储空间，注意力要额外学习位置关系）
    - 好的位置编码两条标准
      - q 和 k 的内积应和它们之间的距离呈一定关系，把位置信息嵌入注意力计算，使注意力分数依赖 token 之间的相对位置
      - 训练时只见过长度 $L_{train}$ 的序列，推理时能处理 $L_{test} > L_{train}$ 且性能不严重下降（训练短，推理长，还能用）
  - 什么是 RoPE（Rotary Position Embedding）
    - 每次计算自注意力分数时，让 Q、K 矩阵中每个行向量根据各自位置旋转一个角度
    - 位置 m 的 token 向量 (x1, x2) 绕原点旋转 $m\theta$ 度：第 1 个 token 旋转 0，第 2 个旋转 $\theta$，第 3 个旋转 $2\theta$
    - 核心思想：通过旋转矩阵给 token 向量"旋转"特定角度，把位置信息编码到向量中；既能让模型理解位置关系，又能支持长序列外推
    - 每个位置对应不同旋转角度，位置信息被"编码"到向量的方向中
  - RoPE 的数学之美：点积中自动出现相对位置
    - 公式：$\langle \text{旋转 } m \text{ 的 } q,\ \text{旋转 } n \text{ 的 } k \rangle = Q^T \cdot R(n-m) \cdot K = Q^T \cdot \begin{bmatrix} \cos((n-m)\theta) & -\sin((n-m)\theta) \\ \sin((n-m)\theta) & \cos((n-m)\theta) \end{bmatrix} \cdot K$
    - 图中说明：$q \cdot R[(n-m)\theta] \cdot k$——位于位置 m 和 n 的向量各自旋转后，内积只取决于原始向量和旋转角度差 $(n-m)\theta$；与绝对位置 m、n 无关，只与相对距离 $|n-m|$ 有关；注意力权重自然带有相对位置信息
    - 公式中的 (m-n) 正是两个位置之间的相对距离：相对位置信息自动嵌入向量运算结果；模型无需额外学习位置关系；注意力分数天然包含位置信息
    - 位置编码不再是"外加"的信息，而是内在融入向量的几何结构
    - 【结论】注意力分数完全由相对位置差 (n−m) 决定
- 总结（对比 正余弦位置编码 vs RoPE）
  - 编码方式：词嵌入 + 位置向量（相加融合）vs 对 Q/K 向量做旋转变换
  - 位置信息：绝对位置，相对位置需模型间接学习 vs 点积结果天然包含相对位置 (n−m)
  - 外推能力：超长序列区分度下降 vs 相对位置设计，外推表现更好
  - 计算开销：需额外存储位置编码向量 vs 旋转操作，无额外存储

# 7.大模型模块详解/图解MOE结构

- 第一部分：MoE 基础概念
  - 引言：最新 LLM 标题常出现"MoE"；MoE 模型就是把 FFN 层替换成 MoE 层，每个 MoE 层由一些专家网络和一个路由网络组成
  - 什么是 MoE
    - 混合专家模型（Mixture of Experts）：用多个不同子模型（"专家"）提升 LLM 性能的技术
    - 两个主要组件：专家（Experts）——每个 FFNN 层配备一组"专家"，运行时选择其中部分，专家通常也是 FFNN；路由或门控网络（Router / gate network）——决定哪些输入 token 发送给哪些专家
    - 【结论】"专家"并非专攻"心理学"或"生物学"等领域，最多只在词汇层面学习语法信息：专长在于处理特定上下文中的特定 token
    - 每个专家不是完整 LLM，而是 LLM 架构中的一个子模型部分
  - Dense Layers
    - MoE 要替代的对象是稠密层：LLM 中的前馈神经网络（FFNN）；标准 decoder-only Transformer 中 FFNN 在层归一化之后应用
    - FFNN 利用注意力生成的上下文信息进一步转换捕捉更复杂关系；规模迅速膨胀，通常对输入做维度扩展再缩放
  - Sparse Layers
    - 稠密模型：所有参数（权重和偏置）都被激活参与计算，输入以某种程度激活全部参数
    - 稀疏模型：仅激活总参数的一部分；把稠密模型分割成若干模块（"专家"），重新训练后每次仅激活其中一个子集
    - 核心思想：每个专家训练中学习不同信息，推理时只调用与当前任务最相关的特定专家
  - 为什么 MoE 能节省算力（以图片给出）
- 第二部分：核心机制——专家层与路由
  - 专家层
    - 专家层本身通常就是完整的基于全连接的 FFNN
    - 大多数 LLM 含多个解码器模块，文本生成前流经多个专家层；不同 token 选择的专家可能各不相同，形成差异化"路径"
    - 稀疏模型的解码器中包含多个 FFNN（每个专家对应一个），推理时可调用多个 FFNN
  - 路由层
    - 专家层之前加入路由网络层（门控网络），训练后能为给定 token 选择最合适的专家；本身也是一个全连接 FFNN，输出一组概率值匹配专家
    - 专家层返回所选专家的输出，并乘以门控值（该专家被选择的概率）；路由网络层 + 专家层（每次仅激活少数）= 混合专家层（MoE Layer）
    - 两种类型：稀疏混合专家（Sparse MoE）仅激活少量专家；稠密混合专家（Dense MoE）激活所有专家（可能不同权重分布）；例：稠密 MoE 把 token 分配给所有专家，稀疏 MoE 只选部分
    - 【结论】当前 LLM 领域提及"MoE"通常特指稀疏 MoE——仅调用部分专家子集，计算成本更低
  - 如何选择激活专家
    - 【结论】门控网络是 MoE 最重要的组件：推理时决定选哪些专家，训练阶段也决定激活哪些专家
    - 最基本形式：输入 x 与路由层权重矩阵 W 相乘（图）；对输出应用 SoftMax 生成每个专家的概率分布 $G(x)$（图）
    - 路由层利用概率分布选择最匹配专家；将每个路由层输出与对应所选专家输出相乘并求和（图）
    - 【结论】MoE 不仅降低算力消耗，往往还带来更好表现：每个专家各司其职专注特定领域或数据分布更易"专精"（每个医生只治一种病）；DeepSeek-R1 采用 MoE 后表现与甚至超越稠密模型，训练和推理成本降低数倍
    - 问题：简单设计往往导致路由层总选同一个专家（某些专家学习速度更快）→ 专家选择分布不均，部分专家几乎得不到训练，训练和推理都出问题
    - 解决：确保训练和推理中各专家发挥同等重要作用——"负载均衡"，防止模型过度依赖特定专家
- 第三部分：负载均衡
  - 负载均衡：KeepTopK 策略
    - KeepTopK 将每个 token 路由到少数被选中的专家，也称 Token Choice 机制
    - top-1 路由：指定 token 发送至单个专家；top-k 路由：同时发送至多个专家
    - 优势：能对各专家的贡献进行加权整合
  - 负载均衡之辅助损失函数
    - 得到各专家"重要性分数"：反映不同专家被选中的总体概率（与具体输入无关）
    - 计算变异系数（CV）量化专家间重要性分数差异程度（公式以图片给出）：分数差异大 → CV 显著升高；分数相近（期望状态）→ CV 降低
    - 训练中利用 CV 值动态更新辅助损失函数，使其尽可能降低 CV（专家间权重均衡）；辅助损失作为独立优化目标加入整体训练
  - 负载均衡之专家容量
    - 不均衡不仅体现在被选中的专家分布上，还反映在分配给各专家的 token 分布中；token 不成比例集中到某专家同样导致训练不足；关键是各专家被调用的频次
    - 专家容量（Expert Capacity）：限制单个专家处理的 token 数量；达到上限时后续 token 自动路由至下一个可用专家
    - token 溢出：所有专家均达容量上限时，该 token 跳过当前专家层直接传递至下一网络层

# Transform笔记

- Transform（理解 / 怎么用两节为空）
- 方法记录
  - `unsqueeze`：PyTorch 张量操作，在指定维度上插入一个新维度（大小为 1）
    - 【代码】`x = torch.tensor([1, 2, 3])` 形状 [3]；`x.unsqueeze(0)` → [1, 3]；`x.unsqueeze(1)` → [3, 1]
  - `k.size(-1)`：获取张量最后一个维度的大小
    - 【代码】`x = torch.tensor([[[1, 2, 3], [4, 5, 6]]])` 形状 [1, 2, 3]；`x.size(0)`=1、`x.size(1)`=2、`x.size(2)`=3、`x.size(-1)`=3（等同 `x.size(2)`）、`x.size(-2)`=2、`x.size(-3)`=1
  - `torch.matmul`：PyTorch 矩阵乘法
    - 【代码】2D：A [2, 2] × B [2, 2] → C [2, 2]，等价 `C = A @ B`；高维批量：A [32, 10, 20] × B [32, 20, 30] → C [batch, n, p]
    - 规则：形状 `[m, n] × [n, p] → [m, p]`；最后两个维度做乘法，前面维度保持或广播
- PyTorch 张量操作学习笔记
  - 张量维度操作
    - `tensor.size()` 获取张量形状：负索引从后往前数，-1 最后一维，-2 倒数第二维；写法更灵活，不硬编码维度数
    - `tensor.unsqueeze(dim)` 插入维度：`y = torch.tensor([[1, 2], [3, 4]])` [2, 2]；`y.unsqueeze(1)` → [2, 1, 2]；`y.unsqueeze(-1)` → [2, 2, 1]；应用场景：为广播做准备
    - `tensor.squeeze(dim)` 移除大小为 1 的维度：`x` [1, 1, 3]；`x.squeeze(0)` → [1, 3]；`x.squeeze(1)` → [1, 1, 3] 不变（该维度大小不是 1）
  - 张量运算
    - `torch.matmul()`：A [32, 10, 64] × B [32, 64, 10] → [32, 10, 10]；应用场景：注意力机制中计算 Query × Key^T
    - `tensor.transpose(dim1, dim2)` 交换两个维度：x [2, 10, 64]；`x.transpose(-2, -1)` → [2, 64, 10]；`x.transpose(1, 2)` 等效；`x.t()` 等同 `x.transpose(-2, -1)` 快捷方式
  - 元素级运算（运算符重载）
    - 比较运算：`x = torch.tensor([1, 2, 0, 3])`，`padding_idx = 0`；`(x == padding_idx)` → tensor([False, False, True, False])；`(x != padding_idx)` → tensor([True, True, False, True])；`(x < 2)` → tensor([True, False, True, False])
    - 【结论】不是 Python 原生语法：Python 列表 `[1, 2, 0] == 0` 会报错；PyTorch 张量返回逐元素比较结果；实现原理是 PyTorch 重载 `__eq__`、`__lt__` 等方法
    - 常见运算符重载：`x + y` → `__add__`；`x - y` → `__sub__`；`x * y` → `__mul__`；`x / y` → `__truediv__`；`x @ y` 矩阵乘法 → `__matmul__`；`x == y` → `__eq__`
  - 实战应用：Transformer 注意力机制
    - 位置编码中的 unsqueeze：【代码】`position = torch.arange(0, max_len)` [max_len]；`position.unsqueeze(1)` [max_len, 1]；`div_term = torch.arange(0, d_model, 2)` [d_model/2]；`pe = torch.sin(position * div_term)` 广播为 [max_len, d_model/2]；`pe.unsqueeze(0)` [1, max_len, d_model/2]
    - Padding 掩码中的运算符重载：【代码】`def get_padding_mask(x, padding_idx)`：`comparison = (x == padding_idx)` [batch, seq_len] 布尔张量；`return comparison.unsqueeze(1)` [batch, 1, seq_len]
    - 注意力分数计算：【代码】`def attention(q, k, v, mask=None, dropout=None)`：`d_k = k.size(-1)`；`scores = torch.matmul(q, k.transpose(-2, -1)) / math.sqrt(d_k)`（k 由 [batch, heads, seq_len, d_k] → [batch, heads, d_k, seq_len]，scores 形状 [batch, heads, seq_len_q, seq_len_k]）；`scores.masked_fill(mask, -1e9)`（True 位置填极小值）；`p_attn = torch.softmax(scores, dim=-1)`；`return torch.matmul(p_attn, v)`
  - 维度索引速查表
    - 获取维度大小：`x.size(0)` 第 1 个维度；`x.size(-1)` 最后一个维度
    - 添加维度：`x.unsqueeze(0)` 开头；`x.unsqueeze(-1)` 末尾
    - 移除维度：`x.squeeze(0)` 移除第 1 个维度（如果大小为 1）
    - 交换维度：`x.transpose(-2, -1)` 交换最后两个维度
    - 形状变换：`x.reshape(new_shape)` 重塑张量（不改变数据）；展平：`x.flatten()` 展成 1D
  - 关键概念总结
    - 广播（Broadcasting）：自动对齐维度运算；`a` [3, 1] + `b` [3] → `c` [3, 3]
    - 运算符重载 vs 函数调用：`x == 0` 等价 `torch.eq(x, 0)`；`x @ y` 等价 `torch.matmul(x, y)`
    - 负索引的妙用：`x.size(-1)` 总是最后一维；`x.transpose(-2,-1)` 总是交换最后两维；`x.view(-1, 1)` 中 -1 表示自动推导维度大小
