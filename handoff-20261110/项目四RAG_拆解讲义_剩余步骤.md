## 前情提要：已经讲完的，五句话接上

结构图五段：① 入库分块 → ② 存进 OceanBase → ③ 召回重排 → ④ 生成 → ⑤ 评测反馈。

1. **第 1 步**定了为什么做：值班工单四成多手册里有答案（4 周 436 条中 181 条，41.5%），做两级分流——交付版让客户在内网自助，内部版让 L1 当场答、少升级。
2. **第 2 步**定了五条约束：客户内网不加组件、发版慢内部要快、精确术语对口语、文档多版本、答错有人照做。环境约束定架构，场景约束定模块。
3. **部件一**（①）：标题感知父子分块，检索要小生成要大；表格和 SQL 整块；子块带前缀和元数据；知识包随版本发。
4. **部件二**（②）：块、版本、向量同一张表，查询先 WHERE 圈版本再搜向量，这是前过滤；换嵌入模型靠新表加一行配置切换，续跑靠三条不变量。
5. **部件三**（③）：两路各 50、RRF 取 30、Reranker 取 5、取父块去重；两个开关是实体词表驱动的精确通道钉顶，和证据不够时才开的 Multi-Query。
6. **部件四前半**（④ 的共用部分）：证据约束的提示词、章节锚点、阈值拒答；检索侧问"找对了没"用 Recall 量，生成侧问"用对了没"用忠实度量。

## 第 4 步 部件四后半：内部版多出来的两步，交付版工具收尾

### 在图上哪里，接前面什么

结构图里内部版那个框，④ 生成之前多两步：**多轮改写**和**工单历史**。它们改的不是模型怎么答，而是交给 ③ 和 ④ 的"问题"和"证据"长什么样。接的点有三个：部件三开关二 Multi-Query 用的改写能力，这里再用一次；部件一说过入库是"按来源分发"，工单就是第四类来源；第 1 步说过内部版的用户是 L1，L1 的使用方式决定了为什么要这两步。

### 多轮改写

**问题**。L1 处理一个工单时会连着问好几轮："memory_limit 默认值多少" → "那 4.2.1 呢" → "改了没生效怎么办"。第二句、第三句单独拿去检索，没有一个词能命中，因为主语在上一句里。首版直接拿当前句检索，L1 反馈"问第二句就开始答非所问"。

**备选**：

| 方案 | 为什么没选或选了 |
|---|---|
| 把全部历史拼起来一起检索 | 向量被几轮话题平均掉，BM25 被历史里的词带偏，越聊越糊 |
| 只用当前句 | 首版做法，丢指代和省略 |
| 用模型把"历史 + 当前句"改写成一个独立的检索问题（选） | 一次便宜的调用，产出一个能单独检索的句子，后面的主干完全不用改 |

**怎么做**。改写只做一件事：补全指代和省略，把"那 4.2.1 呢"变成"OceanBase 4.2.1 中 memory_limit 的默认值"。两条硬规则和 Multi-Query 一样：不新增原对话里没有的实体；改写结果写进日志的 rewritten_query 字段（11-04 讲日志格式时那个字段就是它）。模型不可用时降级用当前句，不中断。

**代价**。多一次模型调用，几百毫秒；改写错了后面全偏，所以日志里必须能看到改写前后，Bad Case 归因时第一眼先看这个字段。

### 工单历史作为知识源

**问题**。手册写的是"应该怎样"，现场遇到的是"某版本的 bug 怎么绕"，这些只在已结案的工单里。L1 最常问的恰恰是这类。

**怎么做**。走部件一的"按来源分发"：脱敏后的结案方案是子块，工单标题加问题描述当前缀，元数据带客户版本、问题类型、结案时间；和手册块存同一张表，多一列 doc_type 标来源。召回时和手册块一起走两路，不单开一路。引用显示成"历史工单 T-xxx 结案方案"，让 L1 知道这是经验不是规范。

**代价**。工单方案可能只对那个环境有效，所以引用必须标来源类型，排序上不做偏袒，交给 Reranker 和 L1 判断；脱敏要做在入库前，客户名、IP、表名都不能进知识库。

### 交付版只读工具，三句收尾

11-07 已经讲过，这里只接上位置。它挂在交付版框里 ④ 之前，和内部版的"工单历史"是对称的：交付版靠只读工具拿**实时状态**，内部版靠工单材料拿**环境信息**（那是项目二的材料解析），边界是同一条——内部人员碰不到客户系统。

1. 四个只读接口（集群版本、租户参数、告警、慢 SQL），按登录用户的 OCP 权限调，模型能看不能动。
2. 工具返回带时间戳，和文档块一起进证据区编号引用，忠实度约束同样管它。
3. 网关保存模型时探测 Function Calling，不支持就降级纯 RAG 并明说查不到实时状态。

### 内部版怎么被工单 Agent 调

内部版对外只暴露一个检索接口，REST 和 MCP 两种封装：输入问题加版本、模块过滤，输出带锚点的证据列表，**不生成答案**。项目二的"知识核对"子 Agent 调的就是它，答案由项目二的主管 Agent 判。这是项目四往项目二连的那根线。

### 想一下

多轮改写和 Multi-Query 都是"让模型改写问题"，区别在哪，先后顺序是什么？

我的答案：多轮改写是**把一句话补全成一个独立问题**，每轮都做，输入含历史；Multi-Query 是**把一个独立问题扩成几种措辞**，只在首轮证据不够时做。顺序是先多轮改写得到独立问题，走主干召回，不够才 Multi-Query。两者共用同一条规则：不新增实体。

### 面试追问预演

| 追问 | 答法 |
|---|---|
| 多轮为什么不直接把历史塞给模型 | 塞给生成可以，塞给检索不行；检索要的是一个干净的查询，历史只用来补全它 |
| 工单方案过时了怎么办 | 元数据带版本和结案时间，引用标明是历史工单，L1 看得出；进评测集的工单样本要脱敏且不回流训练 |
| 内部版为什么不直接生成答案给工单 Agent | 项目二要的是证据不是结论，结论由主管 Agent 逐条判支持还是反驳；检索工具只给证据，边界清楚 |

对应约束：2（内部要快、要接工单）和 3（口语、指代）。

### 往后连什么

## 第 4 步 部件五：评测闭环与反馈日志（复述稿）

11-04 跟着你的追问已经讲完了，这里不重讲，给一份复述提纲，你照着说一遍，说不顺的地方再问。

### 在图上哪里，接前面什么

⑤，只在内部版有。接第 1 步的两级分流（它产出的数就是第 1 步"之后"的那组）、部件四前半的三个指标（忠实度、引用正确率、误拒率都在这里算）。

### 复述提纲

1. **效果怎么看**：两种一起用。工单量是结果指标，在支持侧工单系统统计；L1 的反馈是归因工具，结案时点"已解决 / 未解决"，已解决再勾"有无补充"。交付版不做反馈：数据出不来、问题本来经支持进来、客户对收集数据敏感。
2. **日志为什么必须有**：可复现、可追责、可度量。三级：审计最小集必须，排障集默认开，完整 prompt 只在调试开关。字段五组：标识、输入（含 rewritten_query、按证据来源的分类、过滤条件）、检索中间态（各阶段 top-k）、生成（模型、提示词版本、知识包与嵌入模型版本、回答、引用、是否拒答、耗时）、反馈（仅内部版）。
3. **评测两用**：不用标注的监控（拒答率、重排最高分分布、引用覆盖率、P50 / P95）看漂移；要标注的评测集（Bad Case 队列 → 人工标正确块和可接受答案 → 分层进版本化评测集）算 Recall、忠实度。
4. **离线重放**：日志存了各阶段 top-k，改切分或重排配置对评测集重跑，不上线就能比。66.7 → 76.0 → 85.0 就是这么比出来的。
5. **Bad Case 周例会**：未解决样本归六类——切分、召回、重排、提示词、知识缺失、版本错；知识缺失转文档团队。
6. **日志到训练**：固定管线，但只用内部版数据，目标是人工确认的结案方案，未解决的回答配结案方案构成 DPO 偏好对，评测集样本不进训练集。归因表第三行走到项目三。

## 第 6 步：真实问题案例

### 在图上哪里，接前面什么

每个案例都是部件五 Bad Case 队列里的一类，按"现象 → 定位（看日志哪个字段）→ 修法 → 兜底 / 再做一次会怎么改"讲。主案例是顾问点名的。

### 主案例：检索到旧版本资料怎么办

- **现象**：客户集群 4.2.1，问 memory_limit 默认值，回答说"默认 0 不限制"，那是 4.1 的文档。
- **定位**：日志里 filters 字段为空或版本不对；retrieval 里 rerank_top5 的块版本是 4.1。两种根因：没带版本过滤，或版本拿错了。
- **修法**：版本进元数据做前过滤（部件二）；版本不让模型猜，交付版从只读工具拿集群版本，内部版从工单环境信息拿；文档没有对应版本时查映射表取最接近且不高于的版本，并在回答开头标注"依据 4.2.1 文档"。
- **兜底**：用户反馈"版本不对"的 Bad Case 归到"版本错"类，查是元数据缺失还是切分丢了版本列，修入库规则不改提示词。
- **再做一次**：映射表随知识包发，第一版是手工维护的，再做会从文档目录自动生成。

### 副案例一：错误码精确通道没命中

- **现象**：问"4012 报错"，没带负号，精确通道没抓到，走了普通召回，排第一的是另一个错误码。
- **定位**：日志 retrieval.exact_hit 为空，而问题里明显有错误码。
- **修法**：正则放宽到"可选负号加四位数字"但要求上下文词（报错、错误码、error）同时出现，防止年份误抓；词表加写法变体。
- **兜底**：精确通道最多钉 2 块，误抓代价有上限；没钉到时主干照常，Reranker 还有机会。

### 副案例二：客户配的模型不支持 Function Calling

- **现象**：某客户在网关换了自己的模型，问"我这个集群哪个租户内存最高"，助手答了一段通用说明。
- **定位**：网关保存模型时的探测结果为"不支持工具"，日志里 tool_calls 为空。
- **修法**：按证据来源分类判为 live 的问题，模型不支持工具时直接明说"当前模型无法查询实时状态，请在 OCP 对应页面查看"，不假装。
- **兜底**：探测在保存模型时做，不等用户问了才发现。

### 副案例三：Recall 高，回答还是错

- **现象**：评测集上正确块在前 5，回答却给了错的默认值。
- **定位**：先看 rewritten_query 有没有改歪；再看 citations 引用的块是否支持那句话。引用不支持，是生成侧超出证据，归因表第二行。
- **修法**：收紧提示词，禁止补证据里没有的数值；加在线引用存在性检查。
- **兜底**：提示词改到第十几版还压不住的那部分——推理步骤错、格式乱、该拒答不拒答——是归因表第三行，走项目三微调。这是项目四通向项目三的门。

### 副案例四：参数表被切断

- **现象**：问某参数取值范围，回答只有默认值没有范围。
- **定位**：rerank_top5 命中的子块是表格的后半截，表头不在里面。
- **修法**：表格整块；长表按表头加 30 行拆且每块重复表头（部件一）。
- **兜底**：Bad Case 归"切分"类的比例是衡量切分规则好坏的指标，改完重放看它降没降。

### v5 项目四段落草稿

> 按顾问意见 A 组三条写：职责只写重点，主导在前参与在后，指标围绕解决了什么、提升多少，每条职责"问题 → 方案与为什么 → 机制"。粗体和编号沿用 v4 版式。

**项目四：运维知识库 RAG ｜ 2024.07 - 2025.05 ｜ 产品化二期 2025.08 - 2025.12（参与）**

**项目背景**：OCP 客户支持的值班工单里四成多是手册里有现成答案的参数、错误码、操作步骤问题（抽样 4 周 436 条中 181 条）。先做内部版给 L1 当场答复、减少升级 L3：基于团队既有的 OceanBase 原生向量与全文索引自建，一开始就按"进 OCP、客户侧不加组件"设计，知识包与预计算向量按版本打包。在 L1 验证后，产品团队 2025.08 启动产品化，交付版随 OCP 进客户内网供客户自助，复用同一份知识包、切分规则与召回参数，不共享运行时。

**技术栈**：交付版 Java / Spring Boot / Spring AI；内部版 Python / FastAPI / LangChain；OceanBase 向量与全文索引、BGE-M3 / 通义 Embedding、BGE-Reranker、多厂商模型网关、Function Calling、MCP

**我的角色**：主导内部版全流程（入库与存储设计、召回重排、生成与评测闭环、多轮检索）；二期产品化中主导检索链路与只读工具的 Java 实现，参与入库流水线、模型网关与打包发版。

**核心职责**：
1. **多路召回与重排（主导）**：运维问题里错误码、参数名是精确术语而提问是口语，单路向量召回 Recall@5 仅 66.7%；改为稠密与 BM25 并行召回、RRF 融合、Reranker 精排，错误码与参数名经实体词表命中后走精确通道钉顶，首轮证据不足才开 Multi-Query 补召回一次；对比单路 / 混合 / 混合加重排三种配置后定为默认。
2. **防幻觉与评测闭环（主导）**：仅基于证据作答并附章节锚点，Reranker 分数低于阈值拒答并引导联系支持；版本与模块作为检索前过滤条件，避免命中旧版本资料；300 条评测集标注到块，Recall@5 / MRR 看检索、忠实度 / 引用正确率看生成，分开报；每轮问答落分级日志支持离线重放，内部版 L1 结案反馈回流 Bad Case，沿切分 → 召回 → 重排 → 提示词归因。
3. **多轮检索与只读工具（主导）**：问题先按证据来源分类，决定只检索知识库、调只读工具或两者；交付版接 OCP 集群版本、租户参数、告警、慢 SQL 四个只读接口，按登录用户权限调用、结果作证据，不支持工具调用的模型降级纯 RAG 并明说；内部版把多轮历史改写为独立检索问题，接入脱敏工单结案方案作知识源，并以 REST / MCP 封装为工单 Agent 的检索工具。
4. **知识包入库与存储，二期产品化迁移（入库存储主导，产品化参与）**：标题层级感知父子分块（子块检索、父块生成），参数表与 SQL 整块保留，子块前缀拼标题路径与文档摘要；分块、元数据与向量同表存 OceanBase（HNSW 加全文索引）以支持前过滤；嵌入模型与知识包版本绑定，换模型时双表重建不中断；二期知识包与规则原样迁入交付版，检索链路用同一评测集校验后迁为 Java 实现，入库流水线、网关与打包由交付版团队主做。

**项目成果**：
1. 300 条评测集：Recall@5 单路向量 66.7% → 混合召回 76.0% → 混合加重排 **85.0%**，MRR 0.78；忠实度 91.7%，引用正确率 94.3%；流式首字 P50 0.9s，端到端 P95 3.8s（内部参考环境）。
2. 内部版 8 周试运行，L1 用助手处理的 240 条手册可答类工单中回答核对后直接采用 **55.0%**，该类工单升级 L3 的比例由 14.9% 降至 7.9%；检索以 REST / MCP 复用于工单 Agent；知识包约 9,000 篇文档、约 12 万子块，2025.12 随 OCP 版本交付客户。
