  Recall@5 和忠实度是什么

  评测集里每道题，人工标了"答案在哪个块里"（正确块）和"可接受的回答要点"。两个指标分别量链路的两半：

  - Recall@5，量检索：这道题的正确块有没有出现在重排后的前 5 个里。300 道题里 255 道出现了，就是 85.0%。它只管"找到没有"，不管模型答得怎样。MRR
    是正确块排第几的倒数取平均，0.78 大致是平均排在第 1 到第 2 之间。
  - 忠实度，量生成：回答里每一句话能不能在给模型的那几个块里找到依据。"超出证据"就是回答里出现了块里没有的内容，比如块里只说 -4012
    是什么错，模型顺手补了一个参数默认值，这个值证据里没有，就叫不忠实。91.7% 是 300 条回答里 275
    条没有这种句子。算法是评审模型把回答拆成句子逐句对证据，再人工抽 10% 校准。

  忠实不等于正确：证据是旧版本的，回答忠实但错；模型靠预训练记忆答对了但证据里没有，正确但不忠实，后者更危险，因为用户没法核对。你说"文档只是给 LLM
  更准的数据来源，回答还是 LLM 自己答"，对，忠实度就是在量"它有没有老老实实只用这个来源"。

### 入库分块与知识版本



#### 为什么需要切分父块和子块

检索要小，生成要大。

按标题切出小节，小节就是父块；小节里按段落切子块。检索到子块的时候，返回会把父块一起返回回去，让信息更加完整。

#### 如果没有完整格式的知识库的md文档，应该怎么定义切分规则

  1. 先把格式归一。PDF、Word、HTML 先转成带标题的中间格式。Word 有标题样式直接用；PDF
     靠字号和加粗推断标题层级，现成的版面解析工具能做，MinerU、unstructured 这类；表格单独识别出来。
  2. 没有标题，找次一级的结构信号：编号行"1.1""第三步"、整行加粗、空行分段。有就当标题用。
  3. 都没有，退到按段落聚合：空行分段，段落往上聚到 300 到 500 字，这时候加一点重叠，因为没有父块兜上下文了。
  4. 纯散文最后才考虑语义切分，按相邻句相似度找断点。慢、不稳定，只在小体量的老文档上用。
  5. 体量小、价值高的乱文档，让模型帮着加结构：给它一篇让它插标题、分小节，人工过一遍。成本高、不确定，只给几十篇级别的。

  退到哪一级，用评测集说话：切完在评测集上看块级 Recall，差就再往上加规则。表格和代码不管哪一级都要单独识别，这条不退。

  面试里的一句话："标题切分不是方法论，是运维手册这种结构化文档的最优解。方法论是按来源找天然边界，找不到就按格式归一、结构信号、段落聚合这个顺序退
  ，退到哪一级用评测集定。"

  为什么这和"同表"有关

  前过滤要求"按版本筛"和"按向量搜"在同一个地方、同一次操作里完成。如果向量放在 Milvus、版本放在 MySQL，Milvus
  搜的时候不知道版本，只能先搜再回 MySQL 筛，那就是做法一。把块的文本、版本、向量放在 OceanBase
  同一张表里，一条 SQL 既写 WHERE version 又写按距离排序，数据库自己先筛后搜，那就是做法二。



  再说"1024 维"：这串数字有多少个，由嵌入模型决定，不是我们选的。我们用的 BGE-M3 输出 1024 个数，所以是 1024
  维。换别的模型就是别的数：bge-base 是 768，OpenAI 的 text-embedding-3-small 是 1536，通义的
  text-embedding-v3 默认也是 1024。

  两个连带的事实：

  - 一个数用 4 字节存，1024 个数就是 4KB，12 万个向量约 480MB，这是上一条说内存的来源。
  - 表里的向量列要写死维度 VECTOR(1024)，所以客户换一个维度不同的嵌入模型，这列装不下，必须建新表。这就是后半
    段"双表重建"要讲的原因，现在你知道它从哪来了。

  为什么选
  BGE-M3：运维文档中英夹杂，错误码、参数名是英文，解释是中文，它中英混合效果好；开源，能装进客户内网，这是约束
  1；支持 8192 token 长输入，整张表格进去不截断。

  "每块一个向量"怎么产生

  每个子块的文本，连前缀一起，喂给 BGE-M3，出来一个 1024 维向量，存在这一行的 embedding
  列里。父块不喂，embedding 列是空。入库时 12 万次这样的计算，算完打进知识包。



#### 换模型

  客户在网关里把嵌入模型从 BGE-M3 换成一个 768 维的模型。两件事立刻发生：

  1. 表里 12 万个向量是 BGE-M3 算的，客户的问题向量是新模型算的，两个模型的数字空间不一样，算距离没有意义。所以 12
     万个块必须全部用新模型重算，哪怕维度恰好相同也要重算。
  2. 维度从 1024 变成 768，VECTOR(1024) 这一列装不下 768 个数。所以要建一张新表。

  而重算 12 万块在 CPU 上要一个小时左右。这一个小时里 L1 还在用，不能停。

代价：重建期间两份数据，多占约 1GB；一小时后台算力，客户模型是 API 的话受限速更慢；校验题要随知识包维护。

##### 具体步骤

  当前激活配置（一行）：表 = kb_chunk，模型 = bge-m3，维度 = 1024
                         ▲
  查询：读这一行 ──▶ 用它指定的模型算问题向量 ──▶ 查它指定的表      ← 这一小时里照常跑

  后台任务：
    建 kb_chunk_v2(VECTOR(768))，先不建向量索引
    ──▶ 按 id 顺序每 256 个子块一批：读旧表文本 → 新模型算 768 维 → 写入 v2，记下做到哪个 id
    ──▶ 父块直接拷过去（没向量）
    ──▶ 全部写完，一次性建 HNSW
    ──▶ 校验：知识包里带的 100 道题在 v2 上跑 Recall@5，不低于旧表减 1 个点
    ──▶ 通过：把那一行配置改成 表 = kb_chunk_v2，模型 = 新模型，维度 = 768（一个事务）
        不通过：报错停下，旧表继续服务
    ──▶ 旧表留 7 天，有问题把那一行改回去就是回滚



##### 为什么需要重新向量化

向量列的维度是类型的一部分，不是容量上限，因为距离计算和索引都依赖所有向量同维，维度不一致说明混了模型，应该在写入时就拦住。



#### 换重排模型需要重建嘛？

换重排模型要重建吗：不用，重排是查询时给候选打分，不碰存储。但拒答阈值是建在重排分数上的，不同模型分数尺度不一样，要用同一组校验题重新定阈值。
