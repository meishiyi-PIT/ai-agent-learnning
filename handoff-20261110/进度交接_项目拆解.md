## 5. 项目一：智能数据编排 Agent — 已讲内容与结论

### 规划的 9 步

1. ✅ 问题本质与模型边界
2. ✅ 为什么自定义 DSL
3. 🔶 三层校验（讲了分层原理，**代码未展示，用户未回答分组问题**）
4. ⬜ 接地生成：检索 → Function Calling → 模板

6. ⬜ 试跑、风险分级、审批绑定版本
7. ⬜ DAG 引擎集成：幂等键、UNKNOWN 核对、版本/灰度/回滚
8. ⬜ 评测对照集与回流
9. ⬜ 串线 + 面试追问总复盘

### 第 1 步结论：模型边界

- 核心判断标准：**这件事错了，能不能用确定性代码检查出来？** 能 → 代码做；不能 → 模型做。
- 分工：理解需求 / 选接口 / 填参数 → 模型；校验、权限、风险判级、提交执行 → 平台。
- 一句话：**模型负责理解与生成，平台保证权限、合法性、审批与幂等。**
- 我给出的"真实过程"观点：边界不是一开始定的，分三阶段逼出来——先让模型直接生成验证可行性（只生成不执行）→ 跑样例发现编造接口/类型错/成环，prompt 压不住，逼出三层校验 → 接引擎时才补齐权限/审批/幂等。
- 给用户的作业：回忆一个"被模型坑过一次"的具体例子作面试锚点（用户尚未反馈）。

### 第 2 步结论：为什么自定义 DSL

- 引擎 JSON 中业务意图字段（接口/参数绑定/依赖）约占 1/4，其余是执行器配置、内部 ID、调度元信息、默认值。让模型直接写引擎 JSON，错的往往是那些和意图无关的字段。
- DSL = **只暴露模型必须决定的东西**，从引擎 JSON 反推，Pydantic 收紧（参数来源枚举 `const | input | node_output`，节点 id 正则，引用写成 `node_id.field`）。
- DSL → 引擎 JSON 是**纯函数编译器**，可用对照集做回归测试。
- 四个好处：Pydantic 可约束 / 校验对象稳定 / diff 干净 / 引擎升级只改编译器。
- 我给出的"反复调整过的字段"观点：参数 `source`，从两种（const/上游输出）被"昨天的数据"这类需求逼出第三种 `input`；扇出（上游是数组）故意不支持，走人工编辑，等对照集频率够高再考虑——这是 DSL 松紧的典型决策。
- **已纠正的误解**：DSL 不是被模型"调用"的工具/skill，而是格式约定。完整链路是两份 JSON：模型生成 DSL JSON → 校验 → 代码编译成引擎 JSON → 引擎执行。

### 第 2.5 步（用户追问）：模型怎么生成符合 DSL 的 JSON，实际怎么实现

- 不是 skill。格式定义只放一处：代码里的 Pydantic 模型。
- 三种手段叠用：
  1. `model_json_schema()` 导出 schema + 示例 + 规则塞进 prompt（让模型理解语义）
  2. tool calling 结构化输出（schema 作为工具参数；LangChain `with_structured_output`）；DeepSeek 不稳时降级 JSON 模式
  3. `Orchestration.model_validate()` 解析即结构层校验，失败带路径回灌自校正（输出 JSON Patch 而非整份）
- 要点：Pydantic 的 `Field(description=...)` 认真写，schema 导出自带说明，prompt 与校验永远一致。
- 完整示意代码与讲解思路见下方 **5.1 节**（四个文件，已落盘到本文档）。

#### 5.1 第 2.5 步完整内容：模型如何生成符合 DSL 的 JSON（代码 + 思路）

**先纠正的误解**：用户问"有对应的 skill 内部会去定义格式嘛"。回答：**不是 skill**。Skill 是给模型按需加载的领域知识/流程说明（SmartCS 里 15 类业务流程那种）。DSL 格式不需要"按需加载"，它是每次生成都必须遵守的硬约束，所以定义只放一个地方——代码里的 Pydantic 模型——然后用三种手段叠着逼模型遵守。

**三种手段及分工**：

| 手段 | 作用 | 用法 |
|---|---|---|
| schema + 示例 + 规则进 prompt | 让模型**理解**格式语义（`node_output` 是什么意思） | 必放；示例优先从模板库取和当前需求最像的 |
| tool calling 结构化输出 | 让模型**机械上**遵守字段名和枚举 | 默认开；schema 作为工具参数传给模型；DeepSeek 不稳时降级 JSON 模式 |
| Pydantic 解析 | **兜底**，不信任前两手 | 永远有；`model_validate` 失败 = 结构层校验失败，带路径回灌自校正 |

**一个实际会踩的坑**：schema 里字段的 `description` 写不写、写多长，直接影响生成质量。`ref` 字段不在 description 里说清"格式为 上游节点id.字段名"，模型会写成各种花样。所以把 Pydantic 的 `Field(description=...)` 当成 prompt 的一部分认真写——schema 导出自带说明，prompt 和校验永远一致，不会出现"改了 Pydantic 忘了改 prompt"。

**面试一句话讲法**："DSL 用 Pydantic 定义，schema 导出后作为 tool calling 的参数定义传给模型，返回结果再用 Pydantic 解析；解析失败就是结构层校验失败，带路径回灌自校正。格式定义只在代码里存一份，prompt 和校验共用。"

**四个文件之间的关系**：

```
schema.py  ──导出 JSON Schema──▶  llm.py 的 TOOLS（模型看到的格式）
    │
    └──model_validate──▶  generate.py（解析即结构层校验，失败 → errors）
                                  │
                                  ▼
                         self_correct（错误清单 + JSON Patch → 再解析）
```

三个要点：格式只在 `schema.py` 定义一份；`model_validate` 失败就是结构层错误，错误自带路径直接回灌；自校正输出 patch 不是整份，改动最小也省 token。

##### 文件 1：`dsl/schema.py` — 格式只在这里定义一次

```python
from typing import Literal
from pydantic import BaseModel, Field, model_validator


class ParamBinding(BaseModel):
    name: str = Field(description="接口入参名，必须与接口定义中的入参名完全一致")
    source: Literal["const", "input", "node_output"] = Field(
        description="const=固定值；input=运行时由外部传入；node_output=引用上游节点的输出字段"
    )
    value: str | None = Field(default=None, description="source 为 const 时填固定值")
    ref: str | None = Field(
        default=None,
        description="source 为 node_output 时填 '上游节点id.出参字段名'；为 input 时填外部输入名",
    )

    @model_validator(mode="after")
    def _check_source(self):
        if self.source == "const" and self.value is None:
            raise ValueError("source=const 时 value 不能为空")
        if self.source in ("input", "node_output") and not self.ref:
            raise ValueError(f"source={self.source} 时 ref 不能为空")
        return self


class Node(BaseModel):
    id: str = Field(pattern=r"^[a-z][a-z0-9_]{1,31}$", description="节点唯一标识，小写字母开头")
    api_id: str = Field(description="调用的接口 id，只能来自候选接口列表")
    params: list[ParamBinding] = Field(default_factory=list)


class Edge(BaseModel):
    src: str = Field(description="上游节点 id")
    dst: str = Field(description="下游节点 id")


class Orchestration(BaseModel):
    name: str = Field(description="编排名称，简短描述用途")
    nodes: list[Node]
    edges: list[Edge] = Field(default_factory=list)
    inputs: dict[str, str] = Field(
        default_factory=dict, description="运行时外部输入，键为输入名，值为类型，如 {'run_date': 'date'}"
    )

    @model_validator(mode="after")
    def _structural_rules(self):
        ids = [n.id for n in self.nodes]
        if len(ids) != len(set(ids)):
            raise ValueError("节点 id 重复")
        for e in self.edges:
            if e.src not in ids or e.dst not in ids:
                raise ValueError(f"边 {e.src}->{e.dst} 引用了不存在的节点")
        return self


class ClarifyRequest(BaseModel):
    need_clarify: Literal[True] = True
    questions: list[str] = Field(description="需要用户补充的问题，每条一个具体问题")


class ValidationIssue(BaseModel):
    layer: Literal["structure", "semantic", "constraint"]
    node_id: str | None = None
    field: str | None = None
    code: str
    message: str
```

import json
from openai import AsyncOpenAI

        "parameters": ClarifyRequest.model_json_schema(),

    """返回 (工具名, 参数 dict)。tool calling 失败时降级 JSON 模式。"""
    resp = await client.chat.completions.create(
        model=MODEL, messages=messages, tools=TOOLS, tool_choice="required", temperature=0,
    )
    msg = resp.choices[0].message
    if msg.tool_calls:
        tc = msg.tool_calls[0]
        return tc.function.name, json.loads(tc.function.arguments)

    # 降级：JSON 模式，自己判断是澄清还是编排
    resp = await client.chat.completions.create(
        model=MODEL, messages=messages + [{"role": "user", "content": "只输出 JSON。"}],
        response_format={"type": "json_object"}, temperature=0,
    )
    data = json.loads(resp.choices[0].message.content)
    return ("request_clarification" if data.get("need_clarify") else "emit_orchestration"), data

##### 文件 4：`agent/nodes/generate.py` — 生成、解析即校验、自校正

```python
import json
import jsonpatch
from pydantic import ValidationError
from dsl.schema import Orchestration, ClarifyRequest, ValidationIssue
from generation.prompt import build_messages
from generation.llm import call_structured, client, MODEL


def _pydantic_to_issues(e: ValidationError) -> list[ValidationIssue]:
    issues = []
    for err in e.errors():
        loc = [str(x) for x in err["loc"]]            # 例如 ['nodes', '1', 'params', '0', 'source']
        node_id = None
        if len(loc) >= 2 and loc[0] == "nodes" and loc[1].isdigit():
            node_id = f"nodes[{loc[1]}]"              # 结构错时节点 id 本身可能缺失，用下标定位
        issues.append(ValidationIssue(
            layer="structure", node_id=node_id, field=".".join(loc),
            code=err["type"].upper(), message=err["msg"],
        ))
    return issues


async def generate_node(state: dict) -> dict:
    messages = build_messages(
        requirement=state["requirement"],
        api_defs=list(state["api_defs"].values()),
        template=state.get("template"),
        clarifications=state.get("clarifications", []),
    )
    name, args = await call_structured(messages)

    if name == "request_clarification":
        q = ClarifyRequest.model_validate(args)
        return {"need_clarify": True, "questions": q.questions}

    try:
        draft = Orchestration.model_validate(args)        # 结构层校验就在这里
    except ValidationError as e:
        return {"need_clarify": False, "raw_draft": args,
                "errors": [i.model_dump() for i in _pydantic_to_issues(e)]}

    return {"need_clarify": False, "draft": draft.model_dump(), "errors": []}


SELF_CORRECT_SYSTEM = """以下编排未通过校验。只针对【错误清单】做最小修改，
输出 RFC 6902 JSON Patch 操作数组（不要输出完整文档，不要改动无关内容）。"""


async def self_correct_node(state: dict) -> dict:
    current = state.get("draft") or state["raw_draft"]
    messages = [
        {"role": "system", "content": SELF_CORRECT_SYSTEM},
        {"role": "user", "content":
            f"【错误清单】\n{json.dumps(state['errors'], ensure_ascii=False, indent=1)}\n\n"
            f"【当前编排】\n{json.dumps(current, ensure_ascii=False, indent=1)}\n\n"
            f"【候选接口及定义】\n{json.dumps(list(state['api_defs'].values()), ensure_ascii=False)}"},
    ]
    resp = await client.chat.completions.create(
        model=MODEL, messages=messages, response_format={"type": "json_object"}, temperature=0,
    )
    data = json.loads(resp.choices[0].message.content)
    ops = data if isinstance(data, list) else data.get("patch", [])

    try:
        patched = jsonpatch.apply_patch(current, ops, in_place=False)
        draft = Orchestration.model_validate(patched)
    except (jsonpatch.JsonPatchException, ValidationError) as e:
        issues = _pydantic_to_issues(e) if isinstance(e, ValidationError) else [
            ValidationIssue(layer="structure", code="BAD_PATCH", message=str(e))]
        return {"raw_draft": current, "errors": [i.model_dump() for i in issues],
                "correct_rounds": state.get("correct_rounds", 0) + 1}

    return {"draft": draft.model_dump(), "raw_draft": None,
            "correct_rounds": state.get("correct_rounds", 0) + 1}
```

**第 2 步时给过的两份 JSON 对照图**（用于纠正"DSL 被调用"的误解，接手者可复用）：

```
用户文字："每天凌晨把昨天各门店的订单按品类汇总"
        │
        ▼  模型生成（输出必须符合 DSL 格式）
  DSL JSON（第一份，模型写的）：只有 nodes / params(source,ref) / edges / inputs
        │
        ▼  三层校验（代码，不调模型）
        ▼  编译器（代码，纯函数，不调模型）
  引擎 JSON（第二份，代码翻译的）：多出 task_id / executor / endpoint / timeout_ms
                                   / retry_policy / schedule / metadata ……
        │
        ▼
      DAG 引擎执行
```

一句话：**模型生成 DSL JSON，代码把 DSL JSON 编译成引擎 JSON。** 面试说"模型生成 DSL，经校验后编译为引擎 JSON"，不要说"调用 DSL"。

### 第 3 步（进行中）：三层校验

已讲：
- 分层依据唯一标准：**判断这个错误需要什么信息。** 结构层只要 DSL 本身（Pydantic）；语义层要接口目录 + 权限 + 图算法（接口存在、出入参类型匹配、租户权限、无环）；执行约束层要平台策略（节点数、总超时、读写限制、扇出上限）。
- 分开的三个原因：失败要快省外部调用 / 自校正提示词按层不同（约束层错往往直接降级人工）/ 三层变化频率不同。
- 语义层两个要点：类型匹配要先解析引用再比类型（`list<string>` vs `string` 是扇出问题，报错转人工）；无环用 Kahn 拓扑排序，拓扑序同时给编译器用。
- 我会踩的坑：权限放语义层而非约束层，否则试跑后才发现没权限浪费成本。

**待办**：
- 用户还没回答"六类问题分两组"的问题，接手后先等她答或直接替她答。
- 展示语义层 + 执行约束层的示意代码（`dsl/validator.py`：`validate(orch, catalog, perm, policy) -> list[ValidationIssue]`，含类型解析、Kahn 无环、策略检查），然后进第 4 步。

## 5B. 项目二：工单智能诊断 Agent — 已讲结论（2026-10-31）

8 步：① 业务本质 → ② 两张图 → ③ 材料解析与不可信输入 → ④ 诊断推理 → ⑤ 风险路由与复核 → ⑥ 分层状态与可靠性 → ⑦ 上下文工程 → ⑧ 轨迹级评测。

- **第 1 步 业务本质**：不能操作客户系统 → 产出是结构化处理意见，不是动作；结案 = 回执核对通过。决定了：风险控制落在意见本身（白名单）、工单状态机在服务端、指标叫"首答与结案方案一致率"。模型边界同项目一：规则兜已知、模型提假设找证据、平台保审批/幂等/回执。
- **第 2 步 两张图**：L1/L3 材料、用户、输出不同，L3 图内有 interrupt 复核中断点；共享工具层（无状态函数 + Pydantic 参数）。三类升级条件判法不同：置信不足 = 组合信号（规则命中/检索分/已知问题/模型自评）按保留集调阈值、宁多勿漏；客户执行未解决 = 业务事件由状态机触发；动作需确认 = 模板风险等级的确定性规则。**用户纠正**：L1 工单也跨天多轮，正确区分是"工单生命周期 vs 图的单次运行"，两级的等待都不在图里，客户新消息由状态机起新运行并带工单上下文包；升级包是它交给 L3 图的特例。
- **第 3 步 材料解析**：报告按章节抽字段（OCP 自家格式，按版本维护解析器）；日志按模板归并取 Top-N（级别/次数/基线外/时间近），关键模板清单无条件浮出，错误码正则全量扫；截图 OCR 后错误码模糊匹配。不可信输入三层：解析本身过滤、上下文分区标注、白名单下游兜底。补充清单按诊断类型查规则表，写到 OCP 操作路径。
- **第 4 步 诊断推理**：规则先行截掉约三分之一 → 主管出 2–4 条竞争假设 → 三个子 Agent**按材料类型**并行（上下文天然隔离、可并行、失败隔离；按假设分会重复加载材料）、只回传带锚点的结构化证据 → 主管逐条判定支持/反驳/证据不足（不合并、不四舍五入，引用不存在的证据 id 降为证据不足）→ 已知问题库按版本匹配 → Pydantic 意见。32B 做规划，微调 7B 做领域问答，确定性工具不用模型。
- **第 5 步 风险路由**：命令只能选模板填参数（模板含参数 Schema、风险等级、适用版本、预期回执）；等级查表加环境修正，不问模型（确定、防绕过、可审计）；二级以上 interrupt；批准绑定意见版本，改动即作废；回执按模板预期核对通过才结案；案例回流；审计可回放。**用户追问结论**：① interrupt 不占运行时资源，长挂起要防恢复陈旧（恢复校验：意见版本、环境画像有效期、工单状态、**按客户版本重新匹配已知问题库**）和内部服务发版（AgentRun 存图版本号；批准绑定 DB 里的意见版本而非 checkpoint，resume 失败从已批准意见起"下发模式"新运行）；复核队列与 SLA 归业务层。② 三种"分类"分开：问题类型（规则优先、模型在枚举里兜底）、规则命中（纯代码匹配）、白名单（模型选 id 代码验，管动作不管问题）。**总原则：模型可以"选"，不能"定"**。③ 多工单并行挂起没问题，真正的并发问题是同一工单被重复 resume。④ 私有化场景已知问题带受影响版本/修复版本/绕过方案，意见对已知问题两条路都给（绕过二级、升级三级）。
- **第 6 步 状态与可靠性**：三层——业务状态机（真相）/ AgentRun·AgentBranch（可查询的运行索引，checkpoint 是可恢复的载荷）/ 图内 State（只存过程）。图从不直接改工单状态，只产出事件。三机制防三种竞争：执行租约（谁来跑）、控制版本（跑完算不算数）、意见版本（批的和发的是否同一份）。**Outbox 只保证不丢**（事务外发 + 重试 = 至少一次），不重靠接收端幂等键；通知类尽力去重，状态写入必须幂等。双副本下中继也要拿租约或 SKIP LOCKED；SSE 过 HAProxy 要调 tunnel 超时。"无重复下发"是故意测出来的。
- **第 7 步 上下文工程**：固定顺序从稳定到易变（系统指令 → Skills 概览 → 环境画像 ‖ 工单历史 → 材料 → 证据 → 按需 Skills → 任务指令），前三块吃前缀缓存（前缀里不能有时间戳）；Skills 三级（概览常驻 / 场景分支按分类加载 / 细则按需调工具，有次数上限）；分层压缩先历史再材料、证据不压；超预算前置报错不截断（截断是不可见的失败）；环境画像按 customer_id 代码强制隔离、带版本与有效期。**用户追问"为什么不用外部存储"**：方案本来就是外置 + 索引留上下文 + 按需读回；关键是"谁决定何时读回"——可预判的由代码加载，按需的由模型调且有上限；索引必须留在上下文里。四类记忆：图内 State / 工单上下文包 / 环境画像 / 案例库。
- **第 8 步 评测**：Langfuse 自托管因 trace 含客户日志；run_id 与 AgentRun、审计表统一。150 条保留集来自结案工单，标注"可接受方案集合 + 根因类别 + 应否升级 + 关键证据"，故指标叫"一致率"；版本化冻结。结果级五个指标 + 轨迹级（工具调用正确率、无效步数、token 成本、子 Agent 失败率、Skills 无效加载）。门禁：PR 跑分层子集、每晚全量，三次取中位数 + 容差，违规零容忍，成本不超 110%。**保留集样本不得回流进案例库/已知问题库**（防泄漏）。离线数字与试运行数字分开报；可在面试说但已从简历删的数：升级判定准确率 88.0%、工具调用正确率 91.3%、格式合规 96.3%。

## 6. 后续项目的拆解提纲（供接手者规划）

### 项目二：工单智能诊断 Agent（建议步骤）
1. 业务本质：内部人员不能操作客户系统，只能"看材料、给意见、客户执行、看回执"——这决定了整个系统的形态

5. 三级风险路由与复核：命令只从白名单模板填参数、二级以上 interrupt、复核绑定意见版本
6. 三层状态与四类记忆：业务状态机（服务端）/ AgentRun·AgentBranch（运行态）/ 图内 State（过程）；执行租约 + 控制版本 + 意见版本防并发；客户环境画像隔离

9. 数据口径：150 条保留集 vs 试运行；P95 8ms→5ms（组合索引）等

## 7. 环境注意事项

- Windows + Git Bash。**Bash 命令里不能含中文字符**（会报 "No such file or directory"），引用中文文件名要用 glob，如 `./[^~.]*_189****1714_*.docx`（排除 `~$` 开头的 Word 锁文件）。
- 多行 heredoc 在 Bash 工具中失败；需要脚本时用 Write 工具写文件再单行执行。
- Python 输出中文需 `python -I -X utf8 ...`，否则 gbk 编码报错。
- docx 抽取脚本：`C:\Users\meish\AppData\Local\Temp\dump_docx.py`（纯标准库，解析 `word/document.xml` 与 `word/comments.xml`），用法：`python -I -X utf8 dump_docx.py <docx> > out.txt`。若临时文件已清理，脚本逻辑很短，可重写。
- 没有 pandoc。
